# 故障排查

## 找不到模型配置或 API Key

确认 `~/.harness/config.toml` 或 `--config` 指向的文件包含 `[config]`、`[models]` 和默认 Profile，并为 `api_key_env` 指定的环境变量设置密钥。如使用用户 TOML 的 `api_key` 降级值，macOS/Linux 上 Harness 会在首次加载时自动收紧文件权限为 `600`；显式 `--config` 和工作区配置不接受明文密钥。工作区 `.harness/config.toml` 目前会被拒绝。使用以下命令确认生效配置；输出不会包含密钥：

```bash
bun run dev -- config path
bun run dev -- config show
```

`api_key_source=environment|toml|missing` 可用于确认密钥来源，不会显示密钥内容。

## Python sidecar 无法启动

开发模式优先使用 `packages/agent/.venv/bin/python`。确认虚拟环境存在、Python 版本为 3.11+，并在仓库根目录注入 `HARNESS_NPM_REGISTRY`、`HARNESS_PYPI_INDEX` 后运行 `bun run deps:install`；首次在内网重新解析锁文件才执行 `bun run deps:resolve`。不要只执行 `uv sync`，否则不会应用 DeepAgents 补丁。需要临时指定解释器时设置 `HARNESS_AGENT_PYTHON`。

使用 `--cwd <路径>` 时，该目录必须已经存在；CLI 不会自动创建工作区。显式配置路径建议使用绝对路径，避免它随 Agent 工作目录变化：

```bash
mkdir -p /private/tmp/za38-smoke
bun run dev -- --cwd /private/tmp/za38-smoke \
  --config "$HOME/.harness/config.toml"
```

## Plugin 校验、安装或启用失败

先区分操作入口和错误层级：

```bash
harness plugins validate ./my-plugin
harness plugins install ./my-plugin.zip
harness plugins list
harness plugins inspect <plugin-id>
```

`validate` 不写 registry，`install` 总是先写入 `enabled: false`，启用必须同时提供当前
`capability_fingerprint`。常见错误码及处理方式：

| 错误码 | 处理方式 |
| --- | --- |
| `PLUGIN_SOURCE_NOT_FOUND` / `PLUGIN_SOURCE_TYPE_INVALID` | 确认路径存在；来源只能是普通目录或 `.zip` 文件 |
| `PLUGIN_SCHEMA_UNSUPPORTED` / `PLUGIN_MANIFEST_FIELD_INVALID` | 修复 portable `plugin.json` 的 schema、name 或受约束字段 |
| `PLUGIN_MCP_SCHEMA_UNSUPPORTED` / `PLUGIN_COMPONENT_INVALID` | 查看组件 diagnostics；坏的 Skill/server 不需要重打包其他有效组件 |
| `PLUGIN_NO_EFFECTIVE_COMPONENT` | 包格式可以有效，但当前没有 Harness 可运行组件，保持 disabled 或增加受支持组件 |
| `PLUGIN_CAPABILITY_CONFIRMATION_REQUIRED` | 重新 inspect，复制完整的新 fingerprint 后再显式 enable |
| `PLUGIN_STORE_TAMPERED` / `PLUGIN_STORE_MISSING` | 不要手工修改 store；保留 registry/data 现场并重新安装受信来源 |

Agent Plugins portable `mcp.json` 是 closed schema。`timeout`、Claude 私有 placeholder 或其他
variant 外字段不能添加到 portable server；需要使用既有 Claude MCP 语义时，应放在 Claude
`.mcp.json` 并让 Claude Adapter 处理。双 manifest 的 name/version 不一致也会拒绝安装。

若 `inspect` 显示 `unsupported`，它不是格式损坏，而是 Harness 当前不执行该能力；若显示 Skill/MCP
静态有效但运行时连接失败，则只处理对应 server 的 command、cwd、URL、header、认证或外部进程，
不要通过放宽 schema 解决运行时问题。启用、停用、重新安装和删除均在下一次 Host 启动进入 catalog，
当前 Run 不会热替换；Host 同时会用当前 Adapter 从已安装且 digest 校验通过的 package 重建
component report。

## Adapter 更新后需要重新授权

如果 `plugins inspect` 显示 `authorization_state=reauthorization-required`，说明当前 Adapter
发现的能力指纹与此前确认值不同。Harness 不会自动扩大 Hook、MCP 或其他进程能力，也不要求
重新复制内容未变的 Plugin；stale Plugin 会继续从可执行 runtime catalog 排除。普通对话、内置
Command/Skill/Agent 和其他已授权 Plugin 仍可运行；只有请求实际绑定该 stale Plugin 的
Command/Skill/Agent/Team 或带明确 Plugin provenance 的 Hook/MCP/LSP/Settings 入口时，才在
child、模型或对应 runtime 启动前返回 `PLUGIN_REAUTHORIZATION_REQUIRED`。错误中的
`plugin_id`、`authorization_state`、当前 `capability_fingerprint` 和 inspect/enable 操作可直接
用于恢复。

处理步骤：

1. 完整退出并重新启动 Harness，或重新执行一次 Plugin 管理查询，让当前 Adapter 刷新已安装报告。
2. 运行 `harness plugins inspect <plugin-id>`，确认 package digest、component diagnostics 和
   当前 `capability_fingerprint`；只在确认新增能力来源可信时继续。
3. 使用 inspect 返回的完整 fingerprint 显式重新启用：

   ```bash
   harness plugins enable <plugin-id> \
     --capability-fingerprint <64位SHA-256>
   ```

4. 重新启动 Host 后再运行对应 Plugin 能力。若仍显示 reauthorization，先保留脱敏 diagnostics，不要手工编辑
   `registry.json` 或修改 `trusted_capability_fingerprint`。

同一 package 的 Adapter report 刷新若能力指纹没有变化会保留原 enabled/trusted；只有 package
内容变化才需要沿显式 update/install 边界重新安装。两个并发 Host 刷新不会重复扩大授权。

## Qwen SubagentStop Hook warning

对已命中 matcher 的 Qwen `SubagentStop` Hook，Hook 自身异常、超时、非零退出、非空畸形输出或
runner 关闭时，Harness 会记录脱敏 warning 并返回已经完成的 child 结果；这不是 child delegation
失败。正常 blocking 会继续同一个 child checkpoint，达到 blocking 上限时也会返回最新结果并附
warning。`timeout: 10000` 按 Qwen 毫秒语义仍表示 10 秒。

如果是用户、Run 或 parent cancellation，结果应显示取消而不是成功 warning；如果是 PreToolUse、
权限、Policy、MCP、非 Qwen Hook 或 Hook runtime 构造/身份校验失败，仍按安全策略失败关闭。请只
根据稳定错误码和 warning 排查，不要把 Hook stdout、stderr、命令参数或宿主路径贴到 Issue。

## Managed Plugin Agent 上下文异常

如果 Managed Plugin Agent 的结果声称“上一轮 task 被取消、子代理未启动”，但本次运行日志显示
它已经调用过工具，这通常是 child checkpoint 误复用了父 Thread 或旧 child execution 的状态。当前
运行时会按 project、Thread、Run 和 execution 建立独立的 child 根状态，并在完成、取消或失败后清理；
重启 Harness 后重新运行该任务即可验证。不要通过提示词禁止模型提及取消，也不要过滤结果文本。

如果 Adapter 自动重解析后显示 `reauthorization-required`，先在主仓库执行 inspect，确认当前
`capability_fingerprint`，再显式 enable：

```bash
bun run dev -- \
  plugins inspect "<plugin-id>" --cwd "<workspace-path>"

bun run dev -- \
  plugins enable "<plugin-id>" \
  --capability-fingerprint "<64位SHA-256>" \
  --cwd "<workspace-path>"
```

确认 fingerprint 对应可信的当前 Plugin 后再启用；完成后重启 Host。

## Plugin staging 或 registry 失败

目录和 ZIP 会先进入 `~/.harness/plugins/staging/` 的私有临时目录。symlink、hardlink、特殊文件、
`..`/绝对路径、超大文件、压缩比异常或损坏归档会被拒绝；不要把压缩包解压后手工复制进 store。
Plugin 安装也不是操作系统 sandbox，只有明确启用且报告为 supported/adapted 的进程组件才会启动。

启动时遇到 `PLUGIN_REGISTRY_INVALID` 或 digest 错误时，先完整退出 Harness 和 sidecar。
registry 只承认当前版本：未发布期间旧开发构建产生的旧版本 registry 不会被读取或迁移，会按
“版本或结构无效”失败关闭。如需恢复，删除 `~/.harness/plugins` 后重新安装插件；不要手工改
enabled/trusted 字段或用旧代码绕过校验，应先保留错误码和脱敏 stderr，再按项目维护流程处理。

## Windows 支持状态

Windows 上 sidecar 可正常启动并完成 initialize 握手：Skill 扫描、启停、安装恢复、快照校验与 AGENTS.md 参考读取与 macOS/Linux 行为一致，均以 fail-closed 语义拒绝 symlink 与 `..` 路径穿越。

两点平台差异需要知晓：

- Windows 没有 `O_NOFOLLOW`/`dir_fd`，防护实现为逐级 lstat 拒绝 symlink 并在读取前后复核文件身份；“stat 与 open 之间目录被替换”的竞态防护强度低于 POSIX，目录 fsync 在 Windows 上为空操作（NTFS 元数据一致性由文件系统日志保证）。
- 创建 symlink 需要开发者模式或管理员特权。普通使用不受影响；只有在需要手工构造 symlink 验证边界行为时才会遇到 `WinError 1314`。

ZC-108 的旧库迁移 attempt 使用文件身份（`os.stat` 的 `st_dev/st_ino`）跨进程核对临时文件归属；
Windows 上 CPython 通过 `GetFileInformationByHandle` 返回卷序列号与文件索引，同一卷内稳定，
因此旧库迁移在 Windows 上与 POSIX 行为一致。不要删除 attempt/poison marker 绕过迁移门禁。

Windows 上迁移子进程冷启动明显慢于 macOS/Linux，且受杀毒软件实时扫描和磁盘负载影响波动较大；旧版本数据库首次迁移期间请耐心等待，不要中途强杀进程。启动报 `THREAD_STORE_UNAVAILABLE` 时按“无法恢复 Thread”一节处理。

## 终端界面显示简化

在窄终端（小于 88×28）或 `TERM=dumb` 下，星空与品牌动画会主动关闭以保证可读性。请扩大终端，或使用支持 ANSI 色彩的终端模拟器。

若界面出现 `^[[`、`rgb:`、`Warp(...)` 或鼠标坐标等控制序列，说明 TUI 被管道或输出捕获器启动。请在真实终端的仓库根目录使用 `bun run dev -- ...`，不要通过会捕获 stdout/stderr 的任务运行器启动交互界面。

若启动提示缺少 OpenTUI native artifact，请检查企业源是否已镜像 `@opentui/core@0.4.3` 对应当前平台和架构的 optional package，例如 Apple Silicon 使用 `@opentui/core-darwin-arm64@0.4.3`。项目不再自行编译或回退到不匹配的平台库。

## 网关请求失败

检查 `base_url` 是否为企业 OpenAI 兼容接口根路径、模型名是否可用、企业代理和必要请求头是否已配置。切勿把真实密钥贴进 Issue、终端截图或仓库文件。

模型调用会在一次 Run 的配置预算内自动恢复。模型正文和思考保持实时显示；尚未公开的失败
attempt 不会写入当前 Thread，半条工具调用也会被丢弃。若 provider 在正文/思考已经显示后
才断流，Harness 不会重放整个模型回合（避免重复显示），而是保留已显示的一次片段并返回
稳定终态（`retryable=true`，表示用户可在修复网关后重新发起新的 Run）。这个标记不表示当前模型回合会自动重放。

按终态码处理：

| 诊断码 | 含义与处理 |
| --- | --- |
| `MALFORMED_TOOL_CALL` | 模型返回的工具调用结构不可用；在尚未公开模型输出时 Harness 会丢弃该响应并按预算重试。若已有正文/思考公开，则收敛为 `PROVIDER_OUTPUT_INTERRUPTED`，不重放。 |
| `PROVIDER_OUTPUT_INTERRUPTED` | 已经显示正文/思考后 provider 断流或结构失败；本轮不会自动重试，避免回答重复；终态 `retryable=true` 仅表示修复网关后可重新发起新的 Run。 |
| `PROVIDER_RATE_LIMITED` / `PROVIDER_RETRY_EXHAUSTED` | 429、5xx 或连接/超时等临时故障的预算已耗尽；无 Retry-After 时退避随 attempt 线性增加并封顶。等待服务恢复后重试 Run。若事件中的 `retryable=true`，表示重新运行仍有意义。 |
| `PROVIDER_REQUEST_REJECTED` | 400、401 或 403 等确定性请求/鉴权错误，不会重复请求；检查模型名、网关权限、请求头和配置来源。 |
| `TOOL_CALL_ID_UNAVAILABLE` | 工具结果无法安全配对；不要手工改 Thread 数据，保留脱敏诊断并重新运行。 |

取消 Run、拒绝审批、能力策略拒绝和预算/业务错误不会被当作 provider 临时故障重试。若看到同一 Run 多个失败终态，先保留 `model.failed`、`model.retry_scheduled` 的稳定码、attempt 和等待时长，再提交问题；不要提交 prompt、完整工具参数、响应正文、密钥或企业路径。

## 文件工具提示 Snapshot 过期或未读取

修改现有文件前，先用 `read_file` 读取目标局部内容，再用同一 Thread 返回的 `snapshot_id` 和唯一
`old_string` 调用 `edit_file`。出现 `STALE_FILE`、`SNAPSHOT_EXPIRED`、`UNREAD_RANGE`、
`EXACT_MATCH_NOT_FOUND` 或 `AMBIGUOUS_MATCH` 时，文件可能已变化、读取范围不足，或原文本并不唯一；
重新读取受影响区域后再提交一次唯一的原文本即可。`write_file` 不会覆盖已有文件，删除文件则需要完整
读取后得到的当前 Snapshot；不要改用 `replace_all`、行号范围或批量 patch，它们不是可用入口。

如果 `write_file` 对已有空文件返回 `FILE_ALREADY_EXISTS`，先用 `read_file` 取得该空文件的
Snapshot，再以同一 Snapshot、`old_string=""` 和所需初始内容调用 `edit_file`。`INVALID_EDIT`
表示当前文件并非空文件；从刚读取的非空内容复制唯一 `old_string` 后重试，不要把空字符串当作
一般插入位置。审批 diff 超出行数、字节或终端高度时只是有界预览，界面仍保留允许/拒绝选项；
这不等于工具输入或文件 mutation 硬上限。

如果确认文件 diff 后出现 `COMMIT_CONFLICT`，说明确认等待期间文件已被外部修改；旧确认已经失效，重新读取
当前内容并重新确认。`POST_WRITE_DRIFT` 表示写入已完成，但保存钩子或远端系统又改写了内容；使用返回的实际
Snapshot、`proposed_diff` 和 `actual_diff` 继续处理，不能重放旧调用。成功结果中的 `changed_range` 与
`shown_lines` 使用新 Snapshot 的实际行号；`shown_lines` 为空表示输出按字节截断，重新读取后再编辑。`BACKEND_CAS_UNSUPPORTED`
表示当前远端 backend 无法安全比较并提交，切换到支持 CAS 的执行模式；不要用重复调用替代安全提交。`UNSUPPORTED_FILE_TYPE`
则表示编码、混合换行或二进制内容无法无损处理，应使用对应专用工具。

创建或编辑后的 `diagnostics.status=ok, count=0` 表示可用 LSP 已确认没有 diagnostics；`unavailable`
表示未启用或没有匹配的 LSP，`timeout` 表示只读检查超时。后二者不是“零错误”，但三种状态都不会撤销成功写入。
Harness 不会自动运行 formatter；如果用户或 IDE 显式格式化文件，原 Snapshot 变为 stale，应重新读取。

## 当前 Thread 的模型没有切换

`/model` 只改变下一次 Run，不会中断或替换正在执行、等待审批、等待问题、压缩或取消中的模型调用。请等待 Thread 回到空闲状态后重新选择并发送下一条消息；`run.started` 显示的实际模型是服务端权威结果。

选择后若提示“未来新 Thread 默认未更新”，当前 Thread 已成功切换；检查提示是否为 `config.write` 未协商、受管策略锁定、环境/CLI/显式配置覆盖、CAS 冲突、所选 Profile 缺少凭据或能力，或用户配置写盘失败。解决后再次执行 `/model` 即可；不要手工编辑 SQLite。该失败不会回滚当前 Thread 的选择，后续新 Thread 会继续使用原默认值。

若已恢复的旧 Thread 仍提示需要新建 Thread，通常是 CLI 与 sidecar 协商到了不含 `models.select` 的旧协议 minor。使用同一版本的 CLI 和 Python sidecar 重新构建/启动；不要通过修改 TOML 或直接编辑 SQLite 强制切换。选择不可用 Profile 或服务端拒绝 `run.start` 时，原有选择和历史 Run 不会被改写。

## 协议版本或序号错误

CLI 与 Python sidecar 必须来自同一发行版本。出现 `PROTOCOL_MISMATCH` 时，检查是否混用了旧的 Python 环境或 CLI 构建产物；源码开发时重新运行 `bun run build` 并确认 `HARNESS_AGENT_PYTHON` 指向本仓库虚拟环境。

如果输入 `/mcp` 后同时看到“Agent transport closed”和“MCP 状态查询失败”，通常是 sidecar 在返回 MCP 状态时已经退出。先停止并重新启动 Harness，确认 CLI 与 `packages/agent` 来自同一份源码；若仍复现，保留 sidecar stderr。当前协议允许 Plugin MCP 状态携带 `source` 字段，升级到包含该修复的代码后无需删除 MCP 配置或重新安装 Plugin。

thread 中出现“协议序号缺口”表示同一运行的事件不连续。界面会继续处理后续事件，但应保留 stderr 和终端截图用于诊断。不要把包含密钥、工具完整参数或企业路径的原始帧直接提交到公开渠道。

## 运行时 Skill 快照不一致

`RUNTIME_SKILL_SNAPSHOT_MISMATCH` 表示 AgentEngine Profile 使用的 Skill 快照与构图阶段拿到的快照指纹不同，通常由旧 sidecar 或旧代码残留造成。请完整退出 Harness 和 Python sidecar，再从仓库根目录用同一份源码重新启动；不要手工修改 SQLite 或删除 Skill 文件。当前实现会把策略裁剪后的 Skill view 与 Profile 使用同一指纹，并在 Skill catalog 更新时安全排空旧 Profile。

## 无法恢复 Thread

确认使用的是交互式 `harness --resume` 或 `/resume`，并且当前 project 与创建该 thread 时相同。`THREAD_NOT_RECOVERABLE` 表示索引存在但对应 LangGraph checkpoint 已不存在，重新开启一个 thread 即可。启动阶段如果看到 `THREAD_STORE_UNAVAILABLE: <detail>`，冒号后的稳定诊断码会进一步说明是迁移、权限、损坏还是版本过新；先完整退出旧的 Harness/sidecar 进程，并确认 CLI 与 `packages/agent` 来自同一份源码和虚拟环境，再根据该诊断码处理。不要在未备份前直接删除 `~/.harness/threads.sqlite3`、`-wal` 或 `-shm`。

当前版本会自动备份并迁移严格校验通过的 v1-v6 数据库；其中 v2-v6 的旧 PromptEpoch 会单向转换为 legacy RunContextSnapshot，无法证明的 Run 关联不会被伪造。合并前旧分支还可能把完整的 v6 表结构标成 `user_version=7`，只要它没有 Transcript、Context Snapshot 或 Compression 后继表，当前版本会识别该形状并按 v6 迁移，同时保留 Team 状态表和生成 `threads.sqlite3.pre-v7-migration.bak` 备份。`CHECKPOINT_MIGRATION_LEGACY_TABLE_UNEXPECTED` 仍表示 PromptEpoch 出现在无法证明来源的当前 v7+ schema，必须保留原库排查，不能通过手工修改 `user_version` 或直接删除旧表绕过校验。

`CHECKPOINT_MIGRATION_ATTEMPT_ACTIVE`、`CHECKPOINT_MIGRATION_RECOVERY_REQUIRED` 或
`CHECKPOINT_MIGRATION_WORKER_EXIT_UNKNOWN` 表示上一次 migration child 的退出尚不能在线证明。
不要删除 attempt、poison、state、backup 或 `.tmp`，也不要根据记录的 PID 手工判断可以继续。
先完整退出所有 Harness CLI、sidecar 和 migration worker，再在源码仓库执行只读诊断：

```bash
cd packages/agent
.venv/bin/python -m harness_agent.threads.migration_recovery \
  --database "$HOME/.harness/threads.sqlite3"
```

确认本机所有 Harness worker 都已停止后，才执行写入模式：

```bash
.venv/bin/python -m harness_agent.threads.migration_recovery \
  --database "$HOME/.harness/threads.sqlite3" \
  --confirm-all-harness-workers-stopped
```

命令只处理严格匹配当前 attempt 的固定 marker/temp，不扫描或终止 PID，也不会删除 verified
backup、主库或未登记文件。返回 `CHECKPOINT_MIGRATION_*` 而不是 `OK_*` 时保持现场并排查；不要
通过回退旧代码绕过，新版本 marker 收敛前旧代码并不认识这套失败关闭协议。

如果问题涉及尚未实现的能力，请先查看 [任务看板](../developer/task/任务看板.md)；若不是已知待办，请按 [开发工作流](../developer/project/开发工作流.md) 提供最小复现和日志摘要。

## Web 工作台无法打开或立即断开

`/web` 只在本机回环地址提供页面，浏览器必须能访问 `http://127.0.0.1:<随机端口>`；页面与 CLI 的全部连接都绑定 `127.0.0.1`，不会被防火墙或远程访问放行。产品不会在终端输出携带凭据的页面 URL；若系统默认浏览器没有打开，请检查 `open`/`xdg-open` 是否安装、当前环境是否允许启动 GUI 程序，然后重新执行 `/web`。启动失败只显示脱敏错误，并归还 TUI 输入权，不遗留监听端口。

页面在 65 秒内未完成初始化（浏览器未上报 ready）时，CLI 会把控制权归还 TUI。常见原因是浏览器阻止了页面与随机端口的 WebSocket 连接（企业代理、扩展拦截或 CSP 覆盖）。首次 URL 中的 bootstrap token 在页面打开后 60 秒内有效；renderer 接管成功后，页面改用只绑定当前 handoff、每次成功重连即轮换的单次 token，因此长时间停留后刷新不会因为首次 token 超时而返回 TUI。页面首次打开过慢或连接被代理拦截时仍会校验失败，此时重新执行 `/web` 创建新会话。

如果页面显示 `Web 接管链接无效` 或 `Web 接管不可用`，确认 TUI 与浏览器来自同一次 `/web`；源码开发或更新代码后重新运行 `bun run build` 并重启 CLI。浏览器 DevTools 中的 `[harness-web] bootstrap failed` 只保留截断诊断，不要复制包含页面 URL、token 或工作区路径的原始内容。

交互式 CLI 会把本地诊断写入 `~/.harness/debug/harness-<时间>-<进程>.jsonl`，默认级别为 `info`。需要排查 Browser bootstrap 时，用 `HARNESS_LOG_LEVEL=debug harness` 启动，再执行 `/web`；debug 模式会额外记录经过脱敏、单行化和长度限制的错误摘要。日志目录权限为 `0700`、文件为 `0600`，不会记录页面 URL、UI token、Prompt、JSON-RPC 原始 frame 或 Tool 内容。提交 Issue 前仍应检查并只提供相关行。

关闭页面会结束本次 Web 会话：CLI 归还表现层输入权给 TUI，返回 TUI 后仍是同一 Thread 与 Timeline。刷新页面会在短暂重连宽限内自动重连并重同步完整视图；宽限到期或重连失败才会结束会话。审批与问题使用页面内原生 UI 渲染，不依赖浏览器 `confirm/prompt` 对话框。

如果 TUI 一直停留在“正在回收控制权”，说明会话收敛未完成；先等待片刻（重连宽限默认 10 秒），之后重新执行 `/web` 重试或退出 CLI。不要把页面 URL 或 UI token 粘贴到日志、Issue 或截图。

## 上下文压缩被跳过或失败

`/compact` 会等待服务端的压缩终态，不再使用短于 Model Profile 请求时间的
通用 30 秒 CLI 超时。期间界面显示“正在压缩上下文”并禁止新输入；这些输入
不会被排队后自动执行。如果新版仍出现 `Timed out waiting for context.compact`
或连续的 `Unknown JSON-RPC response id`，先确认 CLI 与 Python sidecar 来自同一份构建，
再保留脱敏 stderr 和终端截图排查；不要在等待期间重复提交同一命令。

`context.updated` 的 `action` 明确区分 `auto_*`、`manual_*` 和 `overflow_*`：

- `manual_skipped` 表示历史不足、连最小摘要包装都无法缩小投影、没有完整 user/tool 原子组，或摘要后上下文没有严格减少。手动 `/compact` 不要求节省 20%，只要投影确实变小就会提交；明显无收益时不会调用摘要模型。
- `auto_skipped`/`overflow_skipped` 表示没有可回收内容、自动熔断开启或预计节省不足 20%。这不是成功重写，上一份 latest-valid checkpoint 继续使用。
- `*_failed` 表示摘要模型空结果、截断/结构错误、来源越界、投影膨胀或持久化校验失败；不会留下孤儿 Artifact、Summary 或 checkpoint。自动连续三次失败才会熔断，`/compact` 仍可手动尝试。
- `overflow_failed` 或 `CONTEXT_OVERFLOW_AFTER_RECOVERY` 表示已完成最多一次恢复重试；不要重复触发同一请求，先缩短输入或开启新 Thread。

排查时只记录 `action`、安全诊断码、token 预算和 checkpoint mode，不要把摘要正文、工具参数、凭据或 AGENTS/Skill 内容写入日志。`context.updated`/TUI 会安全区分 report、micro、full、overflow、skipped 和 failed；异常原文不会穿过 wire 边界。压缩成功后 Todo、审批/执行模式和当前 RunContextSnapshot 来自真实结构化状态；它们不会从摘要文字猜测，也不会重置 interrupt 或子图状态。

## AgentEnginePool 容量不足或资源关闭超时

`RUNTIME_POOL_CAPACITY_EXHAUSTED` 表示当前 AgentEnginePool 已达到 `max_profiles`，而所有已有 AgentEngine 都正在执行、被租用或固定，sidecar 不会为了接收新请求而中断它们。等待当前任务完成后重试，或在用户级 `[runtime_pool]` 中适度增大 `max_profiles`（最大 `64`）。

如果退出时日志出现 `AgentEngine close timed out`，说明某个 AgentEngine 的资源关闭超过 `close_timeout_seconds`。这不会删除 SQLite 中的 thread 数据；重启后可以恢复会话。先检查是否有未响应的工具、Sandbox 或 MCP 连接，再按需将该值提高到最大 `120` 秒。不要把完整 Prompt、模型凭据或企业路径写入诊断日志。

使用以下命令读取当前 sidecar 的脱敏 Pool 摘要：

```bash
bun run dev -- config show
```

输出中的 `runtime_pool_diagnostics` 会显示 Pool 大小、活跃 lease/run、命中/未命中、构建与关闭累计耗时、淘汰原因、关闭失败及最近生命周期事件。`file_tool_metrics` 额外汇总文件工具错误码、Snapshot expired/stale/未读范围、重读次数、edit 成功率、结果字节和 diagnostics 耗时；它不含路径、源码、`new_text`、完整 Snapshot ID 或凭据。`profile_id` 只是短诊断标识，不能用于推导模型、工作区或会话内容；`memory.status = not_collected` 表示当前版本不采集不稳定的进程 RSS，排障应先查看 AgentEngine 数量、淘汰与关闭结果。

## 使用本地诊断日志排查故障

当遇到执行异常、工具报错、模型超时或 MCP 连接问题时，可以使用内置的 `harness logs` 离线分析工具：

1. **查看最近 Thread 列表**：
   ```bash
   harness logs
   ```
   找到发生故障的 Thread ID 前缀。

2. **定位失败点与慢项**：
   ```bash
   harness logs --thread <thread-id-prefix>
   ```
   输出会自动指出失败点（例如某次 Tool 执行报错、MCP 连接失败、压缩异常）以及耗时最长的前 5 个慢项。

3. **开启临时 DEBUG 级别收集更详尽上下文**：
   如果默认 INFO 日志不足以定位问题，可使用环境变量开启 DEBUG 重跑：
   ```bash
   HARNESS_LOG_LEVEL=debug bun run dev
   ```
   DEBUG 会增加内部状态机决策、重试细节和脱敏异常栈。详细配置与规则见 [日志与诊断](日志与诊断.md)。

4. **逐事件表格排查与翻页**：
   ```bash
   harness logs --thread <prefix> --flat --limit 50
   ```
   可使用 `--level warn` 进一步收敛到告警/错误，并用底部输出的 `--cursor` 续页。

5. **提交问题前的脱敏复查**：
   虽然 Harness 日志引擎在任何级别都严格剥离了 Prompt、源码、完整命令、绝对工作区路径、API Key 与 Token，但在将诊断日志或 `--json` 结果复制给第三方前，仍建议快速检视是否包含企业内部特有的敏感命名。
