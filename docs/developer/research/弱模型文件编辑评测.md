# HC-131：弱模型文件编辑评测证据

> 功能 Task：[HC-131](../task/HC-131-统筹弱模型优先的文件读写可靠性.md)；功能设计：[HC-131](../spec/HC-131-统筹弱模型优先的文件读写可靠性.md)

## 结论

当前生产不能提前切换 Snapshot 文件编辑 schema。本功能已建立可复现的合成 fixture、纯内存
simulator、mock replay、指标和真实模型显式入口；但本次执行没有调用真实企业弱模型 Profile，
因此不把 mock 数字伪装成生产模型结论。

最终 ToolNode 路径已补齐实际写后 Snapshot/局部结果、可选 diagnostics 和去敏指标，
但仍未调用真实企业弱模型：当前用户明确要求不使用真实模型。该限制不改变生产 schema，仍不允许把
mock replay 或本地 contract 测试写成完成率、token、调用数、重读或延迟的真实模型报告。

按安全优先门槛，当前唯一 canonical 文件编辑路径仍是：

```text
read → exact-string + prior-read → 既有 Policy / Approval → 失败时重读
```

Snapshot 单区间、Snapshot `edits[]` 和两种插入语义保持为评测候选，不能在缺少真实证据时固化。

## 评测实现

评测代码位于 `packages/agent/evaluations/zc133/`，该目录不在 `za38-agent` wheel 的生产包
列表中；自动测试位于 `packages/agent/tests/evaluations/`。simulator 使用内存 backend，
不调用生产文件工具、不修改当前仓库，也不依赖真实模型。

固定 fixture 版本为 `zc133-v1`，共 25 个合成场景，覆盖：

- 单行/区间替换、删除、显式插入、空文件插入和多处非重叠修改；
- 重复文本、相似函数、长文件局部读取、超长行；
- BOM、CRLF、无末尾换行；
- read 后外部修改、审批后提交前修改、Snapshot 淘汰、跨 Thread、错误路径；
- 未读范围、重叠 edits、已有文件误用 write、畸形参数恢复、无变化和非法范围。

比较的候选为：

1. `exact-string + prior-read` 基线；
2. Snapshot 单 edit，分别使用显式 `insert_before/after_line` 和仅供对照的 zero-width 语法；
3. Snapshot `edits[]`，分别使用显式插入 action 和 zero-width 语法。

simulator 对每个候选验证 Thread/path/backend、强内容身份、已读范围、范围合法性、重叠、
全量预检和零写入失败。安全指标单独统计 `silent_corruption` 与 `partial_write`；完成率、
schema 合法率、恢复成功率、估算 token、工具调用数、重读次数和延迟使用 95% Wilson 区间
或中位数。mock token 是固定字符估算值，不声称是真实 tokenizer 统计。

## Mock replay 结果

命令：

```bash
cd packages/agent
./.venv/bin/python -m evaluations.zc133 --repetitions 3 --output-dir /tmp/zc133-report
```

每个候选运行 25 个 fixture、重复 3 次，共 75 次。结果如下：

| 候选 | 安全 | 完成 | 完成率 95% CI | silent corruption | partial write | schema 合法率 | 中位输入/输出 token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `exact-string` | 75/75 | 63/75 | 0.840（0.741–0.906） | 0 | 0 | 0.840 | 18 / 35 |
| `snapshot-single-explicit` | 66/75 | 66/75 | 0.880（0.787–0.936） | 3 | 6 | 1.000 | 18 / 42 |
| `snapshot-single-zero-width` | 63/75 | 63/75 | 0.840（0.741–0.906） | 6 | 6 | 1.000 | 18 / 42 |
| `snapshot-edits-explicit` | 72/75 | 72/75 | 0.960（0.889–0.986） | 3 | 0 | 1.000 | 18 / 45 |
| `snapshot-edits-zero-width` | 69/75 | 69/75 | 0.920（0.836–0.963） | 6 | 0 | 1.000 | 18 / 45 |

mock replay 中相似函数 fixture 的“合法但错误行号”会造成 Snapshot 候选 silent corruption；
多 edit 的单区间候选还会暴露 partial write。它们均被安全门槛一票否决。该结果只证明
simulator 能捕获风险，不证明任一 schema 在真实弱模型上的完成率。

## 真实模型评测入口

真实调用必须明确指定 Profile、重复次数和输出目录；默认命令永远只运行 mock：

```bash
cd packages/agent
./.venv/bin/python -m evaluations.zc133 \
  --real-model \
  --profile <企业弱模型-profile-id> \
  --repetitions 3 \
  --output-dir /tmp/zc133-real-report
```

真实入口复用用户/显式配置中的 OpenAI-compatible Profile。它只向模型发送合成 fixture，
报告仅保留 Profile 摘要、fixture ID、候选名称和聚合数字；不记录 API Key、Header、endpoint、
源码、工具参数或模型原始响应。自动 pytest 和默认 CLI 不会调用真实模型。

## 决策门槛与后续

- 任一候选出现 silent corruption，立即淘汰；完成率不能抵消安全失败。
- 候选完成率的置信下界必须不低于 exact-string 基线，再比较 token、调用数、重读和延迟。
- 真实 Profile 评测完成前，HC-131 设计保留 exact-string + prior-read canonical 路径。
- 不得把候选 Snapshot schema 写入生产工具；只有真实评测产生足够证据后才能更新 Design。

## HC-185：同文件批量 `edits[]` 候选（2026-10-22）

起因：10-20 至 10-21 的日志里 `edit_file` 失败 19 次，其中 `COMMIT_CONFLICT` 15 次、`STALE_FILE` 3 次，没有一次是文本匹配失败。模型在同一轮对同一文件连发 3 到 8 个 `edit_file`，它们共用一个 `snapshot_id`，第一个成功后凭证作废。

新增候选 `exact-string-edits`：一次 `edit_file` 带 `edits:[{old_string,new_string},...]`，每项仍是精确、唯一、已读范围内的字符串匹配，**不使用行号**，所以不存在上表里 Snapshot 候选的“合法但错误行号”风险。规则对照 [HC-185 Spec](../spec/HC-185-同文件批量编辑.md) §3，在 simulator 中独立实现（不 import 生产代码）。

新增独立 fixture 目录 `batch_fixture_catalog()`（版本 `hc185-v1`，16 个），**不计入**上面 25 个原 fixture 的决策统计，因为基线在“同轮多编辑”里按设计会失败，计入会让对比失真：

- `same-turn-2-edits`、`same-turn-8-edits`（对应线上 Run `1327ba32`）：基线对同一 `snapshot_id` 连发扁平调用且**不重读**，新候选只发一次调用；
- 批内成功：首尾相接的两处、`edits` 顺序与文件顺序相反；
- 批内失败：某项找不到、某项不唯一、两项完全相同、一项包含另一项、某项在已读范围外、空 `old_string` 与其他项混用、超过 20 项；
- 畸形入参：空数组、非数组、项缺字段、项多字段、项字段非字符串。

运行（mock，重复 3 次）：

```bash
cd packages/agent
./.venv/bin/python -m evaluations.zc133 --repetitions 3 --output-dir /tmp/hc185-eval
```

原 25 个 fixture（每候选 75 次）：

| 候选 | 安全 | 完成率 | silent corruption | partial write | schema 合法率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `exact-string` | 75/75 | 0.880 | 0 | 0 | 0.920 |
| `exact-string-edits` | 75/75 | 0.920 | 0 | 0 | 0.960 |

两者的差别只有 `overlapping-edits`：基线的扁平入参无法表达“同批两处”，replay 只能发一个残缺调用，新候选能真实触发并拒绝重叠。其余 fixture 的成败完全相同（`duplicate-text` 的 `AMBIGUOUS_MATCH` 与 `invalid-range` 的 `INVALID_EDIT` 两者一致）。所以这里的完成率差异来自基线无法表达批量，不应解读为 `edits[]` 在单处编辑上更强。

`hc185-v1`（重复 3 次）：

| 候选 | 次数 | 完成率 | silent corruption | partial write | 中位调用数 | 错误码分布 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `exact-string`（仅 same-turn） | 6 | 0.000 | 0 | 6 | 5.0 | `STALE_FILE`×6 |
| `exact-string-edits` | 48 | 1.000 | 0 | 0 | 1.0 | 全部与预期错误码、`edit_index` 一致 |

基线 6 次全部在第二个调用起复现线上的 `STALE_FILE`，且已有前一个调用写入，属于部分写入；新候选 1 次调用完成，批内失败场景全部零写入并报告了正确的 `edit_index`。

对照 Spec §9 的四条通过标准：

1. 全部 fixture 上 `silent_corruption = 0`、`partial_write = 0`：**通过**。
2. `same_turn` 场景 1 次调用完成、基线复现 `STALE_FILE`：**通过**。
3. 原 fixture 上完成率 95% Wilson 区间下界不低于基线：**通过**（新候选 0.920，区间 0.836–0.963；基线 0.880，区间 0.787–0.936）。
4. 失败项场景全部零写入并报告正确错误码与 `edit_index`：**通过**。

局限：mock 只能验证服务端规则，**无法衡量弱模型生成嵌套 JSON 的出错率**。该风险由 Spec §2.1 的严格形状校验、带 `edit_index` 的清晰错误和工具描述兜底；真实企业模型评测需要用户另行明确允许。`mock` 模式下 `decision` 仍保持 `exact-string`，报告原因里会列出通过门槛的候选，作为设计评审输入而非生产结论。
