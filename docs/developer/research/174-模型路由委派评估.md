# 模型路由与任务委派：可行性评估

评估日期：2026-09-10。Harness 源码基线：`9847474`；参考 orchestrator 基线：`9c2a984`。

本文是研究结论和候选方案，不是已确认的 Task、Spec 或实施计划。本轮没有开发代码、修改运行配置或调用真实模型做效果评测。附件中的规则仅作为被评估材料，不视为实施指令。

后续确认（2026-09-10）：用户已按 [HC-174](../task/HC-174-实验性子代理模型分工.md) 直接作为实验功能推进内建 `explore` / 可选 `general-purpose` 的角色模型绑定；第 6 节验证路线 A–E 与“先测收益再扩大”不再构成本任务验收。本文保留为源码事实与否决项依据。

## 结论

可以落地，值得先做范围很小的验证。最有价值的部分是：让低成本子代理承担有边界的代码探索，把阅读过程留在子代理上下文，给主模型返回带证据的短结果。其次才是规格明确、能够自动验证的代码实现委派。

不建议照搬附件的“四层路由 + Mode 平台 + bash 脚本 + 350 行强制 Hook”。Harness 已有大部分基础设施，直接扩展既有 AgentCatalog、task、Managed execution、ModelProfile 和权限链更合适。

`codex-astra-luna-orchestrator` 与 Portal 的共同目标是减少强模型处理机械工作的开销，但粒度不同：前者组织完整任务的分工，后者卸载大块输入输出。两者可以组合借鉴，不能把它们当成已经实现相同功能的两个系统。

是否最终省钱、提速，仍取决于企业实际可用模型的能力、价格、缓存和重试率。配置中称为 `flash` 不代表适合代码工作；小参数本地模型也不能直接类比 Luna。

附件同时假设“主模型能力弱”与“主模型 pro 负责高质量规划”，两者需要在实际部署中澄清。卸载阅读只能减少干扰，不能凭空补足推理能力。若企业暂时没有合格的强模型，仍可验证只读探索的上下文收益，但不应把它宣传成架构设计和复杂调试能力的升级；若采用强主模型，应通过既有模型选择明确启用。

## 1. 原文证据与附件偏差

原文为 Spotify Engineering 于 2026-09-03 发布的 [Portal by Spotify cut my Claude Code token usage by 90%](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90)。它描述两个 worker：读取后摘要，以及参照已有模式生成新文件。报告的是特定案例的主模型上下文节省，且指出推理质量与委派延迟的限制。

继续核查原文链接的 [shunt 仓库](https://github.com/sorantis/portal-ai-plugins/tree/add-shunt-claude/plugins/shunt) 后，需纠正以下推导：

| 附件中的判断 | 核查结论及影响 |
| --- | --- |
| 读、写都通过 Hook 强制委派 | shunt README 明确只有 bulk-reader 有 Hook 强制机制，code-writer 依赖 Skill 和模型选择。不能认为生成路由已获确定性验证。 |
| 写代码节省约 90%、成本约 75%；安全审计约 500 output token | 已读文章与其链接 README 未给出这组完整证据，不能作为 Harness 收益承诺。 |
| 三层插件结构验证了四层智能路由 | Hook、脚本、Skill 是插件组织方式；pro/flash 档位、灰区分类和自动升级是附件作者增加的设计。 |
| 编辑不能委派 | 原文场景中，摘要不能替代编辑前读取；不等于有权限、有原文和验证能力的执行子代理不能编辑。 |
| worker 不存会话意味着只能一次模型调用 | 一次独立子任务可以含多次模型和工具调用。`max_rounds: 1` 与依赖工具逐页读取的探索任务并不匹配。 |

公开的 [benchmarks.json](https://raw.githubusercontent.com/sorantis/portal-ai-plugins/add-shunt-claude/plugins/shunt/evals/benchmarks.json) 明确以字符数除以 4 估算上下文 token。[run.sh](https://raw.githubusercontent.com/sorantis/portal-ai-plugins/add-shunt-claude/plugins/shunt/evals/run.sh) 比较全文与摘要长度，生成场景还以固定系数加权输出；它没有计算完整主模型、worker、复核、失败重试的总账，也没有以正确率作为收益分母。这证明了上下文卸载的可能性，不能替代生产成本与质量评测。

另外，在主模型已经发出带完整代码的 `write_file` 调用之后，PreToolUse 才拦截，主模型生成代码的 token 已经花掉。要节省这部分成本，必须在生成开始前按任务委派，不能靠写入 Hook 事后补救。这是对执行顺序的分析结论。

## 2. Harness 当前具备什么

| 能力 | 当前源码事实 | 对方案的意义 |
| --- | --- | --- |
| 命名模型配置 | 使用 TOML ModelProfile；Plugin Agent 可引用已有 Profile | `pro`、`flash` 可直接作为 Profile ID，首期不必增加 tier_mapping |
| 内置子代理 | `general-purpose`、`explore` 是 Inline 子图，使用传入的父模型 | 现有子代理已能隔离阅读过程，但不会自然变成低价模型 |

## 3. codex-astra-luna-orchestrator 的借鉴价值

本地项目是 Codex 的配置、角色文件、Skill、安装脚本及用量统计脚本集合，不是可移植到 Harness 的独立编排引擎。该项目没有自己的运行时队列、Hook 调度器或 Portal 式输入输出转送服务。

| 维度 | Portal / shunt | codex-astra-luna-orchestrator | Harness 的取舍 |
| --- | --- | --- | --- |
| 分工粒度 | 大块读取和模式化生成 | 探索、实现、测试、审查等完整工作包 | 先探索，后明确规格的实现 |
| 路由入口 | 读取 Hook + Skill/脚本 | 主模型遵守 Skill 并 spawn 指定角色 | 既有 task、AgentCatalog 与 Profile |
| 强模型职责 | 主要推理与修改 | 设计、拆解、集成和独立审查 | 保留关键判断与验收责任 |
| 便宜模型能否编辑 | 案例重点是新文件 | worker 明确允许有边界的实现 | 经评测后允许，仍走文件契约 |
| 硬约束来源 | 特定读取 Hook | 模型/沙箱/并发等宿主配置；委派流程主要是提示词 | 权限和生命周期放在 Harness runtime |
| 收益证据 | 特定上下文缩减测量 | 事后用量工具与单次样例，无对照 benchmark | 必须做本地三组对照 |

具体可借鉴：

1. root 保留架构和整合职责，worker 只完成已界定范围，遇到设计问题上报。
2. 委派写清目标、范围、必要上下文、限制、交付物和验收条件。
3. 独立任务并行，有依赖的任务顺序执行；同一文件尽量只有一个执行者负责修改。
4. reviewer 使用独立上下文和足够能力的模型，关注实际 diff 与证据。
5. 同时统计主、子代理用量，避免只看主模型减少了多少输出。

不建议照抄“凡跨文件就必须 spawn”或给每个任务固定安排 explorer/worker/tester/reviewer。独立上下文也会重复加载提示和资料，主模型等待、整合和复核都增加成本。该项目的用量指南本身也提示编排开销，所列单次样例明确不是 benchmark。

## 4. 推荐的最小方案

### 4.1 只保留一条委派执行链

```text
用户任务
  → 主模型明确问题、范围和验收
  → 既有 task + AgentCatalog 选择受信角色
  → 解析该角色的 ModelProfile 和有效权限
  → 既有 Inline / Managed execution
  → 子代理完成有界工作
  → 有界证据摘要返回主模型
  → 主模型按需读取原文、复核并继续
```

模型绑定以子执行为单位确定，不在同一 AgentEngine 内因一次工具调用而偷偷更换模型。父 Run 的用户选择与历史模型事实保持准确；升级由新的子执行承接，明确记录实际 Profile 和原因。

首个试点使用受信 Plugin Agent 绑定低价 Profile，复用现有 Managed 路径。若试点证明有收益，再决定是否让内置 explore 支持独立 Profile；同一个角色只保留一个 canonical 配置与执行入口。

“能通过现有配置跑通”与“可作为可靠产品交付”要分开。受信 Plugin 绑定已有 `flash` Profile 已经可行；完整子任务用量归账、实际输出契约校验、有界升级仍需补运行时实现。首期实验可按 execution ID 从诊断事件核对用量，但必须检查覆盖与去重；正式功能应将 child 用量贯通执行结果和归账，避免遗漏与重复计算，不能只改界面显示。

不新增 `settings.yaml`、Mode registry、Portal 服务依赖或旁路模型调用脚本。共享能力已有 Plugin 的发布和信任机制，无需首期加入同名个人覆盖与团队模式市场。

### 4.2 首期只有只读探索 worker

输入包含：明确问题、工作区内范围、希望返回的证据、工作预算。不要复制父对话的完整历史，也不要让父模型先读完所有文件再转交。

worker 先用 glob/grep/LSP 定位，再通过 canonical read_file 分页读取。没有 Shell、写入、外部网络工具和嵌套委派。原始代码进入 worker 上下文；模型服务能否接收这些代码仍取决于该 Profile 的数据访问许可，模型强弱不是数据许可。

简单文件清单、符号定位或精确字段提取优先由现有搜索与解析工具完成。只有需要跨文件归纳时才付出一次子代理的开销；“可以委派”不代表“必须再调用一个模型”。

返回结果包含：

- 结论与关键符号；
- 实际读取的文件与源行区间；
- 支撑关键判断的短原文；
- 尚未查到、未覆盖或不确定的部分；
- 执行状态与成本信息。

结构正确不代表事实正确。范围和引文应能由工具读取记录核验；模型自己生成的行号只作导航。主模型准备编辑时仍须自己或由被授权执行者取得有效 Snapshot，不能把摘要当作已读证明。审计原文可保存，但不要通过 tool result、历史投影或错误反馈重新全部塞回主上下文。

### 4.3 先测收益，再考虑读预算门禁

第一阶段不强制拦截所有大文件。当前读取已分页，主要收益来自多文件、多轮搜索的过程隔离。

如果数据表明主模型持续重复、广泛读取，再在 Python 工具/上下文边界加入预算策略：考虑实际返回字节、估算 token、累计阅读量和当前窗口余量，优先建议委派或缩小查询。不能仅凭文件总行数拒绝一次精准读取，也不能仅因存在 offset/limit 或管道就认定输出很小。

`cat file | cat` 仍可能返回全文，`grep` 也可能命中全文件。不要用 Shell 命令字符串分类替代实际输出预算。对只读 worker，直接不提供 Shell 比尝试识别所有绕路方式更简单。

读取工具不能被透明替换为摘要工具：它们的内容和 Snapshot 语义不同。若门禁拒绝，应返回明确理由和可行下一步；worker 不可用时仍应允许受预算约束的精准阅读，避免拒绝循环。

### 4.4 写代码委派在第二阶段验证

适合任务：有明确规格和参考模式、范围有限、能运行针对性检查的新文件、测试补齐、局部机械修改。

主模型先确定行为、边界和验收，再委派；worker 使用既有 Snapshot 文件工具，按文件划分所有权，复用审批和并发保护。返回变更摘要、文件列表、验证结果和未解决问题；不能只返回“已写入”就宣布完成。

复杂调试、安全、并发、协议和生命周期的设计与最终评审由能力足够的模型负责。是否允许 worker 修改已有文件，应由任务明确程度、模型实测能力与验证质量决定；不以“新文件/旧文件”作为唯一难度标准。

自动升级仅在明确失败、契约不满足或 worker 主动报告能力不足时有界触发。只读任务可重新执行；写任务必须先确认是否已有修改，重新读取当前状态后继续，不能把超时视为没有副作用而盲目重跑。权限拒绝不能靠换强模型绕过，用户取消后不能再启动升级。

## 5. 不采用附件中的哪些设计

1. 不把四层路由一次做全：首期只需受信角色绑定和现有权限检查，灰区分类器没有必要。
2. 不把路径包含 auth 当成安全识别的充分条件：风险取决于实际行为和数据流；密钥文件也不应因为换成 pro 就获得读取许可。
3. 不默认启用 economy_mode 并把 inherit 全降为 flash：用户明确选择、审查角色要求和模型可用性优先。
4. 不把所有“读源码”都归为机械 I/O：理解跨模块约束、缺陷和并发语义本身需要推理；摘要可能遗漏关键证据。
5. 不承诺一周上线、覆盖 80% 或节省 90%：这些数字没有 Harness 本地证据。
6. 不依赖“去除 Markdown 围栏”解决提示注入：格式清理与不可信文件内容影响模型是不同问题，权限仍由 Host 强制。

## 6. 验证路线与是否继续的门槛

以下是候选验证顺序，不是已批准执行的开发 Todo。

| 顺序 | 范围 | 可观察结果与继续条件 |
| --- | --- | --- |
| A | 选定真实 pro/flash 候选和代表任务，保留现有基线 | 确认便宜模型能稳定使用文件工具、理解中文规格并提供可核验结果 |
| B | 一个只读 Plugin worker，显式委派；先核对计量覆盖 | 父上下文仅收到有界结果；完整记录根与 child 的质量、模型用量、耗时和失败 |
| C | 比较直接执行、同模型 explore、低价 worker | 区分“上下文隔离收益”和“换便宜模型收益”，质量不降且成本/上下文有实际改善才推进 |
| D | 按观察到的问题补预算门禁与有界升级 | 不阻塞必要精准读取、不出现递归委派或拒绝循环，升级可追溯 |
| E | 开放少量有清晰验收的写任务 | 实际测试与独立复核通过，返工计入总账后仍有收益 |

指标应至少包含：主模型峰值上下文、各 Profile 输入/输出/缓存 usage、worker 用量、复核与重试、任务总耗时、成功率、证据错误与漏检率。网关不返回 usage 时标记未知或估算，不能当作零；自托管还应看 GPU 时间、吞吐与排队。

```text
任务总成本 = 主模型 + worker + 复核 + 重试/升级
单位成功任务成本 = 所有尝试总成本 / 成功完成的任务数
```

探索评测同时覆盖：已知符号定位、跨文件调用关系、未命中搜索、小文件、大文件、容易被摘要遗漏的反例。写任务覆盖：清晰新文件、局部已有文件修改、测试失败、并发冲突和取消/超时。只看摘要变短或测试程序退出成功不足以验收。

推荐先投入只读试点。若低价 worker 的遗漏导致主模型经常重新读全量源码，或主模型本身已很便宜且上下文压力不高，则暂不继续扩大路由系统。
