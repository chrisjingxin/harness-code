# HC-198 会话交接与内容引用预研

> 2026-11-09；供 [HC-198 Task](../task/HC-198-会话交接与内容引用.md) 后续 Spec 评审使用，不是已批准的 Spec、实施计划或产品验收。主仓库只读源码基线为 `harness_lody@7fe0aa2c899a576fa8cb5477a3db0afc4bc378d5`；HC-205 正在同一工作树并行实施。本稿中的“建议”均需对应负责人和统筹审查。

## 1. 用户怎样使用

**交接。** A 在共享会话里选择同工作区的普通用户 B，填写可为空的“已确认事项、下一步、待定问题”并发起。会话时间线出现待接手记录，当前接续人仍是原来的人。B 打开同一个会话并确认后，时间线显示已接手，接续人变为 B；A 也可以在确认之前取消。其他成员仍可以正常参与。原机器离线时仍能记录和确认交接，并查看已有云端历史；后续执行要看原设备、项目、Agent 和授权是否可用。

**引用。** 用户在输入区输入 `@`，查找同工作区可访问的会话或消息，选择有界消息范围或一段正文；服务端固定当时已同步的内容并返回可查看的预览。来源继续输出不会改变这份草稿；用户点“刷新”才产生新草稿并重新预览。发送时服务端再次检查权限和草稿归属，在保存消息与排队执行的同一事务中保存引用和最终输入。历史里可展开原快照，并通过来源定位到原会话和消息；无法定位时保留已发送内容并明确提示。

这两条路径保留用户确认的界面方向：[HC-206](../task/HC-206-既有对话视图复用.md) 增量复用中间对话和输入，[HC-208](../task/HC-208-协作导航与桌面布局.md) 负责新增协作导航和顶栏，[HC-202](../task/HC-202-桌面工作台视图迁移.md) 装配真实数据；不重新画中右区域。产品边界以[顶层设计的交接和引用章节](../architecture/多人协作工作台顶层设计.md#7-任意用户之间交接)及 Task 为准。

## 3. 同一个会话怎样交接

### 3.1 建议的状态和不变量

| 原状态 | 操作人和动作 | 提交结果 |
| --- | --- | --- |
| 无待接手 | 任一有会话访问权的普通成员发起，目标是同工作区另一启用成员 | 新建一条 `pending`，追加时间线事件；`current_user_id` 不变。 |
| `pending` | 仅该记录目标用户确认，且提交时仍为启用成员 | 同事务把记录改为 `accepted`、将同一会话的 `current_user_id` 改为目标、追加一次事件。 |
| `pending` | 仅该记录的发起人取消 | 同事务改为 `cancelled` 并追加一次事件；当前接续人不变。 |
| `pending` | 再发起另一笔 | 返回已有待接手的明确结果，不覆盖原记录。 |
| 已处理 | 同一请求重试；或另一个过期动作 | 授权范围内相同请求重放首次回执；过期/相反动作返回已处理或冲突，不再改状态或产生事件。 |

接续人是协作信息，不是岗位、设备所有者或排他发送许可。发起人也不必等同当前接续人；交接不修改历史作者、设备凭据、原项目、配置或原生会话标识，不复制消息，不发隐藏摘要请求。正在运行的输入按原执行事实继续；B 后续消息仍以 B 的登录身份进入原会话队列。首版不引入自动过期。

### 3.2 最小事务与同步接入建议

1. 身份从服务端登录会话取，按工作区确认操作人及目标用户；发起、确认、取消都带稳定请求 ID 和交接 ID/预期状态。只读授权不是并发保护，提交时还要按第 5 节与停用/移除成员的写入协调。
2. 在单个短事务内锁同一 `wb_conversation` 行，再检查该会话当前待接手记录。所有交接写入口都遵循同一锁与条件更新，保证并发发起只产生一笔待接手；可在后续迁移增加数据库唯一约束作为防线，但具体做法和 TDSQL 支持需验证，不能只靠页面按钮禁用。
3. 确认或取消按交接 ID、会话、操作者和 `pending` 条件更新；只有更新成功的一方分配 `sequence` 并写事件。确认同时更新 `current_user_id`。两者竞争时先提交的一方生效，另一方重读已处理事实；回滚时状态、接续人、事件、回执一起回滚。
4. 复用 `wb_request_receipt` 的工作区、用户、操作、请求 ID 作用域，比较包含目标、说明、会话及动作的完整确定性业务正文。相同正文回放原结果，不同正文冲突。并发唯一键碰撞要先回滚失败事务，再重读并区分“同请求重放”和“已有另一笔 pending”，不能把所有唯一键错误都当成功。若交接复用公开回执查询，同步扩充 RequestOperation 和返回类型（旧 conversation.schema.json 已随 HC-211 拆除）及[路由操作校验](../../../services/collaboration-server/src/main/java/workbench/collaboration/interfaces/http/RouteCatalog.java)，当前两处只接受会话创建、发送和执行取消。
5. 交接作为新的具名会话事件进入现有连续序号和历史/SSE 投影；事件带稳定交接 ID、操作者、目标、状态及必要说明，确认事件能投影新的当前接续人。`ConversationSummary.currentUserId` 提供刷新后的当前值；断线后从历史/游标补齐，重复事件按 ID/序号应用一次。现有 `wb_message` 的 `execution_id` 非空且作者只区分 user/agent，不宜把交接硬塞成一条伪造的 Agent 或用户执行消息。

新表、索引及必要字段应通过后续**新增**版本化迁移提出，由统筹协调最终版本与 Foundation 校验；不修改已经使用的 V001–V003，也不在本稿分配新编号。事件 schema、Java DTO、客户端校验和投影需要一起审查。

### 3.3 离线、历史和执行是三件事

- **交接**依赖云端身份、会话与交接记录，不依赖原 Runner 在线；B 仍须具备会话访问资格。
- **历史**来自云端已提交事件，成员资格有效时可读；项目停止共享后已有共同历史仍可读。来源尚未同步的内容不能凭本机离线推测。
- **新执行**仍绑定原 `deviceId/projectId/agentConfigId/nativeSessionId`。共享目标有效但离线或配置暂不可用时，现有实现允许保存 queued，实际派发要等 ready/能力和授权；停止共享、设备撤销、成员失效等须按原执行规则处理，不等同离线排队。已经派发的工作、未知结果和恢复也保持 HC-195/196 的原事实，不迁机或自动重跑。
- 首次 `nativeSessionId` 可以为空，原 Runner 产生并回传绑定后后续命令沿用同一不透明标识；已有绑定无法恢复时应明确失败，不能悄悄另建会话冒充续接。真实 ACP 能否做到这一点由 HC-197 和真实后端另验。

## 4. 引用怎样做到所见即发送

### 4.1 查找、选区和固定草稿

1. 以登录用户和当前工作区为入口，按现有会话读取权限查找会话/消息，限制结果数量与分页；服务端负责范围过滤，不把搜索结果泄露给非成员。现有会话列表是按创建时间分页，历史是按事件序号读取，**并没有**跨会话全文搜索或按消息 ID 跳转接口，需要新增具名查询和必要索引。
2. 用户选择消息或有界消息区间、单条消息内选区。服务端核对稳定会话/消息 ID 与先后顺序，从已提交的文本中截取；同一次预览读取的会话高水位、消息正文和选区必须属于一致的已提交视图。流式消息也可以引用，但预览标明捕获范围/当时状态。
3. 服务端在同一工作区保存不可变引用草稿，包含创建者、来源会话与消息 ID、顺序/选区、固定正文、捕获时点及校验摘要。预览正文来自这份服务端记录，不接受桌面提交的任意文本冒充来源。摘要用于完整性核对，不代替实际正文和授权检查。
4. 刷新是显式新建草稿并展示新正文；原草稿不原地替换。来源标题变化只影响展示标签策略，不改变固定内容或稳定 ID。来源离线但云端历史仍可读时可从已同步部分预览；删除、取消访问或草稿过期等情况按明确错误处理。

选区单位、消息顺序、换行和 Unicode 边界必须在 Spec 中确定；例如不能让 Java 的 UTF-16 下标与 JS 的字符或 UTF-8 字节下标混用而切断 emoji。一次整段会话引用应要求用户选择有界消息，不默认把工具正文或全部历史注入模型。

### 4.2 一次发送只提交一个固定结果

建议由 HC-195 与 HC-198 共同在现有 `ConversationService.sendInput` 的**同一事务入口**接入，而不是另起一条“先发普通消息、再补引用”的路径：

```text
登录用户 + 工作区 + 目标会话 + 问题正文 + 有序草稿 ID
  → 先检查相同 requestId 是否已有合法回执
  → 新请求重验目标/来源访问和每份草稿的用户、工作区、来源及完整性
  → 从固定草稿构造并校验最终普通文本及可公开事件大小
  → 同事务保存用户消息、正式引用快照、固定执行输入、queued 执行、事件和回执
  → 提交后返回已保存；原设备准备好时再由既有调度器生成 execution.start
```

建议正式引用记录保存来源位置和快照本身，并绑定当前消息/引用顺序；问题正文与引用在历史中可分别展示。将**最终执行文本**作为同事务写入的一份不可变执行输入，后续派发只读取这份输入，而不是实时重新查来源或在 UI 重新拼装。普通无引用输入也走同一条执行输入路径，避免两套行为。具体存储位置、事件载荷和 HC-195 的事务内窄接口由 Spec 与负责人共同确定；这需要改造当前派发器直接读取 `wb_message.text` 的位置，不表示现有代码已经有该字段。

若采用独立的执行输入字段，迁移时从已有用户消息一次性补齐 V003 中尚未派发的执行输入，再统一派发读取方式。已经保存的 start 正文及摘要在恢复时继续原样使用。

已有成功回执的相同重试，在当前用户/工作区及目标会话仍可读的前提下返回首次结果；它不重新发一条消息，也不因来源后来变化而改写已保存事实。第一次提交或更换请求 ID 的新提交则必须重新检查所有来源和草稿：来源不可读或归属不符时整次拒绝，提示刷新或移除，不能悄悄丢掉引用只发送问题。相同 requestId 但问题、目标、有序草稿 ID 或其他业务正文不同必须冲突；草稿 ID 的顺序和重复出现语义需明定。提交失败时消息、引用、执行、事件、序号和回执全回滚。

### 4.3 可验证的“一致”定义

设草稿按用户排列为 `D1…Dn`，每个 `Di` 的正文是服务端预览时保存的原文；用户问题为 `Q`。Spec 应固定一种版本化、确定且可无损还原原文的普通文本包装 `F`，包含引用边界/来源标签及 `Q`。包装、转义、换行、顺序必须让用户可在发送前查看，且不得静默裁剪或改写 `Di`/`Q`；来源内容只是参考资料，不获得系统指令或执行权限。

- **预览**：每个草稿显示其准确来源、范围和完整 `Di`；总预算或包装造成超限时在发送前提示缩小/移除。用户能查看会送出的完整文本或明确可见的包装效果。
- **已保存历史**：展开正式引用得到的正文逐字节等于预览过的对应 `Di`，顺序和来源位置一致；在可读目标会话中保留它，不依赖来源后来仍存在。展示卡片、作者和问题文字可以是结构化呈现，不要求屏幕像素与线协议字节相同。
- **执行输入**：保存的不可变执行文本等于 `F(Q, D1…Dn)`；生成的 `execution.start.payload.input.text` 和 Runner 交给 ACP 端口的普通文本等于这份保存值。重试/恢复重用已登记的原输入和原 start，不重新截取来源。测试应比较预览/正式快照的 UTF-8 字节、包装结果、start 和真实端口收到的文本，而非只比较引用 ID 或摘要。

第一次生成 start 时原生会话 ID 可能尚为空，之后绑定不会回写已保存的原 start 和指纹；下一次输入才使用已确认绑定。以上保证输入交付，不保证任何模型如何理解引用。来源文本可能含指令或伪造分隔符，包装要有确定的转义/边界规则，不能把引用提升为平台授权。

### 4.4 来源定位与读取边界

正式引用应保存工作区、来源会话、消息 ID 和足以定位的消息创建序号/选区；点击时重新按当前账号检查来源访问，打开原会话并定位消息。当前历史接口是 `afterSequence` 之后的事件，可评估以消息创建序号前一位置加载并补齐；长历史、后续追加片段、分页和已删除消息仍需明确 UI 定位协议。不能把一个任意标题或 URL 当授权凭据。

来源不再可读或不存在时，目标会话的已发送快照仍可展开，来源入口显示不可用，不去读取或猜测其他来源。项目停止共享但该成员仍可读云端历史时，不应简单把“停止共享”等同来源不可读；当前代码没有完整会话删除/逐会话 ACL，未来接入时需定义其可读性及竞争规则。

引用发到目标会话后，快照属于该会话中可被其成员阅读的内容。当前以同工作区成员为主要读取边界；如果以后出现来源和目标的不同可见人群，Spec 必须另行裁定发送时如何防止向无权阅读来源的人扩散，以及已发送快照继续可读的边界，不能只验证发送者个人权限。

### 4.5 大小限制：规格与已核对实现分开

[HC-195 Spec](../spec/HC-195-共享会话与实时同步.md) / [HC-196 Spec](../spec/HC-196-设备接入与本机执行.md) 规定当前用户和执行文本均最多 **32 KiB UTF-8、16,384 个 Unicode 字符**，拒绝 NUL/未配对 surrogate；输入 HTTP JSON 正文最多 **64 KiB**，公开事件编码最多 **64 KiB**，执行命令编码最多 **128 KiB**。未来扩容需 HC-198/197 与相关消费者一起评审。

本轮源码核对得到的是更窄的实现证据。MessageText schema（旧 conversation.schema.json 已随 HC-211 拆除）直接声明 `maxLength: 16384`，`ExecutionInput` 引用它。[路由目录](../../../services/collaboration-server/src/main/java/workbench/collaboration/interfaces/http/RouteCatalog.java) 对输入 HTTP 请求设 65,536 字节。[桌面会话客户端](../../../apps/desktop/src/main/collaboration-client.ts) 限制单条 SSE 事件 65,536 字节、单个 JSON 响应 1 MiB。所读 `ConversationController/Service`、共享 schema 和 `ExecutionCodec` 路径未找到独立的 32 KiB UTF-8、NUL 和未配对 surrogate 校验，需要在 Spec 阶段验证实际行为。现有 history 按条数分页，接入引用快照时要同时核对单条事件和整页响应的实际编码大小。

建议首版先在既定预算内设计：对问题、全部引用、包装、JSON 转义、事件和设备命令分别按实际编码校验；预览阶段暴露剩余预算，提交前再次验证，超限零写入、不截断。事件若含正式快照，必须算入同一 SSE 事件限额；若改为分条事件，也要固定同事务提交、连续序号和客户端投影规则。不得仅放宽 HTTP 而遗漏事件、桌面解析器、设备帧、指纹和 ACP 端口。

## 5. 权限竞争与锁顺序

已有共同设计约定新执行使用“授权 → 项目 → 会话 → 执行”的锁顺序；ExecutionStartAuthorization（已随 HC-211 拆除）在派发前实际对发起人、成员、设备/项目做 `FOR UPDATE`，随后派发器锁会话和执行。**不要把这个事实套用到所有当前路径：**[WorkspaceAccess](../../../services/collaboration-server/src/main/java/workbench/collaboration/application/service/IdentityAppService.java) 的 `requireMember` 和 [DeviceService.requireSharedProject](../../../services/collaboration-server/src/main/java/workbench/collaboration/application/service/DeviceAppService.java) 当前是普通查询；`sendInput` 虽按相应顺序调用它们，但这些读取本身不锁成员和项目行。因此，引用发送与来源权限撤销、用户停用、项目共享变化同时发生时，必须先与 HC-195/196 核实真实隔离级别和写路径，不能只写一句“事务内再次查询”就宣称已串行化。

建议评审时固定一套全路径遵守的次序：先按稳定 ID 有序取得需要的用户/成员授权及目标、来源的必要权限/项目行，再将目标和所有来源会话按稳定 ID 去重排序后加锁，最后处理草稿、交接或执行行；参与授权变更、来源删除和消息流式写入的相关路径也必须遵循相容顺序。先读到草稿所引用的来源 ID 后，应在锁内重新核验草稿归属、来源集合和权限；若发现需要追加更早顺序的锁，退出事务重新开始，不能临时反向加锁。具体哪些行必须锁、可用版本比较替代哪些锁、数据库唯一约束与死锁重试策略，都需在目标 MySQL/TDSQL 验证。

特别注意数据库一致读：流式输出同时更新消息正文和事件序号。在可重复读下，若先建立旧快照、再用锁定读取得新高水位、最后用普通快照读正文，可能组合出不同时点。预览要么在明确的一致快照内取对应前缀和正文，要么在会话锁之后使用与之匹配的当前读；不能把两者混用后声称选区精准。发送时固定草稿正文不因来源追加而变化，但授权撤销/删除与发送的先后仍需明确线性化规则。任何数据库锁均不能跨 SSE、设备网络或 Agent 调用持有；可重试的死锁使用同一请求 ID，不制造第二次执行。

## 7. 必须在 Spec 裁定的交界

| 参与方 | 先要达成的接口或裁定 | 可并行部分与真正前置 |
| --- | --- | --- |
| HC-195 / HC-198 | 交接事件和 `currentUserId` 投影；发送事务的草稿校验、正式引用和唯一固定执行文本；回执作用域/冲突；消息/事件体积；历史定位和锁顺序。 | 状态机、只读查询、UI 模型可按已审查接口并行；真实引用发送必须接现有生产保存事务与数据库，不能以替身验收。 |
| HC-196 / HC-197 | 原设备、原生 ID、普通 `input:{text}`、完整输入预算和确定性字节；离线/不可用与恢复失败的结果。 | Java 固定快照可先做；证明原生会话接续和实际 Agent 收到的文本，须真实 Runner、HC-197 ACP 及选定后端接通。 |
| HC-206 / HC-208 | 对话时间线、选区/预览/刷新、过期和来源不可用；待接手入口、设备/项目/接续人和状态提示；个人草稿/滚动不受他人操作覆盖。 | 视图模型和受控数据可并行，中央组件按 HC-205 公共出口及 HC-206 既有复用路径迁出；导航由 HC-208 新写。受控展示不等于真实协作。 |
| HC-202 | 桌面具名接口、账号代次隔离、查询/发送、历史与 SSE 的状态投影、实际定位。 | 公共组件的最小出口可先装配；端到端验收需要 HC-195/196/197/198 的对应真实最小实现，不需等待各整个任务全部完成才开始装配。 |
| 统筹 / 数据库 | 另行分配迁移版本，确定表、唯一约束和索引；串行集成 schema/fixture/OpenAPI、路由、安全装配、Foundation 和共享出口。 | 先评审接口/事务，再安排真实数据库和写文件窗口；不并行覆盖 HC-205 根锁、公共 UI 或其他任务文档。 |

Spec 还须明确：发起/目标候选的失效和错误语义；交接说明长度和是否可见；同一会话是否允许作为自身引用来源；检索范围、分页、选区和文本编码；草稿保存时长、清理和刷新后的旧草稿处理；多引用排序/重复；权限变化与提交的先后；同请求重试与另一次新发送；包装/摘要版本、大小预算、历史定位及不可用提示。草稿不能因清理导致已发送引用丢失，也不能由不同账号复用。

统筹复核建议优先明确两处边界。第一，发起者和目标用户失去成员资格后，怎样解除无法完成的待接手记录，避免它长期占用同会话唯一名额。第二，先按当前的工作区成员规则界定来源可读性，再决定事务需要锁定哪些行。来源项目停止共享仍可保留可读历史，目标项目是否允许执行继续走现有设备和项目授权。

## 8. 后续最小验收场景

1. A 创建会话后当前接续人是 A；A 向 B 发起后仍是 A，B 确认后变为 B。C 不能代 B 确认，A、B、C 的普通发言权不因交接变化；历史作者分别是实际登录用户。
2. 两个不同发起并发只保留一笔 pending；B 确认与 A 取消并发只有一个终态和一条对应终态事件。相同请求并发/重试返回同一结果，正文或目标不同的同 ID 请求冲突；回滚后没有半条状态或序号。
3. 两客户端通过历史与 SSE、断线重连和页面重开得到相同交接状态/顺序；其他人的个人草稿、当前页签和滚动不被替换。
4. 原设备离线时完成交接并读取已有历史；固定目标有效时新输入可 queued，不能宣称 Agent 已执行。停止共享、成员失效或设备撤销分别展示真实限制；设备恢复后仍指向原目标和原生会话，不悄悄迁机或重建。
5. 选择来源流式消息已有片段生成预览，来源继续输出后旧预览不变；显式刷新产生新草稿和不同预览。覆盖中文、emoji、换行、特殊分隔符和消息边界，展示与保存的范围一致。
6. 在授权的同工作区找到会话/消息并发送一个或多个引用；比较预览正文、已保存引用展开文本、固定执行输入、`execution.start.input.text` 和执行端口收到的 UTF-8 内容，验证包装有序且无静默改写。相同 requestId 重试只有一条消息、一组引用和一个执行。
7. 预览后来源访问失效、来源被删除或草稿属于另一用户/工作区时，新发送整体拒绝且无消息/引用/执行/事件/回执残留；如果首次发送已提交而响应丢失，授权范围内重试返回原结果。来源停止共享但历史仍可读的情况单独核对。
8. 发送后来源失效仍可展开原快照；来源可读时点击稳定定位原消息，来源不可定位时明确提示。超字符、字节、事件或命令预算时在保存前拒绝，不产生不能被 SSE/Runner 消费的已提交记录。
9. 注入引用/执行/事件保存失败，以及交接确认与权限撤销、流式输出和跨会话相互引用并发，检查事务回滚、锁顺序和不重复执行；目标 TDSQL 支持、真实 ACP 与双设备按后续集成阶段单独验证。
