# 团队角色初始化

当前只有一份完整 DDL：`server/src/main/resources/db/schema.sql`。应用启动只核对，不执行 ALTER，不自动连接或清空既有库。

## 新的隔离开发库

显式创建新库后，执行唯一 schema.sql，再执行 demo-data.sql，或使用 server:init-demo 初始化演示数据。新演示团队由工号 80278667 作为创建者和管理员，其余为开发者。重复运行不覆盖已有角色，也不恢复被移出的成员。仓库旧数据不能从登记者推定负责人，负责人为空表示待认领。

## 保留历史数据的环境

由运维在维护窗口先按 [HC-240 Spec 第 8 节](../spec/HC-240-Workspace角色管理.md#8-数据库初始化与单一实现路径) 的字段清单补齐结构；没有自动 DDL 迁移链。历史成员的 role 仅在此次准备时显式置 0，表示“尚未初始化”，成员状态、贡献和历史保持原样。已投入使用的权限数据不得重新置 0。

创建受控 JSON 文件，例如：

```json
[
  {
    "workspaceId": "00000000-0000-4000-8000-0000000000c1",
    "adminUserId": "000000000000400080000000000000d1"
  }
]
```

每个尚未初始化的团队都必须有显式映射；管理员必须是该团队现有、启用、在册的用户。只有核实了创建者才填写可选 creatorUserId，否则不填、不按项目负责人或最早加入时间猜测。映射重复、未知团队、资格不符、缺少映射或同团队混杂已生效角色与未初始化角色时整体失败，不做部分提权。

通过既有受限数据库配置运行一次命令（不把密码放命令行）：

```sh
WORKBENCH_ROLES_MAPPING=/absolute/path/workspace-roles.json node scripts/workbench/server.mjs init-workspace-roles
```

也可运行已构建 jar 的 `--workbench.command=init-workspace-roles --workbench.roles-mapping=/absolute/path/workspace-roles.json`。先备份并预检指定环境；命令只更新未初始化成员，所有团队资格检查通过后一起提交。重复执行跳过已初始化的团队，不覆盖后来的角色或移除记录。完成后按正常 start 启动，启动检查会拒绝没有有效管理员或存在未知角色的团队。

本说明不是对目标 TDSQL 或生产数据执行过迁移的证据。本卡仅在自己的临时 MySQL 中验证；目标库准备和完整中间件验收由 HC-204 统一处理。
