# 开发工作流

仓库 Markdown 是协作事实来源。功能交付遵循 `task → spec → plan → todo → implement → review`（见 [AGENTS.md](../../../AGENTS.md)）。日常闭环：

1. 从 [任务看板](../task/任务看板.md) 找到任务，先检查功能板块、上层任务与拆解者；对照当前代码和设计确认任务仍然有效，失真或已被覆盖的任务先更新记录，不能直接实施。
2. 通过 `npm run task:claim -- <ID> --owner <名称> --branch <分支>` 认领；`owner` 表示实现负责人，不覆盖 `decomposed_by`。
3. 在任务范围内实现并补回归测试；不要顺带重构无关代码。
4. 用户可感知变更更新 `docs/user/`；架构、协议或配置变更更新 `docs/developer/`。
5. 记录测试证据，执行 `npm run task:complete -- <ID> --evidence "..." --references "..."`。
6. 如有版本影响，仅通过 `npm run version:set -- <SemVer>` 更新版本与 Changelog。

交互式开发必须在仓库根目录运行 `npm run dev -- --cwd <工作区>`。根 `dev` 只通过 npm workspace 把参数转给 `packages/cli`；CLI workspace 随后启动 Bun/OpenTUI 运行时并继承真实终端的 stdin/stdout。不要再套一层会捕获输出的外部任务运行器。

提交前至少运行：

```bash
npm run project:check
npm run typecheck
npm run test
```

构建相关改动再运行 `npm run build`。`.agent/` 只保存 Agent 的计划、实现状态和交接，不替代本文档、任务源或用户文档。

涉及 OpenTUI 时，先确认当前 npm/pip 源能提供 `@opentui/core` / `@opentui/react` `0.4.3`、当前 runner 的 Core native optional package 和所需 Python 包。企业外用公网源，企业内用企业源。随后运行 `npm run deps:sync` 与 `npm run test:ts`；React `testRender` 会加载当前目标 FFI、创建测试 renderer 并捕获 80×24 与 130×40 帧。只有依赖声明或包源发生变化时，才使用 `npm run deps:sync -- --update-lock`；该模式更新锁后会继续完成完整同步与验证。`HARNESS_NPM_REGISTRY` / `HARNESS_PYPI_INDEX` 只在工具配置仍指向公网、而这一次要改走内网时使用；企业凭据继续由 npm/pip 原生配置或 CI 安全注入。

详细要求见 [变更检查清单](变更检查清单.md) 和 [仓库协作规范](../../../AGENTS.md)。
