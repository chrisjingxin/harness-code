# 双模型文件并行执行规格

## 一、背景与目标

现有 Fusion 用目录键保存唯一写者，一个活动任务就阻止同目录所有其他任务。等待以工具错误交给模型处理，用户经常需要手动结束旧任务。当前快照还把无关任务的改动算入本轮差异。

目标：按实际修改范围分配权限，冲突在 Host 内自动等待，模型不反复重试派单。保留先读后写、批准后复查、停止凭据和可信验收。

## 二、设计思路

输入任务 → 规范化 allowed_paths → 一次申请全部范围 → 有冲突则排队 → 取得范围后捕获基线并派单 → 执行和检查 → 验收或安全暂停 → 释放范围，唤醒等待者。

文件范围预留贯穿一轮执行与审阅；命令保护只持续到命令确认结束。命令保护不等待其他任务交回文件预留，因此两个任务都要运行测试时不会互相卡死。命令等待期间不持有本进程写锁或 SQLite 事务。

## 三、整体架构

| 模块 | 职责 |
| --- | --- |
| fusion/store.py | 文件预留、顺序号、任务状态、原子交接与一次数据迁移 |
| fusion/resources.py | 跨 Host 的短期文件操作与目录命令协调；取消收尾 |
| fusion/guard.py | 文件准备与提交复查；命令登记停止事实；扩展工具保护 |
| fusion/service.py | 自动排队派单；任务范围快照；工作区版本与可信检查 |
| 文件契约、执行后端、Host | 普通模式、Fusion、Compose、直接命令、历史还原统一接入 |
| Protocol、CLI | WAITING_RESOURCE 状态、冲突文件与自动继续提示 |

## 四、详细设计

### 1. 文件范围

- 精确文件按名称匹配；目录包括子路径；./ 表示整个目录。现有目录自动规范为带 / 的目录范围。路径规范化仍拒绝 ..、绝对路径、内部目录和符号链接绕过。
- 文件/目录的祖先、同名与子路径相交即冲突。一次申请全部范围，不能先占 a 再等待 b。
- 每个任务一条预留，包含项目、目录键、任务、owner、generation 和 paths。全目录顺序号为授权提供不可复用的 generation。
- 开新轮或扩大范围时，在确认本任务没有未停止操作后，交回旧范围，再按完整新范围排队，防止交叉等待。
- 自身预留在 Sidekick → Host 的交接中保留；排队者不能阻止占有者检查和结束。

### 2. 自动排队

- 等待请求进入持久化队列，使用 SQLite 自增号排序。较早且范围相交的请求优先；互不相交的任务可以继续。
- 派单未取得范围时，任务为 WAITING_RESOURCE，round/revision 不增加，不保存已派发 outbox。界面显示冲突路径、占用会话和“可用后自动继续”。
- Host 用异步等待和数据库复查协调不同进程，不让模型重发工具，不跨等待持有 SQLite 事务或 Host 写锁。
- 用户取消、线程取消或任务结束时删除对应等待请求。重新启动只重新申请尚未执行的等待；未确认执行过的命令仍不自动重放。

### 3. 命令与文件操作

- 单次文件工具在实际执行期间登记短期写入记录，命令等待这些操作结束；文件真正提交仍受 CAS 和任务范围复查保护。
- 命令及未知写工具取得短期整目录保护；后续文件提交和命令排队。审批期间不占用目录，执行前重新检查授权和快照。
- 不把任务的长期文件预留当成命令互斥条件，避免检查升级死锁。普通模式没有声明范围的命令须等待受保护的任务范围。
- Shell 无法仅靠路径预留隔离进程，命令前后核对真实改动，超范围修改暂停交付；不得把该机制描述为操作系统沙箱。
- 确认停止后自动释放；没有停止凭据保留保护。纯文件结果不明保留文件范围，执行中的任意命令结果不明保留目录保护。
- 同一 Host 的工具锁只保护短事务或实际执行，不允许持有它等待另一个需要该锁才能完成的任务。

### 4. 版本与验收

- capture_snapshot(workspace, allowed_paths) 捕获任务范围；其他任务改无关文件不再算作越界。
- 检查时另取工作区源码快照，排除缓存与环境目录，明确指定的文件仍纳入。检查在目录保护内执行，保存命令前后工作区摘要。
- 票据绑定候选范围摘要和工作区源码摘要。审阅接受前重新核对：候选变动则要求返工；只有其他源码变动则运行新的检查，签发新票据，让 Lead 重新确认。
- 已知停止的检查可创建新一轮检查记录；缺失停止凭据的旧检查禁止重跑。不同检查轮不得混用历史成功记录。
- 普通模式、扩展、直接命令、Compose 和历史还原不能绕过实际写入保护。

### 5. 数据与接口

- 用 fusion_reservations 取代单写者 fusion_leases；fusion_generations 保存目录授权代号；fusion_access 保存等待和短期操作事实。原子迁移保留旧任务及证据，删除旧表，禁止双写。
- Store.acquire_lease 支持规范化 paths；Store.wait_for_lease 在 Host 内等待并通知状态。begin_workspace_phase、start_round 和 begin_effect 在同一短事务复查当前预留。
- FusionTaskStatus.phase 增加 WAITING_RESOURCE；状态展示当前 write_paths；workspace_blocker 补充 kind 与 paths，说明真正冲突的资源。它表示首个实际阻塞者，并不表示整个目录只能有一个任务。
- 工具取消沿用现有 Run 取消；/fusion cancel 可以结束等待任务。/fusion resolve 保留为用户主动处理旧任务的入口，正常排队不提示先结束别人。

### 6. 验收

真实 SQLite 跨连接、双 Host、同文件等待、目录前缀冲突、不同路径并行、交叉扩范围、等待取消、命令等待与退出、审批后再查、未知命令保护、普通工具旁路、外部编辑 CAS、其他任务改动、过期测试重检、协议序列化和 TUI/Web 共享提示均有回归。

### 7. 普通工具残留与暂停恢复

普通工具没有 Fusion task_id，结果不明的短期保护也要能在当前对话处理。fusion.release 接收 operation_id、expected_sequence、stopped_inspection_note，只处理本项目、task_id 为空且 state=unknown 的记录；拒绝运行中的操作和带 Task 的操作。核查说明只保存摘要，记录标记 inspected，迟到回调不能重新标成 unknown。TUI/Web 共用 /fusion resolve --stopped 入口，等待期间及普通 busy 不提示结束其他任务。

主动取消排队后，只读问题不自动恢复原派单；明确发送“继续等待”等继续指令才恢复已保存、尚未执行的请求。此判断不适用于 OUTCOME_UNKNOWN，不代表确认命令停止。

排队顺序记录每次等待更新 heartbeat；5 秒未更新只移除等待位置，活跃等待者会重新进入队列。不得据此释放正在执行的命令、未知保护或已在执行的文件预留。


## 8. Host 意外退出

实际操作记录保存 Host PID。确认 Host PID 已不存在时，将 running 转为 unknown，继续保留保护；子进程可能仍在运行，不能据此自动释放。普通未知操作通过当前对话的 fusion.release 精确核查，活动 Host 的运行记录不可从该入口释放。等待请求的心跳只维护公平顺序，超时不释放文件预留或未知操作。


纯读取快照没有写入副作用，Host 退出后可以回收；历史文件还原归入命令保护。实际操作已登记但副作用记录尚未保存就退出时，待查操作列表仍保留操作编号，不能只显示空的“结果不明”。
