# HC-214 链路日志完整采集

关联任务：[HC-214](../task/HC-214-链路日志完整采集.md)

用户结果与验收以 Task 为准。本文规定 schema v2 的记录形状、谁在什么时机写入、失败时怎么表现，以及 Web 怎么读。实现不得另改公开字段。

## 1. 通俗目标

现在每次运行都会写一份 trace，但里面看不到模型收到的消息、工具的参数和结果，树上还有一串 0 毫秒的记账节点。排障时只能知道「调用过」，不能知道「当时到底发生了什么」。

改完后，一份 trace 就是这次运行的完整记录。树上每一轮是一次模型调用，下面挂着它触发的审批和工具。点开任意一次调用，能看到完整输入、完整输出、耗时、token 和缓存命中。密钥不会落盘。文件放在用户目录，不再出现在项目里。

界面只负责把这份记录展开给人看。日志里可以有界面暂时用不上的字段。

## 2. 已确认决策

这些决定来自 Task，本文不再权衡：

1. 默认采集 `full`，可降为 `meta` 或 `off`。
2. 日志目录是用户目录 `~/.harness/trace/<project>/`，按天数清理。载荷内联在 jsonl，不另存文件。同一会话里内容相同的消息、系统提示词、工具 schema 只写一次。
3. 执行树是 Run → Step。去掉 `run.complete`、`runtime.acquire`、`runtime.release`、`run.execute`、`agent.run` 和正常的中间件节点。
4. 只脱敏密钥类内容。
5. 流式输出记首 token、最后 token、chunk 数和拼好的全文，不记每个 chunk。
6. 子代理的 span 挂在父级 `tool.call` 下面，同属一个 trace。
7. Web 适配新树，详情按参数、输入、输出、用量、耗时、错误分区，原文可展开。
8. 不读 schema v1，不改内网 `[[za38-log]]` 的解析。
9. 本规格取代 HC-180 里「不记录 prompt 和消息正文」的不变量。

## 3. 本规格锁定的实现决定

下面这些是写规格时按现有代码定的，Plan 按此实现。若要改，先改本文。

1. **span 由显式埋点发出，不再靠 LangChain 的通用 chain/tool 回调建树。** 今天 `on_chain_start` 会把每个中间件记成 `graph.node` 或 `agent.run`，`on_tool_start` 只拿到参数键名。v2 里这两类回调不再产生 span。模型与工具 span 改由中间件在真正发请求、真正执行工具的位置发出。回调只继续负责首 token 时间。
2. **父代理的审批 span 加在真正做决定的那一层。** 今天 `evaluate_permission` 只被 `runtime/child_approval.py` 的 `ChildHitlMiddleware` 调用。父代理的决定在 `runtime/agent.py` 的 `_make_approval_preflight` 里完成，它直接调用规则、安全底线、自动模式和分类器，不经过 `evaluate_permission`。所以普通 Build 运行的日志里没有 `policy.evaluate`。v2 要求这两处每次决定都产出同名 span，字段相同。`policy.classifier` 只在 Plan 约束下的命令分类时出现。
3. **Step 是写入时的 span，不是看图时猜出来的。** 每次面向用户的模型调用开始时打开 `step`，下一次模型调用或 Run 结束时关掉。这一窗口内的审批、工具、落库都以它为父。压缩用的摘要模型调用挂在 `context.compact` 下，不占用 Step 序号。
4. **准备阶段的投影不单独占树。** `context.project` 今天在准备和执行各记一次。树上只保留执行阶段那一次；准备阶段的耗时写入 `run.prepare` 的 `projection_ms`。
5. **落库仍是一次事务一条 span。** 不为此改 SQLite 的提交方式。同一 Step 里的多条 `db.persist` 都带 `step`，界面把它们收成一组。
6. **项目目录名复用 `workspace_fingerprint`。** 定义在 `packages/agent/harness_agent/threads/thread_records.py`：对工作区真实绝对路径做 SHA-256。CLI 用同一次启动传入的工作区路径按同一规则计算，不新增协议字段。
7. **配置放在 `[trace]`，不放进 `[diagnostics]` 或 `[telemetry]`。**
8. **单个 jsonl 超过 64MiB 时换一个新文件接着写同一次会话。** 读侧已经有 64MiB 单文件上限，不换文件会被直接拒绝。这不是第二种存储，仍是内联 jsonl。
9. **执行阶段显式绑定这次 Run 的 TraceSession。** 今天只有 `_prepare_run` 上的 `trace_monitor(manual=True)` 在创建时写入 contextvar。`asyncio.create_task(self._execute)` 靠继承拿到它，`_execute` 自己不绑定。`request_interaction` 也只读 contextvar，不读 `RunState.trace_context`。v2 在 `_execute` 入口用 `run.trace_context` 绑定，子任务和审批都从这次 Run 的 session 取，不靠任务继承。

## 4. 一次运行在日志里的形状

```text
输入一次用户消息
  → 打开 trace，写 run 开始
  → run.prepare（准备、受理、拿到运行时；投影耗时记在属性上）
       └─ db.persist            受理这次运行
  → context.project            执行前的那一次投影
  → 若需要压缩：context.compact
       └─ llm.call              只在 full 摘要时出现
  → 重复，直到模型不再要工具：
       step
         ├─ llm.call
         │    └─ llm.attempt    仅重试
         ├─ policy.evaluate     每个工具一次
         ├─ interaction.wait    仅在需要人答复时
         ├─ tool.call           子代理的 step 挂在这个 tool.call 下
         └─ db.persist          这一步里的每次事务
  → db.persist                 运行收尾
  → 关掉 run，带上终态、总耗时、token 汇总、缓存命中率
```

中间件只有在失败，或自身耗时达到 50ms 时，才作为 `graph.node` 出现，父节点是当时打开的 `step` 或 `run`。

## 5. 记录 schema

`schema_version` 为 `2`。一行一个 JSON 对象。事件只有五种：`trace.start`、`trace.end`、`span.start`、`span.end`、`payload`。

每条 span 都有：`session_id`（等于 thread id）、`trace_id`、`run_id`、`span_id`、`parent_span_id`、`name`、`kind`、`start_time_ms`。结束记录再加 `end_time_ms`、`duration_ms`、`status`。`status` 是 `SUCCESS`、`FAILED`、`CANCELLED` 之一。失败和取消带 `error_type` 和最多 512 字的 `status_message`。

**结束记录的 `attributes` 是开始属性和结束属性的并集，同名键以结束时的值为准。** 看图只读结束记录。

`payload` 行：

```json
{"schema_version":2,"event":"payload","payload_id":"p1","sha256":"…","bytes":1204,"kind":"message","body":{}}
```

span 用 `payload_id` 引用它。同一个 `TraceRecorder` 生命周期内，相同 sha256 只写一次。`kind` 取值：`message`、`system`、`tools`、`output`、`tool_args`、`tool_result`、`summary`、`error`。

一次模型调用的结束记录长这样：

```json
{
  "schema_version": 2,
  "event": "span.end",
  "name": "llm.call",
  "kind": "LLM",
  "status": "SUCCESS",
  "duration_ms": 2641,
  "attributes": {
    "step": 1,
    "provider": "deepseek",
    "model": "deepseek-v4-pro",
    "profile": "fast",
    "request": {
      "temperature": 0.2,
      "max_tokens": 8192,
      "stream": true,
      "timeout_s": 120,
      "max_retries": 2,
      "base_url_host": "api.deepseek.com"
    },
    "message_count": 16,
    "message_refs": ["p1", "p2"],
    "system_ref": "p3",
    "tools_ref": "p4",
    "output_ref": "p5",
    "finish_reason": "tool_calls",
    "tool_calls": 1,
    "usage": {
      "input_tokens": 5009,
      "output_tokens": 8,
      "total_tokens": 5017,
      "cache_read_tokens": 4736,
      "cache_write_tokens": 0,
      "reasoning_tokens": 0
    },
    "cache_hit_ratio": 0.945,
    "first_token_ms": 2329,
    "last_token_ms": 2600,
    "chunk_count": 4
  }
}
```

没有的字段省略，不写 `null` 占位。`cache_hit_ratio` 由写入器计算：`cache_read_tokens / input_tokens`，分母为 0 时省略。

## 6. 五类调用的字段

属性名使用上面的蛇形风格。完整正文一律走 `payload_id`，属性里只留引用、计数和枚举。

### 模型 `llm.call` / `llm.attempt`

`llm.call` 是这一次逻辑调用，耗时包含重试。每一次实际 HTTP 尝试是它下面的 `llm.attempt`。没有重试时不写 `llm.attempt`。

| 属性 | 内容 |
|---|---|
| 身份 | `provider`、`model`、`profile`、`api`（`chat` 或 `responses`）、`base_url_host`、`response_id`、`served_model` |
| 请求 | `temperature`、`top_p`、`max_tokens`、`reasoning_effort`、`stop`、`tool_choice`、`parallel_tool_calls`、`stream`、`timeout_s`、`max_retries`、`header_names` |
| 输入 | `system_ref`、`message_refs`、`tools_ref`、`message_count`、各角色条数、`estimated_input_tokens`、`context_window`、`input_cap` |
| 输出 | `output_ref`（正文、reasoning、每条 tool call 的 id、名字和原始参数）、`finish_reason`、`tool_calls` |
| 用量 | `usage` 六项和 `cache_hit_ratio` |
| 时间 | `first_token_ms`、`last_token_ms`、`chunk_count`；span 自己的 `duration_ms` |
| 重试 | `llm.attempt` 上的 `attempt`、`http_status`、`provider_error`、`retryable`、`backoff_ms` |

### 上下文 `context.project` / `context.compact`

`context.project`：`matched`、`count`、`tokens_before`、`checkpoint_id`、`source_seq`。

`context.compact`：`trigger`（`auto`、`manual`、`overflow`）、`tier`（`micro`、`full`）、`tokens_before`、`tokens_after`、`messages_before`、`messages_after`、`context_window`、`input_cap`、`threshold`、`artifacts`（id、字节数、替换的消息序号）、`summary_ref`、`outcome`（`committed`、`skipped`、`failed`）、`skip_reason`、`checkpoint_id`。摘要模型调用是子节点 `llm.call`。

### 工具 `tool.call`

| 属性 | 内容 |
|---|---|
| 身份 | `tool`、`source`（`builtin`、`mcp`、`skill`、`subagent`）、`server`、`call_id`、`policy_span_id` |
| 载荷 | `args_ref`、`result_ref`、`args_bytes`、`result_bytes`、`truncated`、`artifact_id` |
| 结果 | `result_status`、失败时的 `error_type` 和 `status_message` |
| shell | `command_ref`、`cwd`、`exit_code`、`stdout_bytes`、`stderr_bytes`、`timed_out` |
| 文件 | `path`、`operation`（`write`、`edit`、`delete`）、`diff_added`、`diff_removed` |

`command_ref` 指向完整命令文本。`cwd` 和 `path` 保留原样，因为本任务只脱敏密钥。

### 落库 `db.persist`

`operation`、`tables`、`thread_id`、`run_id`、`rows`、`seq_from`、`seq_to`、`bytes`、`lock_wait_ms`、`outcome`（`committed`、`duplicate`、`failed`）、`record_ids`。不写 SQL 和行内容。

### 审批 `policy.evaluate` / `interaction.wait`

`policy.evaluate`：`tool`、`call_id`、`args_ref`、`approval_mode`、`decision`（`allow`、`ask`、`deny`）、`layer`（`L1` 到 `L6`）、`rule_source`、`rule_pattern`、`classifier`、`floors`。

`interaction.wait`：`request_id`、`interaction_type`、`tool`、`wait_ms`、`outcome`、`choice`（`approve_once`、`approve_thread`、`approve_project`、`reject`、`reject_with_feedback`）、`rule_scope`。

## 7. 模块与 interface

对外只有一个模块 `TraceSession`。调用方学习的面很小：档位、打开一次运行、打开一个 span、提交一块载荷、关闭。去重、脱敏、换文件、清理都在内部。

```python
class TraceSession:
    """一次 Run 的 v2 写入器。档位为 off 时所有方法都是空操作。"""

    def span(self, name: str, *, kind: str, parent: str | None = None,
             attributes: Mapping[str, object] | None = None) -> Span:
        """打开 span。返回的 Span 可结束、可嵌套，结束时合并属性。"""

    def payload(self, kind: str, body: object) -> str:
        """脱敏后按内容去重，返回 payload_id。"""

    def close(self, status: TraceStatus, attributes: Mapping[str, object] | None = None) -> None:
        """写 run 的结束记录并关闭文件。重复调用无效果。"""
```

`Span` 只有 `end(status, attributes)` 和「在此期间打开子 span」两种用法。埋点代码拿不到文件路径。

采集适配器是内部 seam，不给业务代码用：

| 适配器 | 挂在哪里 | 产出 |
|---|---|---|
| 模型 | 模型中间件链的最内层，能看到真正发出的请求和返回 | `step`、`llm.call`、`llm.attempt` |
| 工具 | 工具中间件链中包住实际执行的那一层 | `tool.call`，并填写与审批 span 的互指 |
| Shell 返回值 | backend 的 `execute/aexecute` 返回、DeepAgents 格式化或转存之前 | 补入当前 `tool.call` 的原始结果、退出码、截断标志和实际 cwd；后端只提供合并输出时，不虚构分离的 stdout/stderr 字节数 |
| 审批 | 父代理：`_make_approval_preflight`。子代理：`evaluate_permission` | `policy.evaluate` |
| 交互 | 父代理审批走 `_collect_serial_approvals`（Compose 走 `_ComposeStageObserver.interact`），不走 `request_interaction`。span 加在这两处实际调用 `interaction_port.request` 的地方。`request_interaction` 继续覆盖提问等其余交互 | `interaction.wait` |
| 落库 | 现有 `thread.persist` 装饰器的属性提供器 | `db.persist` |
| 压缩与投影 | 现有 `context.compact`、`context.project` | 对应 span |

`_execute` 入口用 `run.trace_context` 绑定本次 `TraceSession`。子代理启动时显式带上这个 session 和当前 `tool.call` 的 span id。不依赖 `create_task` 继承 contextvar。

`run.prepare` 继续用现有函数装饰器。`run.accept` 的模式和审批模式写进 `run.prepare` 的属性。运行时获取和释放的 `source`、`queue_ms`、`build_ms` 也写在这里。Run 的终态只出现在 `trace.end`。

## 8. 采集档位、脱敏、存储

配置节：

```toml
[trace]
capture = "full"       # full | meta | off，默认 full
retention_days = 14    # 1 到 365，默认 14
```

| 档位 | 行为 |
|---|---|
| `full` | 写 span 和 payload |
| `meta` | 只写 span。不写 payload 行，属性里不出现 `*_ref`。计数、枚举、token、耗时保留 |
| `off` | 不创建文件，所有埋点空转 |

脱敏在 `payload()` 和属性写入前执行，三档都适用：

- 键名是 `api_key`、`apikey`、`authorization`、`cookie`、`set-cookie` 的值改为 `"[redacted]"`。
- HTTP 头里这几个名字的值同样替换。`header_names` 只保留名字。
- 环境变量值匹配常见 token 形态（`sk-`、`ghp_`、`github_pat_`、`xox`、`Bearer ` 开头）时替换。其他环境变量原样保留。

目录是 `~/.harness/trace/<workspace_fingerprint>/`。文件名保持 `Trace-log-<时间>-<8位>.jsonl`。一次会话写满 64MiB 后换新文件，`trace_id` 不变。进程启动时删除该目录下修改时间早于保留天数的文件。删除失败只记诊断日志，不阻止启动。

CLI 的工作区读取器改为读这个目录。`~/.harness/trace` 根上的内网索引读取逻辑保持原样，不参与 v2。工作区 `log/` 不再写入，也不再被 v2 读取。

## 9. 看图

解析器只接受 `schema_version = 2` 且事件名属于第五节的行。v1 行跳过。同一 span 的开始和结束合并成一条；结束记录已经自洽，开始记录只用来补没有结束的运行中 span。

树的节点就是第四节的形状。同一 `step` 下的多条 `db.persist` 显示为一组，组内仍可展开。详情面板六个区：参数、输入、输出、用量、耗时、错误。`*_ref` 默认显示字节数和种类，展开后显示 `body`。引用的 payload 不在已读文件里时，该区显示「载荷不在当前读取范围内」，不影响其他区。

简化视图的耗时只读 `duration_ms`。v2 不再写 `duration`。

## 10. 错误语义

| 情况 | 行为 |
|---|---|
| 建目录、序列化、写盘失败 | 这次埋点丢弃，业务继续。诊断日志记一次 `trace.write_failed`，同进程同原因不重复刷屏 |
| 属性或载荷里有不能序列化的对象 | 该字段写成 `{"unserializable": "<类型名>"}`，span 仍关闭 |
| 结束一个没有打开的 span、重复关闭 | 不写事件 |
| 业务抛异常 | span 以 `FAILED` 关闭，异常原样抛出。`CancelledError` 记为 `CANCELLED` |
| 读到半行、坏 JSON、未知事件、v1 行 | 跳过该行 |
| 单文件或单次读取总量超过现有上限（64MiB / 128MiB / 10 万 span） | 维持今天的失败结果，不截断后假装完整 |
| `capture` 或 `retention_days` 非法 | 配置加载失败，沿用现有配置错误语义，不静默改回默认值 |

## 11. 不变量

1. 埋点异常到不了业务调用方。
2. `off` 不产生文件。`meta` 文件里没有 `payload` 行，也没有 `*_ref`。
3. 任何档位的落盘内容都不含 api key、Authorization、Cookie 的原值。
4. 结束记录含开始时的全部属性。
5. 一次 `TraceRecorder` 内相同 sha256 只有一条 `payload`。
6. 面向用户的 `llm.call` 的父节点是 `step`。压缩摘要的 `llm.call` 的父节点是 `context.compact`。
7. 子代理 span 的祖先链上有父级的 `tool.call`。
8. 正常运行的树里不出现 `run.complete`、`runtime.acquire`、`runtime.release`、`run.execute`、`agent.run`。
9. 项目工作区不产生新的 `log/Trace-log-*.jsonl`。
10. 内网 marker 的解析结果与改动前一致。
