# HC-186 移除旧库迁移兼容规格

关联任务：[HC-186](../task/HC-186-移除旧库迁移兼容.md)  
全局架构：[架构总览](../architecture/架构总览.md)

用户结果与验收以 Task 为准。本文规定新库如何创建、旧库如何被拒绝、哪些代码必须删除、错误语义和验证方法；不规定实施步骤。Plan / Todo 必须与本文同名，且不得把 Task 非范围做成范围。

## 1. 通俗目标

线程库不再有「升级」这件事。程序只认一个当前版本（版本号 1）：

```text
打开 ~/.harness/threads.sqlite3
  → 只读检查：库里有没有表？user_version 是几？
  → 没有任何表（含文件不存在）：在一个事务里建好全部表和索引，写入版本 1，提交
  → 版本等于 1：校验结构完整，正常打开
  → 其他任何情况：直接报 CHECKPOINT_SCHEMA_INCOMPATIBLE，不修改文件，不留任何标记文件
```

改后用户看到的区别只有一条：以前的旧开发库会被拒绝，需要手动删除文件后重启。其余 Thread、Goal、Compose、检查点功能与现在完全一致。

## 2. 已确认假设

来自已确认 Task，Spec 不得改写：

1. 遇到旧版本库直接报错并提示删除后重启，**不自动删除、不自动备份重建**。
2. `_SCHEMA_VERSION` 重置为 1。
3. Plugin registry v2→v3 迁移、执行绑定旧格式读取一并移除。
4. 不动 Compose 相关的表和代码；不拆分 `thread_persistence.py`；不改协议和 CLI 命令。

本 Spec 补齐的实现口径：

5. **「空库」的定义**：`sqlite_master` 中没有任何非 `sqlite_` 开头的对象。文件不存在、0 字节文件、只有 `user_version=0` 且没有表的库都算空库。有表但 `user_version=0` 的文件**不是**空库，按不兼容处理（它不是 Harness 创建的）。
6. **版本过新与版本过旧合并成同一个错误。** 重置为 1 之后，现有开发库的版本号（2~20）在数字上比「当前版本」更大，若沿用 `CHECKPOINT_SCHEMA_TOO_NEW`，会误导用户去升级程序。因此删除 `CHECKPOINT_SCHEMA_TOO_NEW`，所有「非空且版本不等于 1」的情况使用同一个新错误码，消息里同时说明两种可能原因。
7. 不引入 `application_id` 等额外身份标记来区分「旧库」和「新程序版本的库」（YAGNI）。当前没有这种需求，需要时再加。
8. **Schema 变更规则（今后生效）**：改表结构 = 修改建库基线 + `_SCHEMA_VERSION` 加 1 + 更新 golden schema 文件。**不写升级代码。** 旧版本的库一律被拒绝，开发者本机需要手动删库。这一条会写入架构总览。

## 3. Capability Map 与 module seam

Module ID 是职责标签，不要求同名目录，也不拆成多份 Spec。

| Module ID | 职责 | 外部 interface | 依赖 |
|---|---|---|---|
| `schema-baseline` | 空库一次性建出最终 schema，并写入版本 1 | `ThreadPersistence.open()` 对空库返回可用实例 | 无 |
| `version-gate` | 非空库的版本检查与拒绝 | `open()` 对不兼容库抛 `ThreadPersistenceError("CHECKPOINT_SCHEMA_INCOMPATIBLE…")`，库文件不被修改 | `schema-baseline` |
| `migration-removal` | 删除升级链、迁移子进程、标记文件、故障注入及对应测试 | 仓库中不再存在迁移相关符号 | `version-gate` |
| `legacy-shapes` | 删除只服务旧库的读取代码与表（执行绑定、Plugin registry 等） | 现役代码不再识别旧数据形状 | `migration-removal` |
| `docs-sync` | 用户文档、架构总览、ADR 状态同步 | 文档与代码一致 | 以上全部 |

依赖：

```text
schema-baseline → version-gate → migration-removal → legacy-shapes → docs-sync
```

`open()` 是唯一的外部 seam。现有调用方（`AgentHost` 等）不需要任何改动，也不应感知到内部不再有升级逻辑。

## 4. 行为规格

### 4.1 打开线程库

`ThreadPersistence.open(project, home)` 的完整判定表：

| 磁盘状态 | 结果 | 是否写文件 |
|---|---|---|
| 文件不存在，或是空库 | 创建基线 schema，`user_version=1`，返回实例 | 是（在单一事务内） |
| 非空，`user_version == 1`，结构完整 | 正常返回实例 | 否 |
| 非空，`user_version == 1`，缺少必需表/索引 | `CHECKPOINT_SCHEMA_INCOMPATIBLE`（视为被手工破坏） | 否 |
| 非空，`user_version != 1`（含 0、2~20、更大值） | `CHECKPOINT_SCHEMA_INCOMPATIBLE` | **否** |
| 不是 SQLite 文件 | `CHECKPOINT_DATABASE_CORRUPT`（沿用现有） | 否 |
| 目录不可写等 OS 错误 | `CHECKPOINT_OPEN_FAILED`（沿用现有） | 否 |

约束：

1. **先只读后写。** 版本判定只使用 `SELECT` 与 `PRAGMA user_version` 读取。只有判定为空库时才进入写事务。不兼容库不得出现 `BEGIN IMMEDIATE`、DDL 或任何写入。
2. **建库是单一事务。** `BEGIN IMMEDIATE` → 事务内**重新**读取空库状态 → 建全部表、索引和 LangGraph checkpointer 表 → `PRAGMA user_version=1` → `COMMIT`。任何一步失败整体回滚，库文件仍是空库，下次启动可重试。SQLite 的 DDL 与 `user_version` 都在事务内，不存在「建了一半」或「表建好但版本没写」的中间状态。
3. **并发首次启动安全。** 两个进程同时首次启动时，后获得写锁的一方在事务内重新读取状态，发现版本已是 1，则不重复建表，转入「版本等于 1」路径。依赖 SQLite 自带的锁（沿用现有 `busy_timeout`），不再使用 `.migration.lock` 文件。
4. **不产生任何附属文件。** 不再创建 `.migration.lock`、`.pre-v*-migration.bak`、`.migration-state.json`、`.migration-attempt.json`、`.migration-poison.json` 及其 staging 文件。打开成功或失败后，数据库所在目录只允许出现 SQLite 自身的 `-journal`/`-wal`/`-shm`（连接关闭后由 SQLite 清理）。
5. 版本为 1 的库仍执行现有的「必需表与索引齐全」校验（复用现有的非迁移专用校验函数）；不再计算数据库指纹，不再比对 source/final fingerprint。

### 4.2 不兼容库的错误语义

- 错误码：`CHECKPOINT_SCHEMA_INCOMPATIBLE`（新增，稳定字符串）。
- 消息格式（一行，保持 `THREAD_STORE_UNAVAILABLE: <detail>` 的现有包装不变）：

```text
CHECKPOINT_SCHEMA_INCOMPATIBLE: found <N>, requires 1; path=<库的绝对路径>; 旧开发库请退出 Harness 后删除该文件再启动；若该库由更新版本创建，请升级 Harness
```

- 可重试性：不可重试；用户处理后再启动即可。
- Host 层映射不变：仍经 `agent_host.py` 的 `ThreadPersistenceError` 分支转成 JSON-RPC `-32020` / `THREAD_STORE_UNAVAILABLE`。不新增协议错误码，不改 `packages/protocol`。
- 日志不记录库内容，只记录版本号和路径。

### 4.3 建库基线（schema-baseline）

1. 基线 = 现有代码在空库上跑完 v1→v20 后得到的最终 schema：**34 张表、18 个索引**，其中包括 LangGraph 的 `checkpoints`、`writes` 两张表，以及全部 Compose 表（Compose 表本任务不动，见 §7）。
2. 基线中**不含**只读遗留表，前提是实施时逐个验证「现役代码没有任何写入语句」：
   - `harness_thread_model_bindings`（已验证：无 INSERT/UPDATE）
   - `harness_thread_runtime_profiles`（已验证：无 INSERT/UPDATE）
   - `harness_thread_history_metadata`（唯一写入点在 v6 导入函数 `_bootstrap_legacy_transcripts`，随其一并删除）
   - 实施时若发现任一表其实有现役写入者，则保留该表并记入 Todo，不得为了凑数删除。
3. **等价性保证（防止删代码时漏表）。** 实施的第一步，在**任何生产代码改动之前**，用现有代码在空库上导出规范化后的 `sqlite_master`（表、索引、列定义），保存为测试 fixture（golden schema）。新的建库函数产出的 schema 必须与 golden 逐项一致（仅允许相差 §4.3.2 中已确认删除的遗留表）。该测试永久保留，今后任何表结构变更都必须同步更新它，从而让 schema 变更在评审中可见。
4. 建库函数是一个**纯 DDL 清单**，放在 `thread_persistence.py` 内的单个函数中（或拆到同目录的独立模块，由 Plan 决定）。它不读取旧数据、不做数据回填，也不调用 `_add_*` 这类增量补列函数；现有 `_add_*` 函数的最终 DDL 被合并进各表的 `CREATE TABLE`。

### 4.4 Plugin registry

1. `registry.json` 只认 `REGISTRY_VERSION`（3）。`version` 为 2、缺失或其他值，统一按 `PLUGIN_REGISTRY_INVALID`（「Plugin registry 版本或结构无效」）失败关闭，**不读取、不修改、不生成备份**。
2. 删除：`_migrate_v2_locked`、`_migrate_v2_plugin`、`_installed_from_record_v2`、`_write_v2_backup_atomic`、`read_registry` 中的 v2 分支，以及 `_registry_state_from_document` 的 `expected_version` 参数分叉。
3. 此行为与 `docs/user/故障排查.md` 现有描述一致（该文档本来就写着旧版 registry 不会被读取或迁移）。

### 4.5 执行绑定

1. 删除：`LegacyModelBindings`、`PersistedBindingState.legacy_models` 与 `has_legacy_runtime`、`SelectionOrigin.LEGACY` 及 `resolve_execution_binding` 中对应分支、`ThreadPersistence._get_legacy_model_bindings`、`_has_legacy_runtime_binding`。
2. `resolve_execution_binding` 的解析顺序变为：请求 → 最近一次 Run → 配置默认，共三级。
3. `describe_thread_binding` 失去数据来源，随之删除；`models.list` 不再下发可选字段 `thread_binding`。该字段在协议里是可选的，**本任务不修改 `packages/protocol` 与 CLI**。协议字段 `thread_binding` 以及 CLI 的 `modelBindingConfirmation` 里对应的 legacy 文案另开后续 Task 清理（见 §8）。
4. `AgentEngineProfile` 的 v1 只读形态（`is_legacy`、`LEGACY_AGENT_ENGINE_PROFILE_VERSION`、`RUNTIME_PROFILE_LEGACY_READ_ONLY`）按 §5 的判据处理。

## 5. 旧形状代码的统一判据

除 §4.4、§4.5 明确列出的之外，仓库里还有大量「legacy」命名的代码，不能凭名字删除。唯一判据：

```text
这段代码的输入，是否只可能来自「升级前的旧库」？
  → 是（现役代码从不产生这种数据）：删除
  → 否（现役路径也会产生或消费）：保留
  → 无法确定：保留，记入 Todo 的「明确不做」清单，由后续任务处理
```

确认方法：对每个候选符号检查「谁写入它」。没有任何现役写入点才算「只来自旧库」。

已知候选（实施时逐项验证，结论写入 Todo）：

| 类别 | 例子 | 初步判断 |
|---|---|---|
| v1~v6 导入与回填 | `_bootstrap_legacy_transcripts`、`_bootstrap_legacy_compression_checkpoints`、`_backfill_artifact_metadata`、PromptEpoch adapter 与 `harness_prompt_epochs` | 只来自旧库，删除 |
| 迁移专用的 schema 契约比对 | `_migration_*_contracts`、`_migration_validate_*`、指纹与 digest 系列 | 迁移专用，删除 |
| 迁移子进程与标记文件 | `run_legacy_migration_child`、`_MigrationFileLock`、`threads/migration_worker.py`、`threads/migration_recovery.py` | 删除 |
| 故障注入全局变量 | `_MIGRATION_POISONED_PATHS`、`_MIGRATION_CHILD_*`、`_MIGRATION_ATOMIC_WRITE_FAULTS`、`_MIGRATION_UNLINK_FAULTS` | 删除 |
| Transcript 里的 `legacy_invalid_fields`、`legacy_incomplete`、`legacy_incomplete_history` | 与 Transcript 和上下文投影读写纠缠 | **默认保留**，除非实施时证明无现役写入点；证明前不动 |
| `context_window.py` 里的 `_legacy_request`、`allow_legacy` | 名字带 legacy，但可能是「旧调用入口」而非「旧数据」 | **默认保留**，不属于本任务 |

## 6. 测试策略

遵循 TDD：每个行为先写失败测试，再写最小实现。

1. **新增并永久保留**：
   - 空库创建：不存在文件、0 字节文件、仅 `user_version=0` 无表的文件，三种都能成功创建 `user_version=1` 且重启后可恢复 Thread。
   - golden schema 等价测试（§4.3.3）。
   - 不兼容库拒绝：对 `user_version` 为 0（有表）、2、20、1000 的库分别断言 `CHECKPOINT_SCHEMA_INCOMPATIBLE`、主库文件字节级不变（哈希）、目录内无附属文件。
   - 建库原子性：在 DDL 中途注入失败，断言回滚后文件仍是空库且可重试。注入方式使用被测函数的参数或 monkeypatch 单个明确的建表步骤，**不得**重新引入模块级故障全局变量。
   - 并发首次启动：两个 `open()` 并发竞争，结果都成功且只创建一套表。
   - Plugin registry：`version: 2` 被拒绝且原文件字节不变、无 `registry.v2.backup.json`。
2. **整体删除**：`tests/threads/test_migration_recovery.py`。`tests/threads/test_thread_persistence.py` 中以迁移、旧版本、备份、指纹、毒化、`zc108` 为主题的用例（按测试名初步统计约 51 个，总数 96），以及 `test_hc175_plugin_management_red.py` 中的 v2 迁移用例。
3. **改写**：依赖「手工构造旧版本库」fixture 的测试（`tests/support/thread_fixtures.py`、`test_thread_title.py`、`test_context_lifecycle.py`、`test_context_projection.py`、`test_compose_work_item_store.py`、`test_goal_store.py`、`test_agent_spec.py`、`test_agent_engine_profile.py`）改为直接用新库，不再 `PRAGMA user_version=N` 回写旧版本。
4. 删除用例时遵循：只删除「被测对象已不存在」的用例；行为仍存在的用例（Transcript 幂等、事务回滚、项目隔离等）必须保留。
5. 全量门禁：`cd packages/agent && .venv/bin/python -m pytest -q`；`cd packages/cli && bun test` 的失败项与改动前基线一致；`npm run tasks:check`。

## 7. 与 Compose 统一改造的衔接

- 本任务**保留**全部 Compose 表（`harness_compose_*`）及其读写代码，它们是基线的一部分。
- Compose 统一改造时，删表 = 修改基线 + `_SCHEMA_VERSION` 加 1 + 更新 golden。按 §2.8，那时所有开发库需要再删一次，这是预期行为，不是缺陷。
- `compose/recovery.py` 被 `tools/file_tools.py` 使用，其对 `threads/compose_work_item_store.py` 的依赖不属于本任务。

## 8. 边界

**Always**
- 改动前先导出 golden schema，再动生产代码。
- 删除代码时同步删除只为它存在的测试，且逐个确认被删测试的主题。
- 不兼容库的任何路径都保证主库文件字节不变。

**Ask first**
- 判据（§5）无法确定的符号，是否纳入本任务。
- 需要修改 `packages/protocol` 或 CLI 才能完成的清理。
- 基线中是否保留某张「疑似遗留」的表（发现有现役写入者时）。

**Never**
- 不得保留任何形式的「旧库自动升级」「自动备份」「自动重建」。
- 不得重新引入模块级故障注入全局变量。
- 不得修改 Compose 表结构与 Compose 代码行为。
- 不得为了通过测试放宽 `user_version == 1` 的判定。

## 9. 成功标准

对应 Task 验收标准，全部可自动或脚本验证：

1. 干净环境创建的库 `user_version == 1`，重启后能恢复 Thread。
2. `user_version` 为 0（有表）、2、20、1000 的库启动均报 `CHECKPOINT_SCHEMA_INCOMPATIBLE`；消息含绝对路径与处理提示；主库哈希不变；目录内无 `.migration*`、`.bak` 文件。
3. 新库 schema 与 golden 一致。
4. `harness_agent` 与 `tests` 下搜索 `migration_worker`、`migration_recovery`、`_run_legacy_migration_child`、`_MIGRATION_`、`CHECKPOINT_MIGRATION_`、`CHECKPOINT_SCHEMA_TOO_NEW`、`legacy_prompt_epoch`、`harness_prompt_epochs` 零命中。
5. `registry.json` 为 v2 或任何非 3 的版本时报 `PLUGIN_REGISTRY_INVALID`，原文件不变，无 backup 文件；代码中无 v2 解码器。
6. `resolve_execution_binding` 只剩请求 / 最近 Run / 配置默认三级；`LegacyModelBindings` 与 `has_legacy_runtime` 零命中。
7. `docs/user/故障排查.md` 无迁移 attempt / poison / 迁移子进程描述，含「库版本不兼容」处理步骤；`docs/developer/architecture/架构总览.md` 的迁移相关段落已改写；[ADR 0004](../architecture/adr/0004-legacy-migration-supervision.md) 状态改为已废弃并指向本任务，[ADR 0003](../architecture/adr/0003-transcript-context-projection-lifecycle.md) 的迁移小节加废弃说明，ADR README 同步。
8. 全量门禁通过（见 §6.5）。

## 10. 待确认问题

1. §5 中「默认保留」的两类（Transcript 的 legacy 字段、`context_window` 的 `_legacy_request`）是否在本任务内一并清理？Spec 倾向**不**纳入，理由是它们与现役读写纠缠，风险高、收益小，应在 Compose 统一改造后单独评估。
2. 协议字段 `thread_binding` 与 CLI `modelBindingConfirmation` 是否另开 Task？Spec 倾向另开，本任务只让 Agent 不再下发该字段。
