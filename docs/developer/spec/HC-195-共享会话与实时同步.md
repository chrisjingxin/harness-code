## 1. 解决什么问题

HC-194 已能登录、查看工作区和成员，但尚无共享会话。HC-195 让成员读取同一份有序历史，发送后明确知道“云端已保存”“等待原设备”“设备已受理”“正在运行”和“结果待确认”的区别。刷新、重连和 Java 重启都从数据库恢复，不能靠某个窗口或 Java 内存记住任务。

```text
当前成员发送 → 校验绑定和正文 → 短事务保存用户消息、执行登记、共享事件和去重结果
事务提交 → 返回已保存 → 数据库队列选同会话首项 → 先登记派发，再调用设备端口
Runner 持久受理 → Java 同事务保存受理及唯一 allow/deny 决定 → Runner 保存 allow 才能首次调用
Runner 先保存绑定/运行/输出 → Java 去重保存事实 → SSE 推送已提交事件
真实终态提交 → 释放该会话的执行位置 → 才能派发下一项
```

本任务主责 Java `conversation`、`execution`、`realtime` 及对应公共契约。设备登记、项目共享、WSS 和 Runner 账本归 [HC-196](../task/HC-196-设备接入与本机执行.md)；ACP 与文件/Git 分别归 HC-197、HC-199。中央/右侧 UI 由既有复用任务迁出，HC-202 装配，本任务不新画界面。

首个最小契约固定文本输入、文本输出、执行状态及其恢复。附件上传、工具/审批完整载荷、交接和引用业务不在本稿提前实现；它们必须由相应主责补充具名 schema 和共同夹具后接入，不能通过 `payload:any`、裸 ACP 帧或 Harness 私有类型代替。首版不做 CRDT、离线发送、自动迁机、仓库复制、Redis、消息中间件或新微服务。

### 2.2 单一 HTTP 边界的模块化增量

保留一条安全链。公共 Boundary 继续统一来源、版本、追踪号与安全错误；各业务模块向同一个路由目录登记“路径模板、允许方法、查询字段、请求 schema、字节限额、响应种类”。身份、会话和设备各自提供登记项，由统筹顺序装配；同一路径/方法重复登记使启动失败，不建立更高优先级的第二条安全链绕过原规则。

会话 Controller 只消费已校验参数和 Spring Authentication；业务用例在自己的短事务内经同一 `WorkspaceAccess.requireMember(userId, workspaceId)` 检查启用用户/成员，再读写本域数据。该具名入口是对现有身份规则的公开提取提案，使用同一个 DataSource/事务管理器并加入调用方事务，不再开独立连接做“先查权限、稍后写入”。授权记录的锁定方式见第 5 节；需要的 identity 装配改动列给统筹集成，不在本轮编辑 HC-194 源码。

HTTP 错误仍用 HC-194 的 `ErrorResponse`，JSON 成功对象不加套壳。只有 SSE 路由在握手全部校验后选择 `text/event-stream`；失败且尚未提交响应时仍走统一 JSON 错误出口。异步响应开始后不能让原 Boundary 再向流中写 JSON，后续故障按第 8 节关闭流。

主进程在同一客户端会话上下文中增加具名会话方法和 SSE 消费器，复用 Jar、Origin/版本、Cookie 检查、拒绝重定向与代次取消。仅按已登记 schema/路由应用业务限额，不全局放大身份限额。普通请求保留有界超时；SSE 分开约束握手和无数据等待，不使用 10 秒总超时。renderer 不获得 URL、headers、Cookie、CSRF 或通用 fetch。preload/状态聚合和真实 UI 接线由统筹协调 HC-202，不提前扩写身份 UI。

### 2.3 契约与文件归属

拟由本任务维护 `schema/conversation.schema.json`、`schema/execution.schema.json`、`fixtures/conversation.json`、`fixtures/execution.json` 和 `src/conversation.ts`、`src/execution.ts`，均位于 `packages/workbench-contracts/`。会话、执行分别使用 `Conversation…`、`Execution…` 前缀避免 `$defs` 重名，公共 ID/时间/错误只引用 HC-194 唯一源。设备协议引用执行类型，不另写一套相同载荷。

总导出、schema 资源登记、OpenAPI 聚合及错误码集合由统筹顺序集成；主进程校验器加载同一登记集合，Java/Node 消费同一组正反例。Java record/TS 类型只是消费模型，两端线上仍作严格 schema 校验。未知 type、额外字段、错误数字类型和不支持版本均拒绝，不作旧协议 fallback。以上均为拟新增路径，当前不创建生产文件或无效 Markdown 链接。

## 3. 身份、绑定和作者

### 3.1 三种会话不能混用

| 名称 | 保存位置与用途 |
| --- | --- |
| UI 登录会话 | HC-194 HttpSession/WBSESSION，表示哪个普通用户访问服务；Java 重启需重登，不承担共享历史 |
| 平台会话 `conversationId` | Java 数据库中的共同工作记录，绑定一个工作区、原设备、项目和本机 Agent 配置；桌面、消息、队列均使用此 ID |
| Agent 原生会话 `nativeSessionId` | ACP 返回的不透明标识，Runner 管理原生上下文；云端仅保存关联，不能作为平台 ID、授权凭据或 Harness Thread 类型使用 |

新平台会话只能选择已向当前工作区共享的 `deviceId + projectId + agentConfigId`，不得提交绝对目录、shell 启动命令或原生会话 ID。HC-196 负责核实这些 ID 的归属及登记元数据。共享关系、设备未撤销及目标配置登记仍有效，即可离线创建会话、保存 queued 输入；暂时离线或尚未 ready 不返回 TARGET_UNAVAILABLE。ready/真实端口能力只决定何时可派发。云端只保存展示名称和稳定标识，根目录映射留原设备。

`workspaceId/deviceId/projectId/agentConfigId` 创建后不可重绑。本稿不提供换机器、换目录、换后端、导入个人历史或清空原生上下文的接口。云端与 Runner 保存同一个不透明 nativeSessionId，不设代理绑定 ID。首次原生绑定经原设备 `execution.native.bound` 有序登记；后续必须一致。首次固定 start 的 null 不因后来绑定而改写，后续 start 使用已确认原生 ID。不能恢复原生会话时保留平台历史并明确不可继续/待确认，不能静默建一个新原生会话冒充接续。

### 3.2 可见范围与历史归属

启用的工作区成员可读该工作区已经形成的共享历史。项目停止共享后已同步历史保留可读；新建会话、新发送、新派发及首次运行决定须核对当前授权和共享版本。未共享的本机个人历史不上传、不加入列表。原执行已获 allow 后的真实事实补传只核对原设备、命令和绑定，不因原发起人后来停用/移除成员或停止共享丢弃；用户能否阅读这些事实仍按当前身份/成员单独判断。

用户消息作者由服务端当前 userId 固定；正文夹带 author/actor/userId 一律 400。消息记录保留 `authorUserId` 和保存当时的 `username/displayName` 快照，后续改名、退出或切换账号不重写历史作者。执行另存 `initiatedByUserId`，不能因后续接续人变化换掉发起人。Agent 输出作者是绑定 `agentConfigId`，系统状态由 Java 生成；设备无权伪造用户消息或另一执行的事件。

新会话 `currentUserId` 初始为创建用户，仅表示当前接续人；不授予额外权限，普通成员发送能力相同。后续交接变更归 HC-198，本任务不提供任意修改该字段的接口。

个人草稿、页签、滚动、文件预览、工具展开和在线提示不写入共同历史。当前只使用按服务 origin/userId/workspaceId/conversationId 隔离的内存视图；退出、切换和会话失效先隔离旧订阅/数据。磁盘缓存不是本任务交付项。

## 4. 最小数据和稳定标识

ID 复用 HC-194 的小写 UUID。所有线上 occurredAt/createdAt/updatedAt/savedAt 等时间精确复用现有 UtcTimestamp：`YYYY-MM-DDTHH:mm:ss.SSSZ` 字符串（三位毫秒、Z 结尾且日期有效）；不能改成数字 epoch 或另一套时间字段。SQL 内部才存 UTC epoch 毫秒 BIGINT，出入 DTO 时显式转换；Java 生成共享事实时间，设备报告的内层 occurredAt 也是同一线上类型。顺序/版本用受限十进制字符串；`0` 表示尚无来源/会话事件，真实 sequence 从 `1` 开始，无前导零，最大值为有符号 BIGINT 上限。客户端不能转 JS Number 或按普通字符串排序。时间和 UUID 不参与先后排序。

| 对象 | 最小字段与不变量 |
| --- | --- |
| Conversation | `conversationId, workspaceId, title, createdByUserId, currentUserId, deviceId, projectId, agentConfigId, createdAt, nextSequence, activeExecutionId`；内部另存可空 `nativeSessionId`。标题 1～120 Unicode 字符，初版创建后不编辑；activeExecutionId 为空或只指向本会话一项未明确结束的执行 |
| Message | `messageId, conversationId, executionId, author, createdSequence, createdAt, text, state`；author 为明确的 user/agent 判别联合。用户消息保存后不可变；Agent 消息按事件追加文本，state 为 `streaming/completed/interrupted` |
| Execution | `executionId, conversationId, inputId, inputSequence, initiatedByUserId, state, lastConfirmedState, cancelState, reasonCode, createdAt, updatedAt`；内部保存含 shareVersion 的目标快照、固定 start/cancel 内层消息、最后已提交 runnerSequence、一次运行决定消息及结果。`inputId` 就是用户 Message 的 messageId，不另建等价输入表 |
| ConversationEvent | `protocolVersion:1, messageId, type, occurredAt, workspaceId, conversationId, sequence, payload`；沿用 PlatformMessageHeader。这里头部 messageId 标识事件本身，payload.messageId 才是业务消息 ID，两者不得互换；事件追加后不改写 |
| RequestReceipt | `workspaceId, userId, operation, requestId, targetId, canonicalBody, bodySha256, result`；保存首次提交结果。operation 仅 `conversation.create/input.send/execution.cancel`，唯一键为前四项 |

`requestId` 是正文中由宿主为一次用户意图生成并在确认前保留的业务去重 ID；每次 HTTP 尝试的 `X-Request-Id` 仍独立生成，只用于追踪。重复点击/重试保留前者；用户明确再问一次才创建新 ID。`executionId` 由 Java 首次保存时生成，普通重试不能产生第二项执行。start commandId 首次派发前生成并持久化，以后核对/重传均保持同一个 ID 和同一正文。

对外 `ConversationSummary` 精确包含 `conversationId,workspaceId,title,createdByUserId,currentUserId,deviceId,projectId,agentConfigId,createdAt`；内部计数器、原生 ID 和 activeExecutionId 不直接输出。`ExecutionView` 精确包含 `executionId,conversationId,inputId,inputSequence,initiatedByUserId,state,lastConfirmedState,cancelState,reasonCode,createdAt,updatedAt`，reasonCode 为可空的已登记枚举。`lastConfirmedState` 在正常状态等于 state；unknown 时保留进入 unknown 前的已知非终态。

ExecutionReasonCode 限定为 `WAITING_DEVICE/WAITING_PREVIOUS/WAITING_PROJECT/WAITING_EXECUTOR/AUTHOR_UNAVAILABLE/PROJECT_NOT_SHARED/SHARE_VERSION_CHANGED/DEVICE_REVOKED/TARGET_INVALID/PROJECT_ROOT_CHANGED/CAPABILITY_UNAVAILABLE/CANCEL_REQUESTED/DELIVERY_UNCONFIRMED/DEVICE_DISCONNECTED/RUNNER_STATE_UNKNOWN/NATIVE_SESSION_UNAVAILABLE/EXECUTION_FAILED/CANCELLED_BEFORE_DISPATCH/CANCELLED_BY_RUNNER` 或 null；正常受理/运行/成功为 null。设备/ACP 原始错误文本、退出码和堆栈不能替代该枚举。后续增量扩展须同步 schema/消费方/夹具。

Message 的 user 作者精确为 `{kind:"user",userId,username,displayName}`，agent 作者精确为 `{kind:"agent",agentConfigId}`；Message 不包含 system 作者，系统变化使用具名事件。原生 ID 是 1～512 Unicode 字符的不透明字符串，禁止 NUL/未配对 surrogate，不解析内部结构。

### 4.1 表与约束提案

HC-195 维护六张表：`wb_conversation`、`wb_message`、`wb_execution`、`wb_conversation_event`、`wb_conversation_request`、`wb_execution_receipt`。使用 HC-194 的普通 InnoDB/MySQL 方言、ASCII 二进制 ID 比较、utf8mb4 文本、UTC epoch 毫秒、应用侧关联校验；不依赖外键、触发器、CHECK、JSON 专有查询或自生成 UUID。结构化正文以受 schema 校验的 TEXT/MEDIUMTEXT 保存，不依赖数据库 JSON 运算。

主要约束为：Message 主键、Execution 主键及 `UNIQUE(input_id)`；事件主键和 `UNIQUE(conversation_id, sequence)`；请求前述唯一键。执行索引 `(conversation_id, input_sequence)` 选择队首；会话列表索引 `(workspace_id, created_at_ms, id)` 稳定分页。`wb_execution_receipt` 精确保存 `source_event_id` 主键、`device_id,execution_id,runner_sequence,canonical_body,body_sha256,committed_at_ms`，并设 `UNIQUE(execution_id,runner_sequence)`；相同来源事件或序号必须精确匹配原正文。公开事件可空关联 source_event_id，一条回执可以产生零条或多条公开事件。

执行登记本身就是持久待派发记录，不再增加一套内存权威队列或另建消息中间件。消息表为读模型，事件表保存可重放的不可变内容；追加事件和更新消息/执行视图在同一事务提交。Runner 回执登记、对应的零条或多条公开事件以及最后连续 runnerSequence 必须在同一事务保存；没有公开展示变化的回执也不能省略登记。六表各有用途，不用 SSE 投影代替设备回执账本。

一次运行决定直接加在 `wb_execution`：`start_decision_message_id`（可空唯一 UUID）、`start_decision`（可空 allow/deny）、`start_decision_reason`、`start_decision_body`、`start_decision_sha256`、`start_decided_at_ms`；全空表示尚未决定，一次事务全部写入后不可改写。body 保存含稳定头的完整 `execution.start.decision`，messageId 就是决定的稳定 ID，不另加等价 ID 或许可表。固定 start/cancel 正文及 hash、接受回执的连续位置均由这条执行关联，回执详情仍存已有 wb_execution_receipt。决定不是岗位/角色授权模型。

统筹已分配 V002 给 HC-196 的设备/项目/设备请求三表，V003 给本任务六表；V003 必须在 V002 后显式迁移，项目授权和消息/执行在同库短事务核实。本轮仅文档，不创建 SQL。不得改 V001/V002 已执行文件、自动补数据、降低启动校验或写第二套内网 SQL。首版不删除/压缩历史和去重记录，因而恢复游标不会仅因时间经过失效。

### 4.2 本稿的公开事件

| type | payload 的完整业务内容 |
| --- | --- |
| `conversation.created` | `conversation`：去除原生 ID、内部命令/计数器/去重正文的会话概要 |
| `message.created` | `message`：完整新消息，user 含固定正文/作者快照，agent 初始 text 为空且 streaming |
| `message.text.appended` | `executionId, messageId, text`：只追加本条已存在且 streaming 的 Agent 消息；不接受覆盖文本或跨执行归属 |
| `message.closed` | `executionId, messageId, state`，state 仅 completed/interrupted；已关闭消息不能再追加 |
| `execution.changed` | `execution`：完整公开执行视图，含 state、lastConfirmedState、cancelState 和稳定 reasonCode，不含设备凭据/命令正文/原生 ID |

payload 按 type 是闭合的判别联合，不允许任意字段。每项事件在事务内分配会话 sequence 并写入；回滚不消耗已提交序号。Runner 产生的 Agent messageId 需为其账本提前保存的 UUID，Java 验证未被其他会话/执行占用；原生回放必须映射回原 ID，不作为新的用户消息再次追加。

终态必须在全部前序输出落库后保存。succeeded 要求该执行所有 Agent 消息已经 completed；failed/cancelled 时 Java 在同一终态事务把残留 streaming 消息关闭为 interrupted 并追加对应事件，不能让历史永久显示仍在输出。rejected 不得已有执行端口输出；违反状态/归属的回执拒绝，不能通过自动修补正文掩盖协议错误。

## 5. 保存、去重和短事务

### 5.1 一次发送

输入为严格 `{requestId, text}`，text 不能为空白、最多 32 KiB UTF-8 且最多 16,384 Unicode 字符；拒绝 NUL、未配对 surrogate 和非法 UTF-8，保留合法原文的空格、换行、大小写和 Unicode 形式，不在服务端 trim/规范化后再保存不同正文。HTTP JSON 体上限 64 KiB，字节与字符两项均校验；本轮实际 `input:{text}` 就是同一用户原文并沿用同一上限，不先扩充未来引用文本预算。对应公开事件仍须满足其 64 KiB 编码限额，超限整体 413，不先保存部分正文。

```text
来源/形状/CSRF → 当前用户与工作区 → 请求去重查询
已有且正文一致 → 返回首次回执；已有但正文不同 → 409 REQUEST_ID_CONFLICT
新请求 → 锁定授权/项目共享记录和会话 → 再查去重 → 核对固定目标并保存 shareVersion 快照
→ 保存用户消息 → 保存 queued 执行 → 追加 message.created/execution.changed
→ 保存去重回执 → 一次提交 → 返回 inputId/executionId/已提交位置
```

比较内容是按固定字段顺序构造的 UTF-8 业务正文，包含 operation、路径中的 workspaceId/conversationId 和原文 text；JSON 空白、键顺序与转义写法不影响语义。保存 SHA-256 辅助核对，同时保留确定性正文作精确比较，不只比较 hash。创建会话还包括固定目标/标题；取消包括目标执行。作者来自登录会话，也在去重键中。

重复请求先核实当前用户/工作区和会话仍可读，再返回旧结果；它不产生新的设备操作，因此之后停止共享不使已提交的相同请求变成“未保存”。首次请求则必须满足当前项目共享。不同正文即便换了目标会话也不能在同一 operation/工作区/作者下复用该 requestId。权限失效不能借旧 requestId 读取回执。

使用同一 DataSource 和短事务；锁顺序固定为用户/成员授权记录 → 设备项目共享记录 → conversation → execution/request。设备共享撤回采用同一项目共享记录串行化，避免撤回与首次保存/派发各自看到过期权限。成员移除/用户停用不得使用未受约束的应用写入口；和已开始事务竞争时按数据库锁先后决定，已提交响应无法撤回。锁不跨 WSS、模型、SSE 写出或用户等待。

成功首次返回 201 `InputSavedResponse`，相同重试返回 200 且回执内容相同：`{conversationId,inputId,executionId,inputSequence,committedSequence,savedAt}`。回执仅证明保存；实时状态读 Execution 或历史事件，不能把首次 queued 快照当成当前状态。并发唯一键竞争必须整笔回滚后在新事务重读结果，不能在一个已失败事务里继续写入；有限重试仍失败返回 503，不留下半份消息或执行。

提交响应丢失或发生 5xx/超时，宿主保留 requestId 和原文，显示“保存结果待确认”，用同一身份查询回执或原样重试；不能自动换 ID。数据库提交结果不明也采用这一规则，错误的 retryable 不等于“肯定未保存”。首版断网不把新输入加入离线发送队列。

### 5.2 创建和取消

创建输入为 `{requestId,title,deviceId,projectId,agentConfigId}`；同一短事务检查当前授权、保存会话（currentUserId=创建用户）、`conversation.created` 和创建回执。返回 `{conversation,committedSequence}`，首次 201、相同重复 200，正文冲突 409。不连接设备或预先创建 ACP 原生会话。

取消输入为 `{requestId}`，任何仍有权操作该共享项目的工作区成员均可请求，并记录真正请求人；设备所有者在项目停止共享后的明确本机停止能力归 HC-196，不借本接口增加非成员云端权限。相同 requestId 返回首次取消回执；不同 requestId 对同一已请求取消不生成第二条取消命令，也不追加无变化事件。

若执行仍 queued 且没有派发登记，取消事务直接转 cancelled，保证设备从未有机会受理；锁与派发选择互斥。若已 dispatching/accepted/running/unknown，只持久保存 `cancelState=requested` 和固定取消 commandId，提交后经原设备发送。设备收到只变 delivered，不能当作 cancelled。返回 `{executionId,cancelState,stateAtRequest,committedSequence}` 表示该次请求事实；之后的真实终态另读。终态已提交时新取消请求返回实际终态，不把 succeeded 改成 cancelled。

## 6. 顺序、受理、一次运行决定和恢复

### 6.1 状态与队首

| state | 可靠事实；是否占住会话执行位置 |
| --- | --- |
| `queued` | 已保存，未登记派发；等待原因可为 WAITING_DEVICE/WAITING_PREVIOUS/WAITING_PROJECT/WAITING_EXECUTOR；不占 activeExecutionId |
| `dispatching` | 固定 start 已持久登记并占位，可能已送达，尚无 Runner 持久受理事实；占位 |
| `accepted` | Runner 已持久受理；Java 已保存一次 allow/deny，但还不能证明实际调用。deny 也不能释放占位 |
| `running` | Runner 已持久记录实际开始并补传，原生绑定已在此前连续前缀核实；占位 |
| `unknown` | 可能已受理/调用，暂不能核实；保留 lastConfirmedState、原决定及占位，不自动重跑或迁机 |
| `succeeded/failed/cancelled/rejected` | 确切结束事实；释放占位。rejected 证明未调用，failed/cancelled 不承诺回滚已经发生的外部修改 |

`cancelState` 独立为 none/requested/delivered/resolved；只有已请求取消的执行在确切终态时转 resolved，未请求取消仍为 none。accepted、allow、网络 written、取消送达都不是 running 或成功。决定本身只保存在执行内部，UI 从 accepted、取消/原因、后续真实状态理解进展，不增加权限管理界面。

队列按首次用户消息的 inputSequence 升序选择。保存时固定该输入获准的 shareVersion；准备派发时按“用户/成员 → 设备项目 → conversation → execution/request”锁顺序复核同一版本和固定目标，在无 activeExecutionId 时一次事务登记 start/占位。共享已撤回或版本已变化，未派发项明确 rejected；重新共享不把旧队列改成新版本重跑。设备暂离线、未 ready、端口暂不可用或目录暂忙则 queued 等待，不跳过前项、不换机器。不同会话可独立选择，原目录占用由 HC-196/199 维护。

Java 提交登记后才调用 DeviceDelivery.sendStart。一个 HC-195 调度器扫描数据库并处理提交后唤醒，HC-196 上线只唤醒它；内存信号不是可靠队列。首版单活动 Java，不增加集群协议。派发后 15 秒仍无持久受理事实则转 unknown 并向原设备核对；定时器失去唤醒后靠数据库扫描补齐。超时不意味着未送达，网络调用从不在 JDBC 事务内。

主转换为 queued→dispatching/cancelled/rejected；dispatching→accepted/unknown，或经取消先到的明确未调用事实转 cancelled；accepted→running/rejected/cancelled/unknown；running→succeeded/failed/cancelled/unknown。首次调用后即使没有收到 running，Runner 的可靠 finished 事实也可使 accepted/unknown 转对应终态。unknown 恢复不能低于 lastConfirmedState；迟到 accepted 不能降级 running。相同状态/原因/取消状态不重复追加公开事件。

### 6.2 受理与一次运行决定的事务

Runner 对合法来源、完整形状、与已登记目标归属一致且能够落盘的新 start，先把完整内层消息、受理状态及 `execution.accepted` 同一笔本地事务保存，此时禁止首次调用执行端口。accepted 不表示目录/能力预检通过。ID/正文/目标冲突走协议冲突，不伪造 accepted/终态；账本写失败不发成功记录。Java 的 ExecutionReceipts.recordBatch 验证当前可信设备连接、原命令/目标/摘要、连续序号后，在保存首次 accepted 的同一个短事务执行：

```text
按固定锁顺序读取授权/共享事实 → 锁原会话/执行 → 核对并登记 accepted 来源事件
→ 尚无决定时检查取消、原发起人启用/成员、设备/项目/配置及同一 shareVersion
→ 全部通过：保存唯一 allow；否则保存明确 deny
→ 保存 accepted 状态/公开事件/连续位置 → 一次提交 → 返回已提交前缀和原决定
```

这里“检查授权”是决定是否允许新调用，不是决定是否保存已发生事实。已停用、成员移除、停止共享、版本变化或设备/目标失效都应保存受理事实并给出 deny，不能抛普通 UI 401/404 使 accepted 永久无法登记。deny 原因仅 CANCEL_REQUESTED、AUTHOR_UNAVAILABLE、PROJECT_NOT_SHARED、SHARE_VERSION_CHANGED、DEVICE_REVOKED、TARGET_INVALID；allow 的 reasonCode=null。多项同时不满足时按上述顺序取首个原因，决定与原因一起固定。

决定消息为第 7 节 execution.start.decision。其平台头 messageId 在本事务生成并与完整确定性正文存入 wb_execution；以后只读取这一份。回滚/连接失败不发确认、不发 allow，不留下“受理已保存但决定未保存”的半笔成功。事务提交结果不明，调用方重传原 accepted，由数据库唯一约束核对原事实；不得另外生成决定。

Runner 只在保存匹配原 start/摘要的 allow 之后，且当前连接已核对完成、本地共享仍允许、没有取消禁启标记时，才能首次调用。allow 不是绕过本机目录/能力/占用校验的通行证；调用前必须持久记录“下一步可能已产生副作用”的边界。deny 本地保存后禁止首次调用，由 Runner 根据未调用的确切记录生成 rejected；取消导致的 deny 或取消标记则生成 cancelled。Java 收到 deny 仍保持 accepted/unknown 和占位，等这些终态有序落库，不能把决定直接当真实停止。

取得原决定后，本地尚未进入 invoking 的目录身份预检失败，以 notInvoked/rejected/PROJECT_ROOT_CHANGED 收敛；实际执行端口缺失或不支持，以 notInvoked/rejected/CAPABILITY_UNAVAILABLE 收敛。这两个原因不替换成 TARGET_INVALID、failed 或任意错误正文，也不修改原 allow。合法转换是 accepted→rejected，或 unknown 在原命令/序列核对并取得确切未调用事实后→rejected。目录暂忙仍为已受理等待占用，不是拒绝终态；queued 时已知暂不可用仍可等待端口，不能为了演示接生产替身。

### 6.3 决定重传与取消竞争

决定第一次提交后不重新计算：相同 accepted 重复、ack 丢失、决定丢失、Java/Runner 重连均返回原 startDecision 和当时最新已提交连续前缀。之后原发起人停用或停止共享，不能把原 allow 改成 deny，也不能删除真实输出；原 deny 后重新共享也不能改成 allow。新的输入才重新检查当前授权。网络外壳只换 connectionId，决定的头、时间、正文和指纹不变。

Runner 必须保留 accepted 的完整内层消息，直到“该序号已获前缀 ack”且“原决定已在本地提交”两项均成立；不能仅因 ack 到达就清掉恢复决定所需的正文。已受理且尚无决定时每 5 秒重传同一 accepted，包含 ack 已到/决定丢失的情况；Java 即便只收到精确重复也返回原决定。重连也可经 reconcile 取得原决定，收到不同决定 ID/正文立即冲突而不是替换。取消先到已形成真实终态的项不等待一个不存在的决定。

| 竞争顺序 | 必须产生的结果 |
| --- | --- |
| queued 取消先取得锁，尚无 start | 同事务 cancelled，不派发、不造 Runner 回执或决定 |
| 已登记 start，取消在首次决定前提交 | 取消意图/固定 cancel 保存；首次 accepted 事务决定 deny/CANCEL_REQUESTED，等待 Runner cancelled 证明 |
| allow 先提交，取消后提交 | 保留原 allow，独立持久 cancel。即使 allow 尚未到达，也不改写决定；Runner 先收到 cancel 则禁启，先调用则请求真实取消并等待终态 |
| cancel 先于 start 或决定到 Runner | 先持久 executionId/startCommandId 禁启标记；cancel.received 与随后能证明的 cancelled 在同一执行序列内保存。迟到 start/allow 不能启动 |
| deny 已提交，之后又请求取消 | 保留原 deny；cancel 仍可送达帮助收敛，Runner 未调用证明决定 rejected 或 cancelled；Java 不凭 deny 释放队首 |
| 真实终态先提交，随后取消 | 返回原终态，不重写为 cancelled，不新建第二个执行 |

取消先到且账本未见 start 时，cancel 自带原 startCommandId/startBodySha256 和固定目标，Runner 同一事务保存禁启及连续的 cancel.received、证明 notInvoked 的 cancelled，从 1 开始使用原 executionId 的 runnerSequence；不等待重发 start，不伪造 accepted/运行决定。恢复清单 cancelBeforeStart 带来源前缀、已确认位置及完整真实终态，原消息可恢复补传。若 start 后来首次到达，只比对原目标/正文并返回既有取消结果，不新生成 accepted 或第二个终态。Java 只在确有已持久 cancel 命令的情况下接受这条特例。

decision/终态/取消的数据库竞争都使用同一执行行锁。已获 allow 的在途工作仍需遵守本地后来确认的停止共享：尚未调用可明确拒绝启动，已调用则保留实际结果、由所有者明确停止。它不使原决定改变，也不授权普通成员在停止共享后发起新控制。设备层鉴权继续使用当前可信设备连接，不复用 UI 登录凭据。

### 6.4 原生绑定与顺序恢复

首次 start.nativeSessionId 可以为 null。Runner 保存 allow 后在原项目创建/恢复原生会话，把同值本地绑定与 `execution.native.bound` 先持久保存，再有序发送；该事件必须在 running/output 前。Java 同一事务核对原目标：云端绑定为空则首次保存该不透明值，已有则必须精确相同。即使不生成公开 SSE 变化也登记来源回执和 runnerSequence，并推进前缀确认。

第一次固定 start 的 null/摘要保持原样；重复 start 从本地既有 conversation 绑定读取同一个原生值，不再创建会话。后续 start 必须使用 Java 已确认的 nativeSessionId。每项执行在实际调用前都补传 native.bound，表明沿用同一绑定；恢复过程不重新发送旧 Prompt，也不把 Agent 原生回放当新消息追加。恢复失败且能证明未调用时生成 rejected/NATIVE_SESSION_UNAVAILABLE；一旦越过可能调用边界且无法核实结果则 unknown，不能静默创建替代原生会话。

| 重启时持久事实 | 恢复动作 |
| --- | --- |
| queued、没有 start | 当前授权/版本及 ready 允许时继续队列 |
| 已登记 start，从未收到 accepted | unknown，先核对同一 ledgerId；可信 notFound 且没有受理/调用事实时可重送同一 start，不能换 ID/正文/版本 |
| accepted 与决定已在 Java，Runner 未存决定 | 重发原决定和前缀；deny 仍等待未调用终态，allow 仍需本地检查后首次调用 |
| Runner 已存 accepted，Java 缺前缀 | 重传原来源事件，经 recordBatch 保存受理/唯一决定；恢复摘要不能绕过回执事务另造 accepted |
| 已存 allow、本地未越过调用边界 | 核对原决定/取消/共享/绑定/目录占用，才允许原项第一次调用；不是重跑已调用任务 |
| native.bound 已在本地，Java 尚未确认 | 原 ID/序号重传，同值登记，固定 start 的 null 不变；不得另建原生会话 |
| 调用边界已持久，原进程/工具结果不能确定 | unknown，保留会话和目录占用；上下文可恢复不等于旧输入可重跑 |
| 本地已真实终态，Java 尚未保存 | 先补连续前缀和原终态，Java 提交后释放队首，再处理后项 |
| Java 已终态，Runner 重传 | 精确重复返回最新前缀/原决定；矛盾终态或后加输出拒绝，不覆盖历史 |

Java 重启丢失全部连接可达性，HC-196 用新 connectionId/当前 socket 及持久 ledgerId 完成核对；不持久连接版本或增加服务实例三元组。可信 notFound 只适用于原账本且从未确认受理的项；已确认 accepted/running 后“账本不存在”、账本变更或不明进程都不能成为重送证明。设备失联/重启未核实则追加一次 unknown，保留原决定。事实补传不重新检查发起人的现时发送权限，仍核对原设备/命令/绑定以及外层设备凭据的有效性。

resendSame 还要求当前发起人/共享版本仍允许且没有取消；不满足则 waitForEvidence 并送出已经持久存在的 cancel（如有），等待原设备未调用/终态事实，不能把授权失效本身当停止证明。已有决定无论后来授权如何都只重传原决定；它不是本次新发 allow。恢复中发现所报 storedDecisionMessageId 与原决定不同或原生绑定不同，返回冲突并保留占位，禁止以另一决定/绑定接续。

只有可靠事实使 unknown 收敛。本任务不提供强行清队列/改失败/人工重跑未知副作用的入口；外部文件、Git 或工具副作用不承诺全局 exactly-once。

## 7. 与 HC-196 的共同交界

以下已按统筹第 5/6 节裁定收敛成单一契约，主要交界方向复核通过，当前进入 Plan/Todo 文档待审；不是生产接口已实现或实际集成已通过。执行 wire/指纹唯一源归 HC-195，HC-196 设备帧只包连接归属，不另写 execute/receipt/permission 载荷。

### 7.1 具名端口和结果

| 端口及主责 | 完整业务输入 → 结果/错误；事务 |

| HC-196 `DeviceDelivery.sendStart/sendCancel` | `{deviceId,connectionId,message}`，message 分别为下述固定 start/cancel → written/offline/superseded；只观察传输，事务提交后调用，不推进受理/运行/终态 |
| HC-195 `ExecutionReceipts.recordBatch` | `{deviceId,connectionId,executionId,events}`；HC-196 已核对当前 socket/连接，events 为同一执行有序 Runner 内层消息，最多 64 条/256 KiB → `{ack:{executionId,lastCommittedRunnerSequence},startDecision:完整原决定或null}`。一次事务登记回执、首次 accepted/决定、绑定、公开投影和前缀；提交后才返回成功 |
| HC-195 `ExecutionRecovery.reconcile` | `{deviceId,connectionId,ledgerId,executionId,startCommandId,startBodySha256,localState,storedDecisionMessageId,nativeSessionId}`；localState 仅 notFound/accepted/notInvoked/invoking/running/terminalPending/unknown，可空值显式为 null → `{action:continueOriginal或resendSame或waitForEvidence或terminalSaved,ack,startDecision}`。返回原决定，不另算授权决定；网络核对在事务外，终态/绑定等事实必须经 recordBatch 保存，不能凭摘要另造回执 |

recordBatch 错误是闭合联合：`{kind:gap,executionId,expectedRunnerSequence,lastCommittedRunnerSequence}`；或 `{kind:conflict或targetMismatch或bindingConflict或invalidTransition,executionId}`；或 `{kind:storeUnavailable,executionId}`。整批失败不推进前缀、不发成功 ack/allow；冲突暂停该项核对，不覆盖已有事实。reconcile 另可返回同样的冲突/storeUnavailable，ledgerId 不符归 conflict，不以新空账本当 notFound。

DeviceDelivery 的同一传输装配还负责发送 recordBatch/reconcile 返回的 `execution.start.decision` 与 `execution.events.ack`，不另外生成决定。决定丢失由原事件重传/恢复核对再次取得原决定。外层当前 connectionId 可以换，内层消息不可改。成功结果的 ack 是数据提交位置；决定是否送达/Runner 是否已存决定均不能从 socket written 推断。

新操作锁顺序始终为用户/成员 → 设备项目 → conversation → execution/request。既有事实登记仅取核对需要的固定目标/会话/执行锁，不要求发起人仍启用；首次 accepted 需要决定时先按完整顺序取授权事实，禁止先锁执行再倒取授权锁。设备撤回自身事务不反向持项目锁再拿会话锁，提交后唤醒 HC-195 收敛 queued。所有网络均在事务外。

### 7.2 唯一内层消息与字段顺序

所有内层对象精确为 `{protocolVersion:1,messageId,type,occurredAt,payload}`，顺序也按此排列。messageId 是该命令、决定或 Runner 来源事件本身的稳定 ID；commandId/sourceEventId 只在文字或 SQL 列中称呼这同一值，不在消息重复增加等价字段。payload 中 startCommandId/cancelCommandId 是引用另一条命令，startDecisionMessageId 是引用原决定，均不是自身 ID 的副本。对决定不增加 permissionId。连接外壳由 HC-196 定义，仅包含连接归属与完整内层消息；Java/Runner 均以当前 socket、已认证 deviceId 和一个 connectionId 检查，不增加连接三元组。

下表 payload 按列出顺序排列，字段全部必需。`D` 表示固定目标前缀，精确顺序为 `workspaceId,conversationId,executionId,inputId,deviceId,projectId`。`R` 是来源前缀，顺序为 D 后加 `startCommandId,runnerSequence,startBodySha256`。D/R 仅是文档简写，线上平铺字段，不建立 D/R 对象或类型别名。所有持久消息 payload 最后附 bodySha256，表中不反复列；ack 例外，只有它的两字段。

| type / 方向 | payload：完整顺序；含义 |
| --- | --- |
| `execution.start` Java→Runner | D、`inputSequence,initiatedByUserId,agentConfigId,shareVersion,nativeSessionId,input`；nativeSessionId 为 null 或原生字符串，input 精确 `{text}`，本轮同 32 KiB/16,384 字符上限 |
| `execution.cancel` Java→Runner | D、`startCommandId,startBodySha256,requestedByUserId`；自身头 ID 是稳定 cancel 命令 ID，不在被取消执行之后排队 |
| `execution.start.decision` Java→Runner | D、`startCommandId,startBodySha256,decision,reasonCode`；decision 为 allow/deny，allow 原因为 null，deny 仅第 6.2 节六种原因；头 ID 就是唯一决定 ID |
| `execution.accepted` Runner→Java | R；仅证明本地已持久受理，头 occurredAt 就是设备发生时间，不另加 receiptId/acceptedAt |
| `execution.native.bound` Runner→Java | R、`startDecisionMessageId,nativeSessionId`；原决定必须是本执行 allow，同一原生值先落本地；Java 只登记关联，不向 UI 输出 |
| `execution.running` Runner→Java | R、`startDecisionMessageId,nativeSessionId`；前序 native.bound 已核对，实际开始事实而非创建 Promise |
| `execution.output` Runner→Java | R、`startDecisionMessageId,change`；change 为下文三种严格消息变更之一，原决定为 allow |
| `execution.terminal` Runner→Java | R、`startDecisionMessageId,nativeSessionId,state,reasonCode,invocationState`；决定引用可空，nativeSessionId 可空；state 为 succeeded/failed/cancelled/rejected，invocationState 为 notInvoked/finished |
| `execution.cancel.received` Runner→Java | R、`cancelCommandId`；核对原 cancel，只令 cancelState=delivered |
| `execution.events.ack` Java→Runner | `executionId,lastCommittedRunnerSequence`；只确认已提交连续前缀，不加决定/来源事件 ID。可按最新前缀重新发头；不是持久执行命令，不影响副作用去重 |

所有 Runner 事件在同一 executionId 下从 1 连续编号，accepted/native.bound/running/output/cancel.received/terminal 共用 runnerSequence；取消本身不另起一套事件序号。正常路径第一项是 accepted；第 6.3 节已持久 cancel 先到的特例可从 cancel.received 开始。来源事件的头 messageId 就是 SQL source_event_id，不能另传 eventId/receiptId。workspace/conversation/input/设备/项目/命令摘要必须全部与首次固定 start 或预存 cancel 对应。

change 精确为以下联合：`{type:"message.created",messageId}`（Java 补固定 agent 作者、空文本和 streaming）；`{type:"message.text.appended",messageId,text}`；`{type:"message.closed",messageId,state}`（completed/interrupted）。不能指定 user/system 作者、覆盖正文、任意 type 或原始 ACP payload。每块 text 至多 8 KiB UTF-8、整个公开事件至多 64 KiB 编码，超过时由 Runner 在持久编号前分片，不静默截断。

terminal：succeeded/failed 必须 invocationState=finished；rejected 必须 notInvoked；cancelled 可为 notInvoked 或已停止的 finished。succeeded 的 reasonCode=null，failed 仅 EXECUTION_FAILED，cancelled 仅 CANCELLED_BY_RUNNER；rejected 仅 AUTHOR_UNAVAILABLE/PROJECT_NOT_SHARED/SHARE_VERSION_CHANGED/DEVICE_REVOKED/TARGET_INVALID/NATIVE_SESSION_UNAVAILABLE/PROJECT_ROOT_CHANGED/CAPABILITY_UNAVAILABLE。后两个为取得原决定后的本地未调用拒绝，不加入 Java 首次 deny 的六原因集合。CANCELLED_BEFORE_DISPATCH 只由 Java 在 queued 取消时使用，Runner 不伪造它。没有可靠结束/未调用证明只能报告恢复 unknown，不发送 terminal。正常执行需引用已保存 allow；deny 后终态引用原 deny 且只能 notInvoked 的 rejected/cancelled；取消先到且尚无决定的 notInvoked cancelled 可引用 null。nativeSessionId 非空须与此前 native.bound 一致，不能用 terminal 首次改绑。终态前全部输出须已在连续前缀中，Java 按第 4.2 节闭合消息后才释放队首。

### 7.3 确定性字节和去重

持久内层消息的 bodySha256 位于 payload 最后。计算时移除这个字段，按第 7.2 节列出的顶层、payload 和嵌套字段顺序编码为紧凑 JSON，UTF-8、无 BOM、无额外空白。固定头的 protocolVersion/messageId/type/occurredAt 和完整 payload 全部参与，连接外壳/connectionId 不参与。JSON 字符串仅转义双引号、反斜杠和控制字符；\b/\f/\n/\r/\t 用短转义，其余 U+0000～001F 用小写十六进制 \u00hh，其他合法 Unicode 原样编码，不转义斜杠，不做 trim/Unicode 正规化/换行转换。协议版本为数值整数 1，序号/版本均为标准十进制字符串，不接受浮点。SHA-256 为小写 64 位十六进制。

双方先校验闭合形状、日期/字符有效性，再用该规则重算 hash；既保存含 hash 的完整确定性内层正文，也保存摘要和稳定 ID。重复对比完整确定性正文，不能只信远端 hash。语义相同的 JSON 键顺序/空白/转义差异在确定性编码后相同；头时间或正文实际变化即冲突。start 指纹是其含固定 null 原生 ID 的首次正文；原生绑定形成不能改变该指纹。所有来源、决定和 cancel 同样固定头/时间，不在每次重传重新盖时间。

Java/TS 唯一共同 fixture 应覆盖中文、emoji、引号/反斜杠/换行/控制转义、null 与后续原生绑定、头时间变化、重连只换外壳、相同 ID 不同正文。它是后续实施输入，本轮不生成生产 schema/fixture。

### 7.4 recordBatch、确认丢失和复核边界

Java 按 source messageId 及 `(executionId,runnerSequence)` 两个唯一约束逐项核对。精确重复可位于批次前段，新后缀必须从最后已提交序号加 1 连续开始；缺号不保存后缀、不先放行终态。一个调用只含一个执行，整批校验和事务提交；需要首次决定时在该事务生成。ack 指向该执行数据库当前连续前缀，startDecision 读取执行行原消息。无公开投影的 native.bound 仍持久登记，不会因不发 SSE 而漏确认。

ack/决定丢失时，Runner 重传未确认来源事件；全部已提交的批次仍返回最新前缀和同一原决定，不重新推进状态。重连时 reconcile 同样返回原决定/ack，并让缺少的来源事件先经 recordBatch；摘要不代替真实终态证据。首次决定尚未提交则绝无 allow 可重传；数据库失败不能由 HC-196 在传输层补一个默认 allow。

已获 allow 的 binding/running/output/terminal 和取消事实登记不因发起人随后停用/失去成员或项目停止共享被拒；只校验可信原设备、固定命令、绑定和连续来源事实。新 UI 阅读/新操作仍检查当前身份/成员/共享。设备凭据本身撤销和非当前 socket 的拒绝由 HC-196 管，不可把 UI 发起人的失效误用成设备事实丢弃条件。

当前八项裁定及第 6 节补充均已写入，原先双方案不再留给实现者选择。统筹已对照 HC-196 的取消先到清单/补传及其最新修订结果，主要交界方向通过；Plan 继续安排同源字节夹具和实际装配验证，不能把文档复核当生产验收。HC-197/198/199 后续扩展仍由各自主责明确接入，不提前实现、不用任意 payload 占位。

## 8. HTTP 历史、分页与 SSE

### 8.1 路由及最小响应

所有路径以 `/api/v1/workspaces/{workspaceId}` 为前缀，均要求当前登录/成员；写操作还要现有 CSRF。ID 非法 400；未知/无访问权统一 404。不接受任意查询字段、重复参数、未知排序或客户端作者。

| 方法与后缀 | 输入 → 正常响应 |
| --- | --- |
| `POST /conversations` | 第 5.2 节创建正文 → 201/重复 200 创建回执 |
| `GET /conversations` | `limit` 默认 50、1～100；可空 `beforeCreatedAt` 与 `beforeId` 必须成对 → `{conversations,nextPage:null\|{beforeCreatedAt,beforeId}}`，按创建时间/ID 降序，只含本工作区，ID 作同时间的稳定次序 |
| `GET /conversations/{conversationId}` | 无查询 → `{conversation}`；概要为本次读取事实，不把其最新 sequence 当成本机已应用历史游标 |
| `POST /conversations/{conversationId}/inputs` | 第 5.1 节正文 → 201/重复 200 InputSavedResponse |
| `GET /requests/{requestId}` | 必填 `operation`（上述三值之一）→ `{operation,result}`；只查当前作者在当前工作区的请求，找不到 404；与发送可读性一致 |
| `GET /conversations/{conversationId}/executions/{executionId}` | 无查询 → `{execution}`，严格核对同会话/工作区 |
| `POST /conversations/{conversationId}/executions/{executionId}/cancel` | 第 5.2 节正文 → 200 取消回执 |
| `GET /conversations/{conversationId}/history` | `afterSequence` 默认 0、可选 `throughSequence`、`limit` 默认 100/1～200 → `{conversationId,throughSequence,events,nextAfterSequence,hasMore}`，events 按 sequence 升序 |
| `GET /conversations/{conversationId}/events` | SSE；首次 query `afterSequence` 或重连 Last-Event-ID，规则见下文 → 200 text/event-stream |

会话列表 cursor 的时间复用 HC-194 UTC 表达，ID/时间精确校验，不用 OFFSET。新会话在分页过程中排到列表前面，刷新列表时再看；不承诺跨多次列表请求的数据库快照。历史分页则有明确固定上界，二者不能混为一套 cursor 语义。

新增错误：409 `REQUEST_ID_CONFLICT`（同业务 ID 不同正文）、409 `CURSOR_AHEAD`（游标超过已提交位置）、409 `PROJECT_NOT_SHARED`、409 `TARGET_UNAVAILABLE`（登记目标被撤销或配置标识已失效，非暂时离线/未 ready）、409 `EXECUTION_STATE_CONFLICT`。内部 SHARE_VERSION_CHANGED 映射 PROJECT_NOT_SHARED，DEVICE_REVOKED/TARGET_INVALID 映射 TARGET_UNAVAILABLE。错误沿现有四字段信封，除现有 503 外 retryable=false；不能据此自动换目标。设备帧 gap/conflict 等具名错误由 HC-196 映射设备通道，不混入用户 HTTP 任意字符串。

### 8.2 从历史转实时，没有空窗

首次 history 在一次短只读事务内核实成员并读取本会话已提交高水位 H（当前最大 sequence），返回 `throughSequence=H` 和 `afterSequence < sequence <= H` 的一页。后续页原样带 H，仅查询这一区间；`nextAfterSequence` 为该页最后事件的 sequence，无事件时等于请求起点。hasMore 只表示到 H 尚有事件，不随新事件变化。

显式 throughSequence 必须不大于当前高水位，afterSequence 不得大于 throughSequence；前者超前返回 CURSOR_AHEAD，后者为 INVALID_REQUEST。limit 和 sequence 查询值只接受各自范围内的标准十进制，不接受负数、指数、小数或前导零；UTC 时间/UUID 仍按共同表示校验。每页在同一读取事务取上界与事件，不能用 Java 本地计数猜测已提交位置。

history 的内容是不可变事件，重放得到消息/执行展示；不把不断变化的 Message 行当成 H 时的快照夹到页面里。流式文本的每段已提交增量都在历史中。初版保留完整日志，打开大历史以有界分页逐步重放，不另存一份可能落后的共享快照。

```text
history 第一页确定 H → 分页重放至 H → SSE afterSequence=H
SSE 先从数据库读 sequence>H → 补上读历史期间产生的所有提交 → 继续读新提交
```

SSE 自始至终按数据库游标向前读，进程内通知只是提前唤醒，另有固定周期补查，不能仅“先查历史再挂内存监听”。每次读批次是独立短事务，释放数据库连接后才写网络；不同 sequence 必须顺序写出。事务提交后进程崩溃、通知遗漏或 history/SSE 之间延迟都不会丢记录。

单 history 响应最多 1 MiB，按事件字节和条数两个限额截页；至少能放下一条合法事件。单公开事件最多 64 KiB UTF-8，单 Agent text 增量最多 8 KiB，超过的原始块应由 Runner 在持久编号前分片。不能静默截断文字或在 Java 丢事件以降压。更多总量/制品限制需 HC-197 定义，限额触发不允许伪装成功。

### 8.3 SSE 帧、游标与慢连接

持久事件的 SSE `event: conversation.event`，`id: <conversationId>:<sequence>`，data 为第 4 节完整 ConversationEvent；id 与 data 的会话/顺序必须一致。事件内部头部 messageId 用于精确去重，SSE id 是恢复位置，不是业务消息 ID。首个起点可用 `afterSequence`；重连可只传 Last-Event-ID；若两者同时出现必须相同，不猜测哪个较新。非法、重复参数、跨会话 ID 为 400，合法起点超过当前高水位为 409 CURSOR_AHEAD。

宿主只在完整解析、schema 校验、身份代次核对和本机顺序应用成功之后推进游标。收到重复事件仅在身份/内容一致时忽略；缺号或同 sequence 不同内容即停止应用，从最后连续位置补齐，不能跳过。HTTP 发送回执/概要中的位置不推进流消费游标。初版 cursor 与历史均仅在当前用户内存保留，重开从 history 恢复，不能仅持久保存 cursor 而没有对应已应用历史。

固定每 15 秒写无 id 的 SSE 注释心跳，不进入历史、不推进游标。握手最多 10 秒，无任何数据/心跳 45 秒后客户端关闭并从最后连续位置重连。客户端网络重连固定 1/2/5 秒退避，之后 5 秒，成功有事件/心跳后重置；401 不自动重登，403/404/426 停止并显示对应状态；503 保留身份等待服务恢复。退出/切换/取消订阅立即停止重连。

每连接只持一个有界读取批次，不建立随会话长度增长的内存消息箱。服务写出等待超过 10 秒则关闭慢连接，未完成帧不推进客户端游标；断开后仍从数据库补齐。连接结束、异常、窗口关闭均释放 emitter/定时任务/监听，不把 SSE 背压传递成长期数据库事务。

### 8.4 长连接持续授权

握手走 HC-194 同一 Host/Origin/协议/HttpSession 检查，查询用户 enabled/工作区成员后才发 200。SSE 不是另一个 bearer 登录接口，也不接受 query 中 token/作者。UI 会话与 HC-196 设备 WSS 凭据继续分开。

本轮实际读取当前 JAR 的依赖目录，内嵌为 Tomcat 11.0.27；application.properties 配置 session.timeout=30m，没有本项目的 sessionActivityCheck/lastAccessAtStart 自定义。Servlet 6.1 的 [HttpSession API](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/http/HttpSession.html)要求请求作用域之外经 Accessor 访问；Tomcat 的 [StandardSessionAccessor 11.0.27](https://github.com/apache/tomcat/blob/11.0.27/java/org/apache/catalina/session/StandardSessionAccessor.java#L56-L79)会先查现有会话有效性，再包围 consumer 调用 access/endAccess。这是源码核对，未启动容器或做运行验证。

统一采用这一条可实现规则：握手中从同一个已认证 HttpSession 取得 getAccessor()，异步读取/心跳前经 accessor.access 读取该会话里的 Spring SecurityContext，核对原 userId；不跨请求保存裸 HttpSession 或沿用工作线程 SecurityContextHolder。Accessor 不可取得则握手失败，不造替代会话库。短回调仅核对现有身份，之后在短只读事务复核 enabled/成员并取一批事件，释放连接后立即写出。退出/失效的 HttpSessionListener 关闭对应订阅，停用/移除成员在下一批或 15 秒复核发现后关闭；已交给网络的旧字节无法撤回。

据此修正首轮“SSE 心跳不续期”的承诺：服务端往流写注释本身不产生新 HTTP 请求，但上述周期 Accessor 访问属于容器认可的会话活动，持续订阅可保持同一登录有效；不再承诺按最后一次键鼠操作或普通短请求计算 30 分钟。停止全部用户请求/订阅后由原 HttpSession 的 30 分钟闲置规则失效，不另存 lastActivity 或增加身份计时状态。依据为该版 [StandardSession 的 access/endAccess 与失效计算](https://github.com/apache/tomcat/blob/11.0.27/java/org/apache/catalina/session/StandardSession.java#L448-L519)及[Manager 配置](https://tomcat.apache.org/tomcat-11.0-doc/config/manager.html)：活动检查/访问起点由容器决定，本任务不另改这组开关。流最多 30 分钟后关闭以释放资源，重连仍使用当前 Jar 重新握手；这不是强制退出或新建身份。

200 后明确会话失效/账号停用、成员撤回或数据库不可用，尽力发送无 id 的 `event: stream.problem`，data 为严格 ErrorResponse（AUTHENTICATION_REQUIRED、RESOURCE_NOT_FOUND、SERVICE_UNAVAILABLE），然后关闭。Accessor 无法访问但不能分辨失效/容器故障时，只报 SERVICE_UNAVAILABLE 并关闭，由下次 HTTP 握手确认是否 401，不把容器错误擅自当退出。控制帧不递增 sequence，发送失败仍关闭。断库停止受保护正文输出且不擅自退出；账号代次变化后迟到帧丢弃。所有关闭路径解除定时任务、失效监听、emitter 与 Accessor 引用，不在销毁后继续访问会话。

## 9. 为 HC-198 保留的同事务业务入口

HC-195 的发送用例是唯一“保存用户输入”入口。未来 HC-198 通过具名 `SendReferences.attachToInput` 加入该短事务：输入当前 userId/workspaceId/conversationId/inputId、已固定的引用草稿 ID；重新核对草稿所有者/来源可访问性，把固定快照与消息关联，并返回实际给执行端的固定文本。该入口不得联网读 Runner、重新截取最新正文或自行提交事务；失败回滚消息、引用、执行、事件和去重回执全部写入。

顺序为 `授权/去重 → 引用草稿核验 → 保存消息与正式引用 → 固定实际执行输入 → 执行登记/事件/回执 → 一次提交`。去重指纹届时包含草稿 ID/固定内容身份；精确重试直接返回已保存结果，不再次生成引用快照。HC-195 本轮不在 HTTP 加一个尚不可用的 referenceDraftIds 字段，也不放“空引用成功”的默认实现；HC-198 审查时一起增量修改唯一 schema/调用方和夹具。

未来交接用 `ConversationChanges.applyInTransaction` 加入同库事务，在相同 conversation 行锁下更新 currentUserId、追加具名交接事件；操作主体仍由当前登录会话确定。HC-198 维护 pending/accepted/cancelled 和引用业务，HC-195 提供顺序分配/追加的受限入口，不能把 JDBC Connection、任意 SQL、通用 JSON payload 暴露给调用方。具体输入判别联合由 HC-198 Spec 审查时补齐，当前不实现交接状态或触发 Agent。
