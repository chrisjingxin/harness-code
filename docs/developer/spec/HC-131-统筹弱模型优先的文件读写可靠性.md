# HC-131：弱模型优先的文件读写可靠性设计

> 原始需求：[HC-131](../task/HC-131-统筹弱模型优先的文件读写可靠性.md)

## 通俗问题说明

Harness 当前让模型通过 DeepAgents 的 `read_file`、`write_file`、`edit_file`，以及
Harness 自己的 `apply_patch` 修改工作区。对企业内能力较弱的模型，首要目标不是让每次
编辑都成功，而是保证模型定位不准、文件已经变化或工具参数不完整时明确失败，不能静默
改到错误位置。

本设计采用以下主线：

```text
定位相关文件/区间
  → read_file 返回短 Snapshot ID 与普通行号
  → 模型只提交 Snapshot、已读内容中唯一的原文本和新文本
  → Harness 校验 Thread、路径、已读范围和当前文件内容
  → 生成确定 diff 并走既有 Policy / Approval
  → compare-and-replace 提交
  → 重新读取实际落盘内容并返回新 Snapshot 与局部结果
```

第一阶段不做 fuzzy matching、跨版本 anchor 恢复或模型自纠错。失败后的唯一恢复方式是按
错误提示重新读取受影响区间。

生产 Agent、受控子 Agent、工具目录、schema 指纹和审批策略均已移除不校验 old/context
的批量补丁入口。该风险清理和后续 Snapshot pipeline 都属于本功能的实施阶段，不再维护
实现型 parent/child Task。

## 二次校验结论

### 保留的方向

- 保留 Strict Snapshot、局部读取、普通行号、服务端隐藏完整 hash。
- `write_file` 只创建新文件；已有文件必须走 `edit_file`。
- `edit_file` 对 Snapshot、范围和当前磁盘内容全部 fail closed。
- 一次编辑成功后返回新 Snapshot 和变更附近内容，避免模型完整重读。
- 第一阶段不做 whitespace/fuzzy/hash-anchor recovery；遇到 stale 直接重读。
- 写入逻辑集中到一个 Harness-owned mutation pipeline，模型工具不各自实现写盘。

### 对聊天方案的修正

1. **当前 `write_file` 已经是 create-only。** 仓库锁定的 DeepAgents 0.6.8 在目标存在时会
   拒绝写入；无需以“当前会覆盖文件”为前提重做。
2. **当前 `edit_file` 已经做唯一精确匹配。** 它不是静默误改的主要来源，但“必须先读”
   目前主要依靠 prompt，没有 Harness 强制的版本绑定。
3. **`apply_patch` 是确定的 P0 缺口。** `tools_file._apply_hunks()` 只按 `old_start` 和行数
   切片，不验证 `-old` 与 context；它必须先下线，不能等待大改造完成。
4. **Snapshot 只证明文件版本，不证明模型语义意图。** 模型仍可能选择一个合法但错误的
   行号。因此必须限制在模型实际看过的行，并用真实弱模型评测比较完成率、错行率和重试。
5. **Snapshot 必须按 Thread 隔离并有界。** 当前 AgentEngine 可跨 Thread 共享；仅按路径
   或进程存储会泄漏已读范围，也可能让另一个 Thread 复用 Snapshot。
6. **“prepare 全部成功”不等于多文件原子提交。** Oh My Pi 的当前实现也明确说明多文件
   commit 可能只写入前缀。第一阶段只承诺单文件 compare-and-replace，不宣称跨文件事务。
7. **自动 formatter 不进入首版 pipeline。** 它可能在用户批准的 diff 之外继续改文件。
   首版只做可选、限时、只读的 diagnostics；formatter 保持显式后续动作。
8. **本机原子替换不能覆盖所有外部竞态。** Harness 内部写操作可线性化，并能发现提交前
   已发生的外部变化；不遵守协作锁、恰好与最后提交同时发生的 IDE 写入仍是残余风险。
9. **远端 sandbox 不能假定有本机 `Path`、文件锁或 rename。** Mutation 必须通过 backend
   adapter 表达 compare-and-replace 能力，并对不支持的后端 fail closed。

### 本地参考实现核对

- Oh My Pi `packages/hashline/src/snapshots.ts`：Snapshot 是有界的 session store，记录完整
  内容和 `seenLines`；本设计采用 Thread 隔离、有界存储和已读区间，但不采用首版 stale
  recovery。
- Oh My Pi `packages/hashline/src/patcher.ts`：多文件先 prepare，但 commit 明确非原子；本
  设计不把它误写成 all-or-nothing。
- Qwen Code `packages/core/src/tools/priorReadEnforcement.ts`：读后再写和 stale 检查值得借鉴，
  但“任意局部读即可覆盖整个文件”仍保留未读内容风险；本设计把可编辑范围限制到已读行。
- Codex `codex-rs/apply-patch/src/lib.rs`：找不到 context / old lines 即失败；本设计沿用
  verify-before-mutate 原则，不沿用让弱模型生成 patch 的接口。

## 已确认现状

- `runtime/agent.py` 通过 `create_deep_agent()` 注入 DeepAgents 内置文件工具，并用静态
  `_BUILTIN_TOOL_SHAPES` 计算工具 schema 指纹。
- DeepAgents 0.6.8 的 `FilesystemMiddleware` 是 `create_deep_agent()` 必需脚手架，不能简单
  exclude 后替换；Harness 需要明确的 tool interposition seam。
- `LocalShellBackend` 使用 UTF-8 文本读写；当前 edit 会把换行规范化为 LF，不能宣称已保留
  CRLF/BOM。
- `ConcurrencyGuardMiddleware` 已使用 Host 级异步读写锁：模型写工具之间串行，读工具可
  并行。它解决 Host 内并发，不解决外部 IDE 写入。
- `WorkspaceBoundaryMiddleware`、Capability Policy、Approval Mode、敏感路径与规则持久化
  已经存在；新工具必须复用这些边界，不建立第二套授权系统。
- 本地与远端执行共用 `BackendProtocol`，但不同 backend 的读取、提交和原子能力不同。
- `/.harness/` 是只读虚拟命名空间；它继续通过 `read_file` 读取，但不生成可写 Snapshot。

## 已确认的文件工具接管边界

实现先建立运行时边界，不提前选择尚未通过评测的 Snapshot edit/insert 参数。
DeepAgents 0.6.8 的 `FilesystemMiddleware` 继续作为受保护脚手架存在；Harness
在其后注入 `HarnessFileToolsMiddleware`，由注入的 `FileToolContract` 完成两件事：

```text
DeepAgents builtin schema
  → Capability / Deferred / Workspace preflight
  → Harness contract 按名称去重替换 schema
  → Concurrency guard
  → Harness contract dispatch（不调用 builtin handler）
```

主 Agent、declarative `general-purpose` 和受控 inline worker 使用同一 contract 配置，
各自只创建属于本图的 middleware 实例；这样不会形成第二套 Agent runtime，也不会让
同名工具通过 `tools=` 追加出两个 ToolNode 入口。当前默认 contract 只镜像已确认的
exact-string `read_file`/`write_file`/`edit_file`/`delete_file` 及搜索工具形状；未来
schema 由构图参数替换；接管层不写死 `edits[]`、insert 或 Snapshot mutation 字段。

`ThreadSnapshotStore` 是 Host 生命周期内的进程内有界存储。记录 key 包含当前
`RunContext.thread_id`、canonical backend path、backend identity 和强内容 hash；同一
内容的重复读取复用记录并合并半开 `seen_lines`，内容变化生成不可猜测的新 ID。TTL、
path version、总 Snapshot 数量和总字节预算按确定性 LRU 规则淘汰，句柄在 Thread/Host
关闭后失效。它不写 Transcript、SQLite 或工作区；`/.harness/` route 保持只读且不创建
可写 Snapshot。不同 `adispatch` 可经 `asyncio.to_thread` 同时登记同一个 Host Store；Store
因此用独立的短期 `threading.Lock` 线性化 records、identity index、字节预算、TTL/LRU、失效和
关闭。backend I/O、内容 hash/行元数据计算、审批、CAS 与 diagnostics 均在锁外，不扩大 Host
`AsyncRWLock` 的语义，也不把不同 Thread 的文件读取串行化。

文件 mutation 依赖 `TextMutationBackend` contract：完整文本读取、create-if-absent、
compare-and-replace 和 delete-if-unchanged。Local adapter 使用安全 virtual path、
无符号链接跟随、临时文件和同目录 rename；Remote adapter 只有在 provider 声明原生
CAS 时才允许提交，缺少能力统一返回 `BACKEND_CAS_UNSUPPORTED`，不退化为盲写。

## 目标与非目标

### 目标

- 在生产弱模型上，任何 stale、未读范围、非法范围、重复/重叠 edit 都不会落盘。
- 模型只需理解 `snapshot_id + old_string + new_string`，不接触完整 hash 或 unified diff。
- Snapshot、写入、diff、审批和结果生成只有一个 canonical 实现。
- 本机和远端 backend 的保证被显式区分；不支持 compare-and-replace 时拒绝写入。
- 编辑后的实际落盘内容成为新 Snapshot 的事实来源。
- 用可复现评测证明新接口至少不劣于当前 exact-string 基线，再切换生产 schema。

### 非目标

- 不实现 fuzzy replacement、whitespace normalization 或跨版本 anchor recovery。
- 不提供跨文件事务、回滚日志、文件移动或目录删除。
- 不自动运行 formatter，不把 LSP/formatter 的额外改动混入已批准 diff。
- 不编辑二进制、图片、PDF、Notebook 或无法无损解码的文件。
- 不把 Snapshot 落盘到工作区、SQLite 或 Thread transcript。
- 不通过 Protocol 暴露 Snapshot；它是 Agent 内部工具契约。
- 不保留旧 `apply_patch`、旧 `edit_file` 参数或兼容 alias。

## 关键 invariant

1. **事实来源唯一**：当前 backend 中实际存在的文件内容是唯一事实来源；缓存只用于证明
   模型看到过什么。
2. **Thread 隔离**：Snapshot key 至少包含 `thread_id + snapshot_id`，不能跨 Thread、跨
   Host 或跨进程恢复。
3. **路径绑定**：Snapshot 绑定 canonical backend 路径和 backend identity；路径、route 或
   backend 不同即拒绝。
4. **已读范围**：修改/删除只能使用当前 Thread 得到的 Snapshot；唯一 `old_string` 覆盖的
   每个源行必须属于该 Snapshot 的 `seen_lines`。零行空文件没有可伪造的源行，其受限初始化
   改由 Snapshot 与当前完整 identity 同时证明内容仍为空。重复读取相同内容时可以合并已读区间。
5. **内容绑定**：提交前当前完整内容必须与 Snapshot 的强 hash 和必要元数据一致；短
   `snapshot_id` 只是不可猜测句柄，不是内容 hash。
6. **单文件全预检**：一次 edit 只接受一个 `old_string → new_string` 替换；Snapshot、唯一
   匹配、已读范围、no-op 和大小限制全部通过后才生成 proposed content。
7. **唯一匹配**：非空 `old_string` 必须在当前文件中恰好出现一次；零次或多次出现都拒绝，
   不能以 `replace_all`、相邻文本猜测或 range 参数放宽。空 `old_string` 只代表把已读且当前
   仍为空的整个文档替换为初始内容，不能表示非空文件中的位置。
8. **审批内容一致**：用户看到的是有界 proposed diff 预览；批准绑定一次性 prepared plan 中
   已固定的完整 proposed content。预览截断或受终端高度隐藏不取消允许/拒绝选项；批准后若
   文件变化，提交必须返回冲突，不能把相同批准套到另一个文件版本。
9. **实际落盘再建 Snapshot**：提交后重新读取 backend；若保存钩子或远端系统改变了内容，
   返回 drift warning，并只为实际内容生成新 Snapshot。
10. **失败可恢复**：所有预期失败返回稳定 error code、简短原因和唯一下一步；不让弱模型
    在多个恢复策略中猜测。
11. **资源有界**：Snapshot store 有 path、version、总字节和 TTL 上限；淘汰后返回
    `SNAPSHOT_EXPIRED`，要求局部重读。
12. **虚拟文件只读**：`/.harness/` 读取不产生可用于 edit/delete 的 Snapshot。

## 公开工具接口

现有 mock replay 未能替代真实弱模型门槛，因此当前按 fail-closed 决策保留已验证的
exact-string + prior-read。行号 range、基于行号的 `edits[]` 与插入候选仍不得进入生产 schema。
（HC-185 例外：字符串型同文件 `edits[]` 不依赖行号，已经 zc133 mock 评测通过安全门槛，见 [HC-185](HC-185-同文件批量编辑.md)。）

### `read_file`

```text
read_file(
  file_path: string,
  offset?: integer,   # 0-based，与现有契约一致
  limit?: integer
)
```

普通工作区文本返回：

```text
snapshot_id: s_7K2M9Q
shown_lines: 121-180
total_lines: 742

121│ class UserService:
122│ ...
```

规则：

- 默认局部读取 100 行，单次最多 200 行、32 KiB 可见文本；超出字节上限时不授予该窗口
  `seen_lines`，模型必须缩小读取范围。
- 服务端为完整文件计算强 hash，但只把请求区间送进模型 context。
- 相同 Thread、路径和内容的重复读取复用 Snapshot，并合并 `seen_lines`。
- 超长单行可以视觉分段，但只能用原始整数源行号编辑；分段编号不可作为 edit 边界。
- 空文件可以返回 Snapshot；非文本文件沿用 multimodal read，但不返回可写 Snapshot。
- `/.harness/` 返回原有只读内容，不返回可写 Snapshot。

### `write_file`

```text
write_file(
  file_path: string,
  content: string
)
```

- 仅创建不存在的 UTF-8 文本文件；存在时返回 `FILE_ALREADY_EXISTS`。
- 复用 Workspace/Capability/Approval；不接受 `snapshot_id`。
- 成功后读取实际落盘内容，返回 `snapshot_id`、实际 `changed_range`、行数和有界局部窗口；`shown_lines`
  非空时这些行直接成为新 Snapshot 的 `seen_lines`，使模型可继续编辑而不完整重读。

### `edit_file`

```text
edit_file(
  file_path: string,
  snapshot_id: string,
  old_string: string,
  new_string: string
)
```

当前生产约束：

- 非空 `old_string` 必须从当前 Snapshot 已读内容复制，且在当前文件中恰好出现一次。
- 仅当 Snapshot 与当前完整文本都证明已有文件为空时，`old_string=""` 才表示替换整个空文档；
  空字符串不能用于非空文件的开头、结尾或任意位置插入，`write_file` 仍只创建不存在的文件。
- `old_string` 覆盖的全部源行必须属于 `seen_lines`；`new_string=""` 表示删除该文本。
- 不接受 `replace_all`、行号 range、`edits[]`、批量替换或隐式插入参数。
- 成功后依据 commit 后实际重读内容返回新 Snapshot、`changed_range`（新版本 1-based 行号及增删统计）
  和变更附近窗口，最多 200 行、32 KiB；按字节截断时不授予 `seen_lines`。
- 已启用本机 Plugin LSP 时，异步 ToolNode 在提交后额外返回最多 1 秒、20 项、8 KiB 的只读摘要；
  `unavailable`、`timeout` 和 `ok,count=0` 必须区分，失败不回滚提交。

> 非空文件的纯插入和多处修改仍是候选接口，必须在真实 Profile 评测后通过独立任务变更，
> 不能由实施 Agent 自行约定 `start_line=0`、`start>end` 或把空字符串解释为位置。HC-141
> 只增加“已读空文档整体替换”这一窄例外，不是一般插入接口。

### `delete_file`

```text
delete_file(
  file_path: string,
  snapshot_id: string
)
```

- 文件必须存在、属于同一 Thread/路径/backend，且当前内容仍匹配 Snapshot。
- 删除继续按 DELETE 风险进入既有审批；Snapshot 不能代替用户授权。
- 成功后使该路径在当前 Thread 的所有 Snapshot 失效。

## SnapshotStore

```text
ThreadSnapshotStore
└─ thread_id
   └─ canonical backend path
      └─ content identity
         ├─ snapshot_id（随机、不可猜测）
         ├─ backend_id / route
         ├─ strong_content_hash
         ├─ size / line_count / text metadata
         ├─ seen_lines（区间集合）
         └─ created_at / last_used_at
```

- 默认只保存验证所需元数据和有界原文；实现可保存完整规范化文本以支持 diff，但必须受全局
  字节预算约束，不能无界缓存企业源码。
- Snapshot ID 不进入 Transcript 持久化之外的长期存储。Thread 恢复、进程重启、LRU/TTL
  淘汰后，旧 ToolMessage 里的 ID 会返回 `SNAPSHOT_EXPIRED`。
- 相同内容的重复 read 复用一份记录并合并 `seen_lines`；内容变化生成新 ID，旧版本只在
  有界历史内保留用于返回明确 stale/expired，不做 recovery。
- Store 内部状态锁保证同 identity 并发 read 只保留一条记录并合并 `seen_lines`，同时使
  records/index/总字节、TTL/LRU、path/Thread 失效和 Host close 在每个公开操作返回时一致；
  该锁不跨 backend I/O 或任何 await。
- 日志只记录 code、文件相对路径、字节/行数和 hash 前缀；不记录源码内容、new_text 或完整
  Snapshot ID。

## Mutation pipeline

```text
tool args
  → schema / path / capability validation
  → acquire Host write lock（未来可细化为 path lock）
  → resolve Thread Snapshot
  → read current full text through backend adapter
  → validate hash + (seen range + unique exact match | current empty-document identity)
  → apply one exact-string replacement or the restricted empty-document replacement in memory
  → reject no-op / size overflow / unsupported file
  → existing Policy / Approval decision
  → compare-and-replace expected current content
  → re-read actual content → calculate changed range → create new Snapshot + bounded context
  → optional bounded read-only diagnostics → aggregate redacted metrics

拟议 diff、审批、提交后重新读取、变更窗口、diagnostics 和观测都收敛在同一条 canonical
路径，不能按实施阶段另起模型文件工具入口。
```

### Backend adapter

Mutation 不直接依赖本机 `Path`，而依赖以下语义接口：

```text
read_text_document(path) -> raw content + encoding/BOM/line-ending metadata
create_text_document(path, expected_absent, content)
compare_and_replace_text(path, expected_content_identity, proposed_content)
delete_if_unchanged(path, expected_content_identity)
```

- Local adapter 使用安全路径解析、无符号链接跟随、临时文件 + 同目录 rename，并在提交前
  复核 expected identity；Host 内调用由现有锁线性化。
- Remote adapter 优先使用 backend 原生 CAS/version 能力；若只有 exact `edit`，可以把完整
  current content 作为内部 expected old text，不进入模型 context。无法证明 compare-and-
  replace 时返回 `BACKEND_CAS_UNSUPPORTED`，不能退化为先读后盲写。
- 所有 adapter 在 commit 后重新读取，Snapshot 绑定实际落盘内容。
- BOM、CRLF/LF 和末尾换行必须 round-trip；混合换行或无法无损处理时 fail closed。

### Approval

- WorkspaceBoundary、Capability Policy、敏感路径、Approval Mode 和规则持久化继续是唯一授权
  来源。
- Snapshot 校验发生在授权之外：即使规则允许，stale/未读/非法范围也必须拒绝。
- 审批描述应展示文件、操作类型、增删行统计和有界 diff 预览；不能只展示模型提交的行号。
  预览截断或因终端高度隐藏时仍保留允许/拒绝选项，并明确批准对象是该次调用固定的完整拟议内容。
- 批准到 commit 之间再次校验 expected identity；冲突后旧批准失效，模型重读重试。

canonical 写入由 `FileMutationService` 承担：文件 contract 只在完成 Snapshot、唯一
exact-string 和已读范围校验后，传入 current、proposed content 与内部 metadata，service 不接收模型原始
tool args。它以 Thread、tool call 和参数指纹缓存有上限的一次性计划，并把同一份 diff 接到既有 HITL 的动态
description；commit 无论成功、冲突还是 I/O 失败都会消费该计划。Local/Remote adapter 完成提交后必须重新
读取实际内容，Snapshot 只依据这次重读创建；实际内容不同于 proposed 时返回 `POST_WRITE_DRIFT`，同时给出
已批准 `proposed_diff` 与实际 `actual_diff` 的有界提示。新 Snapshot 只绑定实际版本。

### Formatter 与 diagnostics

- 不自动 formatter。若用户、IDE 或 Skill 显式格式化，随后 Snapshot stale，必须重新读取。
- LSP diagnostics 是异步 ToolNode 提交后的只读提示：最多等待 1 秒，最多返回 20 项或 8 KiB；失败不回滚
  成功写入，也不把“无 LSP”或超时误报为零错误。
- 摘要只返回严重级别、短 code 和源行范围，不返回诊断 message/source/data；完整诊断按需使用 `lsp` 工具读取。
- `FileToolMetrics` 只聚合 error code、Snapshot expired/stale/未读范围、重读、edit 成功、结果字节和 diagnostics
  延迟；它不记录源码、`new_text`、完整路径、完整 Snapshot ID 或凭据。

## 错误语义

工具返回稳定 JSON 形状：

```json
{
  "ok": false,
  "error": {
    "code": "STALE_FILE",
    "message": "文件在 snapshot 后发生变化。",
    "next_action": "重新读取受影响区间后重试。"
  }
}
```

| code | 触发条件 | 唯一恢复动作 |
| --- | --- | --- |
| `SNAPSHOT_REQUIRED` | 修改/删除缺少 ID | 先 `read_file` |
| `SNAPSHOT_EXPIRED` | 重启、TTL/LRU 淘汰或未知 ID | 局部重读 |
| `SNAPSHOT_SCOPE_MISMATCH` | Thread、路径或 backend 不一致 | 读取目标路径 |
| `STALE_FILE` | 当前内容与 Snapshot 不同 | 局部重读 |
| `UNREAD_RANGE` | `old_string` 涉及模型未见源行 | 读取该区间 |
| `EXACT_MATCH_NOT_FOUND` | 已读原文本不再存在 | 重读目标区间 |
| `AMBIGUOUS_MATCH` | `old_string` 出现多次 | 重读后提交更唯一的原文本 |
| `FILE_TOOL_SCHEMA_INVALID` | 使用 replace_all、range 或 edits[] | 使用当前 schema 重试 |
| `FILE_ALREADY_EXISTS` | `write_file` 目标已存在 | 读后 edit |
| `FILE_NOT_FOUND` | edit/delete 目标不存在 | 重新定位路径 |
| `UNSUPPORTED_FILE_TYPE` | 二进制/Notebook/不可无损文本 | 使用专用工具 |
| `NO_CHANGES` | proposed content 与当前内容相同 | 不再重试相同编辑 |
| `COMMIT_CONFLICT` | 批准后、落盘前内容变化 | 重读并重新审批 |
| `BACKEND_CAS_UNSUPPORTED` | backend 不能安全比较并提交 | 更换受支持执行模式 |
| `COMMIT_FAILED` | I/O 或远端写入失败 | 检查错误后重读当前状态 |
| `POST_WRITE_DRIFT` | 保存钩子改变了拟议内容 | 使用返回的新 Snapshot 检查差异 |

错误消息控制在弱模型易解析的短句；同一 code 只给一个推荐动作。

## 弱模型评测门槛

最终验收必须使用实际企业生产弱模型 Profile，对固定 workspace fixtures 重复运行，至少覆盖：

- 单行替换、区间替换、非空文件纯插入、空文件初始化、删除、多处非重叠修改。
- 重复文本、相似函数、长文件局部读取、超长行、无末尾换行、BOM/CRLF。
- IDE 在 read 后、审批前和提交前修改文件。
- Snapshot 过期、跨 Thread 复用、路径写错、未读区间、重叠范围。
- 新文件创建、已有文件误用 write、删除 stale 文件。

比较至少包括：

1. 当前 exact-string + fail-closed prior-read 基线。
2. `snapshot + 单 range` 候选。
3. `snapshot + edits[]` 候选。

决策按以下顺序：

1. 任一候选出现静默写错文件/错版本、越过未读范围或测试判定的 silent corruption，直接
   淘汰，不能用更高成功率抵消。
2. schema 合法率、任务完成率不得低于基线的统计置信下界；否则保留 exact-string canonical
   路径，只落地 Snapshot prior-read 与结果优化。
3. 在安全性和完成率不降级后，再比较中位 input/output token、工具调用数、重读次数和延迟。
4. 数组 schema 只有在减少调用/token 且不降低 schema 合法率时进入正式接口。

评测命令必须显式 opt-in，不读取或记录真实 API Key；自动化测试使用 mock model 和固定
tool-call replay，不能调用真实模型。

## 当前评测决策

评测实现已将 25 个合成 fixture（`zc133-v1`）、纯内存 simulator、mock replay、Wilson
置信区间和去敏报告写入 [弱模型文件编辑评测](../research/弱模型文件编辑评测.md)。mock
重复 3 次的结果能捕获 Snapshot 候选的合法错行和单区间多 edit partial write，但它不能代替
实际企业弱模型证据；本次执行没有调用真实 Profile。

因此当前唯一 canonical 生产路径仍是 `exact-string + prior-read`。Snapshot 单区间、Snapshot
`edits[]` 以及显式/zero-width 插入语义均保持候选状态，不进入生产 schema，也不允许接管层
提前固化。真实评测需显式运行：

```bash
cd packages/agent
./.venv/bin/python -m evaluations.zc133 --real-model \
  --profile <企业弱模型-profile-id> --repetitions 3 \
  --output-dir /tmp/zc133-real-report
```

只有真实 Profile 的安全门槛通过后，才可以先更新本 Design，再调整 Snapshot edit/insert
形状；否则继续沿用 exact-string canonical 路径。

## 实施顺序

1. 移除批量补丁入口并保留风险回归。
2. 建立弱模型 fixture、指标和 schema 决策门槛。
3. 建立 FileTools interposition seam、ThreadSnapshotStore 和 backend adapter。
4. 切换唯一 canonical `read_file/write_file/edit_file/delete_file` 契约。
5. 完善 diff/approval、compare-and-replace、格式保持和 post-write re-read。
6. 返回新 Snapshot/局部内容，加入有界 diagnostics 与观测，并完成真实模型验收。

以上只是同一功能 Task 内的依赖顺序，对应实施计划和 Todo，不创建独立 Task 或 Design。

## 可观察验收

- 给 `apply_patch` 一个 hunk 行号正确但 old/context 错误的输入，目标文件保持字节不变，且
  生产模型不再看到该工具。
- 模型未读文件、只读了其他区间、跨 Thread 复用 ID 或文件已变化时，edit/delete 均返回
  对应稳定 code，文件字节不变。
- 同一调用中第二个 edit 非法时，第一个 edit 也不会落盘。
- `write_file` 对已有文件返回 `FILE_ALREADY_EXISTS`，不覆盖内容。
- 批准后外部修改文件时返回 `COMMIT_CONFLICT`，旧批准不能继续提交。
- BOM、CRLF/LF、末尾换行在支持的文本中保持；不支持的混合/编码输入明确拒绝。
- edit 成功后不完整重读即可继续使用新 Snapshot；结果只包含变更附近有界内容。
- 本地与远端 backend 都有契约测试；不支持 CAS 的 backend 明确拒绝。
- 实际弱模型评测满足安全门槛并记录模型、fixture 版本、重复次数和指标，不记录凭据/源码。
- Python focused tests、项目级 `bun run test`、`bun run typecheck`、`bun run project:check`
  通过；用户与架构文档、任务状态和版本影响闭环。

## 风险与退出条件

- 若实际弱模型在 range schema 上明显低于 exact-string 基线，退出条件是保留 exact-string
  作为唯一模型接口，但仍增加 Thread Snapshot prior-read、stale 校验和 mutation pipeline；
  不保留两个编辑工具让模型选择。
- 若远端 backend 无法提供 compare-and-replace，首版只在受支持 backend 启用编辑，不能
  退化为盲写。后续需由独立任务扩展 provider 契约。
- 若 Snapshot 完整内容缓存带来不可接受的内存占用，改为强 hash + 已读区间 + 有界窗口，
  提交时重新读取当前完整内容；不能通过放宽 Thread/内容校验换性能。
- 多文件事务、stale recovery、hashline 和 formatter 只有在生产指标证明重读/工具调用成为
  主要瓶颈后再建立新的上层任务，不属于 HC-131 完成条件。
