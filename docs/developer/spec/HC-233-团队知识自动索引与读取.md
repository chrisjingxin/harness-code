## 1. 用户结果与范围

用户进入自己的本机会话，不必先手动 `@`，Agent 就能看到当前团队知识的标题目录；发现相关知识后，调用只读工具读取正文，再结合实际读到的版本处理用户需求。

团队知识本身继续共享：A 在某个 Workspace 新建或修改知识，B 在同一个 Workspace 的知识列表应能看到变化。这里只同步知识库页面与列表，不追更已经注入 Agent 的目录、已经返回的正文或既有手动引用。

| 本期交付 | 本期保持现状 |
| --- | --- |
| 自动附带现有知识标题目录；工具按需读取固定版本正文 | 知识的创建、编辑、分类、版本历史和归档 UI |
| 复用现有轻量通知刷新另一账号的知识列表 | Java 知识 API、数据库、线上契约和服务端通知方案 |
| 读取过程和来源复用既有工具展示 | 中间消息/头像/输入区、右侧文件区域的整体布局 |
| 保留手动 `@` 和固定版本引用 | Harness 内核、其他 Agent 的内部上下文管理 |

不增加用途摘要、向量召回、自动摘要模型、知识写入工具、知识专用 ACP 方法或新的同步通道。Project 看板、他人会话和产品任务不纳入自动目录。首版仍按每人一台设备，跨成员会话只读。

## 3. 用户交互

### 3.1 本人会话发送

```text
用户输入并发送
  → 沿用本人会话、目录及身份校验
  → 读取当前 Workspace 的标题目录缓存
  → 把目录作为独立参考文本块附带给当前 Agent
  → Agent 判断相关性，必要时调用团队知识只读工具
  → 桌面以当前登录身份读取固定版本正文
  → 现有工具卡展示读取结果，Agent 继续本轮工作
```

- 新建准备页不因展示目录而登记会话或执行；完成现有会话准备、用户主动发送后才消费目录。
- 首版每次发送附带一个有上限的目录快照，不管理不同 Agent 的系统提示、上下文压缩或首次注入去重状态。目录只存在于本轮实际发送材料，不自动写入 `ConversationDraft.referenceIds`，不添加一排用户没有选择的引用卡。
- 用户消息区、草稿和 Java 定稿上传继续使用原始用户文字；不得把内部目录伪装成用户输入。实际读取的工具记录沿用当前工具事件及上传摘要规则，不增加全库正文上传。
- 每轮已经交给 Agent 的内容保持原样。知识更新不会追加隐藏消息、唤醒 Agent、改写历史或替换旧版手动引用；后续发送按当时取得的目录执行即可。

### 3.2 目录内容与大小

目录的业务内容只有标题。引用 ID 和版本号仅用于工具定位与展示来源，不增加摘要、分类解释或正文。

示意数据如下，实际引用 ID 使用现有 UUID 格式：

```json
{
  "items": [
    { "title": "接口错误码规范", "referenceId": "knowledge:<知识ID>:<版本ID>", "version": 3 }
  ],
  "hasMore": false
}
```

目录前提供固定、简短的使用说明：这是当前团队可读知识的标题目录，标题仅供发现；相关时调用读取工具查看原文，不能只看标题就宣称读过具体规范。动态字段通过 JSON 序列化，与固定说明分开；知识内容不授予文件、命令或其他成员 Agent 的执行权限。

首版目录正文上限为 **8 KiB UTF-8**，作为实现常量，不新增设置项。自动目录只请求现有列表的第一页，页内按知识 ID 稳定排序，跳过归档项，按完整条目装入预算；不为凑完整目录连续拉全库分页。没有条目时正常发送，不显示错误。

`hasMore` 在服务端仍有下一页或本页因预算未全部附带时为真，并提示可调用列表工具继续查找。未遍历全库时不声称已展示全部条目或编造总数。列表工具从服务端页重新查询，不能把自动目录最后显示的条目当作服务端游标而跳过同页剩余项。

## 4. 桌面只读工具

MCP 是 Agent 可以调用工具的标准连接方式。本卡提供桌面侧的知识工具服务，经已有标准 ACP 的会话 MCP 配置交给 Agent；下表是桌面 MCP 工具规格，不是新增 Java API 或 ACP 方法。

| 工具 | 输入 | 输出与行为 |
| --- | --- | --- |
| `list_team_knowledge` | 可选 `query`、`afterId`，省略时为空查询、第一页 | 调用现有 `listKnowledge`；返回当前页的 `title`、`referenceId`、`version` 与 `nextAfterId`，不返回正文。分页和搜索范围沿用服务实际语义。 |
| `read_team_knowledge` | 必填 `referenceId` | 只接受现有 `knowledge:` 固定标识，解析 ID 和版本后调用 `readKnowledgeVersion`；返回 `title`、`referenceId`、`version` 和 `text`。不接受“latest”或按标题猜测正文。 |

- 工具不接受模型传入的账号、Workspace、Project、会话、服务地址或登录凭据。这些范围由受信任的本机会话绑定决定；同名标题仍按不同引用 ID 区分。
- 列表工具返回整个服务端页及原始下一页游标，不擅自截断页后套用服务端游标。现行默认页大小为 50，不为本功能修改服务分页规则。
- 正文读取沿用现有服务的长度、版本和归档可读语义；不默认缓存全库正文。失败返回明确的工具错误和既有可展示错误原因，不用另一版本冒充读取成功。
- 手动 `@` 仍由 HC-219 显式固定并附带正文。同一知识本轮已手动引用时，自动目录标明“本轮已引用”，优先使用该固定版本，不再自动附带另一份正文或把它悄悄换成当前版。工具实际读取始终返回请求的原版本；用户主动比较多个版本的材料继续保留。
- 结果标明可回查的标题、版本及现有引用 ID。来源定位复用知识详情入口，定位失败保留工具结果；定位本身不向草稿添加引用或发送消息。

## 5. 模块与通用接线边界

知识业务集中在规划新增的 `desktop/src/main/team-knowledge-context/` 目录，按目录整理/缓存、正文读取、MCP 服务适配分工；不拆新的顶层 workspace，不把实现写入 Harness Python 或通用 ACP 包。

| 归属 | 职责与影响范围 |
| --- | --- |
| 桌面知识模块 | 标题投影、缓存、固定版本读取和两种只读 MCP 工具 |
| `desktop/src/main/local-execution-coordinator.ts` | 捕获当前登录、绑定和用户固定引用；装配本轮目录；异步取材后复核绑定；不让网络等待阻塞取消与审批队列 |
| `desktop/src/main/collaboration-ipc.ts` | 与现有身份、知识写操作和窗口生命周期一起装配知识模块 |
| `desktop/src/main/project-updates-ipc.ts` | 复用既有知识更新通知使目录缓存失效，不新增 SSE 连接或改变通知确认机制 |
| 桌面现有知识页面及工具展示 | 继续消费列表刷新；展示读取来源、版本与必要的不可用提示；按需补桌面私有类型，不改公共 UI 风格 |
| 通用 ACP 维护方 | 按会话绑定接入宿主提供的标准 MCP 配置，覆盖新建、加载、恢复；运行时不导入协作客户端或知识类型 |

首版桌面知识 MCP 使用 **回环 HTTP**：仅监听 `127.0.0.1` 的系统分配端口，为当前会话生成临时只读访问凭据，Java Cookie 继续由主进程持有。地址和临时凭据通过标准会话 MCP 配置传给 Agent，不进入模型文字、UI、用户消息或云端历史。

MCP 配置属于本机会话绑定，不能挂在共享 Provider 的全局配置上。换账号、绑定失效、切换 Agent 或关闭窗口时撤销对应访问；重新加载或恢复会话使用当前有效配置，不把临时地址和凭据持久化到原生会话绑定文件。取消当前轮次只结束本轮读取，不永久关闭仍可再次发送的会话服务。

此处只定义桌面消费通用能力所需的结果，不代写通用运行时内部接口或生命周期设计。实现前由对应维护方确认具名接点，保留已有其他 MCP 配置，不擅自改其公开接口。首条路径验证当前 Harness；其他 Agent 仅在其实际支持 HTTP MCP 时启用本功能，不新增一组 transport 回退或适配器专有方法。

## 6. 缓存、读取权限与异常

- 标题页仅在主进程内存缓存，按服务 origin、账号、登录代次和 Workspace 隔离；同团队的不同 Project 可复用标题页，工具读取仍绑定到各自本人本机会话。
- 同一范围的并发列表请求合并；第一页有效期 **60 秒**。过期或收到知识更新后，由下一次发送/目录工具读取触发刷新，不做后台定时全库下载。知识创建、编辑或归档成功也使当前团队缓存失效。
- 请求和回包都核对当前登录代次与有效绑定，已失效的回包不能写入新账号缓存。正文每次通过既有 `applicationWorkspace` 路径由服务确认权限；不因本地缓存存在就宣称仍可读。
- 知识服务只提供只读访问，不改变本机工作目录、既有文件审批或其他成员的 Agent 状态。

| 情况 | 用户与 Agent 看到的结果 |
| --- | --- |
| 团队没有知识 | 正常发送，目录为空；列表工具仍可使用 |
| 目录请求暂时失败 | 不阻断原本可发送的普通对话；提示“团队知识目录暂不可用”，不把旧缓存当作已确认的当前目录。可通过列表工具或后续发送重新读取 |
| Agent 不支持 HTTP MCP，或工具未接通 | 不注入承诺能读取正文的目录；输入区显示轻量的自动读取不可用提示，保留手动 `@` 和正常对话 |
| 某个固定版本不可读 | 工具明确返回未读成功，其他正常交互继续；不自动读取新版替代 |
| 登录身份失效 | 沿用现有退出/认证处理，停止旧身份的工具访问；不按普通网络故障继续使用旧授权 |

提示复用当前输入区和工具卡样式，不增加弹窗审批、全局新设置或另一套知识面板。

## 7. 团队知识共享与列表刷新

这一节落实用户补充的“A 新建后 B 能看到”，复用当前知识库能力，独立于 Agent 是否已经收到某份目录。

现有源码已经有如下链路，但本轮没有运行双账号验证：

```text
A 保存知识到 Java
  → KnowledgeAppService.changed 发布 knowledge.updated
  → B 的当前 Workspace 轻量 SSE 收到事件
  → dispatchProjectUpdates 触发 refreshKnowledgeMetadata
  → knowledgeRevision 变化，知识列表与候选元数据重新查询
  → B 看到新增条目或更新后的标题、版本
```

[服务端事件](../../../server/src/main/java/workbench/collaboration/application/service/KnowledgeAppService.java) · [客户端事件分派](../../../desktop/src/renderer/features/project-updates/use-project-updates.ts) · [正式知识列表](../../../desktop/src/renderer/features/collaboration/knowledge/live-team-knowledge.tsx)

- A、B 须属于同一 Workspace，并各自登录；知识是团队级数据，不按当前 Project 分成互不相通的副本。
- A 保存成功后，B 已打开的知识列表在收到通知后刷新；B 尚未打开知识页时，之后进入页面正常查询并看到服务端已保存的条目，无需重启或重新登录。
- 同一刷新修订也更新现有知识数量和 `@` 候选；归档项按既有规则退出列表。若 B 当前搜索条件不匹配新条目，遵循搜索条件展示，不要求强行插入搜索结果。
- 通知只携带变更线索并刷新元数据，不把全量正文推到 B，不因列表更新调用 Agent。B 需要正文时仍明确打开条目、手动引用或由本轮 Agent 调用读取工具。
- B 已打开的固定版本、编辑中的内容、已发送消息与已注入目录不强制替换。断连期间仍可用现有列表刷新入口或重新进入页面查询；通知恢复沿用已有机制，不新建离线同步系统。
- 若必要双账号冒烟发现这条既有链路有缺口，先定位到服务事件、客户端分派或列表消费；本卡修复桌面消费缺口，服务端问题按现行归属交给同事，不复制一套后端通知设计。

## 8. 必须保持的行为

1. 未发送时不运行 Agent，不因自动目录创建协作会话或修改用户草稿。
2. 自动发现阶段只读取列表；实际需要正文时才请求固定版本，不能为了填目录预取全库正文。
3. 显式引用继续使用 HC-219 的固定版本、预览和取消逻辑；自动目录与列表同步不修改已注入材料。
4. MCP 工具由当前账号的本人本机绑定调用，不接受模型自报团队或账号，不获得知识写入或远程执行能力。
5. 元数据刷新与 Agent 运行分别处理：知识库要共享可见，已运行轮次无需热更新。

## 9. 必要验证与交付判定

设计阶段只检查规格、链接和任务一致性。实现后沿用每卡必要冒烟，核心演示合成一条主流程：

1. 两个隔离桌面登录同团队不同账号，B 已打开知识列表；A 新建一条标题清晰的知识。B 收到既有通知后看到新增条目，打开时能读到服务端保存的正文。
2. B 在本人本机会话中提出相关问题，不手动 `@`；受控 Agent 收到标题目录，实际调用 MCP 固定版本读取，现有工具区显示结果与版本，再完成回复。观察目录阶段正文读取请求为零。
3. 该流程顺带核对普通对话不因知识目录失败而不可发送，手动固定引用和原用户文字保留；不要求逐一操作全部页面、主题、异常或输入细节。

受控 Agent 证明桌面到工具的真实链路与请求次数，不能据此宣称真实模型一定会自主选择正确知识。完整 Windows/macOS、多 Agent、集群与组合回归留统一验收；本期先完成一条当前 Harness 的可运行路径，不以提示词样稿替代工具接通。
