关联任务：[HC-185](../task/archive/HC-185-同文件批量编辑.md)。状态：用户已于 2026-10-22 确认范围与 §11 的 5 项设计决定；[Plan](../plan/HC-185-同文件批量编辑.md)、[Todo](../todo/HC-185-同文件批量编辑.md) 已齐，实现已完成，待用户验收（见 Task 的实现与 Review 记录）。源码基线为当前工作区（HEAD `a2a97109`）。

本文细化 Task，不是实现完成声明。按 HC-131 的既有规定，`edits[]` 在没有评测证据前不得进入生产 schema，所以本 Spec 把交付拆成三个停点，**停点 A 是评测闸门，不通过就不进入停点 B**（见 §9）。

## 1. 用户看到的变化

现状：模型在同一轮里对同一个文件连发 3 到 8 个 `edit_file`，它们带同一个 `snapshot_id`。第一个提交成功后文件变了，凭证作废，后面的全部失败（10-20 至 10-21 日志：`COMMIT_CONFLICT` 15 次、`STALE_FILE` 3 次），并且每个编辑各弹一张审批卡片。

改后：一次 `edit_file` 调用可以带多处修改，整批要么全部写入，要么一个字节都不写；用户只看到一张审批卡片，里面是整批合并后的 diff；模型拿到一个新的 `snapshot_id`。

```text
输入  file_path + snapshot_id + edits[{old_string, new_string}, ...]
判断  ① 入参形状与数量/大小是否合法
      ② snapshot 是否仍是当前文件版本
      ③ 每一处都在“同一份读到的内容”里精确匹配且唯一、且完全落在已读行范围内
      ④ 各处匹配区间互不重叠
执行  一次性算出新全文 → 一张审批卡片 → 审批通过后一次 compare-and-replace
输出  成功：新 snapshot_id + 改动附近窗口；失败：错误码 + 第几处出错，文件保持原样
```

单处修改就是只有 1 个元素的 `edits[]`。旧的扁平 `old_string`/`new_string` 入参被**移除**，不保留兼容（仓库处于发版前，按 AGENTS.md 的“单一 canonical 路径”处理）。

## 2. 公开 interface

### 2.1 `edit_file` 入参

```json
{
  "file_path": "/src/app.py",
  "snapshot_id": "snap-…",
  "edits": [
    {"old_string": "从已读内容复制的唯一原文本", "new_string": "替换后的文本，可为空表示删除"}
  ]
}
```

| 约束 | 值 | 说明 |
|---|---|---|
| `edits` 长度 | 1 到 20 | 日志里观察到的最大一次是 8；上限留余量，防止超大参数。超过报 `TOO_MANY_EDITS`。 |
| 单个字符串 | ≤ 64 KiB | 沿用 `MAX_EDIT_TEXT_BYTES`，超过报 `EDIT_TEXT_TOO_LARGE`。 |
| 全部 `old_string`+`new_string` 总和 | ≤ 256 KiB | 新增 `MAX_EDIT_BATCH_BYTES`，超过报 `EDIT_TEXT_TOO_LARGE`。 |
| 提交后全文 | ≤ 2 MiB | 沿用 `MAX_MUTATION_BYTES`。 |
| 每项字段 | 恰好 `old_string`、`new_string`，均为字符串 | 缺字段、多字段、非字符串、`edits` 不是非空数组，一律 `FILE_TOOL_SCHEMA_INVALID`，并在可定位时带 `edit_index`。 |
| 顶层字段 | 恰好 `file_path`、`snapshot_id`、`edits` | 带旧的顶层 `old_string`/`new_string`、`replace_all` 等一律 `FILE_TOOL_SCHEMA_INVALID`（沿用现有顶层键检查）。 |

`edits` 内的顺序不要求等于文件中的顺序。每一处都在**同一份提交前内容**上匹配，不是“前一处改完再匹配后一处”，所以模型不用推算前面的替换对后面位置的影响。

空文件初始化：`old_string=""` 仍只在“Snapshot 与当前文件都是零行空文本”时允许，并且**只能作为 `edits` 唯一的一项**。空串与其他项混用，或文件非空，报 `INVALID_EDIT`。

### 2.2 成功返回

字段沿用现有 `edit_file` 成功 payload，仅以下两处语义变化：

- `replaced`：由固定的 `1` 改为 `len(edits)`。
- `changed_range`、`shown_lines`、`content`：仍是**一个**窗口，范围是整批所有改动的最小外包区间前后各 3 行，上限 200 行、32 KiB。多处改动相距很远时窗口会被截断，`truncated=true`，窗口外的区域不授予已读范围（与现有行为一致，见 §10 风险 R2）。

不新增字段，不改 `packages/protocol`。

### 2.3 失败返回

沿用 `{"ok": false, "error": {"code", "message", "next_action"}}`，新增**可选**字段 `error.edit_index`（从 0 开始，对应 `edits` 数组下标）。只报告按下列顺序发现的第一个错误；任何错误下文件内容不变，也不弹审批卡片。

发现顺序：入参形状 → 数量 → 大小 → Snapshot/文件身份 → 按数组顺序逐项匹配 → 重叠 → 空变更 → 提交后全文大小。

| 错误码 | 何时出现 | 带 `edit_index` | 状态 |
|---|---|---|---|
| `FILE_TOOL_SCHEMA_INVALID` | 入参形状不合法（含旧扁平入参） | 能定位到某项时带 | 已有，更新文案 |
| `TOO_MANY_EDITS` | `edits` 超过 20 项 | 否 | **新增** |
| `EDIT_TEXT_TOO_LARGE` | 单串或总和超限 | 单串超限时带 | 已有，补文案 |
| `SNAPSHOT_*` / `STALE_FILE` | 与现在相同 | 否 | 已有 |
| `EXACT_MATCH_NOT_FOUND` | 第 K 处在文件中找不到 | 是 | 已有，更新文案 |
| `AMBIGUOUS_MATCH` | 第 K 处在文件中不唯一（含 `aa` 在 `aaa` 里的重叠匹配） | 是 | 已有，更新文案 |
| `UNREAD_RANGE` | 第 K 处不完全位于已读行范围 | 是 | 已有 |
| `INVALID_EDIT` | 空 `old_string` 用在非空文件，或与其他项混用 | 是 | 已有，更新文案 |
| `OVERLAPPING_EDITS` | 两处匹配区间有交集（含完全相同的两项、一项包含另一项） | 是，取文件中位置靠后的那一项 | **新增** |
| `NO_CHANGES` | 整批应用后全文与原文相同 | 否 | 已有 |
| `COMMIT_CONFLICT` | 审批后提交前文件被外部改动 | 否 | 已有 |

首尾相接（前一处结束位置等于后一处起始位置）不算重叠，允许。

## 3. 处理流程（`_prepare_edit`）

所有步骤发生在审批卡片出现之前，结果冻结后供审批与提交共用。

1. 校验入参形状、数量、大小（§2.1）。
2. 计算指纹：对整份 `args` 取 sha256，`edits` 顺序参与指纹，所以审批后改任何一项或调换顺序都会被现有“改参即作废”机制拒绝。
3. 命中缓存或已消费则按现有规则返回/报 `COMMIT_CONFLICT`。
4. 解析 Snapshot，读取当前文件，`_require_current` 校验身份（不变）。
5. 对每一项：把 `old_string`、`new_string` 的换行统一成文件换行风格；在**原始当前全文**里 `find`，不存在报 `EXACT_MATCH_NOT_FOUND`；`find(…, start+1)` 仍能找到则报 `AMBIGUOUS_MATCH`；用 `_source_line_range` 算源行区间，不在已读范围内报 `UNREAD_RANGE`；记录字符区间 `[start, start+len(old))`。
6. 按 `start` 排序，相邻两项若 `后.start < 前.end` 报 `OVERLAPPING_EDITS`。
7. 从后往前把每项替换进全文（先改后面的，前面的下标不受影响），得到 `proposed`。
8. `proposed == current` 报 `NO_CHANGES`；`proposed` 超过 2 MiB 报 `EDIT_TEXT_TOO_LARGE`。
9. 调用 `FileMutationService.prepare` 冻结 `current`、`proposed` 与 `expected_identity`。

提交阶段（`FileMutationService.commit`）一行不改：仍是持写锁后一次 compare-and-replace，再重读磁盘、计算 `changed_range` 与 drift。批量能原子，是因为在第 7 步已经合成**一份**完整新全文。

## 4. 审批

- 一次 `edit_file` 调用对应一张卡片，diff 是整份 `current → proposed` 的 unified diff（现有 `_render_diff` 已支持多 hunk），沿用 16 KiB、200 行的显示上限与截断提示。
- `approval_description` 文本增加一行 `修改处数：N`。需要给 `MutationMetadata` 增加 `edit_count: int = 1`；`MutationMetadata` 本来就不保存原始参数，计数不泄露正文。
- `FileDiffPresentation`（协议）不变，不新增 `edit_count`，所以 `packages/protocol` 和 Web/终端审批卡片组件都不用改。
- `approval_preflight` 仍调用同一个 `_prepare_edit`，任何一处失败都返回 False，不弹注定失败的卡片，真实错误由随后的 `ToolMessage` 告诉模型。
- 路径类策略（敏感路径、工作区边界、Plan 模式、自动模式）只读取 `file_path`，不受影响。

## 5. 会话计划文件 `/.harness/plan.md`

计划文件走虚拟 backend 的单次 `edit`，没有 Snapshot，所以不存在“自己的编辑互相作废”的问题，批量没有收益。本任务规定：计划文件只接受 `len(edits) == 1`，更多项返回 `TOO_MANY_EDITS`，`next_action` 提示拆成多次调用。入参形状仍是 `edits[]`，不为计划文件保留另一套入参。

## 8. 不变量与非范围

不变量：

1. 整批原子：任何一处失败，磁盘内容与调用前逐字节相同，且没有任何审批卡片被创建。
2. 审批后提交的一定是审批时看到的那份拟议全文（指纹绑定 + 一次 compare-and-replace）。
3. 每一处都必须完整落在已读行范围内；批量不扩大模型的已读权限。
4. 所有匹配都在**同一份**提交前内容上进行；`new_string` 的内容不会参与同批其他项的匹配。
5. 一个 Snapshot 在一次成功批量提交后作废并签发新的 Snapshot；这一点与现在相同。

非范围：

- 不做服务端自动顺延自己造成的过期（方案 B）。
- 不做模糊匹配、`replace_all`、行号 range、隐式插入。
- 不改全局写锁与 `ConcurrencyGuardMiddleware`。
- 不改 `FileDiffPresentation` 与 `packages/protocol`。
- 不给旧的扁平入参留 alias/fallback。已持久化的历史 Thread 里旧格式的 `edit_file` 调用，在 CLI 中按“入参无法解析”走通用输出，不保留专门的旧格式渲染（退出条件：无，直接移除）。
- 不调用真实企业模型做评测，除非用户之后另行明确允许。

## 11. 风险与待用户确认

已确认的设计决定：

1. `edits` 上限 20 项、总字节 256 KiB。
2. `edit_index` 从 0 开始，与数组下标一致。
3. 空文件初始化必须是唯一一项。
4. 计划文件只接受 1 项。
5. 旧格式的历史 Thread 工具调用在 CLI 里不做专门渲染。

已知风险：

- R1：弱模型可能写错嵌套结构。缓解：严格形状校验、带 `edit_index` 的清晰错误；真实评测待用户允许。
- R2：多处改动相距很远时，成功后的窗口被截断，窗口外区域没有已读范围，模型接着改那里会得到 `UNREAD_RANGE`，需要先 `read_file`。这是现有行为，批量让它更少出现但没有消除；根治要靠方案 B 的范围顺延，本任务不做。
- R3：模型仍可能在一轮里对同一文件发多个**独立**的 `edit_file` 调用，这时第二个及以后仍会 `STALE_FILE`/`COMMIT_CONFLICT`。缓解：工具描述与提示词明确要求合批；是否需要更强手段（方案 B 或重复失败熔断）等上线后看日志再定。
- R4（已核对，不再是风险）：`file_tool_catalog` 的参数类型记号只是参与指纹的字符串，直接写 `array` 即可。
