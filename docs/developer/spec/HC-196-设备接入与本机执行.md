## 2. 身份、登记与本机项目

### 2.1 设备身份与明确触发

设备绑定一个固定服务 origin、一个工作区和一个普通用户所有者。所有者是用户关联，不能由消息正文或切换 UI 账号改写。首版一个 OS 用户的数据目录只托管一个这样的设备身份；同账号可在不同物理设备登记不同 ID。设备显示名 1～80 个 Unicode 字符，改名不改变身份。

1. 登录用户在本机点击“登记此设备”；main 核对当前身份代次和工作区，生成 `registrationId`、`deviceId`、`installationId`、`ledgerId`（小写 UUID）及 32 字节密码学随机秘密。先保存本地待登记记录，再用当前 UI 会话和 CSRF 调用登记 HTTP；ledgerId 标识这一本账本，之后连接或进程重启均不改变它。
2. Java 从会话取得所有者，复核 enabled 和成员关系，保存设备及秘密的 SHA-256 摘要；只返回安全元数据，不返回秘密。设备 ID 冲突不得覆盖已有设备。
3. 响应丢失时，用同一登记 ID、设备 ID、秘密和展示内容重试；同所有者、同正文返回原结果，任一内容不同返回 `REGISTRATION_CONFLICT`。main 不生成第二台设备绕过不确定结果。
4. 本地成功保存登记确认后才允许 Runner 建连。整个异步过程绑定原 UI 身份代次，切换账号不把旧回包交给新账号；已有设备身份不随 UI 退出而清除。

凭据在线上表示为 `Authorization: Bearer <deviceId>.<secret>`，secret 是 32 字节的无填充 base64url（43 字符）。摘要比较使用恒定时间比较；服务不保存明文、不在 URL/query、Cookie、日志、SSE、React 或安装包中传递秘密。本地凭据位于第 6 节同一受限账本中，受当前 OS 用户的目录/文件权限保护；不声称防御已控制该 OS 账号的进程，不引入第二套明文配置或凭据存储 fallback。

设备 Bearer 证明设备归属，不直接授予新执行权。原发起人后来停用、所有者失去工作区成员关系或项目停止共享时，Java 拒绝新的业务授权，但有效设备凭据仍可连接并核对/补传原命令事实；既有获准工作的真实结果不能因后来权限变化被丢弃。显式撤销设备凭据后才拒绝该凭据并关闭连接，本地未确认结果保留，不能把凭据撤销写成执行终态。UI 退出只结束用户网络通道；后台 Runner 和所有者不变。换到另一 UI 用户后可按普通成员访问共享项目，不能管理该设备、本地目录或 Agent 启动配置。演示登录仍不是人员强认证，不因本任务新增认证承诺。

设备撤销是所有者显式动作，不删除账本、原生上下文或云端历史，不把撤销当成实际执行已停止。首版不实现所有权转移或静默凭据轮换；本地凭据遗失/设备数据丢失时登记新设备，旧设备未确认工作保留未知结果，不把新设备认作旧设备恢复。

### 2.2 项目登记与共享

项目登记只能来自可信主窗口的具名本机动作：当前 UI 用户必须等于设备所有者，main 调原生目录选择器，Runner 接收选择结果。WSS 和云端 HTTP 不提供“登记任意路径”命令。

| 本地保存 | 云端保存 |
| --- | --- |
| `projectId`、真实根目录、目录身份、显示名、允许共享标记、共享版本、允许的 Agent 配置 ID | `projectId`、`deviceId`、`workspaceId`、所有者、显示名、共享开关/版本及实际能力摘要 |
| Agent 配置 ID 到受控程序/参数/环境注入的本机配置；模型/Git 凭据留执行机器 | 配置 ID、显示名、是否可用；不含命令、环境值、目录或凭据 |

本地用 `realpath` 取得存在的目录并记录文件系统目录身份；拒绝网络共享盘及不能可靠识别的根。大小写比较按实际文件系统语义处理，不对路径统一小写；同一真实目录的符号链接别名归同一占用键，重叠的父子根也互斥。每次调用前重新核对目录仍是原目录；被删除、替换或重定向时返回 `PROJECT_ROOT_CHANGED`，不自动绑定新目录。目录迁移须所有者重新登记新项目，不修改已有会话的目标。

登记默认不共享，也不上传个人历史或扫描全部文件。所有者再明确点击“共享到工作区”，本地先记录允许共享及动作 ID，再经设备凭据 HTTP 发布无路径的项目元数据；Java 检查设备/所有者/成员，提交共享版本。Runner 保存相同版本确认后才宣告该项目可受理。两侧状态不一致时不可用，不能“本地失败但云端成功”后继续执行。

项目已共享时，启用的工作区成员具有同等访问能力；复制链接不授予权限。停止共享可由所有者在本机或已登录的另一桌面显式发起：本机动作先禁止本地新受理，再通知 Java；远程动作先提交 Java 禁用/新版本，再通知设备。本机未送达显示“本机已停止，云端待确认”；云端已停止而设备离线显示“云端已停止，设备待同步”。恢复共享必须是新一次所有者本机确认，旧共享版本不能恢复。

停止共享提交后 Java 阻止新的实时项目读取、写入和执行授权，未派发输入由 HC-195 按授权失败收敛；Runner 收到新版本后禁止新 start 首次调用；合法原命令的 accepted 仍仅证明落盘，不因停止共享丢掉受理事实，并为尚未进入调用的原项持久保存本地禁止启动事实。此前已有 allow 的原项不改写其运行决定；尚未调用且已在本地确认停止共享的项产生“确实未调用”的拒绝终态，已进入调用的项只保存真实结果或真实取消结果。重新共享不清除旧项的禁止启动事实。停止共享不撤回启用工作区成员对云端共同历史的阅读；原项补传后的内容也归共同历史，非成员/停用用户仍不可读。共享撤回与首次运行决定以同一项目记录的事务顺序判定，不能只靠通知到达先后。

设备暂时离线只影响派发：共享及固定目标仍有效时，成员仍可创建会话或保存 queued 输入。`ready`、本地执行端口暂时不可用和用户/项目授权失效分别表达，不把在线条件混入保存权限。

## 3. HTTP 与 WSS 安全边界

### 3.1 两类请求严格分开

下表为新增路由规格，均在 HC-194 固定 origin 下。成功 JSON 不另包 `data`，错误沿用四字段 `ErrorResponse`；未知方法、重复/多余查询参数和额外字段拒绝。ID/UTC 时间沿用共同定义；shareVersion 为无前导零的非负十进制字符串，范围不超过有符号 BIGINT，线上不转 JS Number。展示名 1～80 个 Unicode 字符，不接受 NUL/未配对 surrogate。

所有公开 occurredAt、createdAt、updatedAt、revokedAt、lastSeenAt 及分页 beforeCreatedAt 直接引用 HC-194 的 UtcTimestamp：形如 `2026-11-08T02:03:04.005Z` 的 UTC 字符串，固定三位毫秒并校验真实日期。SQL BIGINT 可存 epoch 毫秒，传输须映射回该字符串，不新建线上数字时间或另一份时间类型；可空时间为 UtcTimestamp 或 null。

完整 DTO 如下；未列字段不返回，所有可空字段仍必须出现：

| 类型 | 完整字段 |
| --- | --- |
| DeviceSummary | `deviceId,workspaceId,ownerUserId,name,createdAt,revokedAt,connectionState,lastSeenAt`；revokedAt/lastSeenAt 为 UTC 时间或 null，connectionState 仅 offline/reconciling/ready；安装标识、账本、秘密不出 UI |
| AgentConfigSummary | `agentConfigId,name,available`；available 为实际端口可用性布尔值；最多 50 项、ID 不重复，未接真实端口为 false，不增加任意 capabilities 对象 |
| ProjectSummary | `projectId,deviceId,workspaceId,name,shareEnabled,shareVersion,createdAt,updatedAt,agentConfigs`；agentConfigs 为上述完整数组，不含目录/命令/环境值 |
| DeviceRegistrationResponse | `registrationId,device`，device 为首次提交的 DeviceSummary 快照 |
| DeviceListResponse | `workspaceId,devices,nextPage`；devices 为 DeviceSummary 数组，nextPage 为 null 或 `{beforeCreatedAt,beforeDeviceId}` |
| ProjectListResponse | `workspaceId,deviceId,projects,nextPage`；projects 为 ProjectSummary 数组，nextPage 为 null 或 `{beforeCreatedAt,beforeProjectId}` |
| ProjectSavedResponse | `requestId,project`，project 为该次提交的完整 ProjectSummary 快照；用于发布与停止共享 |
| DeviceRevokedResponse | `deviceId,revokedAt`；revokedAt 为首次撤销的服务时间 |

| 方法与路径 | 身份与结果 |
| --- | --- |
| `POST /api/v1/workspaces/{workspaceId}/devices` | UI 会话 + CSRF；严格 `{registrationId,deviceId,installationId,ledgerId,name,secret}`；201 首次/200 相同重试，DeviceRegistrationResponse |
| `GET /api/v1/workspaces/{workspaceId}/devices` | UI 会话 + 当前成员；`limit,beforeCreatedAt,beforeDeviceId` → 200 DeviceListResponse |
| `GET /api/v1/workspaces/{workspaceId}/devices/{deviceId}/projects` | UI 会话 + 当前成员；`limit,beforeCreatedAt,beforeProjectId` → 200 ProjectListResponse |
| `POST /api/v1/workspaces/{workspaceId}/devices/{deviceId}/revoke` | UI 会话 + CSRF + 所有者；严格 `{requestId}` → 200 DeviceRevokedResponse |
| `POST /api/v1/workspaces/{workspaceId}/projects/{projectId}/stop-sharing` | UI 会话 + CSRF + 所有者；`{requestId,expectedShareVersion}` → 200 ProjectSavedResponse，过期版本 409 |
| `POST /api/v1/device/projects` | 设备 Bearer + 当前所有者仍启用/为成员；严格 `{requestId,projectId,name,shareEnabled,expectedShareVersion,agentConfigs}` → 首次创建 201/后续或精确重试 200 ProjectSavedResponse |
| `GET /api/v1/device/channel`（Upgrade） | 仅设备 Bearer，成功 101；固定子协议 `workbench.device.v1`，不建立用户 HttpSession |

设备 HTTP 不读取 WBSESSION，也不以 UI 登录替代设备凭据；UI 路由不以设备凭据替代用户登录。设备专用路由拒绝 Cookie 与设备认证混用，UI 登记不接受 Authorization。只对上述设备 Bearer 路由隔离 Session/CSRF；原有身份与新增 UI 写接口保留 CSRF。不能全局关闭 CSRF、任意 CORS 或将全部 `/api/v1/**` 放行。接入需统筹顺序修改全局 HTTP 白名单/安全装配，本任务不直接改共享文件。

设备列表只包含当前用户拥有的设备，或至少有一个当前共享项目的设备；所有者可看到自己的未共享/已撤销记录，其他成员只看到当前共享项目。项目列表按同一规则过滤；无可见设备返回统一 404，合法空列表返回 `[]`。两类列表按 `(createdAt,ID)` 降序；limit 默认 50、范围 1～100，before 时间/ID 必须成对，均精确校验，不接受 OFFSET。响应按 256 KiB 上限截页（至少一项合法 DTO 可放入），nextPage 为本页最后项；无剩余项为 null。新增项由刷新首屏取得，不承诺跨页快照。

发布项目首次 expectedShareVersion 必须为 `"0"`，创建后为 `"1"`；已有项目须匹配当前版本。共享开关、展示名或配置集合的实际变化使版本递增，无变化不递增；同版本不同请求竞争者得到 SHARE_VERSION_CONFLICT。项目归属创建后不可改。停止共享已经为 false 时，在 expected 仍匹配的前提下返回原状态，不反复递增。各写操作先在授权范围核对稳定请求 ID/完整业务正文，再核对 expected 版本；相同重试返回首次快照，不因当前版本后来变化而失败。设备登记用 `(workspaceId,ownerUserId,operation,registrationId)` 去重，UI 管理用相同前缀加 requestId，设备发布用 `(deviceId,operation,requestId)`；路径目标也是正文的一部分。秘密只保存其摘要并参与一致性比较，不保存明文登记请求。新请求不得覆盖其他设备/项目 ID。登记/撤销请求体限 16 KiB，项目发布限 64 KiB；均只接 JSON，GET 无正文，安全错误不返回凭据/路径。设备拥有者失效时，项目发布返回 403 DEVICE_ACTION_REJECTED，不影响既有结果补传。

两类请求均校验固定 Host、精确 Origin 和 `X-Workbench-Protocol-Version: 1`；Runner 设置 `Origin` 为配置的 HTTPS/HTTP 服务 origin，而不是 wss/ws origin。WSS 路径无 query，禁止 URL 凭据及重定向，握手错误仍为 HTTP 安全 JSON。缺失/错误/已撤销设备凭据统一 401 `DEVICE_AUTHENTICATION_REQUIRED`，不能由响应区分设备是否存在。所有者/发起人后来停用或离开工作区不使既有有效设备凭据无法补传原事实；每个新业务动作仍独立复核授权。UI 不存在/非成员/非所有者管理请求统一 404 `RESOURCE_NOT_FOUND`。

只从已有 `WORKBENCH_SERVICE_ORIGIN` 取得单一地址；Runner 由宿主启动参数接收该经校验 origin，不能由 renderer 或远端命令覆盖。HTTPS 固定映射 WSS；既有 `http://127.0.0.1:<port>` 研发入口映射同主机端口 WS，不增加第二个开关。远程只使用受信任 TLS，沿用宿主 CA 信任；不忽略证书、不开任意 localhost Origin、不回退明文。Runner 主动出站，不在执行机器新增可远程访问的监听端口。

### 3.2 通道实现与限制

Java 在既有 MVC 单应用使用 Spring `WebSocketHandler` 和握手拦截，版本跟随现有 Boot BOM，不引入 STOMP/SockJS 或新服务。Runner 选定 `ws:8.22.1` 的 Node 客户端，以支持受控握手 headers、ping/pong 和体积限制；2026-11-07 已只读核对 npm 官方元数据及该版本源码文档，未安装。关闭 per-message 压缩，不需要原生性能扩展。固定版 API 见 [ws 文档](https://github.com/websockets/ws/blob/8.22.1/doc/ws.md)，Java 接点见 [Spring WebSocket](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)。锁/包聚合由统筹集成，不复用旧 CLI 的 ws 依赖链。

所有平台消息组合 HC-194 四字段头：`protocolVersion:1`、稳定 `messageId`、判别 `type`、UTC 毫秒 `occurredAt`，再带本节定义的具体载荷；不存在 `payload:any`。服务端派发时间取服务时间，设备观测时间只供诊断，共同历史时间/顺序由 Java 产生。UUID、十进制字符串序号、严格额外字段拒绝和 JSON Schema 校验均沿用 HC-194。

固定上限：完整 WSS 文本消息 1 MiB，单执行来源消息 64 KiB、单文本增量 8 KiB，执行命令/决定编码后 128 KiB，设备控制消息（含恢复分页）/执行批量外壳 256 KiB。命令编码限额留出 JSON 转义和固定头/目标字段空间，不扩大正文：当前 `input:{text}` 与用户 text 相同，最多 32 KiB UTF-8、16,384 个 Unicode 字符，拒绝 NUL/未配对 surrogate，保留合法原文；输入 HTTP 正文 64 KiB。未来引用扩容由 HC-198/197 另审，本轮不先放宽。超限在发出/调用前拒绝，不静默截断或正规化。业务正文超限代码 `PAYLOAD_TOO_LARGE`；畸形消息/未知 type 关闭 1008，消息体积超限 1009，暂时内部故障 1011；安全错误不携带凭据或原始帧。JS/Java 均限制解码后完整消息，拒绝二进制业务帧。

### 3.3 业务错误与重试意义

新增错误仍须由统筹登记到同一个公共错误集合；下表区分用户 HTTP、设备协议拒绝和本机状态，不把本机 IO 原始错误直接传给其他成员。`retryable` 只表示可再次查询/尝试相同身份的请求，不证明尚未产生副作用。

| 错误 | 处理与重试规则 |
| --- | --- |
| HTTP 401 DEVICE_AUTHENTICATION_REQUIRED | 设备认证不成立，停止连接重试；UI 身份仍按 HC-194 单独处理 |
| HTTP 403 DEVICE_ACTION_REJECTED | 有效设备凭据的所有者当前不能发布新项目/共享，不自动重试新动作；旧执行事实仍可补传 |
| HTTP 409 REGISTRATION_CONFLICT / REQUEST_ID_CONFLICT | 已有 ID 对应不同正文，不覆盖、不换 ID 自动再登记 |
| HTTP 409 SHARE_VERSION_CONFLICT | expectedShareVersion 过期，先读状态并重新由所有者确认，不自动恢复共享 |
| 同源执行错误 targetMismatch/conflict/bindingConflict/invalidTransition | 目标/正文/绑定/状态不一致，停止该项新动作并核对，不自动改写字段；错误联合归 HC-195 |
| 本机 PROJECT_NOT_SHARED / PROJECT_ROOT_CHANGED | 原决定保存后、尚未 invoking 的确切拒绝，按同名 ExecutionReasonCode 形成 notInvoked rejected；不临时映射 TARGET_INVALID，不换目录或共享版本重做旧命令 |
| 本机 CAPABILITY_UNAVAILABLE | 派发前暂不可用可保持 queued；合法 start 已 accepted 且原决定已保存后，本地真实端口/能力预检失败以同名原因形成 notInvoked rejected，不永久挂 accepted、不伪造成功/failed |
| 设备拒绝 PROJECT_BUSY | 当前人工项目操作无调用/副作用，即时返回忙，不隐式延迟执行；已受理 start 等待目录占用，不用一个永久忙回执使其无法首次运行 |
| 本机 LOCAL_RUNNER_ALREADY_ACTIVE / LEDGER_MISMATCH | 拒绝第二实例或新工作；不能删除锁/账本绕过 |
| 本机 LOCAL_STORE_FULL / LOCAL_STORE_UNAVAILABLE | 停止新受理/调用，未确认结果保留；恢复记录能力后先核对原命令 |
| 原有 HTTP 503 SERVICE_UNAVAILABLE / 设备 1011 | 数据库或服务暂时不可用；不把错误当成功/未受理证明，先按原 ID 查询/重连核对 |

执行拒绝使用 HC-195 的具名消息和状态语义，只有已保存且能证明未调用才报告 rejected；存储失败只发送尽力的通道故障并关闭，不能伪造“已持久拒绝/已受理”。

## 4. 唯一连接与恢复握手

### 4.1 当前 socket 与 connectionId

首版只有一个活动 Java 应用。设备认证成功后，Java 在内存生成随机 UUID `connectionId`，按已认证 deviceId 替换唯一当前 socket；不把连接代次写入数据库，也不引入集群连接协议。Runner 同时只保留一个连接尝试，开始替换即使旧 socket 业务回调失效。

```text
认证 → 内存登记当前 socket/connectionId → 旧连接失去业务资格并尽力关闭
welcome → 同 ledgerId 枚举/查账本 → 补连续事件、原运行决定和项目共享状态
核对结束 → ready → 唤醒 HC-195 唯一调度器 → 派发新工作
```

Java 接收/发送业务外壳时同时核对当前 socket、connectionId 和认证所得 deviceId，旧 close 只清理它自身。Runner 在接收时同样检查当前 socket/connectionId，丢弃旧 socket 缓冲区迟到帧。旧连接中已提交的业务事实保留；已开始的本机执行不随取代重新运行或自动取消。Java 重启连接表为空，全部重新核对；持久 ledgerId 只识别同一本地账本，不充当连接标识。

### 4.2 外壳与唯一执行内层

单消息外壳精确为 `{connectionId,message}`，message 是一个完整平台消息；执行来源批量外壳精确为 `{connectionId,messages}`，messages 为 1～64 条同 executionId 的 HC-195 Runner 来源消息，合计不超过 256 KiB。两种外壳不得混用字段，批量外壳只装执行来源，不装设备控制或命令。设备归属从认证 socket 获得，不允许外壳另外指定用户、设备或顺序。

所有内层含 `{protocolVersion:1,messageId,type,occurredAt,payload}`。设备控制帧 payload 由下节定义；execution.start/cancel、execution.start.decision、accepted/native.bound/running/output/terminal/cancel.received 以及连续前缀确认的内层，全部引用 [HC-195 第 7 节](HC-195-共享会话与实时同步.md#7-与-hc-196-的共同交界) 的唯一 execution 定义。本稿不再另造设备 execute/receipt/event/permission 类型、正文或事件序号。消息头 messageId 本身就是该命令、来源消息或运行决定的稳定 ID；commandId/startCommandId 等仅在关联处引用原头 ID，不能再为同一事实生成等价 ID。

重连只更换外壳 connectionId，完整执行内层的 ID、occurredAt、payload 和指纹均原样重传。批量包装、socket.send 回调、HTTP 101 和 ping/pong 都不是业务持久确认。Java 只在 HC-195 提交连续前缀后返回 `{executionId,lastCommittedRunnerSequence}` 的同源确认，Runner 不按逐消息 ID 清理事件。gap/conflict/targetMismatch 的结构/错误语义同样引用 HC-195；缺号不提交后缀，冲突不覆盖原记录。

### 4.3 控制帧的完整字段

控制帧也使用上节五字段内层，payload 精确按下表，额外字段拒绝。控制头 ID 在同一次请求/响应重传时保持不变；新连接生成新的 resumeId 与控制消息，不能重用旧控制请求。关联请求只引用其 messageId，不重新生成另一份请求身份。

恢复中需要的本地记录仅报告本地持久事实，不是第二套执行协议：

- `LocalExecutionRecord` 为 `{kind:"execution",start,decision,cancel,localState,lastRunnerSequence,lastCommittedRunnerSequence,nativeSessionId,terminal}`。start 是保存的完整 HC-195 ExecutionStart；decision/cancel/terminal 分别是完整同源运行决定/取消命令/终态来源消息或 null。localState 采用 HC-195 恢复联合中的 accepted/notInvoked/invoking/running/terminalPending/unknown，不含 notFound。两 sequence 均为十进制字符串，可为 `"0"`；`0 ≤ lastCommittedRunnerSequence ≤ lastRunnerSequence`。nativeSessionId 是本地已确认值或 null，约束同 HC-195。terminalPending 必须带完整持久终态；其他阶段 terminal=null。
- 取消先于 start 的记录为 `{kind:"cancelBeforeStart",cancel,lastRunnerSequence,lastCommittedRunnerSequence,terminal}`。完整同一本账本尚无原 start，原 cancel 合法且能证明未调用时，同一事务保存禁启记录、连续 cancel.received 和 invocationState=notInvoked 的 cancelled（决定引用 null），共用原 executionId 的 runnerSequence。terminal 必须为该完整持久终态，不为 null；两序号规则同上。来源归属/原 start 摘要从 cancel 取得，不伪造 accepted/native.bound/决定，也不等重发 start。账本或实际调用不明则 unknown，不冒充本分支。迟到 start 只比对并保存原文，不造第二份来源/终态或调用。排序键为 cancel.payload.startCommandId。
- 所有 execution.* 对象均直接引用 HC-195 schema，不在 device schema 复制字段；恢复记录中的 localState 和游标仅用于本地事实枚举，不新增云端业务状态机。

| type / 方向 | payload 的全部字段 |
| --- | --- |
| `device.welcome` Java → Runner | `{deviceId,workspaceId,ownerUserId,ledgerId,resumeId,heartbeatIntervalMs:15000,heartbeatTimeoutMs:45000}`；ledgerId 为登记时已保存值；尚不可接新 start |
| `device.resume.request` Java → Runner | 判别联合：`{resumeId,kind:"inventory",afterStartCommandId}`，afterStartCommandId 为 UUID 或 null；或 `{resumeId,kind:"lookup",startCommandId}`，精确查询一项，不允许同时带两种参数 |
| `device.resume` Runner → Java | `{resumeId,requestMessageId,ledgerId,afterStartCommandId,records,nextAfterStartCommandId}`；对应 inventory，请求头 ID 写 requestMessageId；records 为上述记录数组，最多 100 项/256 KiB，按排序键 ASCII 升序；首游标可为 null，结束 next 为 null |
| `device.command.status` Runner → Java | found 分支 `{resumeId,requestMessageId,ledgerId,startCommandId,result:"found",record}`；record 为上述记录；或 notFound 分支同样四个关联字段加 `result:"notFound"`，不带 record。只有完整、同一本账本无命令也无取消禁止标记才可 notFound |
| `device.project.changed` Java → Runner | `{resumeId,projectId,shareEnabled,shareVersion}`；resumeId 为当前恢复 ID，在线变化时为 null；不含根目录或启动配置，不创建本地目录映射 |
| `device.project.saved` Runner → Java | `{resumeId,requestMessageId,projectId,shareVersion,result}`；result 仅 applied/notRegistered，后者表示本地无该映射，项目保持不可用；只在共享元数据/禁止启动事实已持久后回复 |
| `device.ready` Java → Runner | `{resumeId,ledgerId}`；只表示本轮核对结束及传输可派发，不代表模型/项目可用或原任务已完成 |
| `device.execution.problem` Java → Runner | payload 直接引用 HC-195 recordBatch/reconcile 的完整闭合错误联合（kind、executionId 及该分支必需字段），不另抄执行错误形状、不放任意诊断；gap 补原缺口，其余冲突暂停该项 |
| `device.problem` 任一方向 | `{resumeId,requestMessageId,code,message}`；前两项可 null；code 仅 INVALID_CONTROL_FRAME/LEDGER_MISMATCH/RESUME_TIMEOUT/COMMAND_CONFLICT/LOCAL_STORE_FULL/LOCAL_STORE_UNAVAILABLE；message 为固定安全文案，不能包含原始帧/路径/SQL |

inventory 页只枚举“未有真实终态、或仍有未确认来源消息、或仅有取消禁止标记”的记录；已完整确认的终态不在主动枚举中，但针对它的 lookup 仍须返回原持久记录。每页以请求游标之后的排序键取条数/字节双限额，至少容纳一条合法记录，next 为还有记录时的本页最后键；空页必须 next=null，不能让调用方猜是否结束。恢复期间禁止派发新的队列项；HC-195 经 reconcile 决定重送的已登记原 start/cancel 可以核对，新增受理事实按同一恢复进展处理后才 ready。原项从清单消失只可能是终态全部获得连续确认，Java 已有该事实。真实运行仍可产生后续事件，按下一节有限上界核对，不持有跨网络数据库事务或复制全部正文到内存。

设备收到 changed 的新版本后，先保存元数据；shareEnabled=false 同事务为所有未 invoking 的原项登记禁止启动。相同版本相同内容幂等，较旧版本不能覆盖；同版本不同内容是控制冲突并停止核对。收到服务器共享状态为 true 不替代本地所有者曾明确共享的事实，也不能清除本地离线停止或旧项禁止启动标记。没有本地根的云端项目返回 notRegistered，Java 只将该项目标不可用，不凭通知在本机建目录。

### 4.4 核对过程与结束条件

1. Java 认证后发送 welcome，再发 inventory 请求，Runner 先核对登记 device/workspace/ledgerId。不同账本、损坏库、无法读库均发送 problem 并停止，不返回空记录冒充未受理。
2. Java 顺序取得 inventory 的全部页，要求请求游标/响应关联匹配、键严格递增、无重复或缺页；连接串行处理控制消息，不并发推进同一枚举。对每条记录保存其返回时 lastRunnerSequence 为本轮补传上界 H；进程内只需保存 ID/序号等有界元数据，不持久建立第二个恢复服务。
3. HC-195 给出这台设备所有“已登记派发但未确认终结、或取消/决定待核对”的 startCommandId；不在清单的逐项 lookup。found 同样取得 H；notFound 仅交 ExecutionRecovery.reconcile 判断，HC-196 不自行重排、删除或重新生成命令。取消先到记录是 found，其 H 包含同源取消来源，不用重送 start 才承认取消；若原 start 迟到，只保存/核对原文并返回既有取消结果。只有可信 notFound 且 HC-195 选择 resendSame 时才重送其首次原文；本轮因此新产生的受理前缀/原决定也须核对后才结束。
4. Runner 从 Java 已确认连续位置之后补发同源来源批次，直到每项 H 都被 recordBatch 提交确认。H 之后的实时新输出继续可靠保存；不要求正在运行的 Agent 输出停止。缺号则重发缺口，冲突则停止该项并交 HC-195 核对。所有待确认的原决定通过原 ExecutionStartDecision 重传；Runner 先落盘、串行消费后续控制帧，不能由恢复清单反推或重造 allow。
5. Java 对该设备全部已登记项目逐项发送当前 changed，并收到每项 saved；变更在核对中发生时须再次发最新版本。notRegistered 使该项目不可用，但不阻止其他项目恢复。未解决 ledger/控制冲突、H 之前缺号、未回的 lookup/项目版本、未交 HC-195 处理的矛盾事实都阻止 ready；已明确记为 unknown 的执行可以完成核对，但仍占会话/目录，不因此可重跑。
6. 上述有限清单全部完成，Java 发 ready 并调用 ExecutionDispatch.onDeviceAvailable 唤醒唯一队列。Runner 核对相同 resumeId/ledgerId、所有先前控制写入已完成后转 ready；没有持久 allow 的项仍不能首次调用。若 ready 丢失或连接替换，重新按新 resumeId 核对，不绕过该过程。ready 后新追加事件正常按连续前缀确认；待决定/待取消仍重传其原内层。

每个恢复请求或补传进展最多 30 秒无有效响应/提交进展则关闭并重连，ping/pong 不冒充恢复进展；已成功提交前缀不回滚，下一连接继续核对。已写出 start 后 15 秒仍无受理事实，仅由 HC-195 转 unknown/DELIVERY_UNCONFIRMED，不能当未受理或释放会话。Java 每 15 秒 ping、45 秒无有效 pong 判失联；Runner 按 1/2/4/8/15 秒上限退避并加入小幅随机抖动，认证/版本/TLS 固定错误停止并显示原因。休眠唤醒先重连核对，旧 open 标志不能开启新工作。服务/设备读写均按每 socket 串行发送，收帧与持久化等待不跨模型运行，取消不等待 execute 完成。

## 5. 命令、受理与首次调用

### 5.1 唯一标识和不可变内层

| 标识 | 用途与唯一来源 |
| --- | --- |
| conversationId | Java 平台会话，固定绑定原 deviceId/projectId/agentConfigId，不是 ACP 会话 |
| requestId / inputId | requestId 是用户意图去重 ID，逐次 HTTP X-Request-Id 只追踪；inputId 等于已保存用户 Message 的 messageId |
| executionId | HC-195 为该 inputId 保存的一次执行，不因网络/重启再造 |
| messageId | 对 execution.start/cancel 就是命令 ID；对 Runner 来源就是稳定来源 ID；对 execution.start.decision 就是该决定稳定 ID。关联字段 startCommandId/cancelCommandId 只引用相应原头 ID |
| runnerSequence | 同 executionId 内全部 accepted/native.bound/running/output/cancel.received/terminal 来源消息从 1 连续编号，采用十进制字符串；不是会话 sequence |
| nativeSessionId | 云端和 Runner 保存同一个 ACP 不透明字符串；首次可 null，产生绑定后只接受同值，UI 不读取/解释 |

执行命令、来源、决定和确认的字段集合、bodySha256/startBodySha256 与闭合 payload 均以 HC-195 修订第 7 节为唯一源。设备只消费，不增加第二套正文。execution.start 使用 initiatedByUserId、input:{text}、shareVersion 和固定目标；execution.cancel 使用 requestedByUserId。发起人由 Java 当前身份固定，Runner 不信任用户自行填写的作者，不接受额外 rootPath、shell、args 或 env。

指纹涵盖固定内层头与完整 payload，排除指纹字段本身和连接外壳；确定性序列化和字节夹具归 HC-195 同一 execution 资源。重发不重盖 occurredAt，不 trim/正规化/改换行，不把仅 text 的 hash 当整命令一致性。相同 ID 先核对完整内层及摘要；不同 ID 但复用同 executionId/inputId 的第二个 start 也拒绝，不靠换命令 ID 获得第二次调用机会。

### 5.2 受理、运行决定与调用

1. 共享/固定目标有效但设备离线时，HC-195 仍可保存 queued；ready 只控制派发。HC-195 唯一调度器在授权 → 项目 → 会话 → 执行的短事务顺序下选择队首，保存固定 start/占位，提交后调 DeviceDelivery.sendStart。网络 written 不等于受理；进发送边界后不因超时回退普通队列。
2. Runner 先校验当前 socket/connectionId、合法完整内层与已登记逻辑目标归属/账本。正常新项同一事务保存 start、受理状态与 execution.accepted（稳定 messageId/runnerSequence），COMMIT 后才补传；accepted 不承诺真实目录/能力预检通过。已有取消先到记录只核对原文并返回原结果，不新增 accepted。ID/正文/目标冲突走协议冲突，写失败不发成功事实；没有原运行决定不调用端口，物理目录/能力预检留到决定落盘后。
3. HC-195 的 ExecutionReceipts.recordBatch 在保存首次 accepted 的同一执行事务中，核对原设备/命令、发起人、shareVersion 和取消事实，保存唯一 execution.start.decision（allow/deny、稳定头 messageId 及完整原文）。决定属于同一执行行，不新增决定表、权限服务或设备许可对象。事务提交后才连续确认来源前缀、发原决定。相同 accepted 重传时返回原决定，不能按后来权限重新生成。
4. Runner 核对决定引用的 execution/start/指纹和当前 socket，持久保存完整决定后才可考虑首次调用。决定丢失就等待或在核对时请求原决定；本地已有决定则逐字核对，第二份相反内容即冲突。deny 只证明 Java 不允许首次调用，不证明本机已经停止；本地能证明未 invoking 才产生 rejected/cancelled 的真实终态。没有本地终态时 Java 不因 deny 释放会话。
5. allow 一经保存不因随后停用/停止共享改写。首次调用须恢复已 ready、未取消/本地停止、真实目录/配置匹配且取得占用；未 invoking 的禁启事实优先于迟到 allow，重新共享不复活旧项。原决定保存后，目录被替换/消失用同源 PROJECT_ROOT_CHANGED，真实端口/依赖能力缺失用 CAPABILITY_UNAVAILABLE，持久 notInvoked rejected 及连续来源，使原项可靠闭合；两原因加入 HC-195 唯一 ExecutionReasonCode/rejected 集合，不临时映射或发任意错误/假 failed。目录忙仍等占用且取消可用，不注入默认成功或生产替身。
6. 调用前在本地事务保存 invoking；COMMIT 成功后才调第 7 节端口，不跨网络/模型持有事务。prepareSession 本身也属于可能有副作用的调用。首次 start.nativeSessionId=null 时，创建/恢复得到的同值先保存为 execution.native.bound 来源再继续，原 start 的 null 与指纹保持首次字节不变；后续 start 使用 Java 已确认的实际标识，不补写旧命令。
7. 实际开始/输出/终态经同一来源序列持久保存后补传；只有真实端口开始才报告 running，只有确切终态才终结。Java recordBatch 对原获准执行的结果只核对原设备、命令、绑定及序号，不把发起人后来停用、项目停止共享或 UI 退出当成丢弃结果理由。提交终态后才推进队首。

Runner/Java 都不以重新生成决定解决断线。未 invoking 且持久 allow、无取消/本地停止的原项，经同账本恢复核对可以第一次调用；invoking 之后不能因为没有 running/terminal 再调用，无法核实就 unknown。已开始工作可断线继续本机记录；尚未开始的项在通道未 ready 时等待核对。

### 5.3 取消、停止共享和决定的竞争

execution.cancel 直接引用 HC-195 唯一命令，不复制取消字段。它不排在模型调用之后等待；Runner 控制与事件记录入口在 execute 等待期间仍可响应。

| 当前事实 | 收敛与禁止事项 |
| --- | --- |
| Java 可证明从未派发 | HC-195 同事务取消 queued；不伪造 Runner 来源消息 |
| 可能已派发、设备离线/未核对 | 保存原 cancel，显示待送达；不据此释放会话或声称停止 |
| cancel 先于 start | 持久保存原 cancel、禁止启动及同一 executionId 连续 cancel.received/能证明的 cancelled，不等待一个不存在的决定；lookup 返回 cancelBeforeStart。迟到 start 只核对原文并返回既有结果，不造 accepted 或第二终态 |
| cancel 先于首次运行决定 | HC-195 首次决定为 deny，Runner 保存后按真实未调用事实产生 cancelled；deny 本身不是停止证明 |
| cancel 晚于已保存 allow，但尚未 invoking | 原 allow 保留；持久取消优先阻止首次调用，产生真实 cancelled 终态 |
| allow 后本地确认停止共享、尚未 invoking | 原 allow 保留；本地禁止标记阻止首次调用，按确切未调用事实 rejected，不改决定 |
| 已 invoking/运行，再收到 cancel 或停止共享 | 不回写“从未执行”。cancel 调端口真实取消并保存 cancel.received，等待真实终态；单纯停止共享不伪造取消 |
| 原执行已有真实终态 | 重传其原终态；晚到 cancel 不覆盖成功/失败，不再调用取消 |
| 崩溃/遗留进程/矛盾决定导致结果无法核实 | unknown，保留会话和重叠目录占用；不新建决定、命令或替代原生会话 |

execution.cancel.received 也进入同 executionId 的 runnerSequence，不表示 cancelled；先到 start 的原取消沿用同一序列，不能另编取消事件流。Java 仍从当前 UI/所有者本机动作授权新取消请求，既有固定 cancel 的重传不产生新用户意图。有效设备通道可补原项事实；凭据已显式撤销则本地保留未确认结果，所有者仍可在本机停止实际运行，不假装云端取消已送达。

### 5.4 未实现能力的真实边界

首个可注册执行内层仅为 HC-195 的文本 start/cancel 和对应具名来源/决定；真实 ACP 端口缺失时返回不可用，受控替身仅用于开发冒烟。工具、审批/提问回答、文件/Git 的线上消息必须由 HC-197/199 与 HC-195 共同补闭合 schema/夹具后注册；本轮不创建 interaction.respond、project.operation 或任意 payload 入口，不把未实现操作返回默认成功。

第 7 节保留后续端口的最小需求约束。人工项目操作应在线即时授权，离线/未 ready/目录忙时直接不可用，不排队一笔隐式提交/推送。已经可能产生副作用的请求仍须核对原稳定消息身份，超时不允许换 ID 盲目重试；其具体线上形状和去重源归 HC-199 后续审查，本稿不维护第二套执行队列。

## 6. 唯一本地持久路径与崩溃边界

### 6.1 存储选择

选择一个嵌入式 SQLite 业务账本，通过 Node 内置 `node:sqlite` 使用，不增加数据库服务、Python、SQLite CLI 或第二个存储实现。沿用 Node `>=22.12.0` 下限；该下限使用 `--experimental-sqlite` 启动参数，启动入口在 import 前检查实际能力，缺失就明确退出，不回退内存/JSON 文件。[Node 22.12 官方文档](https://nodejs.org/download/release/v22.12.0/docs/api/sqlite.html)只证明该版本 Node 的 API/参数，不证明 Electron 宿主可用；本轮未运行它。

Plan 的最早技术验证停点必须先验证实际 Electron 托管路径，而后才展开设备/账本生产实现：使用拟交付的 Electron 子进程入口实际 import node:sqlite、按模式读回并提交/重开隔离账本；用两个真实托管进程证明 owner.sqlite 排他锁、关闭/崩溃释放与拒绝第二实例；同时核对旧 Agent 子进程可能遗留时不会把锁释放误作终态。standalone Node 成功不能替代此停点。本轮仅编写 Plan/Todo，不试运行或改启动配置；宿主不能满足时回调修订单一技术方案，不加存储或运行时 fallback。

固定数据根为当前 OS 用户的应用数据目录下 `workbench/runner/<SHA-256(serviceOrigin)>/`：macOS 使用 `~/Library/Application Support`，Windows 使用 `%LOCALAPPDATA%`。宿主提供确定的根，不能放到项目目录、网络盘或随升级删除的制品目录；无界面托管使用相同规则和同一实现，不另找临时目录。业务均在 `runner.sqlite`，目录 0700/文件 0600；Windows 创建仅当前用户和 SYSTEM 可访问的等价 ACL。无法创建/确认受限目录时拒绝登记与启动，不自动换路径。

`runner.sqlite` 固定 `journal_mode=WAL`、`synchronous=FULL`、启用 macOS 可用的 fullfsync；启动读回确认模式并检查 schema/完整性。它的 WAL/SHM 是同一数据库的组成部分，不能只复制主文件。备份仅在停止 Runner/Agent 后完整处理，不支持正在运行时拷贝到另一台机器。FULL 的耐久边界依赖文件系统/硬件实际兑现同步；不承诺磁盘损坏、数据目录回滚或任意硬件故障后仍全局只执行一次，依据见 [SQLite 同步规则](https://www.sqlite.org/pragma.html#pragma_synchronous)。

为避免两个进程同时读取账本并调用外部端口，同目录另有 `owner.sqlite`，仅用于单实例锁、不保存业务数据：使用独立 SQLite 连接取得 `BEGIN EXCLUSIVE` 并保持到本 Runner 和其托管进程已收敛退出。第二个进程无法取得锁即返回 `LOCAL_RUNNER_ALREADY_ACTIVE`；不按心跳超时偷锁，不删除/替换这个文件。进程崩溃由 OS 释放文件锁；新进程取得锁后仍要按下节核对遗留 Agent，取得锁不证明旧子进程已停止。两文件只使用同一种嵌入式存储，没有网络锁服务或替代账本。

数据库同步操作在 Runner 自身串行记录入口执行，不在 Electron main 执行同步磁盘写入；记录事务有界，不持有到模型调用结束。首次本地 schema 在登记时建立并记录版本；升级只在取得进程锁后显式处理已支持版本，未知/损坏 schema 拒绝启动，不清库重建。账本不存在但云端设备已有派发记录时，不能以新空账本伪造 notFound，必须报告 `LEDGER_MISMATCH`。

### 6.2 必需记录与原子性

| 记录 | 最少内容和约束 |
| --- | --- |
| 设备 | origin、ledgerId、installationId、deviceId、ownerUserId、workspaceId、设备秘密、登记确认；ledgerId 创建后不改变 |
| 项目/Agent 配置 | 本地规范根和身份、共享开关/版本、项目/配置 ID 与本机配置；远端无路径写入口 |
| 命令 | 原 start.messageId 主键，完整同源 start/摘要、原完整运行决定（头 messageId 即决定身份）、原 cancel、accepted/invoking/实际运行/终态或未知状态、取消/本地停止标记；同 executionId/inputId 唯一 |
| 原生绑定 | conversationId、projectId、agentConfigId、nativeSessionId、实际进程归属；原生值与 Java 同一关联值，不存 Harness 私有对象 |
| 来源与确认 | messageId 主键、executionId、连续 runnerSequence、完整内层/摘要、lastCommittedRunnerSequence；同执行序号唯一，连续前缀确认后才清理正文 |
| 目录占用 | 真实/重叠根、实际执行 ID、进程归属和是否结果未知；新进程不能只清内存锁就开始写 |

新命令记录与受理回执同事务；状态变化与对应事件同事务；终态与释放本地占用同事务，且必须已证明不再有本机运行/写进程。事件序号分配和正文保存同事务。受理成功、调用前 invoking、输出事件、终态和 ack 清理均以 COMMIT 成功为边界，不能只写入 JS 缓存。

### 6.3 崩溃后怎样判断

| 最后持久事实 | 重启动作 |
| --- | --- |
| 没有命令，且 ledgerId 相同/完整 | 可对指定命令返回 notFound；Java 决定是否重送同 ID，设备不得自己拉起任务 |
| accepted，未进入 invoking | 补 execution.accepted；缺决定则等原决定，已有 allow/deny 仅核对原完整消息；本地取消/停止仍优先，恢复 ready 后才可能第一次调用 |
| invoking，但无确定开始/终态 | 可能已调用端口；默认 resultUnknown，不自动再次调用 |
| 正在运行/等待人工回答，无终态 | 由注入端口只读核对原生会话和原进程；不能证明连续性就 resultUnknown，不新建替代会话 |
| 本地真实终态、Java 未确认 | 按原 messageId/runnerSequence 补终态与全部前序消息，不执行命令 |
| 消息已提交云端但连续前缀确认丢失 | 重传同内层批次，Java 返回相同连续提交位置，不能重复追加共同历史 |
| 存储损坏/ledgerId 变更/命令正文冲突 | 整台设备暂停新工作并回报具体原因；不清库、不声称尚未受理 |

即使是“invoking 提交后、真正调用前”这一狭小窗口崩溃，也保守按未知处理；这是不重复副作用的代价，不编造跨 SQLite 与 Agent/Git 的全局原子事务。只有原端口能提供同一原生请求的可靠只读事实，才允许补真实终态；恢复会话只恢复上下文，不自动再次提交旧问题。没有终态/停止证明时，阻止该会话后续输入及重叠目录的新写操作，不释放占用冒险执行下一条。

### 6.4 容量、磁盘失败与清理

待确认来源正文上限 256 MiB、本地业务正文总预算 1 GiB，另留 1 MiB 逻辑预算给控制/终态；新命令前检查预算。连续前缀确认后的流式正文可清理，完整 start/决定/cancel/终态、各 messageId/runnerSequence/摘要、输入/执行唯一索引和原生绑定保留，供精确重试及 lookup；不能因清理正文把命令报告为 notFound。未确认正文、unknown 和原生绑定不自动淘汰。保留材料达到预算时停止新受理，不删去重记录腾位置。

逻辑余量不保证物理磁盘尚有空间。任何提交失败均不发成功回执，不新调用外部端口，不切内存继续；暂停新任务并报告 `LOCAL_STORE_UNAVAILABLE`。运行中的事件回调等待持久提交后才确认消费；失败时不确认事件，并请求端口有界停止、拒绝新人工回答/新外部动作。已进入 Agent/Git 的副作用可能仍在完成，不能回滚或宣称全部被阻断；无法保存/核实的结果标未知，保留旧记录待本机处理。HC-197 必须配合背压与停止，不能把 Runner 的记录能力包装成对任意 Agent 内部工具的逐次事务保证。

## 7. 注入端口与目录占用

以下为后续 HC-197/199 审查的最小本机端口，尚未实现/确认；不能据本节把新线上消息注册为可用。Runner 管路由、持久化和占用，真实端口负责 ACP 或文件/Git；类型最终从各自业务命名空间导出，不复制协议或引入 Electron/Java 内部类型。

### 7.1 文本执行端口（HC-197）

| 方法 | 输入 → 输出/错误 |
| --- | --- |
| capabilities(agentConfigId) | 本机配置 ID → `{available,sessionResume}`，两项为实际能力布尔值；缺配置/依赖为 CAPABILITY_UNAVAILABLE，不按 Agent 名称猜测 |
| prepareSession(context,nativeSessionId,sink) | 固定执行/项目/配置 ID、本机解析根与原原生值或 null → 同一不透明 nativeSessionId；首次/恢复绑定先通过 sink 持久 native.bound 后才继续；已有绑定不支持恢复为 NATIVE_SESSION_UNAVAILABLE |
| execute(context,nativeSessionId,input,sink) | 同一 executionId/nativeSessionId、唯一 input:{text} → 等待真实文本输出/终态；不存在另一个输入正文参数或会话别名 |
| cancel(executionId) | 原执行 → cancellationRequested/alreadyTerminal/unavailable；发出信号不构成 cancelled |
| inspect(savedExecution) | 原持久执行/进程引用 → running、真实 terminal、可靠证明的 notInvoked 或 unknown；只读，不自动启动 Prompt/工具 |
| stop() | 停止新调用并核实托管进程退出；不能确认则明确报告并保留 unknown 占用 |

sink 的可生产业务部分只复用 HC-195 native.bound/running/文本 output/terminal 的闭合类型；Runner 生成并持久 messageId、runnerSequence 和完整来源头，sink 的 Promise 仅在 COMMIT 后成功，失败必须传播并有界停止。accepted 和本地控制事实由 Runner 产生，端口不能伪造另一用户输入或任意事件。工具/审批/问题的端口与线上类型待 HC-197/195 审查，不先塞一个空对象或 any 占位；产品未注入真实端口时 available=false。

prepareSession 也在 invoking 边界之后，响应丢失不盲目重建。首次 native.bound 的值与云端关联同值；原 start 的 null 不回写。已有非 null 绑定时，恢复必须返回同值，否则拒绝续聊并保留事实。历史回放只用于核对已有来源，不能再次追加为新输出；无法可靠关联时拒绝恢复，不把回放全文加到会话尾部。本稿不固定 ACP SDK 或替它实现生命周期。

### 7.2 项目端口（HC-199）

项目端口尚未注册线上联合，生产缺失时明确不可用。后续最小需求如下，供 HC-199 确定实际 DTO/同源 schema 后审查；本稿不提供接受任意 operation 对象的通用入口，不把表中概念字符串当已可执行命令。

| 业务 | 后续端口必须遵守的输入/结果边界 |
| --- | --- |
| 目录/文件只读 | Runner 已绑定根、相对路径和有界分页/读取范围 → 条目/编码/正文/实际截断与下一位置，不含外部路径 |
| Git 状态/Diff | 原项目及服务生成的审阅标识、选中相对路径 → 同审阅版本的实际 HEAD/变更/有界 Diff，过期明确冲突 |
| 选择提交 | 审阅标识、所选相对路径、提交说明 → 实际 SHA/警告或失败；只提交所选，保留原暂存策略/hooks/签名 |
| 非 force 推送 | 已确认提交 SHA、审阅标识 → 现有 upstream 实际结果，不接任意 remote/refspec |

Runner 在授权后解析本机根并提供占用；项目服务再核对路径穿越/符号链接、实际快照、HEAD/索引/upstream 等边界。Git 作者/凭据保留执行机器语义，平台操作人另记 requestedByUserId。已进入副作用后不能因超时换身份重做；具体请求/结果和未知恢复协议由 HC-199 确认，当前不造 any/默认成功。

### 7.3 同一目录的占用

同一真实或重叠根的 Agent 和 Git 写入共用 Runner 一个占用入口，别名不新建锁域。人工读取/状态查询在写入期间也返回 PROJECT_BUSY，避免中间状态被当成稳定审阅；不重叠项目可并行。同一会话仍由 HC-195 保证只有一项未收敛执行。Runner 不复制/重新排序云端用户输入；已受理 start 只等待本地占用，保持已受理待开始，取消/本地停止可以阻止首次调用。人工项目请求即时拒绝忙，不留待稍后执行。unknown 占用跨重启保留；用户外部 Git 不受此锁控制，项目服务仍须重验实际状态。

## 8. 双方状态怎样收敛

执行业务状态唯一归 HC-195，第 5 节决定只属该执行行，不是另一套状态机。设备可达、取消送达与结果确定性分别表达，不能压成一个 online/failed。

| 显示事实 | 设备侧遵守的收敛 |
| --- | --- |
| queued/等待原设备 | 云端已保存且未进入派发边界，离线不丢输入、不换目标；共同历史可读 |
| dispatching/可能已受理 | 首次 start 已保存，缺受理证明；超时/失联可 unknown，不能普通重排或换 ID |
| accepted/已受理待开始 | 本地受理已 COMMIT，可能等原决定或目录；不能据此显示 running |
| running | 来自真实端口的持久来源；后来失联只叠加失联，不凭连接状态制造终态 |
| succeeded/failed/cancelled/rejected | 真实端口终态或确切未调用证明；Java 连续提交终态后才推进后项；决定 deny 不等于该事实 |
| 取消待送达/停止中 | 原取消意图或 cancel.received 只描述送达；必须等同一原项真实终态 |
| unknown | invoking/运行或派发后无法核实，保留最后确认阶段及会话/目录占用；可信原终态可迟到收敛，不自动重跑 |

Java 重启保留原 start/cancel/运行决定、来源去重与队列；内存连接全部重新核对，UI 依 HC-194 失效但设备独立凭据仍可重连。是否重送只由 ExecutionRecovery.reconcile 判断：此前从未确认受理、当前完整同 ledgerId 明确 notFound 且授权/取消仍允许时，可重送原 start；已有 accepted/running 事实却本地声称 notFound 是冲突，不是重跑证明。cancelBeforeStart 已可按同源序列保存取消/终态，不要求重送 start 才补回执，更不能清掉取消。

本地已有决定时只核对/重传同一完整决定；缺决定时 Java 重传执行行原决定，不能按当前权限重造 allow/deny。原 allow 后发生的停用/停止共享不改变决定，也不挡住原设备真实输出的连续入库；本地已确认停止且尚未调用仍以持久禁止事实拒绝首次调用。deny、取消请求或凭据撤销均不能替代实际终态。

Runner 重启先取得单实例锁，核对账本与遗留进程，再恢复。PID 相同不等于同一原进程，无法确认归属/退出就 unknown；invoking 后不因没有 running 再调用。机器休眠/关机/断网不能接新云端工作，已开始项可继续记录，需要人工回答时等待重连、不默认批准。恢复上下文不自动重送旧 Prompt，不新建原生会话冒充续聊，不迁到另一机器同名项目。

unknown 只有原设备可信事实才能收敛；本任务不新增强制成功/失败、清队列、重跑未知副作用或解除目录占用入口。不能恢复的设备数据保留未知说明，不为清空列表伪造完成。首版无工具/审批线上形状时对应动作不可用。

## 9. 与 HC-195 的共同交界

本稿已按统筹八项裁定及计划输入修订，主要交界方向已通过，具体装配/夹具与 Plan/Todo 继续交统筹审查。本节只保留唯一职责/调用顺序，不留首轮双方案；本轮只读对方稿，不编辑或向对方聊天发消息。

### 9.1 HC-196 提供的端口

| 端口 | 完整输入 → 结果/错误及事务边界 |
| --- | --- |
| SharedProjectAccess.requireSharedTarget | `{userId,workspaceId,deviceId,projectId,agentConfigId,expectedShareVersion}`，expectedShareVersion 为 null 或标准十进制字符串 → `{deviceId,projectId,agentConfigId,shareVersion,deviceName,projectName,agentName}`。加入同一调用方 JDBC 短事务并锁设备/项目记录；未知/不属工作区 RESOURCE_NOT_FOUND、停止共享 PROJECT_NOT_SHARED、版本不同 SHARE_VERSION_CHANGED、设备撤销 DEVICE_REVOKED、登记目标不匹配 TARGET_INVALID。不把 offline/未 ready/端口暂不可用变成授权失败，不调用 WSS。首次运行决定把已知授权失败保存为 deny，而不是丢弃 accepted；既有获准结果补传不调用该新授权入口 |
| DeviceDelivery.sendStart/sendCancel | `{deviceId,connectionId,message}`，message 为同源固定 ExecutionStart/ExecutionCancel → written/offline/superseded；只检查当前 socket/连接并发送原文，written 不是受理。事务提交后调用，失败交 HC-195 核对，不改 execution 表。相同传输装配发送 HC-195 返回的原 start.decision/events.ack，不在设备域计算 allow |

SharedProjectAccess 的 userId 仍按 HC-194 同源 enabled/成员入口核对，不复制身份实现。展示快照不含路径/凭据。expectedShareVersion=null 用于首次选择当前目标；保存输入后 HC-195 固定该版本，派发/首次决定使用同一版本，不能替换为新共享版本重试旧输入。设备可达/端口可用是独立临时事实：HC-195 只在设备 ready/端口可派发时登记发送边界，离线仍允许保存共享会话和 queued。

### 9.2 HC-195 提供的端口与设备调用

| 端口 | 设备侧提供/消费与失败处理 |
| --- | --- |
| ExecutionDispatch.onDeviceAvailable | 恢复 ready 后传已认证 deviceId → 无业务数据的唤醒确认；只唤醒 HC-195 一个数据库调度器，不在设备域选择队首或建第二个扫描队列 |
| ExecutionReceipts.recordBatch | `{deviceId,connectionId,executionId,events}`，events 是外壳中同一执行的完整同源消息、有序且最多 64 条/256 KiB → `{ack:{executionId,lastCommittedRunnerSequence},startDecision}`，startDecision 为完整原决定或 null。HC-195 一笔事务登记来源、首次 accepted/决定、绑定/可见事件/状态及连续位置；返回后才送同源 ack/决定 |
| ExecutionRecovery.reconcile | 按 HC-195 唯一请求 `{deviceId,connectionId,ledgerId,executionId,startCommandId,startBodySha256,localState,storedDecisionMessageId,nativeSessionId}` 提交本轮可信事实 → `{action,ack,startDecision}`，action 仅 continueOriginal/resendSame/waitForEvidence/terminalSaved。status/inventory 的完整原消息用于核对；storedDecisionMessageId 只取 decision.messageId 或 null，不另生成决定引用。notFound 时原目标/指纹从 Java 已保存命令取得；所有绑定/终态仍须 recordBatch 入库，不能凭恢复摘要绕过来源事务 |

reconcile 的 localState 直接采用 HC-195 notFound/accepted/notInvoked/invoking/running/terminalPending/unknown 联合：本地没有决定/尚未调用为 accepted，决定已保存且能证明未调用为 notInvoked，已保存真实终态为 terminalPending（即便已收到旧 ack，仍供 Java 查核）。cancelBeforeStart 按同事务真实取消终态映射 terminalPending、决定引用 null；事实不明属于 unknown，不保留等待 start 的伪未终态分支。执行/原 start 摘要取已保存 start 或 cancel，不重造。

recordBatch/reconcile 的成功和错误联合唯一源归 HC-195 第 7 节：gap 带 expectedRunnerSequence/lastCommittedRunnerSequence，conflict/targetMismatch/bindingConflict/invalidTransition 保留占位并暂停该项，storeUnavailable 不确认。设备传输只映射这些闭合结果；source 内容或完整原决定矛盾不能自动修复。gap 从连续位置补原消息，不能先发后来的终态；数据库失败不默认 allow。决定/ack 丢失按原消息重传：accepted 即便已获前缀确认，只要本地还没有原决定，仍每 5 秒补发同一 accepted；其正文须保留到“已确认且原决定已本地提交”两项均满足，避免卡在已受理永远无决定。

### 9.3 事务、事实与后续接入

新保存/派发/首次决定按用户/成员 → 设备项目 → conversation → execution/request 的共同锁顺序；首次 accepted 同事务产生唯一决定，不能先锁执行再倒查授权。既有获准事实只取固定归属/会话/执行所需锁，不要求发起人仍启用。停止共享/设备撤销自身事务不反向取会话锁，提交后通知 HC-195 按共同顺序收敛 queued；授权生效不依赖通知及时。JDBC 事务不跨 WSS、模型或等待，任何业务失败整笔回滚，不半写后由传输补成功。

当前复核重点为：第 3 节精确 HTTP/版本语义、第 4 节外壳和恢复结束条件、取消先到的同源序列特例、决定/前缀丢失的补发，以及 recordBatch/reconcile 的实际装配和同一字节夹具。它们是统筹对照修订稿的检查项，不是仍可选用首轮旧协议。HC-197 的实际恢复/停止证明与 HC-199 的文件/Git 类型仍需各主责审查；未满足时不可用，不造工具/审批/项目 any 类型。

HC-198 后续通过 HC-195 的同一发送事务接入固定引用/交接，HC-196 只消费已保存的 input:{text} 和原目标；当前执行文本仍 32 KiB，不重新截取引用、不在网络派发后补关联，也不在本任务新增引用业务。
