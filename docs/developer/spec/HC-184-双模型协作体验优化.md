# HC-184 双模型协作体验优化规格

## 一、背景与目标

见 [Task](../task/archive/HC-184-双模型协作体验优化.md)。解决正常请求误拒绝和已停止任务占用，使安全确认在当前会话完成。用户授权的需求来源和未知操作的停止保护继续有效。

## 二、设计思路

原始消息由程序冻结 → Lead 填目标、步骤和路径 → Sidekick 经现有执行器完成 → 程序记录执行退出与操作停止 → 安全暂停让出目录 → 继续时重新取得目录和核对文件。

## 三、整体架构

| 模块 | 改造职责 |
| --- | --- |
| runtime/fusion/tools.py、roles.py | 移除模型填写 user_requirements；字段错误给出安全、可执行说明。 |
| runtime/fusion/service.py | 冻结完整需求；恢复前重新取得写者；保留检查、审阅门禁。 |
| runtime/fusion/store.py | 停止回执、闲置释放、幂等暂停、核查并取消的单事务。 |
| host/fusion_runtime.py | 真正退出后记录 Worker 停止；受控续接上次完整 checkpoint。 |
| host/agent_host.py | 管理取消入口接受停止核查说明，继续使用 RunCoordinator 停止与空闲锁。 |
| Protocol、CLI FusionFeature | 同步取消参数；当前会话解析占用者并按准确版本取消。 |

## 四、详细设计

### 4.1 派单与需求

fusion_delegate 的参数为 goal、brief、allowed_paths、check_plan_ids。删除 user_requirements，不保留旧参数别名。需求只能取自 Task 创建时保存的 source_message：单段保存为一项；明确的行首列表按原文边界拆分，最多 32 项，超出时将尾段作为完整一项保存，不能截掉要求。保存 id 和原文 quote，Lead 不能把实施建议写成用户要求。goal、brief 的空值仍拒绝；参数错误回复安全 JSON，指出字段及修正办法。路径与检查 ID 仍按现有规则检查。

### 4.2 写权限与停止事实

暂停、等待处理且没有 stopped=0 操作、没有 dispatched 派发的任务自动释放自己的写者，不取消任务、不回滚文件。获取目录时也清理同项目中这种旧闲置占用；跨项目、执行中、检查中、审阅中或真正未知的占用继续阻止并发。恢复已有轮次前必须重新取得 host 写者，取得失败改为占用等待。审阅证据仍核对当前快照，不能在别的写者修改期间沿用旧票据。

Worker 经 ManagedAgentExecutor 返回或抛错并完成退出收尾后，记录本轮派发 stopped；单独的命令是否停止仍以各自效果记录为准。若仍有不明命令，继续保持 OUTCOME_UNKNOWN。未知状态重复查询在事实未变化时不增加版本。

同一任务的整轮运行还保存 active_run={owner,run_id}。准备时用短事务取得归属；同 Host 的相同 Run 可幂等读取，其他窗口/Run 不能插入执行。归属与写权限用途不同：前者防止两窗口执行同一任务，后者防止不同任务并发写目录。Root 退出和准备失败时按准确身份清理归属；新空任务在受理前放弃则取消，已有任务暂停并保留；人工停止核查可清除崩溃遗留归属。查询不得把另一 Host 的运行改为未知；没有退出事实的 WORKER_RUNNING/CHECKING 不能直接续跑。首轮基线及恢复审阅快照均在取得目录后读取。任务终态不可被迟到回调恢复；已取消或被新 Run 接替的执行在下一次模型请求前停止，不再要求补报告。

### 4.3 中断后的上下文

记录 worker_checkpoint_interrupted，区分完整返回和中断。只有已明确停止或用户核查过的中断，才能加载 completed_checkpoint_id 指向的上一完整记录；禁止自动重放半轮待执行工具。若第一轮从未完成，保留文件和任务事实，清理这次半轮 checkpoint，并带完整任务单重新开始。非中断情况下丢失、篡改或不匹配的历史仍拒绝；未确认停止时不能清理 checkpoint。

### 4.4 当前会话处理占用

- /fusion resolve：刷新当前任务，按服务端 workspace_blocker 读取占用任务的当前版本，再调用既有取消入口；成功刷新当前任务，提示发送“继续”。
- /fusion resolve --stopped <核查说明>：用户确认旧操作全部停止后，在当前会话核查并结束占用任务。
- /fusion cancel --stopped <核查说明>：同样处理当前任务的未知状态，省去先 recover 再 cancel 的两次提交。
- /fusion recover 仍用于核查后继续原任务，语义与结束任务不同。

fusion.cancel 在现有 task_id、expected_version 外增加可选 stopped_inspection_note（1–4000 字符）。该字段只由用户显式 --stopped 输入，不能由模型或客户端自动生成。Host 先执行既有停止 Run 流程；Store 在一个事务中保存核查、结束任务、释放其写者。无说明且仍有不明操作时拒绝，不能按时间或进程不存在擅自释放。变化后的任务/占用者、跨项目身份和无说明的 --stopped 均拒绝。v3.11 未发布契约原地同步两端生成物和共享正反例，不增加数据库表或依赖。

### 4.5 连续失败与可见性

控制工具错误显示字段和下一步，并作为失败工具结果进入原有时间线。连续三次同一控制工具和错误、期间没有成功结果或新用户消息时，停止本轮并保存明确原因，避免模型反复猜参数。已公开输出后断流不会自动重放；执行退出明确且无未知命令时可直接继续，真正未知仍按核查路径处理。界面用中文解释断流及当前会话下一步，保留协议错误码。现有 Lead/Sidekick 实时分组、取消、检查状态和日志脱敏继续有效。

命令结果不明时，两角色立即结束模型循环；Worker 最终输出门禁允许结束本轮，不再因缺少报告请求模型，任务仍保持 OUTCOME_UNKNOWN。Root 退出时重新生成待查清单，已明确停止的派发不再显示为待查。

### 4.6 验证与影响

先失败测试，再实现。覆盖短需求、列表、尾段完整性、伪造参数、闲置和真实占用、租约代号、两任务竞争、取消模型等待、未知命令不释放、同处处理占用、原子核查取消、版本冲突、跨项目、正常返工及中断后续接、无真实密钥的 Host 闭环、Protocol 双端及 TUI/Web。执行相关与完整回归、类型、构建、协议、依赖、文档和任务检查；区分已有失败。审查结果写回 Task。
