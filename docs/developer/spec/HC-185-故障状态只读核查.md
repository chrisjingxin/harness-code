# HC-185 故障状态只读核查规格

## 一、背景与目标

见 [Task](../task/archive/HC-185-故障状态只读核查.md)。故障任务可以询问和读取证据；未知状态仅阻止写入，不应阻断解释与核查。

## 二、设计思路

用户新消息 → Host 根据持久化状态选择普通执行或只读核查 → 核查只暴露读文件与状态工具 → 返回已知事实、未知项和下一步；不变更停止记录或租约。另一路由状态查询统一返回当前任务及目录占用，避免只查当前会话造成误导。

## 三、整体架构

| 模块 | 职责 |
| --- | --- |
| FusionRuntime、FusionRunBinding、RunContext | Host 决定 inspection_only；只读运行不取得或清理任务 active_run，不占写租约、不恢复 Worker。 |
| roles、guard、service | 独立只读能力与提示；状态查询允许，写控制拒绝；自然结束不强制派单/报告。 |
| Store、Host、Protocol | fusion.status 返回必需的可空 workspace_blocker；跨项目仍隐藏身份。 |
| FusionFeature、RunFeature | 无当前任务仍解释目录占用；resolve 使用准确占用者；Fusion 拒绝在普通显示状态下也有中文说明。 |

## 四、详细设计

### 4.1 只读运行

已有任务为 OUTCOME_UNKNOWN 或 reason=workspace_busy 时，Host 固定本轮 inspection_only=true，不按用户措辞猜测是否允许写入。该标记仅在私有 Binding/Context 中传递，用户/模型不能指定。只读运行不调用 claim_run/resume/continue_pending，不取得写者，也不在结束或准备失败时释放其他运行的归属、删除 Worker checkpoint。Thread 本身仍使用普通 RunCoordinator 并发限制。目录占用先刷新；占用已解除则正常恢复。核查可以使用更新后的 Lead 配置，恢复写入仍要求原配置指纹一致。

Lead 能力只保留项目读取工具和 fusion_status，不暴露 ask_user、Shell、文件修改或其他控制。Service 在实际调用边界再次拒绝写控制；查询可读准确任务和占用事实，但不借其他运行的身份执行。Final gate 允许正常答复，Guard 不对只读核查套用“未知状态立即结束”的普通执行规则。连续三次同一工具拒绝（包括模型误选了未暴露的工具）时带说明结束，不更新任务。所有普通执行中的未知循环停止保护继续有效。

任务在读取中变化时保持本轮只读，不提升写权限。无法取得 PID 或停止证据时明确说无法确认，不能把超时记录等同于运行中的测试进程，更不能代替用户自动填写 --stopped。模型上下文说明实际命令工作目录、虚拟路径含义、同会话/其他会话的身份。

### 4.2 目录状态

fusionStatusResult 增加必需的 workspace_blocker，类型沿用现有 FusionWorkspaceBlocker，值可为 null；同步生成源及所有调用方，不保留旧响应形状。Store 从当前实际工作区读取目录写者，安全闲置按 HC-184 规则让出；本任务自己的写者不作为其他任务占用。其他项目只显示 owner_unavailable，不暴露会话身份。

CLI 将本次目录占用与 Thread 绑定缓存；刷新、解析及响应写回均检查当前 Thread/Task/占用者。无本会话任务而有占用时，显示占用事实和当前会话处理方法，不显示孤立的“没有活动任务”。resolve 可处理这种场景，仍按准确版本和用户明确停止确认取消。

### 4.3 命令目录

Worker 提示中给出真实工作目录，说明文件工具的 / 是虚拟项目根，而 execute 已在项目目录。Fusion 命令校验在副作用登记前拒绝显式 cd / 和以 / 为起点的 find（含嵌套 Shell）；带引号的 Python 普通字符串不误判，项目相对目录命令仍允许。返回 FUSION_COMMAND_INVALID 及目录纠正说明。

### 4.4 验证与范围

先观察失败测试。覆盖真实 Host 未知状态询问、占用状态询问、无模型写工具、写控制拒绝、无租约/归属/停止事实改动、已有活跃执行不受影响、取消与准备失败、状态无当前任务/跨项目、resolve 和异步身份、嵌套 Shell/引用数据。使用内存模型、虚构凭据和临时目录，不调用用户模型服务。更新用户指南、长期架构、完整回归及既有问题归因后交付单一停点 A。
