# HC-179 内网依赖源码化规格

关联 Task：[HC-179-内网依赖源码化](../task/HC-179-内网依赖源码化.md)。本规格只细化已确认的临时 Windows x64 内网预验证范围，不扩大目标包数量，也不改变正式 master 的依赖策略。

## 范围变更（2026-09）：npm 包管理器迁移

企业内网对 `bun install` 客户端做了网络限制：少量包可安装，本仓库约百条外部解析记录会触发限制导致安装失败；Bun 二进制本身在内网可用。因此 JavaScript 依赖的**安装器**从 `bun install` 迁移为 `npm`（`npm ci` / `npm install`），lockfile 从 `bun.lock` 迁移为 `package-lock.json`。**Bun 保留为运行时**：构建（`bun build`）、测试（`bun test`）、工程脚本（`bun scripts/…`）和 TUI 仍要求 Bun `1.2.19`。

命令映射：

| 阶段 | 原命令 | 新命令 |
|------|--------|--------|
| 冻结安装（deps:install） | `bun install --frozen-lockfile --registry <内网源>` | `npm ci --registry <内网源> --legacy-peer-deps` |
| 重新解析（deps:resolve） | `bun install --registry <内网源>` | `npm install --registry <内网源> --legacy-peer-deps` |
| JS lockfile | `bun.lock` | `package-lock.json` |

迁移约束：

- **peer 依赖策略**：仓库根 `.npmrc` 固定 `legacy-peer-deps=true`，且安装命令显式携带 `--legacy-peer-deps`。该模式不自动安装 peerDependencies，与 Bun 行为对齐，并规避 `typescript@^5`（`bun-ffi-structs` peer）与仓库 `typescript@6.0.3` 的 ERESOLVE 冲突。双写（.npmrc + 显式参数）防漂移。
- **版本事实源**：`packageManager` 字段改为 `npm@<精确版本>`（npm 工具链门禁读取）；Bun 运行时版本约束迁移到 `engines.bun = "1.2.19"`（`expectedBunVersion` 改读该字段，npm 对未知 engines 字段无操作）。`engines.node` 声明最低 Node 版本（20），`install.ts` 校验 node/npm 均满足。
- **overrides**：根 `package.json` 的 `overrides`（`fast-uri`）为 npm 原生字段，保留。
- **lock 生成流程**：开发机生成外网基准 `package-lock.json` 提交（供结构门禁与单测 fixture 对照）；内网首次 `deps:resolve` 在显式内网源下重新解析并替换为内网 URL 版本，审查后提交。冻结安装的 lock 来源校验（仅内网主机白名单）不变，公网 URL 的基准 lock 会被 freeze 模式拒绝，强制内网重解析。
- **vendored 五包 lock 语义**：`package-lock.json` 中五个目标包必须呈现为 workspace link 解析（`node_modules/<pkg>` 条目 `link: true`、`resolved` 指向 `third_party/npm/<pkg>` 相对路径），不得出现五包的 registry resolved 条目或嵌套 locator；npm 的 workspace 链接（POSIX symlink / Windows junction）经 `realpathSync` 校验后必须落在 `third_party/npm/`。
- **workspace 依赖声明改为精确版本**：npm 不支持 `workspace:` 协议（pnpm/yarn/bun 特性，npm 遇到即 EUNSUPPORTEDPROTOCOL）。CLI 的 `@opentui/core`、`@opentui/react`、`react-devtools-core` 与五包间运行时边（`core → bun-ffi-structs`、`core → core-win32-x64`、`react → core`）改为精确锁定 vendored 版本（`0.4.3` / `7.0.1` / `0.2.4`），`@za38/protocol`（私有包，registry 无版本）用 `*`。npm 在版本可被 workspace 满足时链接 workspace；实际解析仍由 lock link 条目与安装后 realpath 门禁 fail closed 保障，vendor_policy 禁止任何清单残留 `workspace:` 声明。
- **vendored 平台包移除 os/cpu**：npm 对带 `os`/`cpu` 的 workspace 成员在平台不符时直接 notsup 失败（生成与安装皆然，`--os`/`--cpu` 配置无法覆盖该校验）。vendored `@opentui/core-win32-x64` 清单移除 `os`/`cpu` 声明，使 macOS 开发机与 Windows 内网共用同一份平台全量 lock（lock 记录所有平台的 optional 包，macOS 开发继续从 registry 解析 darwin 原生包）；win32/x64 定位由 tarball provenance、`opentui.dll` 门禁与 deps:install 的 win32/x64 平台门禁保障。provenance normalizations 同步：三个 workspace 归一化条目移除（依赖字段回到 tarball 原值），新增 os/cpu 移除记录，三包 `directorySha256` 更新。

## 用户可观察行为

执行 `bun run deps:install` 或 `bun run deps:resolve` 时，Harness 先验证当前执行平台为 `win32/x64`，再验证 node/npm/uv/Python/Bun 工具链版本，然后验证五个本地发布目录、显式发布入口、provenance 和 frozen `package-lock.json`。五个目标包必须从 workspace 解析；其他依赖仍由显式内网 npm/Python 源解析。任何本地工件篡改、版本/平台错误、缺发布入口或 DLL、重复补丁、嵌套 registry locator 或 registry 回退均在联网和安装前返回非零错误。

npm 安装完成后，五个目标包还必须从 CLI 和包间真实消费者位置解析到各自的 `third_party/npm/` realpath；入口 `package.json` 和运行/声明文件必须存在。安装前没有 `node_modules` 时只运行静态门禁，不因缺少安装产物误报。

执行 `bun run deps:check` 时，除既有 Python/DeepAgents/Anthropic 检查外，还只读复核源码化 npm 包、实际 lock 解析和补丁证据。执行 `bun run deps:test` 时运行源策略、源码化包状态机和既有依赖回归测试。

## Canonical 目录和依赖契约

源码化包固定位于：

```text
third_party/npm/@opentui/core
third_party/npm/@opentui/react
third_party/npm/@opentui/core-win32-x64
third_party/npm/bun-ffi-structs
third_party/npm/react-devtools-core
third_party/npm/provenance.json
```

根 workspace 同时声明 `third_party/npm/*` 与 `third_party/npm/@opentui/*`。CLI 的 `@opentui/core`、`@opentui/react` 和 `react-devtools-core`，以及五包之间的运行时依赖边 `core → bun-ffi-structs`、`core → core-win32-x64`、`react → core` 精确锁定 vendored 版本（npm 的 workspace 链接语义，见「范围变更」），vendored `@opentui/core-win32-x64` 清单不携带 `os`/`cpu` 声明。OpenTUI import、JSX runtime、native loader 和其余非目标 optional package 保持发布内容语义。

为使发布包作为本地 workspace 安装而不引入第六个 vendor，`@opentui/react`、`bun-ffi-structs` 和 `react-devtools-core` 的源仓库开发期 metadata 不进入 consumer workspace lock；`@opentui/react` 保留精确的 `@types/react@19.2.14` 开发期类型依赖，确保从 vendor realpath 解析声明时 JSX 类型仍与 CLI 一致。所有 package.json 归一化及 `react-devtools-core` 的 `ws ^7 → 7.5.10` 修改必须在 provenance 中记录。发布目录中的 JS、声明、资源、README、完整 `dist/**` 和 tarball 自带许可证文件不得删减。

## Provenance 与门禁

`third_party/npm/provenance.json` 为机器可读真源，记录目标 `win32/x64`、每个包的 tarball URL、现有 lock integrity、MIT license、源码化目录相对路径和 `sha256-path-content-v1` 目录摘要，并记录根 patch 文件 SHA-256 与必要的 workspace 归一化。

目录摘要按排序后的相对 POSIX 路径、文件 SHA-256 和长度计算；因此文件内容、路径、完整 `dist/**` 或缺 DLL 的任何变化都会改变摘要。五个包还必须通过显式入口文件清单，不能只依赖对当前目录重新计算 hash。`normalizations` 中的 workspace 改写使用 `kind: "workspace-dependency"`、`package`、`field`、`before`、`after` 五个字段逐条记录，且集合必须与实际 vendored package.json 的 workspace 边完全一致；缺失、错误或额外漂移均 fail closed。`@opentui/core-win32-x64` 还必须声明 `os: ["win32"]`、`cpu: ["x64"]` 并包含非空 `opentui.dll`。root `patchedDependencies` 不得再包含 `react-devtools-core@7.0.1`；vendored package.json 必须声明 `ws: "7.5.10"`，且 provenance 必须能校验现存 patch 来源。

## 错误语义与非范围

门禁错误必须返回非零并指出包名和失败事实，不自动下载、修补、改写 lock 或退回 registry。npm 版本、node 版本与 `engines.bun` 的 Bun 版本任一不符时，与既有工具链错误同样在联网前 fail closed。`npm ci` 在 `package-lock.json` 与 `package.json` 不一致时本身即失败，不回退为 `npm install`。五包完整性检查不替代 Python 的 DeepAgents 补丁和零 Anthropic 检查；两套门禁都必须通过。

Bun 的职责边界收缩为运行时：`bun build`、`bun test`、`bun scripts/…` 与 TUI 运行不受本变更影响，但 `bun install` 不再是任何入口的一部分，仓库中不得残留引导 `bun install` 的文档或脚本。

本任务不包含：正式 master 的永久 vendoring、npm 之外的包管理器（pnpm/yarn）支持、端侧安装器改造（`scripts/install/` 尚未交付）、跨平台 native 包、浏览器 E2E、Windows 空缓存安装、TUI 验收、push、合并或发布。
