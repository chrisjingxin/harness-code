# HC-179 内网依赖源码化规格

关联 Task：[HC-179-内网依赖源码化](../task/HC-179-内网依赖源码化.md)。五个源码化包仍只服务临时 Windows x64 内网预验证；依赖同步入口扩展为 OpenTUI 已支持的 macOS、Windows、Linux 目标，不扩大源码化包数量，也不改变正式 master 的依赖策略。

## 范围变更（2026-09）：npm 包管理器迁移

企业内网对 `bun install` 客户端做了网络限制，且企业杀毒软件可能拦截 Bun 进程。因此 JavaScript 依赖的**安装器**从 `bun install` 迁移为 `npm`（`npm ci` / `npm install`），lockfile 从 `bun.lock` 迁移为 `package-lock.json`。Bun 精确固定为 `1.3.13`，只保留给当前无法由 Node/npm 等价替代的 OpenTUI/FFI、Bun bundler 与尚未迁移的 Bun 测试边界。

命令映射：

| 阶段 | 原命令 | 新命令 |
|------|--------|--------|
| 冻结同步（`npm run deps:sync`） | `bun install --frozen-lockfile --registry <内网源>` | `npm ci --registry <内网源>` |
| 更新锁并同步（`npm run deps:sync -- --update-lock`） | `bun install --registry <内网源>` | `npm install --package-lock-only --ignore-scripts --registry <内网源>`，校验锁后只做一次 `npm ci` |
| JS lockfile | `bun.lock` | `package-lock.json` |

迁移约束：

- **peer 依赖策略**：仓库根 `.npmrc` 固定 `legacy-peer-deps=true`。该模式不自动安装 peerDependencies，与 Bun 行为对齐，并规避 `typescript@^5`（`bun-ffi-structs` peer）与仓库 `typescript@6.0.3` 的 ERESOLVE 冲突。安装命令不再重复传递该参数。
- **版本事实源**：`packageManager` 字段声明精确 npm 版本，由测试核对声明本身；运行时只要求 npm `>=10`。`engines.bun = "1.3.13"` 声明唯一受支持的 Bun 运行时版本；`engines.node` 声明最低 Node 版本（20）。依赖安装前置校验 npm/uv/Python 的外部版本，Node 版本直接读当前进程，不为安装依赖而启动 Bun。
- **overrides**：根 `package.json` 的 `overrides`（`fast-uri`）为 npm 原生字段，保留。
- **lock 生成流程**：开发机在公网源下生成基准 `package-lock.json` 并提交。企业外冻结同步接受这份公网锁。企业内首次执行 `npm run deps:sync -- --update-lock`，在企业源下重新解析并替换为内网 URL，随后完成同步与验证，审查后提交。内网模式下，锁文件里的公网下载地址仍会失败，必须显式更新锁。
- **vendored 五包 lock 语义**：`package-lock.json` 中五个目标包必须呈现为 workspace link 解析（`node_modules/<pkg>` 条目 `link: true`、`resolved` 指向 `third_party/npm/<pkg>` 相对路径），不得出现五包的 registry resolved 条目或嵌套 locator；npm 的 workspace 链接（POSIX symlink / Windows junction）经 `realpathSync` 校验后必须落在 `third_party/npm/`。
- **workspace 依赖声明改为精确版本**：npm 不支持 `workspace:` 协议（pnpm/yarn/bun 特性，npm 遇到即 EUNSUPPORTEDPROTOCOL）。CLI 的 `@opentui/core`、`@opentui/react`、`react-devtools-core` 与五包间运行时边（`core → bun-ffi-structs`、`core → core-win32-x64`、`react → core`）改为精确锁定 vendored 版本（`0.4.3` / `7.0.1` / `0.2.4`），`@za38/protocol`（私有包，registry 无版本）用 `*`。npm 在版本可被 workspace 满足时链接 workspace；实际解析仍由 lock link 条目与安装后 realpath 门禁 fail closed 保障，vendor_policy 禁止任何清单残留 `workspace:` 声明。
- **vendored 平台包移除 os/cpu**：npm 对带 `os`/`cpu` 的 workspace 成员在平台不符时直接 notsup 失败（生成与安装皆然，`--os`/`--cpu` 配置无法覆盖该校验）。vendored `@opentui/core-win32-x64` 清单移除 `os`/`cpu` 声明，使 macOS、Windows、Linux 共用同一份平台全量 lock；win32/x64 定位由 tarball provenance 与 `opentui.dll` 门禁保障。其他 native optional package 保留 registry 发布元数据，由 npm 当前企业源安装，并在安装后按当前平台验证。

## 用户可观察行为

执行 `npm run deps:sync`（默认冻结同步）或 `npm run deps:sync -- --update-lock`（更新锁并同步）时，Harness 先验证当前目标属于 macOS/Windows/Linux 的 x64/arm64 支持矩阵（Linux 同时校验 `OPENTUI_LIBC`），再由 Node 脚本验证 node/npm/uv/Python 工具链版本，然后验证五个本地发布目录、显式发布入口和 `package-lock.json`。该链路不得启动 Bun。五个目标包必须从 workspace 解析；其他依赖使用本次选中的 npm/Python 源，企业外为公网，企业内为企业源。包名/版本/平台错误、缺必需入口或 DLL、重复补丁、嵌套 registry locator 或 registry 回退均在联网和安装前返回非零错误。任意源码内容的变更由 Git diff/评审负责，安装门禁不重复维护一份同仓库 Hash。

npm 安装完成后，五个目标包还必须从 CLI 和包间真实消费者位置解析到各自的 `third_party/npm/` realpath；入口 `package.json` 和运行/声明文件必须存在。当前平台对应的 OpenTUI native optional package 也必须存在，且版本、`os`/`cpu`（vendored win32/x64 由 provenance 代替）、入口和非空 `.dylib`/`.so`/`.dll` 与选择结果一致。安装前没有 `node_modules` 时只运行静态门禁，不因缺少安装产物误报。

执行 `npm run deps:check` 时，除既有 Python/DeepAgents/Anthropic 检查外，还只读复核源码化 npm 包、实际 lock 解析和补丁证据。执行 `npm run deps:test` 时运行源策略、源码化包状态机和既有依赖回归测试。

## Canonical 目录和依赖契约

源码化包固定位于：

```text
third_party/npm/@opentui/core
third_party/npm/@opentui/react
third_party/npm/@opentui/core-win32-x64
third_party/npm/bun-ffi-structs
third_party/npm/react-devtools-core
third_party/npm/provenance.json
```

根 workspace 同时声明 `third_party/npm/*` 与 `third_party/npm/@opentui/*`。CLI 的 `@opentui/core`、`@opentui/react` 和 `react-devtools-core`，以及五包之间的运行时依赖边 `core → bun-ffi-structs`、`core → core-win32-x64`、`react → core` 精确锁定 vendored 版本（npm 的 workspace 链接语义，见「范围变更」），vendored `@opentui/core-win32-x64` 清单不携带 `os`/`cpu` 声明。OpenTUI import、JSX runtime、native loader 和其余非目标 optional package 保持发布内容语义。

为使发布包作为本地 workspace 安装而不引入第六个 vendor，`@opentui/react`、`bun-ffi-structs` 和 `react-devtools-core` 的源仓库开发期 metadata 不进入 consumer workspace lock；`@opentui/react` 保留精确的 `@types/react@19.2.14` 开发期类型依赖，确保从 vendor realpath 解析声明时 JSX 类型仍与 CLI 一致。所有 package.json 归一化及 `react-devtools-core` 的 `ws ^7 → 7.5.10` 修改必须在 provenance 中记录。发布目录中的 JS、声明、资源、README、完整 `dist/**` 和 tarball 自带许可证文件不得删减。

## Provenance 与门禁

`third_party/npm/provenance.json` 记录五个源码化工件的来源元数据：每个包的 tarball URL、基线 lock integrity、MIT license、源码化目录相对路径，以及必要的 workspace 归一化和 patch 来源说明。其中目标 `win32/x64` 只描述 vendored native 工件，不限制依赖同步的执行平台。tarball URL 与 integrity 只作来源记录，安装门禁不把它们和脚本常量再对一遍。

不再为目录或 patch 文件另存 SHA-256：预期值与内容同在一个 Git 仓库，不是独立信任锚点，却会将 Windows CRLF 等正常检出差异误报为篡改。Git 记录与评审负责内容完整性；安装门禁直接检查包名、版本、license、显式入口、workspace 依赖边、lock 解析和非空原生库。`@opentui/core-win32-x64` 的 workspace 清单必须移除 `os`/`cpu` 以允许跨平台生成和安装同一 lock，但 provenance 目标仍须为 `win32/x64`，且非空 `opentui.dll` 必须存在。root `patchedDependencies` 不得再包含 `react-devtools-core@7.0.1`；vendored package.json 必须声明 `ws: "7.5.10"`。

## 错误语义与非范围

门禁错误必须返回非零并指出包名和失败事实，不自动下载、修补、改写 lock 或退回 registry。依赖安装使用的 npm、node、uv 或 Python 版本不符时，在联网前 fail closed；Bun 版本由真正启动 Bun 的 CLI/构建/测试边界校验，依赖安装链路不为此创建 Bun 进程。`npm ci` 在 `package-lock.json` 与 `package.json` 不一致时本身即失败，不回退为 `npm install`。五包完整性检查不替代 Python 的 DeepAgents 补丁和零 Anthropic 检查；两套门禁都必须通过。

Bun 的职责边界收缩为运行时：OpenTUI/FFI、`bun build` 与尚未迁移的 Bun 测试仍可作为 npm script 的内部实现，但普通工程脚本应优先使用 Node 标准库；`bun install` 不再是任何入口的一部分。

## 范围变更（2026-09）：npm 统一命令入口

用户和开发者执行仓库任务时统一使用 `npm run <script>`。根脚本之间的组合必须使用 `npm run`，跨 workspace 调用使用 `npm --workspace <name> run <script>`；不得再把 `bun run` 当作包脚本调度器。

Bun 只保留在无法仅靠 npm/Node 直接替代的运行时边界：

- `bun packages/cli/src/index.ts`：CLI/TUI 本身以 Bun 运行；
- `bun build` / `Bun.build` / `Bun.write`：当前构建链使用 Bun bundler；
- `bun test` 与 `bun:test`：现有 TypeScript 测试框架；
- `bun scripts/…`：脚本直接使用 `Bun.*`、`import.meta.dir/main` 或依赖同一 Bun TypeScript loader；
- `bun:ffi` 与 OpenTUI native runtime。

因此 `npm run deps:sync` 是唯一 canonical 依赖同步入口，`--update-lock` 是它的显式更新模式。依赖工具链使用原生 `.mjs`、`node:child_process` 和 `node:test`，不新增 `tsx` 等脚本运行器；`deps:sync`、`deps:check`、`deps:test` 与 `test:py` 的完整调用链不得启动 Bun。

根目录和自有 workspace（根、`packages/cli`、`packages/protocol`）的 scripts 不得出现 `bun run`；第三方源码化发布包保持上游内容，不为统一风格改写其开发脚本。README、用户文档和当前工程文档必须以 `npm run` 展示仓库命令；历史 Task/Plan 的执行证据不做机械篡改。

本任务不包含：正式 master 的永久 vendoring、npm 之外的包管理器（pnpm/yarn）支持、端侧安装器改造（`scripts/install/` 尚未交付）、新增 vendored 跨平台 native 包、浏览器 E2E、各平台空缓存安装、TUI 验收、push、合并或发布。

## 范围变更（2026-09）：依赖工具链零 Bun

企业杀毒软件会拦截 Bun 执行，因此“用 npm 暴露命令、内部仍启动 Bun”不满足依赖安装场景。第一个收缩停点只迁移依赖工具链，不改变 OpenTUI 的 Bun 运行时：

- `scripts/dependencies/` 的 JavaScript 入口和策略模块改为 Node 可直接执行的 ESM（`.mjs`）；进程调用使用 `node:child_process`，路径解析使用 `import.meta.url`。
- 依赖策略测试改用 Node 内置 `node:test` 与 `node:assert/strict`，不得新增测试框架或 TypeScript loader。
- `deps:sync`、`deps:check`、`deps:test`、`test:py` 的根 scripts 不得包含或间接执行 `bun`。
- 依赖安装前置不再读取或执行 Bun 版本；`engines.bun = "1.3.13"` 仍是 CLI/构建/测试边界的精确运行时契约。
- 本停点不迁移 `dev`、CLI 构建或 CLI 的 `bun:test` 测试；这些仍属于后续的 Bun 岛收缩工作。

## 范围变更（2026-09）：复用工具已有企业源

企业外和企业内使用同一条安装命令，源跟着本机 npm/pip 配置走，不把公网开发机挡在门外。`deps:sync` 的两种模式按以下顺序解析来源：

1. npm 使用 `npm config get registry` 的当前有效值；Python 优先使用 `PIP_INDEX_URL`，否则读取 `python -m pip config get global.index-url`。
2. 已有 uv 环境配置可作为 Python 工具配置继续使用。
3. 工具配置缺失时使用公网默认源：`https://registry.npmjs.org/` 与 `https://pypi.org/simple`。工具配置仍指向公网、同时设置了内网 `HARNESS_NPM_REGISTRY` / `HARNESS_PYPI_INDEX` 时，这一次安装改用内网源。
4. 一边已经是内网源时，另一边缺失不会默认为公网。最终地址必须是无内嵌凭据、无 query/hash 的 HTTP(S) 地址。
5. 锁文件只核对包的下载地址。公网模式接受 `registry.npmjs.org`、`pypi.org` 和 `files.pythonhosted.org`；内网模式拒绝公网下载地址。funding、仓库主页等非下载链接不参与这个判断。

脚本把最终选中的源显式传给 npm/uv，确保重新解析与冻结验证使用同一来源。`HARNESS_PYPI_ARTIFACT_HOSTS` 仍只用于允许 Python simple index 之外的内网制品主机。

## 范围变更（2026-09）：单一依赖同步入口

用户只需要记住 `npm run deps:sync`。该命令默认执行冻结同步：验证现有 lock 来源，使用 `npm ci` 与 `uv sync --locked` 安装 JavaScript/Python 依赖，应用 DeepAgents 补丁并完成依赖门禁与 runtime smoke，不修改 lockfile。

只有在依赖声明或企业源发生变化时，用户执行同一个入口的显式模式 `npm run deps:sync -- --update-lock`。该模式先用 `npm install --package-lock-only --ignore-scripts` 与 `uv lock --refresh` 更新两个 lockfile，校验锁之后只做一次 `npm ci`，再完成相同的最终验证，因此不得要求用户随后补跑第二条安装命令。

不得在默认模式检测到 lock 不一致后自动更新 lock；这类情况必须失败，并提示显式使用 `--update-lock`，避免普通安装悄悄改变传递依赖或下载来源。旧 `deps:install` / `deps:resolve` scripts 直接删除，不保留 alias。

## 范围变更（2026-09）：停点 B 工程工具零 Bun

Protocol 生成与校验、Task 状态管理、文档检查、版本同步、发布检查和项目检查属于普通工程工具，不依赖 OpenTUI、FFI 或 Bun bundler。以下根命令及其 workspace/子进程调用链不得启动 Bun：`protocol:generate`、`protocol:check`、`test:project`、`docs:check`、`tasks:sync`、`tasks:check`、`task:claim`、`task:complete`、`version:set`、`release:check`、`project:check`。

现有工程工具继续保留 TypeScript 源码，使用仓库已锁定并在根清单直接声明的 TypeScript，由一个 Node ESM loader 转译 `.ts` 并在语法错误时失败；不得新增 `tsx`、`ts-node` 或测试框架。工程测试从 `bun:test` 迁移到 `node:test` 与 `node:assert/strict`。脚本中的 `import.meta.dir` / `import.meta.main` 改用 Node 标准库等价实现，生成内容和错误语义保持不变。协议与 Diagnostic Log 的生成检查和 sidecar 摘要在比较前去掉回车，Windows 检出的 CRLF 不视为内容变化。

停点 B 不迁移 CLI/OpenTUI 运行、Bun bundler、CLI 测试或 E2E；这些属于停点 C 的 Bun 孤岛边界。验收必须包含 manifest 契约、工程工具回归、Protocol 生成结果校验，以及在 PATH 中放置失败假 Bun 后运行代表性工程命令，证明 npm 外壳内部也不会启动 Bun。

## 范围变更（2026-09）：停点 C Bun 收敛到 CLI 孤岛

根 `package.json` 只负责 npm workspace 编排，不得直接执行 `bun`。`npm run dev -- <参数>` 必须通过 `npm --workspace @za38/cli run dev -- <参数>` 保持参数透传；构建和 CLI 测试继续通过同一 workspace 入口调用。仓库自有 manifest 中可以直接执行 Bun 的脚本精确限定为 `packages/cli` 的 `dev`、`build`、`test`：运行路径依赖 OpenTUI/`bun:ffi` 与 `Bun.serve`，构建路径依赖 `Bun.build` / `Bun.write`，现有 CLI 测试依赖 `bun:test` 与 Bun 测试 API。

`syntax:assets` 只是维护期下载、哈希和文件生成，不依赖上述专属能力，必须改用 Node 标准库；不得仅因文件位于 `packages/cli` 就继续保留 Bun。活动 README、用户文档、AGENTS、工程与架构文档统一展示 npm 根入口；历史 Task/Spec/Plan/Todo 证据与 `third_party/npm/**` 上游内容不机械改写。

仓库当前没有 `scripts/install/` 或 Unix/PowerShell 全局安装器，停点 C 只记录审计结论，不创建未交付的安装器。未来若新增全局安装器，JavaScript 包安装必须使用 npm；Bun 仅作为 CLI 运行时前置。浏览器 E2E 已使用 `npx playwright`，本停点不改其行为，也不执行目标 Windows/TUI/E2E 验收。

## 范围变更（2026-09）：跨平台依赖同步

`deps:sync` 的执行目标与 OpenTUI `0.4.3` native loader 保持一致：`darwin/{x64,arm64}`、`win32/{x64,arm64}`、`linux/{x64,arm64}`。Linux 未设置 `OPENTUI_LIBC` 或设置为空/`glibc` 时选择 glibc 包，设置为 `musl` 时选择 musl 包；其他值失败关闭。其他操作系统和架构在联网前失败。

`@opentui/core` 的八个 native optional dependency 都必须精确固定为 `0.4.3`，平台全量 `package-lock.json` 必须保留对应直接记录。只有 `@opentui/core-win32-x64` 是 vendored workspace；另外七个包必须来自当前 npm 企业源，不允许为了跨平台支持新增源码副本或公网回退。npm 安装后按实际平台选择一个包并校验其身份、发布入口和原生库；Linux musl 选择与 OpenTUI 的 `OPENTUI_LIBC` 语义一致。

`npm run deps:test`、`npm run test:project`、`npm run project:check` 等 Node 工程测试在 macOS 上直接运行。根 `npm run test` 仍会转发到 `packages/cli` 的 Bun 测试边界；“通过 npm 入口执行”不等于 CLI/OpenTUI 已脱离 Bun。

## 范围变更（2026-09）：安装门禁按当前平台收敛

`deps:sync` 和 `deps:check` 只阻断当前平台无法安装或实际解析错误，不再因 Windows 上缺少 macOS/Linux 的 native lock 记录而失败。五个源码化包的身份、版本、许可证、必需文件、workspace 依赖边、防 registry 回退、当前平台 native 包和安装后 realpath 仍须 fail closed。

门禁分为三层：

1. **源码快照**：验证五个 vendored 包的身份、版本、license、必需文件和 workspace 依赖边；不计算目录或 patch Hash，Windows CRLF 不会影响结果。
2. **当前平台安装**：冻结同步只要求 package-lock 中五个 vendored workspace link 和当前平台 native 记录有效；Windows x64 的 native 本身就是 vendored link。
3. **全平台审计**：`deps:test` 额外校验 provenance 元数据和八个 OpenTUI native 目标的完整 lock 矩阵，防止提交损害其他平台。

`deps:sync -- --update-lock` 在更新锁前只验证源码快照，不用旧 lock 的缺失阻止修复命令。锁文件写完后先验证当前平台 lock 与来源，再做一次 `npm ci`；安装路径在这次安装之后检查。
