# 返工权限恢复修复规格

## 一、背景与目标

Lead 的返工请求有两处容易被误拦截：重复列出原路径被当作扩权；暂停后使用自然语言提出修复要求被当作只读查询。目标是让原有授权能继续使用，并确保新反馈在执行前被处理。

## 二、设计思路

返工路径 → 规范化 → 判断是否超出原范围 → 仅真正扩范围时要求理由 → 申请新一轮权限 → Sidekick 执行。

暂停后输入 → 区分查看、继续原操作、提出新修改 → 查看保持只读；继续恢复保存的操作；新修改交给 Lead 先处理，随后派单。

## 三、整体架构

| 模块 | 改造内容 |
| --- | --- |
| runtime/fusion/service.py | 使用已有路径覆盖规则判断实际新增范围；保持原轮次授权失效机制 |
| runtime/fusion/followup.py | 集中识别明确继续和返工指令，普通问题与否定语句不恢复执行 |
| host/fusion_runtime.py | 暂停排队后允许明确返工；冻结本轮是否恢复旧操作 |
| host/run_execution.py | 仅明确继续原操作时，才在模型执行前补完已保存派单或检查 |
| 角色提示、工具说明、用户指南 | 说明同范围返工、带新要求返工和停止核查的区别 |

## 四、详细设计

### 1. 路径与权限

- 空列表、原路径、重复原路径、已授权目录中的子路径，都沿用原任务单，不要求扩权理由，不增加 revision（任务单版本）。
- 先规范化全部输入；绝对路径、越界路径、内部目录、符号链接等仍拒绝，不因原范围是 ./ 而放行。
- 新文件不在原范围内，或从单文件改为父目录，都属于扩范围；必须提供 reason，增加任务单版本并重新申请完整范围。
- 每次实际返工都产生新的 generation（本轮权限代号），旧轮权限不能继续提交。

### 2. 暂停后的输入

- “继续”“继续等待”“继续返工”等明确且没有新内容的继续指令，恢复已保存、确认安全的原操作。
- “继续返工，把问题修好”“请修复 a.py 的边界问题”等具体修改指令，恢复 Lead 的派单工具，先处理新反馈；不自动重放旧派单或旧检查。
- 查看、疑问、否定、引用的指令、先检查再决定是否继续，均不因包含“继续/返工”而恢复排队。
- 判定采用本地明确规则，不增加模型调用；不能识别的普通表述仍可用“继续”或明确返工指令。
- OUTCOME_UNKNOWN 始终只读，任何继续或返工文字都不能代替停止凭据。当前仍在等待的运行保持现有独占控制。

### 3. 验收与边界

- 真实 Host 和 Sidekick 图使用原生 read_file/edit_file/write_file，覆盖四种审批模式、原范围、扩范围和检查失败后返工成功。
- 服务测试覆盖目录包含关系、规范化、真正扩权、版本不增加而权限代号更新。
- 准备与运行测试覆盖自然语言返工、查询、否定、未知状态以及带新反馈时不执行旧操作。
- 不改协议、数据库结构、模型配置；不自动批准工具，不放宽 Plan 限制，不修改真实用户任务。
