## 1. 用户结果与完整流程

用户在本人会话提出开发需求时，Agent 自动看到当前 Team 的知识标题，相关时读取具体规范，并结合本机项目记忆继续工作。团队知识适用于普通开发任务和跨机引用。

A 在对话里提到 `../billing/src/config.ts`，后面又说「旁边那个结算工程」。B 引用这段对话后，B 的 Agent 阅读共享原文，结合 B 自己的项目记忆判断涉及哪些工程。能找到 B 的本机副本就继续，存在歧义就询问 B。确认过的新信息记入 B 的文档，后续对话可以复用。

本文中的 **Team** 对应现有 **Workspace**。**Project** 是团队内的协作事项，例如「支付联调」，可以涉及订单和账务两个仓库。同一仓库也可以被多个 Project 关联。 [现有协作模型](../architecture/多人协作工作台顶层设计.md)

```text
A 正常使用自己的本机会话，形成可共享的定稿
  → B 主动采用 A 的固定引用原文
  → B 发送消息，桌面完整附带 B 当前 Team 的两份简短 Markdown 正文
  → B 当前 Agent 阅读完整记忆，理解工程线索，按需查团队知识和规范
  → 信息仍不明确时询问 B，缺本机目录时请 B 选择
  → B 当前 Agent 在本机继续工作，并提交新事实
  → 桌面核对后更新 B 的 team.md、personal.md
  → 后续发送和查询使用已经保存的新内容
```

团队知识库继续由用户维护，A 保存后 B 的列表按既有通知刷新。AI 可以读取相关知识，再归纳到自己的本机记忆。项目级与团队级踩坑作为团队“经验”级知识经审核共享，由 [HC-241](../task/HC-241-知识分级与审核沉淀.md) 承接。 [团队知识读取与刷新](#5-团队知识自动目录与读取)

两份本机 Markdown 是类似 AGENTS.md 的简短概览，保存工程关系和本人目录，每次发送完整提供当前有效正文。桌面按账号和 Team 确定文档范围，内容与当前需求的关系由 Agent 理解。用户维护的知识库提供团队共享的规约、术语和说明，继续使用标题目录与按需读取。工程目录已经找到时，Agent 开发接口仍可发现并读取「接口错误码规范」。

## 2. 存放位置与身份隔离

每个「服务实例 × 登录账号 × Team」独立保存一对 Markdown。服务实例沿用桌面的规范服务来源，由主进程计算目录标识。账号和 Team 使用平台稳定 ID，名称变化后继续使用原文件。

```text
~/.harness/workbench/project-memory/
  <服务实例标识>/
    <账号 ID>/
      <Workspace ID>/
        team.md
        personal.md
```

`~` 取操作系统用户主目录，macOS 和 Windows 使用各自的本机路径。两份文件由桌面读写，保存在本人电脑。

会话新建时记录选中的 Team，已有团队绑定不随侧栏切换或加入其他团队改变。无团队会话在发布前不读取、注入或写回团队记忆；本人主动将其发布到有权访问的活跃 Project 并确认后，允许显式绑定目标 Workspace。绑定成功后的下一次主动发送开始使用该账号、目标 Team 下的两份文档，后续写回归这个 Team。发布操作本身只改变绑定与共享状态，不自动启动 Agent；正在运行的轮次保留其发起时的资料范围。停止共享后保留已有 Team 绑定。带团队的个人会话与 Project 会话使用相同记忆规则，离开原团队后撤销相关知识和记忆访问。本机会话与发布行为由 HC-239 处理。

| 场景 | 读取、注入和写回规则 |
| --- | --- |
| 同一台电脑从 A 切到 B | 只加载 B 在当前 Team 的文件。登出使 A 的待处理结果和工具访问失效。 |
| A 加入两个 Team | 分别保存两对文件。每轮完整附带该会话所属 Team 的两份有效正文，更新也归这个 Team。 |
| 在侧栏切换 Team 时旧轮次仍运行 | 旧轮次保持原来的范围，写回前复核账号和原 Team 的权限。新页面使用新 Team 的资料。 |
| 恢复本人原有会话 | 复用该账号、Team 和会话的原生 Agent 绑定，下一次发送附带当时可读的记忆版本。 |
| 某个 Team 首次使用 | 从当前可见的 Project、团队仓库登记和已有本人会话目录记录初始化。 |
| 无团队会话主动发布到 Project | 由本人确认绑定目标 Workspace；下一次主动发送读取本人在目标 Team 的两份文档，发布前的无团队轮次不产生团队记忆提案。 |

范围由桌面主进程从当前登录身份和真实会话绑定取得。读写工具、缓存、暂存更新及原生会话恢复都使用这组范围。账号切换后，已离开的账号产生的迟到结果直接丢弃。 [现有个人状态隔离](../../../desktop/src/main/personal-store.ts) · [原生会话绑定](../../../packages/acp-runtime/src/native-binding.ts)

完整注入的范围是当前服务实例、登录账号、会话所属 Team 下仍有权读取的两份业务正文。团队仓库与 Project 关联沿用服务端登记，源自会话的事实保留来源 Project，读取前复核当前权限。权限范围内的正文全部附带，不按当前 Project、工作目录或提问关键词再筛选工程。跨机器引用继续采用用户主动取得的固定快照。 [项目权限与固定快照](../architecture/多人协作工作台顶层设计.md)

## 3. 两份 Markdown 记录什么

| 文件 | 条目类型 | 内容与来源 |
| --- | --- | --- |
| `team.md` | 团队 Project | Project 名称、用途、相关 Project、涉及的仓库 ID。平台登记提供标识，当前 Agent 从已读材料归纳用途和关系。 |
| `team.md` | 团队仓库 | 仓库名称、简称与别名、用途、团队 Git 地址、关联 Project。复用现有 `repositoryId`。 |
| `personal.md` | 本机工程副本 | 本机根目录、相对路径、本人副本 Git 地址、对应团队仓库和 Project。目录由用户选择、实际 Git 配置和本人会话记录确认。 |

A、B 各自积累本机文档。共享的工程别名和规约通过团队知识库提供，成员读取后可以在本机记忆里记录来源。 [现有团队仓库类型](../../../packages/collaboration-client/src/types/organization.ts)

### 3.1 简短正文与维护字段

两份 Markdown 是本地记忆的持久化文件。正文采用简短的普通 Markdown：每个工程用一两句概括用途与关系，并保留必要的仓库地址和本人目录映射。正文持续整理同一份当前事实，不追加历轮对话、工具输出或修改流水。

文件头使用 YAML 保存 `formatVersion`、`documentRevision`、`updatedAt` 及各条目的维护字段。查询与更新工具使用这些字段核对身份、来源和版本，桌面同步渲染对应的简短正文。维护字段留在这两份文件内，不另建一份 JSON 持久化文件。注入模型的是两份文档的完整业务正文；文件头的技术维护字段通过工具按需查询。

| 维护字段 | 业务含义 |
| --- | --- |
| `entryId`、`entryRevision` | 主进程生成的本地条目标识和修订号。每次实际修改后递增，用来识别过期更新。 |
| `kind` | `team_project`、`team_repository`、`personal_directory` 中的一种。 |
| `name`、`summary`、`aliases` | 工程名称、一两句用途说明、对话中常用的简称。 |
| `projectIds`、`repositoryId`、`repositoryIds`、`relatedProjectIds` | 已有平台关系。Project 条目用 `repositoryIds` 关联多个仓库，仓库和个人副本用 `repositoryId`。普通非 Git 工程允许没有仓库 ID。 |
| `remoteUrl`、`upstreamUrl` | 实际 Git 远端和团队上游地址。个人 fork 分别记录本人的远端与团队上游。 |
| `rootPath`、`relativePath` | 个人目录的固定路径基准及相对目录。`~` 从当前电脑的系统用户主目录解析。 |
| `sources`、`confirmedAt` | 来源记录及最近确认时间。来源可指向 Project、仓库登记、本人会话、固定快照、知识版本或用户确认。 |

下面分别展示两份文档的业务正文示例。修订号、条目标识、来源等维护字段由桌面管理，不混入这段概览。

`team.md` 正文示例：

```markdown
# 团队工程概览

## 支付联调
涉及账务服务与结算服务，完成支付后的记账和结算。

## 账务服务（billing、账务工程）
负责账务记账，与结算服务协同完成支付流程，参与支付联调。
团队仓库：https://git.example.com/team/ledger-service.git
```

`personal.md` 正文示例：

```markdown
# 个人工程目录

## 账务服务
对应团队账务工程 billing，参与支付联调。
本机根目录：~；相对目录：dev/ledger-service。
本人仓库：https://git.example.com/b/ledger-service.git
团队上游：https://git.example.com/team/ledger-service.git
```

同一仓库的多个本机副本分别记录。其他盘符下的工程使用用户选定的本机根，例如 `D:/work`。普通非 Git 目录按用户确认的目录与工程关系保存。

平台已有的项目和仓库登记可以直接生成对应记录。会话中新出现、尚无平台登记的工程先以本地 `entryId` 保存已知名称、用途和来源，待确认仓库或 Project 后补齐关联。本人历史会话的目录记录在被打开或使用时逐步核对、补齐。单条维护记录的保存上限仍为 4 KiB UTF-8，正文使用简短概括。

### 3.2 在生成和更新阶段控制篇幅

两份业务正文合计上限为 **8 KiB UTF-8**。初始化、用户确认保存和 AI 更新时，桌面根据拟合并结果检查正文长度。这个限制用于约束写入后的文档篇幅；发送时完整附带有效正文。

当前 Agent 在本轮归纳新信息时，同时精简重复描述和冗长措辞。保留已确认的工程身份、用途、关系、仓库地址与本机路径，地址和路径保留准确值。超出上限时，更新工具返回 `error` 及需要精简的原因，原文件保持有效内容。Agent 可用当前轮次简化表述后重新提案；确实无法容纳时展示超限原因，留待调整篇幅约定。

发送端不按关键词、当前目录或 Project 相关性删减工程，也不截断正文尾部。文件暂不可读或现有总输入限制无法容纳两份完整正文时，明确反馈本轮记忆未能完整附带，普通消息按现有规则处理。团队知识标题目录继续按第 5 节独立组织。

## 4. 模型、ACP 和本机工具如何配合

模型配置沿用用户当前所选 Agent 的配置。B 的当前 Agent 负责理解共享原文中的工程线索、决定何时查询、归纳新事实。桌面使用普通代码读文件、查现有接口和合并更新。 [MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)

本机 MCP 工具服务由桌面工程实现并随应用管理。创建或恢复支持该能力的 Agent 会话时，桌面将工具连接配置经标准 ACP 交给 Agent。服务访问绑定当前会话的账号和 Team，登出或绑定失效时撤销。工具返回资料后，由同一个 Agent 继续处理。同一个会话工具服务提供本地记忆查询、更新提案，以及团队知识列表和正文读取。各工具按自身职责校验，服务的临时凭据绑定当前本机会话。

### 4.1 每轮自动附带的内容

用户主动发送本机会话时，桌面通过现有 ACP `session/prompt` 文本块附带使用说明，以及当前账号、会话所属 Team 下 `team.md` 和 `personal.md` 的完整有效业务正文。B 引用 A 时，完整附带的是 B 自己的两份文档。 [桌面发送入口](../../../desktop/src/main/local-execution-coordinator.ts) · [ACP 文本内容](https://agentclientprotocol.com/protocol/v1/content#text-content)

使用说明采用 Skill 式的简短指引。Agent 先阅读完整本机记忆，按需查团队知识，仍有歧义时问用户。处理开发任务时，也按标题发现并读取相关的团队规范。每次用户发送都附带第 7.1 节的更新指引，当前 Agent 在取得新增或被纠正的项目事实后、结束本轮回复前按条目调用更新工具。两份 Markdown 正文作为具名参考文本附带；正文内容按普通资料处理，目录授权继续使用现有端口。

| 首版约定 | 具体规则 |
| --- | --- |
| 完整正文与篇幅 | 每次发送完整附带两份有效业务正文。合计 **8 KiB UTF-8** 上限在生成和更新时检查，固定使用说明单独保存。 |
| 逐轮更新提醒预算 | 第 7.1 节的固定精简模板最多 **256 字节 UTF-8**。详细参数与处理规则由工具定义和桌面逻辑承担，其他材料继续使用各自预算。 |
| 注入范围 | 按当前服务实例、账号、会话所属 Team 与权限确定两份文档范围。范围内的全部工程信息完整附带，由 Agent 理解与当前任务的关系。 |
| 正文完整性 | 不按提问关键词、当前 Project 或工作目录筛选、排序取舍或裁剪正文。按文档原有顺序附带，自动记忆不使用 `hasMore` 表示遗漏工程。 |
| 与团队知识目录共存 | 第 5 节的知识标题目录单独使用 8 KiB UTF-8 预算，最终发送还需满足现有总输入上限。用户原文、主动引用和附件优先；两份记忆正文无法完整附带时，明确提供实际状态。 |
| 更新时机 | 首次发送和恢复后的每次发送都读当前有效版本。落盘更新在下一次发送或工具查询时可见。 |
| 发送前检查 | 读取后再次核对登录代次、Team 和 Agent 绑定。两份文档为空或暂不可读时，普通消息仍可发送，并提供实际可用状态。 |

自然语言里的工程关系和当前任务相关性由 B 的 Agent 判断。桌面负责当前身份下两份简短正文的完整装配。即使本轮没有明确写出某个工程名，该工程已记入文档的信息仍会提供给模型。共享原文保留原有路径与上下文，工作台显示和 Java 上传中的用户消息使用用户原始文字。 [ACP 发送实现](../../../packages/acp-runtime/src/session.ts)

### 4.2 本地记忆工具约定

下面两个工具运行在桌面提供的 MCP 服务内。工具范围由真实会话绑定决定，输入只描述要查找或更新的条目。工具结果使用现有工具卡呈现。

| 工具 | 输入 | 输出与行为 |
| --- | --- | --- |
| `query_project_memory` | 可选 `query`、`repositoryId`、`entryId`、`kind` | 查询当前账号、当前 Team 的两份文档，返回 `entries`、`documentRevisions`、`hasMore`。每次最多 10 条，完整结果最多 8 KiB UTF-8。含条目标识、修订号、用途、仓库信息、个人映射和来源。 |
| `propose_project_memory_update` | `operation` 为 `upsert` 或 `remove`，以及 `kind`、`entryId`、`baseEntryRevision`、变更字段 `fields` 和已读来源 `sourceIds` | 核对并暂存本轮更新，返回 `pending`、`no_change`、`conflict`、`needs_confirmation` 或 `error` 及原因。`pending` 表示已接收，成功轮次结束后才提交。 |

- 两份正文已自动完整附带。`query_project_memory` 用于显式核对最新记录、来源和修订号，以及为更正准备条目级提案。查询参数用于这次工具调用，不决定自动注入哪些工程。省略查询参数时，按当前账号和 Team 下可读记录的 `entryId` 稳定顺序返回；显式查询支持工程名、别名与 Git 地址匹配，精确 ID 优先。工具结果的条数和大小上限仅约束结构化查询结果，`hasMore` 不表示自动正文有缺失。
- 已有条目的更新需要带上查询得到的 `baseEntryRevision`。新增记录使用 `0`，`entryId` 由桌面生成。团队 Project 和仓库按平台 ID 识别已有条目，个人副本按仓库身份和规范本机目录识别。
- 工具核对来源属于当前 Agent 实际读过或当前用户确认的材料。账号、Team、登录代次、当前轮次以及来源范围都由桌面补全。
- Agent 可以提出目录候选。桌面检查候选与已确认目录记录、实际 Git 配置的对应关系，需要用户选择时返回 `needs_confirmation`。映射记录与当前会话目录授权分别核对。
- 用户明确纠正时可以更新或移除对应条目。AI 提议与已确认记录冲突时返回当前记录和原因，Agent 可以重新查询或向用户确认。
- 同一个 MCP 服务还提供第 5 节的 `list_team_knowledge`、`read_team_knowledge`。知识条目的创建、编辑和版本维护继续使用现有用户入口。

### 4.3 工具暂不可用时

两份 Markdown 的自动文本注入复用现有发送链路。文档无法读取或解析时，保留原文件，工具说明实际原因，普通对话可以继续。MCP 未接通或 Agent 暂不支持计划使用的工具传输时，注入材料标明实际可用能力。用户可以手动采用团队知识、确认目录，桌面直接保存已确认的映射。AI 提交更新工具可用后，才启用本轮归纳写回。

工具服务通过当前登录身份调用既有 Java 接口，Java 凭据由桌面持有。当前 Agent 负责全部模型推理，四个工具使用文件读写、查询与校验代码。 [MCP 工具职责](https://modelcontextprotocol.io/docs/learn/server-concepts)

### 4.4 同一个本机 MCP 服务

首版使用桌面管理的回环 HTTP 服务，仅监听 `127.0.0.1` 的系统分配端口。主进程为当前会话建立临时访问凭据，通过标准 ACP 会话配置交给实际支持 HTTP MCP 的 Agent。登录凭据和临时工具凭据仅供对应通信使用。

知识工具只读当前 Team 已授权的知识。记忆查询和提案工具只服务当前账号、Team 和会话，两份 Markdown 的写入仍由桌面校验和提交。MCP 配置按会话装配，保留用户已有的其他 MCP 配置。

新建、加载和恢复使用当前有效配置。换账号、绑定失效、切换 Agent 或关闭窗口时撤销对应访问。取消当前轮次结束该轮读取和提案处理，仍可发送的会话保留后续工具访问能力。工具地址与临时凭据只在当前连接期间使用，原生会话恢复时重新装配。

异步获取知识期间，其他会话的取消和审批仍可处理。资料读取完成后和真正提交前复核登录代次与绑定。通用 ACP 维护方确认具名接点，桌面按已交付能力接线。 [当前 ACP 会话](../../../packages/acp-runtime/src/session.ts)

## 5. 团队知识自动目录与读取

### 5.1 标题目录与上下文预算

用户进入本人本机会话并主动发送时，桌面附带当前 Team 可读知识的标题目录。目录的业务内容只有标题，知识 ID 和版本用于工具定位。平台现有知识条目继续由用户维护。Agent 发现相关标题后，实际调用读取工具，再使用读到的正文处理需求。

```json
{
  "items": [
    {
      "title": "接口错误码规范",
      "referenceId": "knowledge:<知识ID>:<版本ID>",
      "version": 3
    }
  ],
  "hasMore": false
}
```

固定说明提示 Agent 相关时读取正文，并标明资料来源。动态标题通过 JSON 序列化与说明一起交给当前 Agent。目录只存在于实际发送材料，用户草稿、消息展示及 Java 上传继续保存用户原始文字。自动目录与 HC-219 的手动固定引用分别记录。 [固定引用装配](../../../desktop/src/main/local-execution-coordinator.ts)

标题目录正文预算为 **8 KiB UTF-8**，与两份本机记忆正文的 8 KiB 篇幅上限分别计量。使用现有知识列表的第一页，页内按知识 ID 稳定排序、跳过归档项，按完整条目装入。该页仍有下一页，或部分条目超出预算时，`hasMore` 为真。Agent 可用列表工具继续查找。当前 Team 没有知识时正常发送，目录为空。

### 5.2 按需读取与固定版本

| 工具 | 输入 | 输出与行为 |
| --- | --- | --- |
| `list_team_knowledge` | 可选 `query`、`afterId`，省略时查询第一页 | 使用现有 `listKnowledge`，返回当前页的 `title`、`referenceId`、`version`、`nextAfterId`。 |
| `read_team_knowledge` | `referenceId` | 解析 `knowledge:<知识ID>:<版本ID>`，使用现有 `readKnowledgeVersion`，返回标题、引用标识、版本和正文。 |

- 两个知识工具的账号、Team、会话和服务地址由主进程绑定。每次正文读取沿用现有 `applicationWorkspace` 身份及服务端权限校验。 [现有知识客户端](../../../packages/collaboration-client/src/collaboration-client.ts)
- 列表工具返回整个服务端页与原始下一页游标。当前默认页大小为 50。自动目录因预算截取过该页时，列表工具仍从该服务端页查询，再使用实际服务端游标翻页。
- 正文读取使用指定的固定版本，并返回实际来源。归档和旧版可读性按现有服务规则处理。失败时返回实际错误，Agent 可以请用户重新选择材料。
- 本轮用户手动 `@` 某条知识时，使用用户选定的固定版本，并在自动目录标明本轮已引用。同一版本正文在本轮只附带一次。用户主动比较多个版本时，各自保留来源。
- 读取结果沿用现有工具展示，并可定位知识详情。知识更新只影响后续取到的目录和版本，已经交给 Agent 的材料、已发送记录和用户固定引用保留原内容。

### 5.3 标题缓存与跨用户刷新

标题页只在主进程内存缓存，按服务来源、账号、登录代次和 Team 隔离。同团队不同 Project 可以复用有权访问的知识标题页。并发请求合并，第一页有效期为 **60 秒**。过期后在下一次发送或工具查询时刷新。

本机保存、编辑或归档知识成功，以及收到现有 `knowledge.updated` 通知时，使标题缓存失效。Agent 已取得的正文和本机记忆中的已有事实保留对应来源，后续需要时可以再次查询。

现有源码包含下面的列表刷新链路，本轮据源码核对，双账号运行验证列入第 9 节。

```text
A 保存知识到 Java
  → KnowledgeAppService.changed 发布 knowledge.updated
  → B 的当前 Workspace 轻量 SSE 收到事件
  → dispatchProjectUpdates 触发 refreshKnowledgeMetadata
  → knowledgeRevision 变化，知识列表与候选元数据重新查询
  → B 看到新增条目或更新后的标题、版本
```

[服务端事件](../../../server/src/main/java/workbench/collaboration/application/service/KnowledgeAppService.java) · [客户端事件分派](../../../desktop/src/renderer/features/project-updates/use-project-updates.ts) · [正式知识列表](../../../desktop/src/renderer/features/collaboration/knowledge/live-team-knowledge.tsx)

- A、B 登录同一个 Workspace。知识在团队内共享，下属 Project 使用同一套有权访问的知识。
- A 保存成功后，B 已打开的知识列表收到通知后刷新。B 后进入知识页时，正常查询即可看到服务端已保存的内容。
- 同一修订刷新知识数量和 `@` 候选。归档条目按现有规则退出列表，页面按用户当前搜索条件显示结果。
- 通知携带变更线索，桌面随后读取相关元数据。正文在用户打开、手动引用或 Agent 实际调用读取工具时取得。
- B 已打开的固定版本、编辑内容和已注入材料保留原内容。断连期间沿用现有刷新入口，通知恢复继续使用现行机制。
- 冒烟发现列表可见性缺口时，先确定属于服务事件、客户端分派或页面消费，再按现有分工处理。

### 5.4 暂不可用时的反馈

| 情况 | 行为 |
| --- | --- |
| 知识目录请求暂时失败 | 普通消息继续发送，提供「团队知识目录暂不可用」状态，下一次读取可以重试。 |
| 工具未接通或 Agent 暂不支持 HTTP MCP | 说明自动读取能力暂不可用，保留手动 `@` 和已经取得的本机记忆文本。 |
| 固定版本当前不可读 | 工具返回实际原因，用户可以重新读取或移除对应引用。 |
| 登录身份失效 | 沿用现有认证处理，撤销旧身份的读取与写回。 |

提示使用现有输入区和工具卡样式。新建准备页的展示、知识列表更新和记忆文件变化只更新本机资料及视图，Agent 仍由用户主动发送启动。

## 6. 跨机引用与目录纠正

B 从原有 `@` 入口预览固定快照，采用后进入自己的会话草稿。只读浏览时直接显示原文。B 主动发送后，Agent 根据实际采用的对话范围理解口语化指代，并结合 B 的记忆查找工程。引用范围不足时，询问 B 以便补充需要的材料。 [现有固定引用交互](../spec/HC-219-引用任务与团队知识.md)

1. **先读完整本机文档。** B 的 Agent 从已附带的两份简短正文理解工程名、别名、用途与关系，再核对 B 当前 Team 下的个人副本。多个工程分别解析，需要最新记录、来源或修订号时调用记忆查询工具。
2. **核对本机副本。** 使用目录前检查实际位置和 Git 远端，个人 fork 可以用已登记的团队上游确认。多个副本均匹配时，优先使用当前会话绑定的副本，其他情况请 B 选择。
3. **必要时查询团队知识。** 仓库身份缺失或别名有冲突时，先查标题，再读相关固定版本。仓库身份已确定、只缺 B 的本机目录时，直接请 B 选择目录。 [知识读取工具](#52-按需读取与固定版本)
4. **B 确认后继续。** Agent 可问「这里指订单服务还是账务服务？」。需要目录时使用系统文件夹选择器，结果绑定发起时的账号、Team 和工程。取消选择时保留原草稿和引用，B 可以继续读讨论。

### 6.1 确认目录与会话起始目录

引用旁的「关联本机目录」只更新该仓库的个人映射。当前会话继续使用原起始目录。用户主动选择切换会话工作目录时，才沿用现有入口变更绑定。文件夹选择器可以共用原生能力，回填结果按具体动作处理。 [当前目录选择入口](../../../desktop/src/renderer/features/session/use-project-sessions.ts)

一个会话可以在 Agent 实际支持并已授权的范围内访问其他目录。例如从订单服务开始，找到 B 的账务服务副本后，继续沿用 Agent 已有的额外目录授权。当前 Agent 只能使用一个目录时，B 可以在目标工程新建本机会话，带上固定引用继续。 [本机目录与执行边界](../architecture/多人协作工作台顶层设计.md#9-acp-与-harness-的接合点)

### 6.2 旧记忆的纠正

对应引用提示或记忆工具结果提供「重新选择目录」和「移除该条记录」。目录移动或 Git 对应关系变化时，Agent 得到实际失效原因，请 B 重新确认。用户选定后立即更新这一条个人记录。

目录仍对应同一仓库、但引用中的文件不存在时，提示检查本机分支或版本。Team 内同名工程、同仓库多个副本和普通非 Git 工程继续通过用户选择消除歧义。已明确纠正的项目别名或关系也通过条目更新保存。

例如，A 原文写「billing 工程的 src/config.ts」，B 已确认的副本在 `~/dev/ledger-service`。Agent 结合团队别名判断后，使用 B 副本内的 `src/config.ts`。后续原文说「旁边那个工程」时，由 Agent 结合已采用的上下文继续判断，有歧义就问 B。共享原文和原快照保持来源内容。

对来源明确的新文件引用，后续可携带「仓库 ID + 仓库内相对路径」。当前首版使用现有快照、仓库登记与用户确认，快照扩展接点由契约维护方确认。 [现有快照结构](../../../packages/collaboration-client/src/types/organization.ts)

## 7. AI 更新、并发与失败处理

### 7.1 AI 发起更新的具体触发

每次用户主动发送本机会话，包括恢复后的发送，桌面都经第 4.1 节的 ACP 文本块附带下面的固定精简指引。该更新提醒正文上限为 256 字节 UTF-8，当前示例为 187 字节。Agent 在正常处理本轮任务时完成事实归纳和提案，沿用当前模型配置。详细参数与行为以工具定义及本节规则为准。

> 本轮获得或纠正工程信息时，先核对记忆；有依据的新信息在回复结束前调用 propose_project_memory_update 提交，无变化不更新，不确定先问用户。

| 本轮事件 | AI 的处理与目标文档 |
| --- | --- |
| 从实际读到的 Project、仓库登记、固定引用或知识版本中确认新工程、用途、别名、团队 Git 地址或工程关系 | 查询或使用已附带的条目，向 `team.md` 提交有来源的新增或修改。未登记工程按第 3 节保存已知事实。 |
| 用户选择本机目录，或实际文件、Git 检查确认本人副本及对应团队工程 | 复用已保存的用户确认结果，向 `personal.md` 补齐仍缺少的目录、相对路径、本人远端与团队上游对应信息；取得事实后再提案。 |
| 用户纠正工程别名或关系，或确认目录移动、仓库对应关系改变 | 基于当前条目版本提交对应修改，明确移除时提交 `remove`。用户在界面的确认与移除按第 7.2 节立即保存。 |
| 同一轮同时取得团队工程关系与本机副本信息 | 分别提交两份文档中的相关条目，保持同一工程的关联标识一致。 |
| 普通讨论没有新项目信息，或本轮材料与现有条目一致 | 保持原条目；重复提案返回 `no_change`，文件和修订号保持原样。 |

A 的引用原文提供来源工程的名称、用途或仓库线索，相关提案保留引用出处。B 的 `personal.md` 目录取自 B 实际核对或本人确认的结果；A 的路径在 B 机器上的对应位置由 B 当前 Agent 查找和确认。

某个 Team 首次使用时，桌面按第 2、3 节从已有登记和本人目录记录初始化两份文件。后续新增、纠正沿用上述逐轮触发规则。初始化保存基础记录，AI 归纳取得的新用途、关系和映射通过实际工具调用补齐。

### 7.2 从 AI 提案到实际落盘

AI 负责归纳并提交条目级变更，桌面主进程负责格式渲染、合并和文件写入。完整顺序如下：

```text
用户发送 → 桌面完整附带两份有效 Markdown 正文及固定更新指引
  → Agent 读取材料、确认新事实，与已有条目比较
  → 回复结束前调用 propose_project_memory_update，附条目版本和事实来源
  → 工具校验条目和拟合并正文篇幅并暂存，返回 pending
  → 本轮正常完成 → 主进程复核账号、Team、来源与条目版本
  → 按条目合并，原子写入 team.md 和/或 personal.md
  → 展示实际保存结果 → 下一次发送和查询使用新版本
```

| 触发 | 处理方式 |
| --- | --- |
| 用户在界面选定目录或移除条目 | 桌面立即保存确认后的变更，返回保存结果。 |
| Agent 调用更新工具 | 暂存到当前账号、Team、会话和轮次，工具返回 `pending` 以及变更涉及的条目。 |
| Agent 正常完成本轮 | 主进程核对身份、来源、条目版本后提交暂存更新，更新文件修订号。 |
| 本轮取消、失败或定稿前退出 | 丢弃本轮尚未提交的 AI 更新。已经由用户确认并保存的条目继续有效。 |
| 文件写入失败 | 保留旧文件，通过现有状态反馈告知记忆写回失败，用户对话可以继续。下一次查询返回实际已保存版本。 |

工具调用时就校验数据，提交时再检查实际条目版本。工具返回的 `pending` 只表示已暂存，工作台在提交成功后反馈「项目记忆已更新」。若最终发生冲突，保留已有条目并显示原因，下一次交互可重新查询。

只有本轮正常完成事件会提交已暂存的 AI 提案。没有工具提案时不产生 AI 写入；用户在界面的直接确认仍按上表即时保存。对话文字中的总结或「已记住」不作为保存依据。工具不可用时沿用第 4.3 节的实际能力反馈。真实模型自主调用的效果需要在实施冒烟中记录。

### 7.3 合并规则

同一账号、Team 的文档更新通过短时写锁串行合并。主进程读取最新 Markdown，核对每条的版本，按条目合并并复核两份正文的合计篇幅后，用临时文件原子替换对应文件。锁只覆盖本地读改写。

- 两个会话更新不同条目时，可以依次合并。它们修改同一条目时，后一条过期更新返回冲突原因，保留当前记录。
- 相同轮次的重复提案按条目标识和变更内容去重。重复事实返回 `no_change`，新增或实际变化时才递增修订号。
- 平台登记和用户确认提供项目身份与本机映射的依据。会话总结提供用途、别名和关系线索，提案保存来源以便后续回查和纠正。
- 同时涉及团队用途和个人目录时，分别写入两份文档。每份文件保存自己的修订号和结果，某一份失败时报告具体文件，重试使用相同变更内容核对去重。

当前 Agent 在本轮推理中归纳事实并提交工具调用。桌面提交结果跟随当前轮次和已有状态反馈返回，后续查询和发送读取落盘内容。

### 7.4 用户可见的轻量反馈

更新过程沿用现有工具卡。桌面根据工具提案与文件保存结果驱动状态，模型无需在正常回答结束后额外追加更新播报。默认文案描述本次实际保存的变更，文件名和条目详情放在展开内容中。

| 实际阶段 | 默认展示与详情 |
| --- | --- |
| 工具已暂存提案，返回 `pending` | 「准备更新项目记忆」，详情说明等待本轮正常完成，尚未保存。 |
| 本轮完成后主进程实际写入文件 | 使用同一张卡显示正在保存状态，完成后直接切换结果。 |
| 对应文件保存成功 | 简短变更摘要，例如「已记住账务工程的新目录」。由桌面按实际变更条目生成，展开查看文件名、条目和变更内容。 |
| 写入失败 | 「项目记忆保存失败」，展开查看具体原因与受影响文件。 |
| 提案取消、冲突或部分文件保存 | 展示对应实际结果；取消的提案标明未保存，各文件按自己的保存结果展示。 |
| 没有提案或返回 `no_change` | 不额外显示更新提示，工具记录继续使用现有查看方式。 |

「准备更新」与工具调用成功仅表示提案已接收，成功提示在文件实际保存后出现。卡片状态随桌面保存结果更新，下一次发送仍按第 4.1 节读取有效资料。

## 8. 桌面模块与现有能力接点

### 8.3 已批准的 MCP 会话装配接点（2026-11-23）

统筹已审查并批准本段桌面接点。`LocalExecutionCoordinatorOptions.contextSession` 提供 `prepare(scope, bindingId): Promise<LocalAcpSessionSetup>` 和 `release(scope, bindingId): void`。这是桌面组合接口，复用已有通用ACP的建会参数，不增加线上方法。

```text
真实账号及会话归属、目录授权已通过
  → 生成bindingId → contextSession.prepare取得本卡MCP配置
  → 再核对登录代次 → targetHost.bind(scope, cwd, setup)
  → 连接/恢复，沿既有session-state显示setupDiagnostics
  → 换Agent、范围变化或关闭：按旧scope和bindingId先撤销工具凭据，再关闭旧Agent会话
```

- `prepare`的授权核对当前登录身份与本人真实会话记录，不等待协调器尚未建立的执行binding，避免互相等待。组合入口调用已有`context.prepareSession`，释放调用`context.revokeSession`，旧bindingId的迟到释放不能撤销新凭据。
- MCP配置准备失败时撤销本次临时凭据，普通Agent绑定仍按原路径继续，在现有`setupDiagnostics`展示“项目记忆工具暂不可用”及真实原因。Agent不支持HTTP MCP时由已交付通用ACP跳过该服务，并沿原有能力诊断显示原因，不阻塞普通发送。
- 账号在准备或bind期间变化、bind失败时均撤销对应bindingId；换Agent/关闭先撤销再等待进程退出。复用有效绑定不重复生成凭据；会话Team/Project范围变化后重新准备配置，原生恢复仍沿既有公共能力。
- `prepareSession`保留调用方已有MCP配置和附加目录，只装配本卡保留服务名`workbench-context`。当前桌面注册表没有额外宿主MCP配置来源，Agent自身已有配置不由本卡改写。
- 本段不修改`sendPrompt`正文装配及requestId/ACP turnId约定；实际逐轮材料、来源登记和终态联调仍按第8.2节分别推进。资料读取失败、总输入无法完整容纳等涉及发送点的反馈继续留具名待项，不以此装配段宣称端到端通过。
