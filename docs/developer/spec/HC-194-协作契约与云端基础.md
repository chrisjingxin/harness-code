## 1. 用户收益与本次边界

现在基础窗口能打开，但没有共同账号、工作区或云端 API。HC-194 让两台电脑分别选择 `user01`、`user02` 登录同一工作区，看见真实当前用户与成员；切换账号后不会沿用上一账号的请求、缓存或凭据。后续会话、交接和执行都以这个身份边界为入口。

```text
桌面选择预置普通用户 → 主进程获取 CSRF 凭据并提交登录
Java 查询用户并建立会话 → 主进程查询当前用户/工作区 → React 显示身份与成员
访问工作区 → Java 复核用户启用状态与成员关系 → 返回限定范围的数据
```

本阶段交付独立契约、Java 单应用、三张业务基础表、版本迁移、显式演示数据初始化、登录/退出/成员查询以及最小桌面登录视图。真实人员认证、注册、密码、岗位、角色管理、邀请和成员管理界面不在范围内。免密码登录只表示用户选择了演示身份，不证明真实人员身份。

### 2.1 桌面构建、JAR、SQL 与 VERSION

保持 HC-193 的七个 npm workspace 与唯一根锁；Java 不是 npm workspace。普通 `npm ci`、`npm run dev/build/typecheck` 与文档/桌面边界检查不执行 Maven、不要求 JDK/数据库。新增明确的服务端入口，例如 `npm run server:build`、`server:migrate`、`server:init-demo`、`server:start`，只有显式调用才检查 Java 工具和环境；具体脚本由 Plan 落实，本稿不声称已有这些命令。

产品版本仍由根 `VERSION` 唯一决定，当前为 `0.2.0`，HC-194 不升版。Maven 应用版本使用 `${revision}`，服务端构建入口读取 VERSION 并以参数传给 Maven，缺值即失败，不在 POM 再维护一份产品版本。JAR 名称为 `collaboration-server-<VERSION>.jar`，内嵌相同产品版本与契约资源；公开 `/meta` 返回该构建版本。Boot 父版本与产品版本不是同一件事。

SQL 的 `V001` 等编号表示数据库演进顺序，独立于产品 SemVer；一个产品版本可携带多份历史 SQL。已执行文件不得改写，修复追加新编号。构建同时交付 JAR 和其中同字节的迁移 SQL/校验清单；运行 JAR 不读取仓库绝对路径。产品版本变更沿用 `version:set`，后续工程检查核对服务端构建取值与 SQL 制品一致性，不把调用 Maven 加入纯桌面检查链。

## 3. 独立契约与双端校验

### 3.1 唯一输入及出口

`packages/workbench-contracts/schema/` 是 JSON Schema 2020-12 的唯一源目录；本阶段 `platform.schema.json` 定义身份基础、请求/响应、错误和共同消息头。后续会话/设备/项目/引用等由对应任务在业务命名空间文件定义，再以本地 `$ref` 聚合，不让所有同事同时改一个形状文件，也不复制定义。`openapi/platform.openapi.json` 使用 OpenAPI 3.1.0，记录 HTTP 方法、路径、状态码、请求头及 schema 引用；根聚合入口由统筹顺序集成。本阶段不创建未来业务空文件。

schema 与 OpenAPI 是同一契约包内的不同职责；不从 Java 控制器或旧 protocol 反向生成第二套形状。各业务任务主责自己的类型/fixture/命名空间，公共定义只引用一处，具体分工见[并行开发约定](../project/协作任务并行开发约定.md)。

采用**同源 schema、双端运行时校验**，本阶段不引入 Java/TS 代码生成器。Java record 和 TS 类型是消费模型，不能代替线上校验。新传输类型从 contracts 根公开入口导出；另增显式 `@workbench/contracts/schema` 纯 JSON 导出供校验和 Maven 打包使用。现有 `DesktopHost`、`WindowState` 与 `window.workbench` 的五个窗口方法原样保留；schema 不复制这些不走云端的窗口端口。

Java 在 Maven resources 阶段从当前仓库 contracts 的唯一源目录复制 schema/OpenAPI 到 JAR，包含已登记的本地引用资源；禁止手工维护服务侧副本。源码相对位置只用于构建，部署不要求源码树。TS 校验器由 desktop main 消费，contracts 根类型入口不导入 Node/Electron/Ajv 运行时；UI 不需要引入校验依赖或获得网络能力。

### 3.2 校验行为

- Java 对请求 JSON 校验通过后才进入用例；序列化的成功/错误响应也按对应 schema 校验。主进程对发出的请求与收到的响应分别校验，再转成向 UI 暴露的安全结果。服务端响应自身不合规格时，输出固定最小 `INTERNAL_ERROR`，不得把非法 DTO 继续发出。
- 双端均不隐式转换类型、不补默认字段、不移除未知字段；核心对象 `additionalProperties:false`，所有必填字段必须出现。可空字段明确列为 `string | null`，不能把缺失、空串和 null 混用。拒绝畸形 JSON、非有限数字和未知协议版本。
- 使用双方一致的简单 ASCII 正则和长度约束；ID/时间不用仅作注解的 `format` 充当实际校验。schema 只引用随制品提供的资源，不联网解析任意 `$ref`；应用启动先编译 schema，错误时不开放业务。
- `fixtures/` 保存同一组正反例及预期通过/失败清单。必要契约检查至少覆盖正常登录/用户/成员、缺字段、多字段、错类型、非法 ID/时间/版本、错误信封和 Java DTO 序列化结果；Java 与 Node 必须读取同一份夹具，不分别写两份“预期”。完整组合回归归 HC-204。
- 请求体本阶段上限 16 KiB；用户/成员列表响应上限 64 KiB。正文超限不进入业务。未来附件/消息限额由各 Task 定义，不继承这个身份接口限额。

### 3.3 共同表示与协议版本

| 概念 | 统一规则 |
| --- | --- |
| ID | 应用生成小写 UUID 字符串，36 位，`8-4-4-4-12` 十六进制；不把登录名、目录或底层 Thread/Run ID 作为平台 ID |
| 时间 | UTC、毫秒精度、固定 `YYYY-MM-DDTHH:mm:ss.SSSZ`，由服务端生成；同时校验日期有效性，不能只靠正则接受不存在的日期 |
| JSON 名称 | camelCase；Java 内部类型与 SQL 列名通过传输/数据访问层映射，不直接暴露数据库行 |
| 数量/顺序 | 普通有界数量用整数；未来持久递增 sequence 若用 BIGINT，线上用非负十进制字符串，避免 JS 整数精度丢失 |
| HTTP 版本 | `/api/v1` 加必填 `X-Workbench-Protocol-Version: 1`；未知或缺少版本得到 426 `PROTOCOL_VERSION_UNSUPPORTED`，不携带业务数据 |
| 请求追踪 | 主进程为每次 HTTP 尝试生成 `X-Request-Id` UUID；Java 校验后原样响应，缺失/非法时生成新值。它用于查日志，不是写操作去重凭据 |

首版只支持协议 1，不提供旧版本 fallback 或并行 handler。产品 SemVer、协议版本、SQL 编号互不替代；修改已确认线上契约时更新源与消费者，在后续 Task 明确协议变更。

给 HC-195/196 仅保留 `PlatformMessageHeader` 的四个字段：`protocolVersion:1`、`messageId:Id`、`type`（小写点分名称）、`occurredAt:UtcTimestamp`。它是待组合的结构基础，没有 `payload:any` 或可直接受理的通用消息入口。业务 Task 必须为各 type 增加完整判别联合和载荷 schema，再接对应通道；未经登记的 type 一律不派发。事件持久顺序/游标、命令去重和回执关联分别在 HC-195/196 固定，不凭这四个字段宣称具备可靠投递。

## 4. 身份、工作区与 HTTP API

### 4.1 DTO

| 类型 | 必需字段与含义 |
| --- | --- |
| `UserSummary` | `id`、`username`、`displayName`；不含角色、岗位、密码、会话 ID 或设备凭据 |
| `WorkspaceSummary` | `id`、`slug`、`name`；slug 是稳定初始化键，不是授权信息 |
| `MemberSummary` | `user:UserSummary`；成员列表只返回启用用户，不包含角色或设备所有权 |
| `CurrentUserResponse` | `user:UserSummary`、`workspaces:WorkspaceSummary[]`；未登录不返回假用户 |
| `DemoUsersResponse` | `users:UserSummary[]`；只列启用的预置用户，最多 3 个，按 username 排序 |
| `WorkspaceListResponse` | `workspaces:WorkspaceSummary[]`，按 slug 排序；当前至多一个，无成员关系时为 `[]` |
| `MembersResponse` | `workspaceId`、`members:MemberSummary[]`，按 username 排序；当前用户如仍启用且是成员也在列表中 |
| `CsrfResponse` | `headerName:"X-CSRF-TOKEN"`、`token`；仅主进程可见，不转发给 renderer |

username 是 1～32 位小写 ASCII 字母/数字，首位字母；不自动 trim、转换大小写或接受显示名登录。displayName 为 1～80 个 Unicode 字符，工作区名称为 1～120 个；slug 为 1～64 位小写字母/数字/连字符、首尾不为连字符。初始化显示名分别为“用户 01/02/03”，工作区 slug 为 `demo`、名称“演示工作区”。内部用户表保留 enabled 字段；对外成功响应只代表经过查询确认仍启用的普通用户。

### 4.2 路由与正常结果

成功响应直接返回对应对象，不再包一层 `success/data`；所有 JSON 使用 `application/json`、`Cache-Control: no-store`，包含请求 ID 响应头。没有 HTML 登录页、302 登录跳转或 Basic/form login。健康检查不携带身份和数据库连接详情。

| 方法与路径 | 会话要求 | 输入 → 正常结果 |
| --- | --- | --- |
| `GET /health` | 匿名，无协议头要求 | 成功启动后数据库探测成功 → 200 `{"status":"UP"}`；运行期数据库暂不可用 → 503 `{"status":"DOWN"}`；启动校验失败的进程不提供此接口 |
| `GET /api/v1/meta` | 匿名 | 无正文 → 200 `{productVersion,protocolVersion:1,loginMode:"demo"}`；不创建登录会话 |
| `GET /api/v1/auth/csrf` | 匿名或已登录 | 无正文 → 200 `CsrfResponse`，必要时创建匿名会话并通过 Cookie 绑定 token |
| `GET /api/v1/auth/demo-users` | 匿名 | 无正文 → 200 `DemoUsersResponse`；这是演示选择器，其他业务仍受登录保护 |
| `POST /api/v1/auth/demo-login` | 匿名会话 + CSRF | 严格 `{username}` → 200 `CurrentUserResponse`，轮换会话 ID；已登录会话提交返回 409 `ALREADY_AUTHENTICATED` |
| `GET /api/v1/auth/me` | 已登录 | 无正文 → 200 `CurrentUserResponse`；不存在/停用用户使会话失效并返回 401 |
| `POST /api/v1/auth/logout` | 已登录或匿名会话 + CSRF | 无正文 → 204，失效会话、删除 Cookie；重复调用需先取得当前 CSRF token，仍返回 204 |
| `GET /api/v1/workspaces` | 已登录 | 无正文 → 200 `WorkspaceListResponse`，只取当前用户仍有关系的工作区 |
| `GET /api/v1/workspaces/{workspaceId}/members` | 已登录且为指定工作区成员 | ID 合法 → 200 `MembersResponse`；工作区不存在或当前用户非成员统一 404 |

上表未定义的业务路径返回 404，已定义路径错误方法返回 405；查询接口不接受多余查询参数。登录用户名不存在或停用均返回 401 `DEMO_LOGIN_REJECTED`，不建立已登录身份；请求中夹带 `userId/role/workspaceId` 等字段返回 400。合法用户无工作区关系仍可登录，返回空列表，不能默认加入 `demo`。

### 4.3 错误与授权顺序

错误统一为 `{"error":{"code":"…","message":"…","requestId":"…","retryable":false}}`，四字段必需；HTTP 状态是分类依据，code 是稳定程序分支，message 只供显示。错误不包含 SQL、堆栈、Cookie、token、连接串或服务端绝对路径。日志仅保留 requestId、路由模板、错误码与必要内部诊断，不记录身份请求/响应头或完整正文。

| HTTP / code | 发生条件与处理 |
| --- | --- |
| 400 `INVALID_REQUEST` | JSON/字段/ID/查询参数不合规格；修正输入后再发 |
| 401 `AUTHENTICATION_REQUIRED` | 无会话、过期、服务重启或原用户停用；UI 清除受保护数据并回登录 |
| 401 `DEMO_LOGIN_REJECTED` | 预置账号不存在/停用；保持登录选择器并提示 |
| 403 `CSRF_INVALID` | token 缺失/失效；主进程刷新 token，原写操作不自动重放 |
| 403 `REQUEST_SOURCE_REJECTED` | 非允许的 Origin/Host；不能靠关闭校验重试 |
| 404 `RESOURCE_NOT_FOUND` | 资源不存在或不属于当前成员可读工作区；不泄露其是否存在 |
| 405 `METHOD_NOT_ALLOWED` / 415 `UNSUPPORTED_MEDIA_TYPE` | 路由方法错误 / 登录正文不是 JSON |
| 409 `ALREADY_AUTHENTICATED` | 已登录身份直接再次登录；走显式退出/切换流程 |
| 413 `PAYLOAD_TOO_LARGE` / 426 `PROTOCOL_VERSION_UNSUPPORTED` | 请求超限 / 版本不支持；不重试原数据 |
| 503 `SERVICE_UNAVAILABLE` | 数据库暂不可用；`retryable:true`，不把会话判断成退出 |
| 500 `INTERNAL_ERROR` | 未预期错误或服务响应不合契约；`retryable:false`，保留请求号供诊断 |

先验证请求来源、版本/体积与语法；需要 CSRF 的请求再验证 token；受保护用例查询当前用户启用状态后核对成员关系，最后执行数据读取。401 与 403 的优先级因此可区分：带失效 token 的写请求可能先得到 403，`/me` 的 401 才作为身份已失效的确认。数据库读取失败统一 503，不返回 401 或空列表掩盖故障。

作者和操作人永远由服务端会话取内部 userId；正文中的 actor 不可信。成员关系在每次受保护读取时查询，不把登录时列表当永久授权缓存。当前成员列表读取在一次短只读事务内完成成员检查与查询；移除关系后新请求不可访问，已经提交给网络的旧响应无法撤回。后续写操作须在自身事务重新验证授权，不跨网络/模型调用持有事务。

## 5. 一个可运行的桌面 Cookie / CSRF 方案

### 5.1 网络入口与来源

云端地址由桌面宿主启动配置提供，一个 origin（scheme/host/port），不带用户名密码、query/fragment 或任意 API 路径。外网/内网使用 HTTPS 和受信任证书；仅本机开发允许 `http://127.0.0.1:<port>`。服务器配置同一个外部 origin。经反向代理时由部署固定外部地址，不用不可信的 `X-Forwarded-Host` 动态生成允许来源。

**只使用主进程 Node fetch + 内存 CookieJar 一条 HTTP 通路。** 不混用 renderer fetch、Electron 默认 Cookie 存储或用户浏览器会话。主进程把具体业务方法映射到固定路径；不暴露 URL、HTTP 方法、headers、Cookie 或通用 fetch IPC 给 React。显式 `redirect:"manual"`，任何 3xx 当连接错误，不跟随到其他站点；Cookie 仅按配置 origin、Path/Secure 匹配发送，拒绝服务端设置 Domain 扩大范围，Jar 不落盘、不进日志。

每次 native 请求由 main 设置 `Origin:<配置服务 origin>` 与 `X-Workbench-Protocol-Version:1`；这个 Origin 表示宿主允许访问的服务，不伪称本地页面与云端同源。Java 将其与固定外部 origin 精确比对；缺失、`null`、其他 origin 拒绝。`/health` 只核对服务 Host，不要求 Origin。CORS 不开放 renderer、`file://`、任意 localhost 页面或 `*`；没有给浏览器开发一套带凭据跨域通道。Origin 不是人员认证，主要防其他网页借 Cookie 发请求；真正访问边界仍是演示会话和成员关系。

主进程处理 Set-Cookie 时用库解析，不自己按逗号切分；`http:true` 接收 HttpOnly，按严格同站上下文读取本次服务的 Cookie。Cookie 名 `WBSESSION`，host-only、`Path=/`、`HttpOnly`、`SameSite=Strict`，HTTPS 下强制 Secure，唯一 loopback HTTP 开发入口不设 Secure。保持相同 API 和安全链，只有传输属性随是否 HTTPS 确定，不增加多种认证配置。JVM 内存保存 HttpSession，空闲 30 分钟失效；服务重启后需重登，业务数据不丢。首版不把 UI 会话持久化进 TDSQL，也不增加 Spring Session/Redis。

TLS 失败如实显示证书错误；通过给运行宿主导入受信任的 CA 解决，不设置 `NODE_TLS_REJECT_UNAUTHORIZED=0`、全局忽略证书或接受全部证书。数据库 TLS 同样按目标环境证书接入，不以关闭验证作为默认连接示例。

### 5.2 登录、退出与失效

CSRF（防跨站请求伪造）使用 Spring Security `HttpSessionCsrfTokenRepository`，token 存匿名/已登录会话。保留默认 token 请求处理器，`/csrf` 返回该处理器对外的 token 值；main 原样放入 `X-CSRF-TOKEN`，不自行解码。登录和退出均受 CSRF 保护，没有为了演示跳过登录校验。此方式参考 [Spring Security 的专用 token 端点说明](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html#csrf-integration-mobile)。

```text
新主进程 → 空 Jar，查询 meta/demo-users → GET csrf，保存 Cookie 与 token
选择用户名 → POST demo-login（Cookie + token）→ Java 查询 enabled 用户
登录成功 → 轮换会话 ID、保存 SecurityContext、清除旧 token → 返回用户/工作区
main 再 GET csrf → 保存新 token → GET me 复核 → 发布已登录状态
退出 → POST logout（当前 Cookie + token）→ 服务失效会话/删除 Cookie → main 丢弃 Jar
```

JSON 登录由 Spring Security 的认证入口处理，调用会话认证策略和 SecurityContextRepository；不能只在自写控制器中设置 ThreadLocal 便声称登录。策略至少执行会话 ID 轮换与 CSRF token 清除；SecurityContext 只保存内部 userId，业务请求重新查询启用状态。LogoutHandler 同步清会话与上下文，响应为 204。登录/退出后重新取 token 是必须接线，不能沿用原 token。

普通 GET 在当前账号不变时可人工重试；登录响应丢失时先用同一 Jar 查询 `/me` 确认是否已成功，不盲目重发登录。无法确认时显示连接错误并阻止业务发送。关闭应用丢弃内存 Jar，下一次启动重新选择身份，不实现“记住登录”。

### 5.3 用户切换、缓存与受限 UI 端口

新增独立 `CollaborationHost`，由 preload 在 `window.collaboration` 暴露：`getState()`、`listDemoUsers()`、`signIn(username)`、`signOut()`、`listMembers(workspaceId)`、`onStateChanged(listener)`。订阅返回取消函数；不改 `window.workbench` 的窗口方法或其参数。所有入口沿用 HC-193 主窗口/main frame/可信页面校验并验证参数；不接受任意 frame、窗口 ID 或服务 URL。

业务方法返回可序列化结果：`{ok:true,value}` 或 `{ok:false,error:{code,message,requestId,retryable}}`。这是 IPC 结果，不给 HTTP 额外套壳。网络/TLS/非 JSON 或响应校验失败分别转为 `NETWORK_UNAVAILABLE`、`TLS_ERROR`、`INVALID_SERVER_RESPONSE`；requestId 本机生成或使用已校验的服务返回值，不透传 Error/Response 对象。拒绝未经校验的 IPC 来源；合法业务失败显示安全错误。

`getState`/状态订阅只包含 `signedOut`、`loading`、`signedIn {user,workspaces}` 或 `connectionError {lastKnownUser:UserSummary|null,error}`。连接错误不等于确认退出，也不能据旧用户状态继续发送；只保留“上次身份”提示，不展示旧工作区正文。异步数据返回不携带 token/sessionId；main 内部保存的会话代次只用于判断结果是否过期。

账号切换按 `signOut` 完成后 `signIn` 顺序执行，不提供直接用新用户名覆盖旧 Cookie 的路径。开始退出或切换即递增代次，阻止新业务请求，取消旧请求/用户订阅、清 renderer 旧数据和草稿引用。旧请求即使稍后完成也因代次不同而丢弃；旧结果不得写入新 Jar、身份状态或缓存。每个代次使用独立 Jar、AbortController 和 CSRF token；退出调用保留旧 Jar 直至尝试完成，但不能继续为新身份使用它。

退出网络失败时仍可清本机凭据并回到选择器，界面明确“本机已退出，服务端退出未确认”；旧服务会话至超时前可能存在，不声称已撤销。下一次登录使用全新 Jar，不能恢复旧账号。用户、工作区列表与成员的缓存仅存内存，键至少包含服务 origin/userId/workspaceId；本阶段无历史磁盘缓存。后续若持久化须保持同样隔离。

最小视图沿用现有主题：未登录显示“演示登录”及服务返回的普通用户选择器；已登录显示当前 username/displayName、工作区与成员、退出/切换入口。无工作区显示“当前账号未加入工作区”，无网络显示真实连接错误，不提供本地假登录；不重排基础窗口或提前实现 HC-202 完整界面。

该身份视图限制在 workbench-ui 的独立 identity 区域和具名端口，不重写 theme/common/rendering、conversation、project 或 navigation/layout。HC-208 后续组合身份入口，HC-202 负责真实装配；本阶段的最小身份展示不是最终左侧导航的第二套实现。共享主题/包出口/根锁/preload 等修改由统筹协调串行合入，不阻塞 HC-205 独立抽离公共 UI。

用户退出仅结束 UI 身份与用户网络通道。HC-196 的设备凭据、设备所有者、项目绑定和后台执行不随 UI 用户自动重绑或删除；HC-194 不创建这些存储。未来 Runner WSS 只能使用设备凭据，不能复用 WBSESSION；换账号后能否管理设备由 HC-196 授权决定。

## 6. TDSQL 基础表、迁移与初始化

### 6.1 SQL 与接入边界

唯一业务库为 TDSQL MySQL 兼容版，Java 经 JDBC 访问；开发/外网可用 MySQL 8.4 对同一 SQL 做必要冒烟，但这不是目标内核已确认，更不是 TDSQL 验收。SQL 只用常规 InnoDB 表、主键/唯一索引、参数化 CRUD、简单 JOIN 和短事务，不依赖 MySQL 8 专用 JSON 查询、CTE、CHECK、全文索引、触发器、存储过程、外键或数据库自生成 UUID。

用户补充（2026-11-06）：本机 MySQL 制品按实际操作系统、CPU 架构和适配系统版本选择，不能把本机 x86_64 包固定为全员依赖；ARM 设备使用官方对应 ARM 制品。共同约定是 MySQL 8.4 LTS 与同一套 SQL/JDBC，具体可取得的补丁、包名与校验值在各环境的实施记录中固定，不要求所有架构存在同名或同补丁二进制。已下载的包先核对架构/官方校验，可用才复用；没有匹配制品时记录技术阻塞，不误装其他架构或改用另一种数据库。

腾讯的 [JDBC 接入](https://cloud.tencent.com/document/product/557/10238)仅证明接口方向；示例中的旧驱动类名不照搬。用 `com.mysql.cj.jdbc.Driver` 或 JDBC 自动发现。实际产品、兼容大版本、代理/普通表模式、驱动握手、字符集和迁移权限必须从目标环境取得；[官方使用限制](https://cloud.tencent.com/document/product/557/47511)不足以替代实例验证。[Flyway MySQL 模块](https://documentation.red-gate.com/flyway/reference/database-driver-reference/mysql)并未承诺所有 TDSQL 产品可自动识别。[Connector/J 9.7.0 发布说明](https://dev.mysql.com/doc/relnotes/connector-j/en/news-9-7-0.html)列出的服务端范围为 MySQL 8.0 及以后，因此本稿不承诺 5.7 内核可接入；若目标内核不在驱动支持范围，先回调统筹修订单一版本基线，不保留运行时驱动 fallback。

连接只需 `SPRING_DATASOURCE_URL/USERNAME/PASSWORD` 等标准配置；不把真实地址/密码写入文档、源码或启动命令参数。应用初始化核对 utf8mb4、短事务提交与实际表引擎；目标为分布式实例时，本阶段基础表限定普通表，必须证明同一业务事务可原子提交，不自行选择分片键。提供端无法满足时为环境阻塞，不降级为部分写入。

### 6.2 三张最小表

SQL 表名加 `wb_` 前缀以避开保留字；ID/登录名/slug 使用 ASCII 二进制排序规则，名称使用 `utf8mb4_unicode_ci`，不依赖 MySQL 8 才有的 0900 collation。时间为应用产生的 UTC epoch 毫秒 `BIGINT`，JDBC 转成统一 UTC 字符串；不依赖数据库/session 时区或 CURRENT_TIMESTAMP 默认值。

| 表 | 必需列、约束与索引 |
| --- | --- |
| `wb_user` | `id CHAR(36)` 主键，`username VARCHAR(32)` 非空唯一，`display_name VARCHAR(80)` 非空，`enabled TINYINT` 非空，`created_at_ms BIGINT` 非空；enabled 仅由应用写 0/1，无岗位/角色/密码列 |
| `wb_workspace` | `id CHAR(36)` 主键，`slug VARCHAR(64)` 非空唯一，`name VARCHAR(120)` 非空，`created_at_ms BIGINT` 非空 |
| `wb_workspace_member` | `workspace_id CHAR(36)`、`user_id CHAR(36)` 组成主键，`created_at_ms BIGINT` 非空；增加 `(user_id,workspace_id)` 索引，支持当前用户查工作区 |

关联由应用核对，不建外键；无自动物理级联删除。成员有效性由关系存在且用户 enabled 判定。HTTP 不开放用户/工作区/成员写接口；演示中停用或移除关系只通过受控数据库操作，不新增管理平台。

### 6.3 版本迁移与失败边界

`src/main/resources/db/migration/V001__identity_workspace.sql` 只创建上述三表，Flyway 使用 `flyway_schema_history` 记录版本与 checksum。没有 `IF NOT EXISTS` 掩盖未知表形状，不启用 baselineOnMigrate，不调用 clean；发现已有未登记表、checksum 漂移或中断的 DDL 时停止，不自动修复/删除数据。

迁移是显式的一次性命令，以具有 DDL 权限的连接运行，完成后退出；普通服务启动只 validate 历史/所需版本，不能自动改表，业务账号只需必要 DML 和迁移历史的读取权限。内网交付同一份 SQL，由 DBA 在授权窗口使用同版本迁移入口执行并登记，不能手改 checksum 或裸执行后假造历史。若现有 DBA 规程无法使用该入口，先约定同一 SQL 的登记方式再实施，不另外维护一份“内网脚本”。

MySQL/TDSQL DDL 不假定能事务回滚。一次性迁移失败以非零码退出，保留失败版本/无敏感信息的日志，由实施者检查实际表形状后修复或恢复演示库，再以同一迁移工具校验；禁止启动时循环 repair。

**启动和运行期只有一条清晰路径：**启动时先编译契约 schema、连接数据库、validate 迁移历史/checksum/所需版本，全部成功才开放 HTTP；任一步失败直接非零退出，不留一个等待修复的 HTTP 服务。因此，schema 非法、数据库连接失败、权限不足、迁移未执行或未知版本属于启动失败，不通过 `/health` 维持 DOWN 状态。

成功启动后，`/health` 用一次有界数据库查询判断 UP/DOWN；数据库暂时断开或查询失败时返回 503 DOWN，依赖数据库的业务返回安全的 503 `SERVICE_UNAVAILABLE`，保留内存登录会话，不将查询失败当成用户不存在/退出。数据库恢复后探测与业务自然恢复，不要求重启、不增加可配置状态机。运行中不循环校验或修复 DDL；改库需按显式维护/重启流程重新通过启动校验。

### 6.4 显式幂等演示数据初始化

`init-demo` 是迁移成功之后单独调用的一次性操作，常规服务启动不重新补账号/成员，避免移除成员后重启又被自动加回。该命令用一个短 JDBC 事务处理全部用户、工作区、成员：

```text
查 username=user01/02/03 → 已存在则保留 id/显示名/enabled，否则生成 UUID 并插入
查 slug=demo → 已存在则保留 id/名称，否则生成 UUID 并插入
按查得的真实 ID 查三条成员关系 → 只补不存在的关系 → 一次提交全部新增行
```

重复运行不重复建记录、不换 ID、不覆盖显示名/停用状态，也不碰其他业务历史；显式再次调用表示允许补回缺失的预置成员关系，不能把它作为普通启动“修复”。若并发初始化撞唯一键，整笔回滚并重新读取后至多重试一次；仍冲突则失败，不用 `INSERT IGNORE` 吞掉其他数据错误。任何中途异常回滚全部本次 DML，不留下只建用户却漏建成员的半成品；日志只报告插入/保留数量。

成功后数据库应恰有这三个预置用户名、一个 demo 工作区及三条对应关系（不要求库里没有其他合法数据）。两次初始化前后对比原 ID/名称/enabled 和行数能观察幂等性；若原用户已停用，初始化不能重新启用，登录继续拒绝。服务运行不依赖“本次插入成功”内存状态，所有查询来自数据库。
