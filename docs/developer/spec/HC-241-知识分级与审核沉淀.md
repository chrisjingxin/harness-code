## 1. 要解决什么问题

团队已有知识页面、固定版本、引用和标题读取工具，但知识的 `category` 只是自由文本，不能决定执行约束、适用仓库或审核。开发者目前只能读，管理员保存即发布；没有从个人会话起草、比较已有结论、审核融合与纠错的完整入口。

本卡把“本人发现 → 本机 Agent 起草 → 本人确认共享 → 管理员审核 → 新版本进入团队 → 使用反馈推动复核”接通。个人与 Project 的踩坑统一沉淀为团队“经验”，不再建立 Project 知识库。

```text
本人点击沉淀 → 核对账号、会话、已确认目录和团队资格
  → 当前所选本机 Agent 阅读本人选择的定稿材料、检索已发布知识
  → 形成新增 / 补充 / 冲突修订草稿与固定版本差异
  → 本人编辑并确认提交 → 管理员批准 / 退回 / 修改后批准
  → 事务发布新版本及贡献记录 → knowledge.updated 使现有目录缓存失效
  → Agent 按范围使用；成员轻反馈 → 管理员待复核 → 再修订或归档
```

服务端不调用模型、不配置另一个模型服务。自动生成仅产生候选草稿；任何自动生成内容均不得越过本人提交与管理员审核直接发布。管理员手工直接维护已有知识仍沿 HC-240 权限，必须明确点击“发布新版本”，不能把 AI 草稿套用到该写接口。

## 3. 三个已批准默认值

| 问题 | 首版默认 | 用户能观察到的结果 |
| --- | --- | --- |
| 规约正文预算 | 每条规约正文 ≤4 KiB UTF-8；本轮规约材料合计 ≤8 KiB UTF-8，含标题、版本及包裹文本，独立于目录和 MD。按完整条目计量，不截断、不漏条；超限时整组不附带，显示实际字节数及可重试状态，普通本机消息沿现有规则继续 | 正常时匹配规约完整送达；整组超限如实显示未附带，不悄悄遗漏条目。草稿可保存，提交/发布超长单条须先精简 |
| 退回提议保存与可见性 | 不自动清理，持续保留；提议人与当前管理员可见，其他开发者不可见。私人草稿仅本人可见；提交过的内容及审核记录保留。本期不增加保留期配置或清理任务 | 本人可从“我的提议”看到理由并重提；他人目录和正文读取接口拿不到退回内容 |
| 默认复核与过期条件 | 新版发布或管理员明确复核后 90 天未复核即到期；当前固定版本收到 1 条未处理“已过期或有误”反馈即进入队列。历史初始化未有真实复核者的条目立即以“尚未复核”进入队列 | 管理员打开队列即可看到原因；有用票不抵消错误票，系统不自动下线知识 |

上述为实现常量，不增设复杂配置或定时模型任务。队列通过当前时间和数据库记录计算，到期自动满足查询条件，无需后台扫描/新服务。规约组放不进本卡预算时整组不附带并明确状态，不裁剪两份 MD 或部分规约凑空间；普通消息继续。用户原始输入超出已有总输入限制沿现行规则，不新增一套限制。

规约加载失败时不能声称“全部已带入”，应显示“团队规约未附带，可重试”，普通本机消息照常沿 HC-239 规则继续；不增加跳过确认弹窗、默认停止或全局防御配置。经验/术语标题暂不可用仍沿 HC-233 的可见降级。401/403 按真实撤权处理，不能用缓存恢复资格。具名状态由模块提供，输入区反馈与 HC-239 协调装配，不能吞掉异常后声称正常加载。

## 4. 结构化知识与适用范围

### 4.1 类型和版本

| 结构 | 字段与约束 |
| --- | --- |
| KnowledgeLevel | `rule` 规约、`experience` 经验、`term` 术语；必填封闭枚举 |
| KnowledgeScope | `{kind:"workspace", repositoryIds:[]}` 或 `{kind:"repositories", repositoryIds:[UUID,...]}`；指定仓库 1～20 个、去重、按 ID 排序，必须属同团队且发布时 active |
| KnowledgeContentType | 本期只生产 `article`。在版本元数据中保留独立的内容类型字段；HC-243 后续增补 `system_map` 契约和内容校验，复用本卡实体/审核，不提前交付假地图入口 |
| KnowledgeSummary | 原字段 + level/scope/contentType、聚合使用/反馈摘要和复核状态；version 仍是条目修改并发版本 |
| KnowledgeVersionSummary/Version | 追加 level/scope/contentType、proposalId（手工发布为 null）、contributors、reviewerId（历史未知为 null）、reviewedAtMs（未知为 null）；正文与这些发布元数据共同固定 |

`category` 保留为可选使用的主题标签（原有自由分类，仍按既有长度约束），不承担级别或权限；不以“规范/约定”等旧字符串猜测 rule。termKey 保持团队内唯一、创建后稳定，不新增同义别名 API。

贡献者是本版实际提交/修改的 UserId 去重集合，服务端由提议人、批准时修改者和明确合并的已发布来源版本计算，不接受模型任意填写人员。authorId 保留本版实际发布操作者；版本页同时显示贡献者、审核人、来源及修改说明。历史版本、原作者和已离开标注不转名、不改写。

### 4.2 会话实际仓库集合

知识适用范围与阅读权限分开：适用范围控制自动目录/规约，不能授予团队或 Project 阅读权。当前团队活跃成员可主动查询、阅读该团队已发布知识的其他范围；工具明确标出“不属本轮自动适用范围”。非成员即使猜中固定引用仍拒绝。

本轮集合 `effectiveRepositoryIds` 只能由主进程产生：

1. 从本人原生确认的当前主目录取 realpath 和目录身份，重新核对 origin/upstream；对照服务端当前团队仓库登记的 remoteUrl，准确对应一个 active Repository 时加入。
2. HC-233 的本人确认映射只有在实际路径仍存在、目录身份和当前 Git 身份一致时才作为证据；其他工程虽完整存在 personal.md 中，不因此全部加入本轮。
3. 会话登记的 repositories 是候选/来源证据，不能独立证明某个目录已授权或当前正访问；需与本轮确认目录/Git 身份交叉核对。不能用 Project 下全部关联仓库、侧栏选择、Agent 自报 ID 或关键词猜测替代。
4. 当前无 HC-242 附加目录正式输入，首版只处理已确认主目录。以后只接收 HC-242 主进程确认过的实际目录集合；本卡不扫描磁盘、不添加附加目录、不改 Agent 文件权限。
5. 比对使用现有目录事实和服务端登记；可安全统一地址首尾空白和末尾 `/`、`.git`，不自动认定 SSH/HTTPS 别名、镜像或不同 host 等价。多条歧义、无 remote、非 Git、未登记及失效映射均不猜测；UI 标明“本轮未匹配团队仓库”。不把含凭据的远端或本机绝对路径上传到统计接口。

`scope.kind=workspace` 始终参与有效团队会话；`repositories` 与 effectiveRepositoryIds 有交集时参与。没有匹配仓库或普通非 Git 目录时只自动使用全团队知识。无团队/失去团队资格时不使用该团队任何知识或 MD，个人执行边界继续由 HC-239/240 处理。侧栏换团队不改会话绑定。

仓库后来归档不改写旧知识 scope，也不把它扩大为全团队；其指定范围不再自动匹配，管理员可通过新版本调整。固定旧版仍按当前成员资格主动读取。

### 4.3 自动上下文、去重和缓存

- 每轮重新得出当前会话的有效团队与实际仓库集合，先查询全部适用规约元数据并按真实游标读完，再读取其 currentVersionId 固定正文。规约不能只用第一页；任一匹配条目未取全时整组不附带并显示真实状态，普通消息仍可发送。
- 匹配的经验、术语及规约标题沿 HC-233 8 KiB 目录、完整条目、hasMore 和真实游标。规约正文独立 8 KiB；两份 MD 继续完整，不作相关性挑选。
- 顺序固定：本机 MD 和提醒 → 适用规约（knowledgeId 顺序）→ 标题目录；固定引用保留来源。规约材料显式标“团队规约及固定版本”，不伪装系统权限或凌驾用户授权。
- 同轮以 `knowledgeId + versionId` 去重：手动引用与自动规约同版只提供一份正文；MCP 再读同版返回 alreadyRead 及来源。手动引用旧版、自动规约新版时两版都保留，标明历史对照和当前规约，不能用旧版覆盖当前规约。
- 发送前固定本轮版本集合；管理员中途发布只影响后续轮次。已发送材料、引用和正文历史不回写成新版。
- 标题缓存仍按 origin/account/generation/Workspace 隔离，原始页可复用，但适用结果必须包含本轮仓库集合或在缓存之后重新筛选。规约当前指针在发送前在线核对，不以 60 秒旧缓存代替当前发布/权限校验。
- 只有真实发布、改版或归档发送既有 knowledge.updated 并失效缓存；提议保存、提交、退回与反馈均不得冒充发布事件。审核/复核页面在操作后刷新，进入页面主动读取；不另造 SSE 协议或常驻轮询。

## 5. 从本人会话得到真实 AI 草稿

### 5.1 可见入口与来源选择

本人、绑定有效团队、已确认本机目录的会话提供“沉淀为团队知识”。他人只读会话不能指挥对方 Agent；需要本人基于可读引用新建本机会话后操作。无团队会话提示先按 HC-239 确认团队绑定，不因沉淀按钮暗中绑定/发布会话。

弹窗先展示准备交给本机 Agent 的定稿范围，默认最近一个完整轮次的用户消息、回复和工具摘要，可改选已完成轮次；合计 ≤64 KiB UTF-8，超限要求本人缩小选择，不截断、不发送思考过程/密钥/完整工具输出。冻结 sourceRevision 和实际材料，起草中新的普通消息不混入。

草稿中的“共享来源摘要”和最终正文分别可编辑。个人会话原文仅在本机起草过程中使用，不随提议自动上传；服务端保存用户明确确认的来源摘要、来源标识和选择范围。管理员看到该摘要不等于获得源 Project/个人会话阅读权；点开源链接必须单独验证真实权限，无权显示“来源正文不可访问”。

### 5.2 本机执行与结构化候选

本卡新增桌面 `knowledge-drafts/` 服务，消费现有 ACP 公共 API，不等待 HC-239 普通发送修正：

1. 主进程从真实本人会话记录读取当前 providerId、实际确认目录和可复用配置；使用现有 registry.getHost(providerId)/LocalAcpHost.bind，启动一次**用户可见的起草运行**。它是当前所选本机 Agent 的临时 ACP 会话，不是新 Codex 对话、后台代理编排或另一模型配置。临时 executionId 与来源 conversationId 明确分开，结束后关闭，不覆盖原会话原生绑定/恢复记录。只消费实际可取得的 Agent 设置；不能取到原会话模型/模式设置时，界面说明本次使用该 Agent 的新会话默认设置，不声称已沿用，也不另配密钥。
2. 原会话有活动执行时入口显示“等待本轮结束后起草”，不同时操作同一个工程。起草弹窗显示准备、检索、归纳、完成/失败，可停止；沿现有审批/表单能力展示实际请求，绝不默认同意。起草指令限归纳与知识读取，不添加目录、写文件或自动提交团队内容；Agent 自身可用能力仍按实际声明和授权，不承诺通用 ACP 提供不存在的硬沙箱。
3. 同一桌面回环 MCP 服务按临时凭据区分用途。普通对话保留 HC-233 四工具；起草凭据仅有 list_team_knowledge、read_team_knowledge 与新增 `propose_team_knowledge_draft`，不开放记忆写回、HTTP 发布/审核或任意 URL。新工具只交付本机候选，名称中的 propose 不代表云端提交。
4. 起草先实际查询已发布知识；检索可显式选择全团队（用于发现跨范围重复）或本轮适用范围。命中相关条目后必须实际读取固定版本，再形成 supplement/conflict；来源台账记录真实工具结果。不存在列表/读取调用时，不显示“已完成已有知识比对”。搜索不能证明所有语义重复已消除，UI 展示实际查询及未读完分页，不虚称完整扫描。
5. 新工具输入为 intent、targetKnowledgeId/baseVersionId/baseItemVersion、title/category/level/scope/contentType/text、relatedReferences、sourceIds、summary/rationale。新建目标为空；补充/冲突目标及引用必须来自本次实际已读固定版本；身份、贡献者、来源会话和已读台账由主进程补全，模型不能自报权限或“已读取”。
6. 正常终态且至少一个合法结构化候选时展示“AI 草稿已生成”，并由本机原版文本与候选全文计算可读差异。不能把用户原文复制到表单算 AI 起草，不能从任意回复抓一段 JSON 后假定成功。取消、失败、结构错误、身份/目录变化均不自动提交或发布；可保留明确标记的未完成预览供本人手工整理，允许重试。
7. 本人修改候选并显式“保存草稿”或“提交审核”后才写服务端。提交前展示级别、适用范围、完整正文、来源摘要和目标版本，明确这些内容会给管理员查看；勾选/点击确认是产品提交动作，不依赖额外聊天确认。

起草临时凭据绑定 origin、account/generation、sourceConversationId、Workspace、executionId/turn；与正式会话凭据共存，不通过 prepareSession 撤销正式会话。必须先订阅再 sendPrompt，使用返回 ACP turnId 关联结构化候选和终态；退出、切号、撤权、关闭窗口和结束均撤销。普通上下文模块的受控 ACP 夹具不替代这条真实起草调用链。

### 5.3 管理员主动整理

知识页管理员可点“让本机 Agent 整理”，显式选用本人可执行会话的 Agent/已确认目录。没有可用会话时引导选择，不借服务器或他人设备运行。按真实分页遍历已发布标题，按需读固定正文；显示已遍历页数、未完成状态和候选数量。每次最多输出 20 个建议，更多由管理员主动继续；未读完不能宣称“全部知识已整理”。

合并建议以一个存续条目的补充/冲突草稿表达，保留各来源固定版本；被合并项的归档另外形成具名 archive 提议，经明确审核后逐条处理，不连带悄悄删除。过期建议同样是 archive 或修订草稿。管理员仍须打开候选、提交和审核，不在 AI 正常终态自动批准；不新增定时整理作业。

## 6. 提议生命周期、审核与贡献

### 6.1 提议字段和状态

`KnowledgeProposal` 必须包含：proposalId/workspaceId、proposerId、intent（new/supplement/conflict/archive）、targetKnowledgeId（新增为 null）、baseVersionId/baseItemVersion（新增为 null）、候选内容、已读相关固定引用、经本人确认的 sourceSummary/sourceRefs、generationKind（agent/manual）、revision、status、createdAtMs/updatedAtMs/submittedAtMs、最后退回理由、publishedKnowledgeId/publishedVersionId、reviewerId/reviewedAtMs。生成方式由受信任桌面动作标记，仅用于呈现来源，不作为权限依据。

```text
本机候选 → 本人确认保存 draft → 本人提交 submitted
draft / returned → 本人编辑（revision +1）→ submitted
submitted → 管理员批准或修改后批准 → published（正文新版本）
submitted → 管理员附理由退回 → returned
draft / returned / submitted → 本人撤回 → withdrawn
```

archive 提议批准结果为已归档，不捏造正文新版本；proposal 状态仍为 published，另记 outcome=archived、publishedVersionId 为被归档固定版。沿既有归档逻辑递增条目 version、保留 currentVersionId 和所有版本。withdrawn 保留提交/审核历史，不出现在日常待审队列。

- draft 仅本人读写；submitted/returned/published/withdrawn 的已提交内容与审核记录仅本人及当前管理员可看，其他成员只看真正发布版本及公开贡献摘要。
- submitted 内容冻结，不能一边审核一边被提议人原地改写。本人可撤回后复制成新 draft；退回后可编辑重提，每次提交保留内容快照与理由，旧审核不套用新 revision。
- 管理员修改后批准须提交完整修改后候选及理由，页面显示“提议版本 → 审核修改 → 最终发布”的差异；原提议人仍是贡献者。开发者对 rule 只能提议，不能通过其他发布接口写入。
- 同一管理员可以审核自己的提议，界面仍要独立提交与批准动作；本期不增加强制双人审核角色或策略。

### 6.2 并发、幂等与发布事务

所有变更带 expectedRevision/requestId；批准还带 expectedItemVersion/baseVersionId，新增使用 termKey 唯一性校验。requestId 为 UUID，同一操作者、团队、动作和载荷重试返回原回执，变更载荷复用 ID 返回 IDEMPOTENCY_CONFLICT；不能在角色撤销后仅凭旧回执绕过当前资格检查。

```text
锁 Workspace 行 → 重读操作者当前 enabled/成员/role
  → 锁提议并检查状态、revision、提议人仍有团队资格
  → 锁目标条目（多来源按 knowledgeId 排序）并核对 currentVersionId / version
  → 校验级别、范围、来源与内容 → 追加不可变正文版本和贡献来源
  → 切换当前指针 / 归档，保存审核记录、提议终态及幂等回执
  → 同事务写既有 knowledge.updated 发件箱 → 一次提交
```

不得跨网络/模型调用持有数据库锁。两名管理员并发批准同一提议，只有一个发布；相同 requestId 重试返回同一版本，不同动作收到 PROPOSAL_STATE_CONFLICT。两提议基于同一知识旧版，先发布者成功；后一个收到 KNOWLEDGE_BASE_CHANGED 并返回当前可读元数据，保持 submitted，不自动覆盖/合并。管理员退回或本人撤回、读新固定版后重起差异；不能直接改 baseVersionId 冒充已经比较。

新建撞 termKey 返回 KNOWLEDGE_KEY_EXISTS，引导改为针对已存在固定版本的提议。目标归档后拒绝改版/批准，返回 KNOWLEDGE_ARCHIVED。批准前重验仓库归属/active，不能把失效的指定范围自动改为全团队。任何错误整笔回滚，不留孤立版本、重复贡献或假通知。

### 6.3 撤权与来源权限

- 每个读、写、工具和异步结果返回前沿 HC-240 真实资格校验；管理员降级立即丢失审核/复核入口，已打开的表单不能继续批准。
- 被移出团队者不能读写原团队草稿、提议、知识、反馈或审核；正文历史贡献保留“原成员已离开”。私人本机原会话不删除，也不把执行权转交管理员。
- 提议人移出团队/停用后，其 submitted 提议标记“提议人已离开，需管理员重新提议”，原提议不可直接批准；当前管理员可复制其已提交内容为新提议，经明确确认审核，保留原提议和原贡献来源。私人 draft 不给管理员接管。重新加入不自动恢复旧待审状态或绕过修订校验。
- sourceRefs 是来源线索，不是授权。服务端对可验证的共享会话/快照来源在提交时检查真实账号、Workspace/Project 资格；个人本机会话标识作为本人确认的来源声明，不能拿它在服务端读取私有正文。审批页只显示本人明确共享的摘要，打开来源仍按当前 Project/会话权限处理。
- 提交过的团队提议是明确共享给管理员的独立材料，后来仅移出某个源 Project 不自动删除该材料或给管理员补 Project 阅读权；需重新取得源正文时照常拒绝无权请求。

## 7. 命中、轻反馈和待复核

### 7.1 “Agent 实际读取”的唯一计数口径

命中定义为：**当前有效本机 Agent 在活动轮次调用 read_team_knowledge，固定版本正文实际成功通过 MCP 工具响应交付**。不能证明模型理解了内容，只证明这一可观测读取行为。普通页面打开、列表/目录展示、预取规约、固定引用解析、send 受理、工具卡渲染、会话回放、失败读取与 alreadyRead 返回均不计命中。自动规约/手动引用的实际送达另有材料证据，不混成工具读取次数。

本机以 origin/account/generation、binding/executionId、稳定轮次、knowledgeId/versionId 建同轮台账，首次实际正文交付生成一个随机 readId；同轮同版、多工具请求及网络重试都复用它，最多计 1。新活动轮次再真实读取可再次计数。readId 不由 Agent 填入，不把 JSON-RPC callId 或可重放事件号直接当新命中。

MCP 服务须在有效 token 的成功正文响应实际完成后回报；序列化/连接失败不报，业务取正文但未交付不报。回报失败使用同一 readId 在本次活跃生命周期内重试；不建后台保活/补数任务，不从恢复历史生成新回报，UI 可显示“统计暂未同步”。读取已经成功时回报失败不改写工具结果。

服务端以 workspaceId/knowledgeId/versionId/readId 唯一键去重，首次写回执及版本聚合计数在同一事务，重复返回现有值。回执只保存上述对象、随机 readId 和时间，不持久化账号、个人会话、问题、cwd、模型输入；身份仅用于当前资格校验。统计是受登录权限约束的第一方桌面遥测，不宣称服务端能独立证明客户端模型实际阅读，不用于员工排名或权限判断。

条目展示“Agent 工具读取 N 次”（历版合计），正文同时展示本固定版计数；已归档旧版真实主动读取仍可计数，但不会因此重返自动目录。起草运行中的真实知识工具读取也适用同一口径。

### 7.2 反馈和去重

- 沿现有知识工具卡和正文页，在实际知道固定版本后显示“有用”“已过期或有误”；后者可附 ≤280 字简短说明。正文页反馈是人的反馈，与 Agent 命中分开。
- 当前成员针对同一固定版本只有一份有效反馈，可在 useful/expired/null 之间修改或撤销；唯一键为 Workspace/knowledgeId/versionId/userId。重试不加票，改票按旧值扣减新值增加；服务端不接受客户端提交聚合计数。
- 公共页面只显示合计和本人选择；说明仅反馈者与当前管理员可读，不展示全员点选名单。反馈本身不改正文/发布版本，也不产生 knowledge.updated。切号、撤权、迟到结果按现有身份代次丢弃。
- 当前版的一条未处理 expired 即进入队列，不因 useful 较多而隐藏。旧版反馈保留并在历史版本中显示；不把旧版的过期票套给已发布新版本。旧版存在问题可由管理员另起提议，不自动修改当前版。

### 7.3 待复核、确认有效和归档

管理员专属队列条件为未归档且（从未复核 / 90 天到期 / 当前版有未处理 expired），可显示多个原因。普通成员列表有“待复核/有过期反馈”标记，规约仍按已发布状态使用并带提示，系统不凭反馈自动删除、降级或换版本。

管理员可以：查看反馈与固定正文；“已核对，仍有效”（必填简短说明）；发起修订/整理提议；归档。确认有效带 expectedItemVersion/currentVersionId 和本次读取的 feedbackWatermark（反馈事件递增水位），只处理截至该水位的反馈，追加复核记录并更新 lastReviewedAtMs；不写正文新版本。之后新来的反馈继续进队列，不能被旧确认吞掉。

发布新正文版本以该次明确批准时间作为本版复核时间，旧版票和审核历史保留。归档沿既有权限、条目版本及通知规则退出自动目录，新引用按现行归档限制；已有固定旧版仍可供当前有权成员主动读取。队列查询用数据库时间，刷新时自动计算，无定时扫描、定时 Agent 或新增通知总线。

### 8.2 形状、上限、排序与错误

- 标题/termKey/category/正文继续现有字符约束（标题 200、termKey 64、category 80、普通正文 16384 字符），同时对实际 UTF-8 总请求限制 128 KiB；规约另受 4 KiB 单条上限。来源摘要 ≤2000 字、sourceRefs/relatedReferences 各 ≤20、退回/修改/复核理由 1～1000 字。起草工具请求仍守回环服务 64 KiB 上限，超限返回具体原因。
- IDs 沿当前 UUID/UserId；revision/version 为正安全整数；requestId/readId 为 UUID。scope.repositoryIds 不重复；无团队的发布/提议请求拒绝。空白标题/正文、空退回理由、未知 level/字段、跨团队仓库或版本拒绝。
- 列表默认 50、最大 100；知识保留 knowledgeId 升序游标，版本保留版本号降序；提议按 proposalId 升序、待复核按 knowledgeId 升序，审核/反馈历史用单调事件 ID 升序。afterId 严格对应本查询的已授权对象，条件变化重置游标；游标不能把个人草稿泄露给其他成员。动态计数不参与分页键，逐页重验资格，不承诺变化中的跨页快照。
- SQL 与集群搜索必须有相同已发布/归档/级别/范围语义；索引命中仍回数据库复核当前指针与权限。客户端分页不会把全团队第一页先截断再按范围过滤，造成后面的适用条目永远不可发现。
- 复用 AUTHENTICATION_REQUIRED、WORKSPACE_MEMBER_REQUIRED、WORKSPACE_ADMIN_REQUIRED、RESOURCE_NOT_FOUND、VERSION_CONFLICT、KNOWLEDGE_ARCHIVED；新增 PROPOSAL_STATE_CONFLICT、KNOWLEDGE_BASE_CHANGED、KNOWLEDGE_KEY_EXISTS、IDEMPOTENCY_CONFLICT、RULE_BODY_TOO_LARGE。错误附安全的可重试说明，不附无权来源正文。
- 规约聚合超预算为本机具名状态 RULE_CONTEXT_TOO_LARGE，列出当前有权条目及预算，整组未附带而普通消息继续；来源正文不可读、Agent/MCP 不支持、缺少结构化候选分别显示真实失败，不用“成功生成”占位。

### 8.3 桌面具名端口

扩展当前 CollaborationAppsHost/客户端、主进程 allowlist 与 preload，按上述业务名提供 proposal/review/feedback/read-report 动作；Cookie/CSRF 仍只在主进程。读命中回报不作为 renderer 可任意调用的“加次数”端口。

本机起草单独提供 `startKnowledgeDraft(scope, selection)`、`cancelKnowledgeDraft(executionId)`、`getKnowledgeDraft(executionId)`、`answerKnowledgeDraftPermission/answerKnowledgeDraftElicitation` 和受限状态通知。scope 来自真实本人会话，selection 只有轮次/消息标识，不接受任意 cwd、可执行文件、网络 URL 或模型密钥；主进程加载实际文本与 provider。状态刷新只随真实运行事件，无常驻轮询。
