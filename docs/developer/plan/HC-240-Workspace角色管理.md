# HC-240 Workspace角色管理

状态：2026-11-23 按统筹已批准的[Spec](../spec/HC-240-Workspace角色管理.md)实施。用户授权整卡；先形成本 Plan，再 Todo，然后依次推进 A～D。共享工作区已有本卡文档，生产修改前复查并保留其他变化，不提交/推送。

## 问题、方案与结果

团队目前没有角色，直接移除会遗留责任。先建立服务端真实权限，再把任务、项目和仓库交接与成员移除放在一个事务，最后在原设置页接入正式操作。剩余成员保留历史只读，原作者不转名，接手人主动用自己的 Agent。

## A：角色与权限基础（可演示停点）

1. 同步 Schema、Java/TS 类型和 fixtures；新增团队角色、成员状态/版本、最新权限快照和管理请求。
2. 单份 DDL 补成员/团队版本、仓库 owner/version、回执及交接历史字段；初始化明确一管理员，历史映射仅对未初始化数据生效。
3. 实现最新成员/管理员检查与团队先行锁；知识直接发布、仓库写入校验 admin，相关写事务统一锁序。
4. 实现加入、角色变化、幂等回执和最后管理员保护。

可见结果：真实接口返回两种角色，开发者写管理被拒，最后管理员被保护。必要验证：类型/契约/Java 构建和隔离 MySQL 上的角色正常链路及保护。

## B：交接与移除（可演示停点）

1. 基于真实责任生成固定排序的完整预览与摘要，支持分页和 Project 接手人资格。
2. 同事务重读/校验完整清单、显式 Project 加权、转交责任、停止共享、撤销成员并保存回执/通知。
3. Task 回 todo、保留旧会话来源；creator 历史不变，离职后有效 Project owner 代管验收；仓库可待认领，活跃 Task/Project 不可空。
4. 同步当前权限与通知接收人过滤，保留原共享历史只读。

可见结果：接手人真实待办更新，旧人被拒，历史仍可读。必要验证：真实主交接路径，顺带预览过期零部分写入、重复回执、Project 显式加入边界。

## C：正式团队设置（可演示停点）

1. 加入具名客户端和桌面桥，真实刷新身份与当前团队权限；窗口激活、轻通知、管理拒绝触发合并刷新，旧回包不复权。
2. 原设置中提供名单、工号添加、角色修改、负责人设置、分组交接预览及逐 Project 阅读权确认。
3. 按最新权限控制知识发布/仓库管理；消费移除字典和角色状态显示离开标识，清除失权团队缓存。
4. 复用 233 当前身份/缓存失效入口，复核工具使用前权限；如需改变其业务接口则回报统筹最小接点。

可见结果：正式 Electron 可完成角色变更和一次交接，旧页面不再提供失权管理。必要验证：隔离 MySQL/Java + 正式 Electron 一条管理员/开发者路径，不以夹具替代。

## D：收口与回调（可演示停点）

按改动运行必要构建、类型、契约、边界和文档/任务检查，保存真实证据。更新用户说明、架构、Todo 和 Task；范围正式路径全部打通才标待验收，未通则进行中。241/243 和目标 TDSQL/完整中间件/双平台留具名联调，不伪造成功。回调唯一统筹 lody 后停止，不轮询、不归档。
