## 5. 停点一：真实 Electron 子进程能持久记录并排他启动

观察：驱动实际 Electron 主进程后，只出现一个拥有 ledger 的 Runner；提交记录、停止/重开仍读同值；第二个真实子进程被 owner 锁拒绝；原持锁进程退出/崩溃后新进程能取锁，但未确认的调用/遗留子进程仍阻止重跑。

1. 选择唯一桌面托管路径 `utilityProcess.fork`，在 app ready 后由 `runner-supervisor.ts` 启动编译后的 `apps/runner` 入口，受限消息端口只承载宿主具名动作/状态；不向 renderer 暴露 UtilityProcess。按 [Electron utilityProcess 文档](https://www.electronjs.org/docs/latest/api/utility-process)使用 Node 子进程和消息端口；这不证明其 SQLite/启动参数已通过。
2. 同一正式子进程中实际 import node:sqlite，记录它的 Node/SQLite 版本；按 Spec 初始化隔离 runner.sqlite、读回 WAL/FULL、写事务、关闭再开验证。Node22.12 参数只按实际能力决定启动设置，不通过换外部 Node 的 fallback 掩盖宿主失败。
3. 实现真正 owner.sqlite 排他连接/生存期，与业务账本分开；两个真实子进程竞争同一目录。用有界、无业务副作用的受控子进程验证正常退出、强制中断、遗留进程/不明调用事实，不按 PID 存在或锁释放推断终态。
4. 限定本地受保护路径，验证权限/目录重开和缺失/损坏账本拒绝。只有能力被证明后才扩大到设备业务；必要构建/类型/边界和真实宿主驱动退出/清理均通过才交停点。

停止条件：实际 Electron 不支持选定 API/参数、无法证明锁边界或进程退出，保留日志与隔离账本，回调统筹修订单一方案；不继续二、不加 JSON/内存/另一个 Node 数据路径。当前桌面制品/发布环境尚未证明可用，此停点专门解除该技术缺口。

## 6. 停点二：真实设备与项目共享元数据，供 HC-195 接保存

观察：通过同一生产身份客户端从 user01 明确登记设备，服务器只存秘密摘要；本地选择的目录与项目 ID 持久对应。项目默认未共享，明确共享后真实 SharedProjectAccess 返回同版本/目标；离线仍可选择有效共享目标，user02 不能管理 user01 设备。重复请求保持首结果，停止共享递增版本而不删历史。

1. 在设备域实现三表、请求去重和 DTO/HTTP 用例，以及加入调用方同一事务的 SharedProjectAccess；复用 HC-194 enabled/成员规则。HTTP时间/游标引用 UtcTimestamp，SQL epoch 毫秒只在数据层转换；版本/序号是十进制字符串。
2. 提供 `V002__device_project.sql` 给统筹顺序加入；设备主表/项目归属与共享版本、请求 scope/正文摘要/首次结果约束对应 Spec。普通启动仅 validate，init-demo 仍只处理原身份基础，不造设备/项目。
3. 统筹接合同资源/错误集合/安全路由/同源授权和现有客户端具名设备方法；保留 Cookie/CSRF 与 Bearer 的精确分流、固定 Origin/TLS、不开放 renderer 网络。秘密只在受限宿主/账本内。
4. 本地 project-registry 实现原生选择结果登记、realpath/目录身份、共享前后持久确认；对外 HTTP 只发标识/展示字段，未实现 ACP 的真实配置 available=false。必要冒烟可由驱动调用同一生产宿主登记方法，完整 UI 在五接入。
5. 在隔离真实 MySQL/Java 执行 V001→V002，验证登录、登记/重试/冲突、成员/所有者、分页/版本、离线授权、共享/停止共享及明确拒绝；新表写失败无半记录，缺迁移启动拒绝。记录原身份快照并还原本轮夹具。

交付给统筹：真实 SharedProjectAccess、已登记 V002/设备 HTTP 最小可运行基线、domain DTO/夹具和安全接入证据。HC-195 据此开始真实目标创建/输入保存；本任务此时不宣称 WSS、队列或 ACP 已完成。

## 7. 停点三：Runner/WSS 实际受理与本地恢复

观察：Java 和真实 Runner 主动出站连接，替换连接后旧帧/旧 close 无效；同一 ledger 重启可回报原命令和连续来源；invoking 后无终态的项保持 unknown，不产生第二次端口调用。生产缺真实执行端口时显示不可用。

1. 按 Spec 补领域控制帧/外壳，execution 消息、确定性指纹与本地拒绝原因均引用 HC-195 唯一源；待该最小契约/接口可编译再接消费，不复制 payload 或放缺失 `$ref`。
2. 实现 Java DeviceChannel/DeviceDelivery 当前 socket/connectionId、严格握手、单次恢复、有限 H 补传和共享版本同步；metadata 与执行事务分包。目录/能力拒绝在 accepted 与原决定已落盘后、invoking 前产生同名 notInvoked rejected，不永久挂起。
3. Runner 实现 ledger 状态/来源原子写、start/决定/cancel 保存、序号与连续确认清理、原生同值绑定、目录占用/背压/容量与写失败停止。accepted 确认但决定丢失仍重传原 accepted；取消先到的禁启/cancel.received/cancelled 同事务，恢复记录含真实终态和两序号，不等 start。
4. 所有控制帧按精确字段/分页结束消费；冲突、缺账本、缺号、超限均不盲目 ready。连接认证与新操作授权分开，既有获准结果仍可提交。所有网络不跨 JDBC/SQLite 事务。
5. 独立冒烟装配通过真实 Java WSS/真实 SQLite，必要时向生产通道注入受控事务端口检查传输契约；受控实现只在开发驱动/测试源码，不进入生产 JAR/默认 Bean。其“提交”只记为传输停点证据，四必须换成 HC-195 真实事务。

必要观察覆盖一条正常受理→决定→本地终态、重复/冲突消息、旧 socket、一次断线重开、cancelBeforeStart 补传与一处实际记录失败。受控执行端口每次调用独立追加本轮副作用计数记录，不自己去重，以便观察 Runner 是否重复调用；这仍不是真实 Agent/Git 证据。实际执行域未装配时对应生产能力保持不可用，不塞空成功对象。

## 8. 停点四：与 HC-195 真实保存/决定/恢复事务联调

观察：同一真实 Java/MySQL 实例含 V003，user01 提交原目标输入后，Runner 的 accepted/决定/来源进入 HC-195 的生产事务。丢响应、重连和重启只增加可靠确认，不新增输入/执行/决定/副作用；终态前不放行后项。

1. 统筹按 V002→V003 迁移/校验接入，串行装配真实 ExecutionReceipts/Recovery/Dispatch。设备只唤醒/送原消息，不改会话表、不另扫云队列；调用加入既有同 DataSource 短事务。
2. 用 HC-195 真实 HTTP 创建共享会话/保存输入、查看执行/历史；队列选择、原决定、唯一约束和连续前缀均来自数据库。Runner 只注入明确标记的开发执行端口；生产仍不冒充 ACP 已接通。
