# HC-179 内网依赖源码化实施计划

关联 Spec：[HC-179-内网依赖源码化](../spec/HC-179-内网依赖源码化.md)。目标是从指定基线 `0bff89e6cd9cf3e326db68d90a39a4f8e1e88885` 产出本地分支 `feat_hc_179_内网依赖源码化`，到“分支可搬运”停点即停止。

> 范围变更（2026-09）：追加「npm 包管理器迁移」阶段，规格见 Spec 同名章节。动机：企业内网网络限制使 `bun install` 在本仓库依赖规模下失败，而 Bun 二进制可用。Bun 收缩为运行时，npm 承担依赖安装。

## npm 包管理器迁移（范围变更新增步骤）

依赖顺序：先固化 lock 门禁的单测契约（source_policy、vendor_policy），再替换安装命令（install.ts），再适配 Python 侧检查，最后切 lockfile 与工程配置。每步以 focused tests 先行。

### N1. 先写失败测试：lock 与工具链门禁的 npm 契约

- `source_policy.test.ts`：`validateNpmLockSource` 读取 `package-lock.json` fixture（内网 URL 通过、公网 URL/缺文件失败）；`expectedBunVersion` 改读 `engines.bun` 的用例；npm 版本校验用例。
- `vendor_policy.test.ts`：lock fixture 换为 `package-lock.json` 结构（五包 `link: true` + `resolved` 相对路径通过；五包 registry 解析、嵌套 locator 失败）。
- `packages/agent/tests/test_dependency_check.py`：`check_npm_lock` 用例。

### N2. 实现门禁适配

- `source_policy.ts`：`validateBunLockSource` → `validateNpmLockSource`（文件名与错误文案，URL 白名单逻辑复用）；`expectedBunVersion` 读 `engines.bun`；新增 `expectedNpmVersion`（读 `packageManager`）与 node 最低版本校验。
- `vendor_policy.ts`：`validateVendoredWorkspaceLock` 解析 `package-lock.json` 的 `packages` 树，断言五包 link 解析与无 registry 回退。

### N3. 替换安装命令与工具链校验

- `install.ts`：freeze 阶段 `npm ci --registry <内网源> --legacy-peer-deps`；resolve 阶段 `npm install --registry <内网源> --legacy-peer-deps`；preflight 增加 npm/node 版本校验，保留 Bun（运行时）/uv/Python 校验；安装后 vendored realpath 门禁不变。
- `check_dependencies.py`：`--bun-lock` → `--npm-lock`，`check_bun_lock` → `check_npm_lock`。

### N4. 切换 lockfile、依赖声明与工程配置

- 根 `package.json`：`packageManager` 改 `npm@<精确版本>`；新增 `engines`（`bun: "1.2.19"`、`node: ">=20"`）；`test:web:e2e` 的 `bunx` → `npx`。
- 新增仓库根 `.npmrc`：`legacy-peer-deps=true`。
- workspace 依赖声明适配 npm（实测约束：npm 遇 `workspace:` 协议即 EUNSUPPORTEDPROTOCOL；带 `os`/`cpu` 的 workspace 成员在平台不符时 notsup 且 `--os`/`--cpu` 无法覆盖）：CLI 与五包间 7 处 `workspace:*` 改为精确版本（`@za38/protocol` 用 `*`）；vendored `@opentui/core-win32-x64` 清单移除 `os`/`cpu`；`vendor_policy.ts` 门禁同步（精确版本断言、禁止 `workspace:` 残留、os/cpu 反向断言、lockJson 去除 bun 尾逗号兼容）；`provenance.json` 移除三个 workspace 归一化条目、新增 os/cpu 移除记录并更新三包 `directorySha256`。
- 开发机在公网源下生成基准 `package-lock.json` 提交；删除 `bun.lock`。生成必须在干净临时副本中进行（arborist 读取 bun 布局 node_modules 会崩溃，且不得改动开发机现有安装树）；生成结果为平台全量 lock（含全部 darwin/linux/win32 optional 条目）。内网首次 `deps:resolve` 重新解析为内网 URL 版本（验收阶段工作）。
- `@types/bun` 与 Bun 相关 devDependencies 保留（运行时仍为 Bun）。

### N5. 文档与验证

- 更新 README、`docs/developer/project/内网依赖安装.md`、`架构总览.md`、Task front matter 中所有 `bun install`/`bun.lock` 的表述。
- 开发机运行：`bun run deps:test`、`bun test scripts/dependencies`、`bun run typecheck`、`bun run project:check`、`bun run docs:check`。`deps:install` 在 darwin 上仍应被 win32/x64 平台门禁在联网前拒绝（正确行为）。

## 可演示停点：npm 安装链路可搬运

用户可检查：

1. `bun run deps:test` 通过，npm lock 门禁用例（公网 URL、registry 回退、嵌套 locator）均失败关闭。
2. 仓库无 `bun.lock`，根目录有 `package-lock.json`（基准版）与 `.npmrc`（`legacy-peer-deps=true`）。
3. `scripts/dependencies/install.ts` 中不再出现 `bun install`，freeze/resolve 分别为 `npm ci`/`npm install` 且带 `--legacy-peer-deps`。
4. 内网 Windows x64 上执行 `bun run deps:resolve` 生成内网 URL 的 `package-lock.json` 后，`bun run deps:install` 可完成冻结安装（该步属于内网验收，不在本停点内）。

## 可演示停点：分支可搬运（原始范围）

## 前置条件与边界

- 工作区起点必须是指定提交且无意外改动；已有用户改动不得清理、stash 或覆盖。
- 只创建/使用本地分支，不 push、不合并 master。
- 五个 tarball 只在实施时放入临时目录并用基线 `bun.lock` SHA-512 校验；临时 tarball 不进入 Git。
- `node_modules`、Bun cache、Python venv、锁文件临时目录均不进入 Git。

## 有序步骤

### 1. 先写失败测试并固定源码化契约

新增 `scripts/dependencies/vendor_policy.test.ts`，用临时 fixture 覆盖正常目录及错误版本、篡改文件、缺发布入口、缺 DLL、错误执行平台、错误包平台、lock registry 回退、嵌套 locator、重复根补丁和安装后 realpath；保留既有 Python Anthropic 回归。先运行测试确认缺少实现时失败。

### 2. 提取并记录精确发布工件

从 npm 精确 tarball 校验五个 SHA-512 后解包到 `third_party/npm/`，保留发布文件、两个包完整 `dist/**` 和 tarball 自带许可证。按发布包作为本地 workspace 的需要只归一化 workspace/dev metadata，保留 `@types/react@19.2.14` 类型解析依赖，固化 `react-devtools-core` 的 `ws@7.5.10`，生成 `provenance.json`；三条 workspace 改写用明确的 `kind/package/field/before/after` 记录，并由门禁校验集合无缺失、错误或额外漂移。

### 3. 接入 workspace 与安装前门禁

修改根 workspace、CLI 直接依赖和包间 workspace 边；从 `bun.lock` 删除五个 registry 解析并加入 workspace 解析，扫描全部 locator，保留其他版本、hash 和内网源策略。实现 `vendor_policy.ts`、`check_vendored_packages.ts`，使 `deps:install`/`deps:resolve` 先 fail closed 于 win32-x64 和静态完整性，Bun install 后及 `deps:check` 再复核五包实际 realpath。

### 4. 保留既有 Python 链路并补齐文档

不改 DeepAgents 补丁、Python venv 选择器或 Anthropic 禁止包检查；更新 README、快速开始、内网安装说明和架构总览，明确临时分支例外、退出条件和 Windows/内网验收边界；创建同名 Task/Spec/Plan/Todo 并同步看板。

### 5. 验证并提交

依次运行 focused dependency tests、`bun run deps:test`、`bun run typecheck`、`bun run build`、`bun run project:check`、`bun run docs:check`、`git diff --check`，再按环境实际运行 `deps:check`。另从 Git 已跟踪内容创建全新 snapshot，删除所有 ignored 安装物后复跑 vendor gate，证明两个发布包的 `dist/**` 不依赖工作树残留。若安装前置因本机 Bun/源/平台限制失败，记录真实错误，不绕过门禁宣称安装完成。维护提交按 Conventional Commit 分开：依赖源码化与门禁、文档与任务链；完成后写中文 `tmp/handoff.md`，停在可搬运分支等待验收。

## 可演示停点：分支可搬运

用户可检查：

1. `git switch feat_hc_179_内网依赖源码化` 后 `third_party/npm/` 五个目录和 `provenance.json` 存在；`opentui.dll` 非空。
2. `bun run deps:test` 通过，篡改/错误平台/registry 回退用例均能失败关闭。
