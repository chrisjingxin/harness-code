# HC-179 内网依赖源码化实施计划

关联 Spec：[HC-179-内网依赖源码化](../spec/HC-179-内网依赖源码化.md)。目标是从指定基线 `0bff89e6cd9cf3e326db68d90a39a4f8e1e88885` 产出本地分支 `feat_hc_179_内网依赖源码化`，到“分支可搬运”停点即停止。

> 范围变更（2026-09）：追加「npm 包管理器迁移」与「依赖工具链零 Bun」阶段，规格见 Spec 同名章节。动机：企业内网限制 `bun install`，且杀毒软件可能拦截 Bun 进程。npm 承担依赖安装，普通工程脚本迁移到 Node，Bun 精确固定为 `1.3.13` 并收缩到专属运行时边界。

> 范围扩展（2026-09）：追加停点 D「跨平台依赖同步」。五个源码化包的边界不变，解除 `deps:sync` 的 Windows-only 执行限制，并按 OpenTUI 0.4.3 的实际 native loader 矩阵校验 macOS、Windows、Linux 安装结果。

## npm 包管理器迁移（范围变更新增步骤）

依赖顺序：先固化 lock 门禁的单测契约（source_policy、vendor_policy），再替换安装命令（最终入口为 `sync.mjs`），再适配 Python 侧检查，最后切 lockfile 与工程配置。每步以 focused tests 先行。

### N1. 先写失败测试：lock 与工具链门禁的 npm 契约

- `source_policy.test.mjs`：`validateNpmLockSource` 读取 `package-lock.json` fixture（内网 URL 通过、公网 URL/缺文件失败）；npm 版本校验用例。曾有的依赖前置 Bun 版本用例在 B3 随职责移除。
- `vendor_policy.test.mjs`：lock fixture 使用 `package-lock.json` 结构（五包 `link: true` + `resolved` 相对路径通过；五包 registry 解析、嵌套 locator 失败）。
- `packages/agent/tests/test_dependency_check.py`：`check_npm_lock` 用例。

### N2. 实现门禁适配

- `source_policy.mjs`：`validateBunLockSource` → `validateNpmLockSource`（文件名与错误文案，URL 白名单逻辑复用）；新增 `expectedNpmVersion`（读 `packageManager`）与 node 最低版本校验。
- `vendor_policy.mjs`：`validateVendoredWorkspaceLock` 解析 `package-lock.json` 的 `packages` 树，断言五包 link 解析与无 registry 回退。

### N3. 替换安装命令与工具链校验

- `install.mjs`：freeze 阶段 `npm ci --registry <内网源> --legacy-peer-deps`；resolve 阶段 `npm install --registry <内网源> --legacy-peer-deps`；preflight 增加 npm/node 版本校验并保留 uv/Python 校验；依赖前置 Bun 校验在 B3 移除，安装后 vendored realpath 门禁不变。
- `check_dependencies.py`：`--bun-lock` → `--npm-lock`，`check_bun_lock` → `check_npm_lock`。

### N4. 切换 lockfile、依赖声明与工程配置

- 根 `package.json`：`packageManager` 改 `npm@<精确版本>`；新增 `engines`（当前要求 `bun: "1.3.13"`、`node: ">=20"`）；`test:web:e2e` 的 `bunx` → `npx`。
- 新增仓库根 `.npmrc`：`legacy-peer-deps=true`。
- workspace 依赖声明适配 npm（实测约束：npm 遇 `workspace:` 协议即 EUNSUPPORTEDPROTOCOL；带 `os`/`cpu` 的 workspace 成员在平台不符时 notsup 且 `--os`/`--cpu` 无法覆盖）：CLI 与五包间 7 处 `workspace:*` 改为精确版本（`@za38/protocol` 用 `*`）；vendored `@opentui/core-win32-x64` 清单移除 `os`/`cpu`；`vendor_policy.mjs` 门禁同步（精确版本断言、禁止 `workspace:` 残留、os/cpu 反向断言、lockJson 严格解析）；`provenance.json` 移除三个 workspace 归一化条目、新增 os/cpu 移除记录并更新三包 `directorySha256`。
- 开发机在公网源下生成基准 `package-lock.json` 提交；删除 `bun.lock`。生成必须在干净临时副本中进行（arborist 读取 bun 布局 node_modules 会崩溃，且不得改动开发机现有安装树）；生成结果为平台全量 lock（含全部 darwin/linux/win32 optional 条目）。内网首次执行 `npm run deps:sync -- --update-lock`，重新解析为内网 URL 版本并继续完成同步（验收阶段工作）。
- `@types/bun` 与 Bun 相关 devDependencies 保留（运行时仍为 Bun）。

### N5. 文档与验证

- 更新 README、`docs/developer/project/内网依赖安装.md`、`架构总览.md`、Task front matter 中所有 `bun install`/`bun.lock` 的表述。
- 开发机运行：`npm run deps:test`、`npm run typecheck`、`npm run project:check`、`npm run docs:check`。在当时的 N5 停点，`deps:sync` 的默认和更新锁模式仍由 win32/x64 门禁拒绝；该历史行为由后续停点 D 替换。

## 停点 E：安装门禁按当前平台收敛

### E1. RED：复现 Windows 误报与无关平台 lock 阻断

- 在 vendored fixture 生成 provenance 后把文本文件转为 CRLF，锁定 Windows 正常检出不应影响依赖门禁。
- 从 fixture lock 删除非 Windows x64 native 记录，锁定“本机安装应通过，全平台审计仍失败”。
- 锁定更新 lock 模式可以先跳过旧 lock，但更新后必须通过当前平台门禁。

### E2. GREEN：拆分源码、本机安装与全平台审计

- 删除与 Git 重复的 vendored 目录 Hash 和 patch Hash，不新增换行归一化层或 `.gitattributes` 特例。
- 保留 `validateVendoredWorkspace` 作为全矩阵审计，新增明确的源码快照与当前平台安装门禁，避免用泛化配置掩盖职责。
- `sync.mjs` 的冻结模式在 npm 前校验本机 lock；更新模式先校验源码，npm 更新后再校验本机 lock。`deps:check` 使用本机门禁。

### E3. 验证与停点

- 运行 focused RED/GREEN、`npm run deps:test`、`npm run deps:check`、工程/文档检查与 `git diff --check`。
- 用 CRLF fixture 复跑源码门禁，证明 Windows 换行不再误报。
- 记录 macOS 实际可达的 `deps:sync` 结果；Windows 企业空缓存安装仍由目标环境验收。

## 可演示停点：Windows 安装不被无关平台阻断

Windows x64 上的 `npm run deps:sync` 只要求当前 vendored DLL/workspace 链路，不因 macOS/Linux native lock 记录缺失失败；同一份变更的 `deps:test` 仍能抦截不完整的全平台提交。
