# HC-205 主题与通用视图抽离：实施计划

2026-11-09 统筹审查通过，按三个可演示停点实施。规格见 [Spec](../spec/HC-205-主题与通用视图抽离.md)，当前阶段及结果见 [Task](../task/HC-205-主题与通用视图抽离.md)，逐项执行见 [Todo](../todo/HC-205-主题与通用视图抽离.md)。

## 1. 交付顺序与不变量

当前旧 Web 有可复用的冷紫主题、头像及代码渲染，新桌面则仍使用临时绿色基础样式。按三个可演示停点，把可复用资源按依赖顺序迁到独立 UI 包，并逐步接入真实宿主：

```text
旧主题/品牌 → 停点一：公共主题和图形可预览
→ 停点二：Markdown、代码高亮、复制及外链宿主接线可供区域消费
→ 停点三：基础页面/原生窗口颜色收敛，构建后 Electron 实际冒烟
```

每个停点先由统筹派发文件归属；只推进当前停点，完成或真实阻塞时回调一次，停止等下一次派发，不轮询、不把清单一次做完。接口已由统筹代表尚未认领的 HC-206/207/208 审查，无须等待这些任务认领；每个停点的产物、实际验证和未覆盖项分开记录。阶段通过只标待验收，不自动归档、提交或推送。

公共接口和渲染行为以 Spec 为准。HC-205 在停点二接入桌面 `copyText` 和 `openExternal`。下游插槽的具体位置与注册生命周期由 HC-201/206/202 在装配相应视图时确定。

始终保留旧 Web 源码和设计稿，旧路径只作迁移来源。新 UI 不导入旧 CLI、旧 protocol、Harness 内部类型或 Node/Electron；不搬迁整个 Timeline/Tool/Composer、文件/Git、协作导航或 Trace，不建立占位扩展注册系统。可复用样式必须按最终层叠结果拆分，而非把整份旧 `styles.css` 复制到各区域。无 Java、数据库、ACP 或旧 Web server 前置。

## 2. 停点一：公共主题、品牌与头像可预览

**可见结果：**使用后续新增的 `npm --workspace @workbench/desktop run dev:ui-preview` 打开独立开发预览，可切换浅/深/跟随系统，看到冷紫品牌标志、用户和 Agent 头像、公共按钮及状态色；缩放和窗口尺寸变化后仍可阅读。对照旧主题最终样式，品牌标志为 `Command` 图形，头像为原 `Sparkles`/`MessageCircle` 图形，而不是另画一套。此时正常基础页面和原生标题栏仍可能是 HC-193 临时颜色，统一由停点三完成，不能把预览当成正式页面已经迁移。

### 2.1 从来源到可使用的基础

1. 从 `packages/cli/src/web/presentation/theme.css` 将公共 light/dark 颜色和 `--brand` 派生关系迁入 `packages/workbench-ui/src/theme/colors.css`；根节点以 `data-theme` 选色。保留背景/文字、行动、成功/等待/失败、Diff、文件类型和语法等公共语义；Trace/Compose 专有 token 留对应任务，优先引用公共基础色。
2. 从旧 `styles.css` 只抽最小 reset、字体/尺寸、焦点、确实跨区复用的按钮/图标按钮与可访问隐藏文字。公共入口 `packages/workbench-ui/src/theme.css` 汇总颜色和公共样式，导出为 `@workbench/ui/theme.css`，页面装配一次。旧侧栏、对话、工具、Composer、文件/Git 和布局规则不进入公共 CSS。
3. 从 `brand-logo.tsx`、`timeline.tsx` 及最终生效的头像规则迁出 `BrandMark`、`RoleAvatar` 到 `common/`，沿用原图形、尺寸和色调；从 `presentation-shared/formatters.ts` 迁出 Spec 规定的纯数值显示函数。通过 `@workbench/ui` 显式导出图形、格式化函数及类型，不导出旧快照/控制器。
4. 新增 `scripts/workbench/generate-native-theme.mjs`：只读取上述唯一公共 CSS 颜色源的浅/深背景和文字，生成 `packages/workbench-ui/dist/native-theme.js` 与对应声明；将 `@workbench/ui/native-theme` 指向该纯数据产物。缺失、重复或不能用于原生窗口的必要色值应让构建报错，不沿用旧产物或手写第二份色表。脚本放在仓库级 `scripts/workbench/`，因为现有边界检查会扫描 UI 包内脚本并禁止 UI 包访问 Node；UI 运行时仍无 Node。
5. 调整 UI 包构建顺序为编译组件并复制公共 CSS、从同一 CSS 源生成原生数据及声明；新的 main 消费放在停点三。清理构建产物后重新构建时必须能再生成两个公开入口，不能依赖以前的 `dist`。依赖版本由统筹在共享 manifest/锁集成时确认；本停点需要图标库，后续 Markdown/高亮所需依赖按停点二接入。

当前 `Workbench` 本身导入旧的 `src/theme.css`，而根出口也重导出 `Workbench`。建立同名新公共样式时，先把基础页原布局/临时颜色从公共入口中分开，限定在基础页面容器内，确保从根出口使用公共组件的预览不会被其 `:root`、`main`、按钮等规则污染。临时基础页仍保持可用，停点三删除其临时色表和 fallback；不能在同一页面叠两套全局 reset 或长期维护两套主题。

### 2.2 本停点最小验证

在获派实施时先建立第 5 节预览的主题/图形部分，Markdown 等样例等停点二再加入，避免引用尚未实现的出口；构建 contracts/UI，运行受影响 UI/桌面的类型和边界检查。实际观察浅/深预览、品牌/头像、文字和状态色，并检查以 CSS 源生成的 `native-theme` 出口可被不加载 React/CSS 的 main 使用；记录实际平台和观察结果。不宣称原生窗口配色、Markdown 或 Worker 已完成。此后 HC-208 可以先使用主题/图形，HC-206/207 可以讨论或使用这些基础；完整公共渲染仍等停点二最小出口。

## 3. 停点二：公共渲染与真实宿主动作

**可见结果：**同一独立开发预览显示 Markdown 列表/表格、TypeScript 围栏代码、Diff 红绿行和文件式只读高亮；代码随输入更新，复制当前原文后可粘贴核对。预览从 `@workbench/ui` 与 `@workbench/ui/theme.css` 消费，不访问旧源码或旧 Web server。构建产物含实际 Worker；最终 `file://` 原生加载和基础页面配色留停点三证明。

### 3.1 迁移顺序和公开范围

1. 迁 `packages/cli/src/presentation-shared/language-catalog.ts` 的 Web 语言/别名与路径字符串识别到 `rendering/syntax/`，移除 TUI 专用字段；迁 `web/syntax/{protocol,language-loader,worker,highlight-service}.ts`、`web/presentation/code/` 的必要实现。静态打包原有 15 种语言及 plaintext，删除 `/web/syntax-worker.js` 和 `/assets/syntax-worker.js` 生产路径依赖，保留 Spec 的大小/行数、缓存、超时、释放和纯文本降级约束。
2. 迁 `markdown.tsx` 和 `code-block.tsx`、实际公共 Markdown/代码/语法/Diff 围栏样式至 `rendering/`；Markdown 保留 GFM、原始 HTML 文本化、图片只显示 alt 和链接 scheme 约束。仅对高亮计算防抖，始终显示及复制当前代码；用完整内容、规范语言和所用主题核对缓存，不能让旧结果或哈希碰撞改变新文本。
3. 从根出口提供 Spec 第 4 节全部接口：`Markdown`、`CodeBlock`、`HighlightedCode`、`SyntaxSpan`/`SyntaxScope`、`useSyntaxHighlight`、`renderSpans`、`RenderingActions`、语言解析及纯格式化函数。低层范围为 UTF-8 字节半开区间，逐行视图由调用方换算偏移，并使用 `wb-syntax` 作用域；不暴露 Worker 协议/服务。将 `marked`、`shiki` 加入 UI 正式依赖并协调根锁，不从旧 CLI 的 node_modules 解析。
4. 按构建工具可静态识别的模块 Worker 引用编译 `rendering/syntax/worker`，通过 electron-vite 将代码和静态语言资源输出到当前 renderer 产物；现有 `tsc` 加 CSS 复制不足以产生这个可运行制品。先使用现有 CSP；如实际构建后证明必要，再由统筹审查最小 Worker 来源声明，不放宽 script 来源或禁用 sandbox。

### 3.2 桌面复制和外链：输入 → 校验 → 执行 → 返回

在统筹分配的共享文件时隙，一次性接通 `DesktopHost.copyText(text): Promise<void>` 和 `DesktopHost.openExternal(href): Promise<void>`：

- `packages/workbench-contracts/src/index.ts` 定义两个具名方法和失败语义；`apps/desktop/src/preload/index.ts` 逐方法转发，`renderer/env.d.ts` 继续使用同一类型，不暴露 IPC 对象。
- `apps/desktop/src/main/desktop-ipc.ts` 复用现有 `verifyDesktopSource`、参数个数与主窗口生命周期管理；`copyText` 校验字符串并调用 Electron 剪贴板，`openExternal` 重新解析且只接受 `http:`、`https:`、`mailto:`，调用原生外链能力。失败时 Promise 拒绝，关闭窗口清理对应 handler。既有导航、新窗口和权限限制保持。
- 独立预览把实际 `window.workbench` 的两方法映射为 `RenderingActions`，其中代码复制走真实端口；正式 renderer 按实际组件装配提供同一动作，不预置假成功或建立浏览器/原生两条生产 fallback。正式基础页此时没有 Markdown 消费者，无需为了占位增加无用业务 UI。
- 组件在调用成功后才显示复制成功；失败或能力缺失如实反馈。安全链接仅在用户明确操作时交给宿主，不自动打开任意第三方地址；必要冒烟不以打开外部网站作为前置。仅靠代码审查或预览中的替身不能声称操作系统外链已实测。

### 3.3 最小代码交付和观察

真实开发窗口中观察 Markdown、代码高亮、中文及 Diff 围栏；复制一段代码并粘贴到预览输入框，核对当前原文。构建独立预览产物并检查 Worker/资源由新依赖生成、没有旧 Web 地址；运行受影响 contracts/UI/desktop 的构建、类型和边界检查。此时公开出口、样式、预览和 Worker 构建可供 HC-206/207/208 开发，不必等整个 HC-205、Java/Runner/ACP 或 HC-202 完成；实际生产 `file://` 加载与完整区域装配尚未证明，回调时须明确这一点。

## 4. 停点三：基础页面收敛与构建后原生冒烟

**可见结果：**启动正常构建后桌面，HC-193 基础页已使用冷紫浅/深主题，目录、主题、缩放、身份/设备控件仍可用；启动独立的构建后组件预览，可见 Markdown、头像、代码高亮和真实复制。原生窗口背景、Windows 标题栏所需色值与网页由同一源生成；当前宿主和另一平台的验证结果分别记录。

1. `apps/desktop/src/renderer/main.tsx` 为正式页面加载一次 `@workbench/ui/theme.css`；`workbench.tsx` 继续用宿主 `WindowState.colorScheme` 设置根节点，不新增第二个主题状态或持久化承诺。将基础页原布局留在限定作用域的 `workbench.css`，移除临时色表和重复 reset。
2. `identity/identity.css` 和 `device-registration/device-registration.css` 用 `--surface`、`--line`、`--accent-soft` 等公共语义变量取代 `--panel`、`--border`、`--soft`、`--wb-*` 的临时颜色及 fallback；正常的身份/设备布局、按钮和不可用/错误显示保持。
3. `apps/desktop/src/main/window.ts` 创建窗口时根据实际 `nativeTheme` 和 `@workbench/ui/native-theme` 取背景/标题栏色；`desktop-ipc.ts` 的系统主题通知、显式浅/深切换和 Windows overlay 复用同一数据。不能保留 main 中独立硬编码色表。UI 包和 main 分别经各自的公开入口消费，不让 main 导入 React/CSS。
4. 做必要构建、类型和边界检查；用 `npm --workspace @workbench/desktop run preview` 观察正常构建后页面，再用第 5 节的 `preview:ui` 观察独立构建后 `file://` 预览。实际确认至少一种已知语言的语法着色来自本次 Worker 产物，未知语言为原文；复制后粘贴核对。不能只凭文件存在或纯文本推断 Worker 已运行。
5. 在真实窗口观察浅色、深色、跟随系统、实际缩放及有限宽度，检查基础页现有控件与公共预览；记录操作系统、窗口大小、缩放、命令、截图或等价证据，以及未实测的外链/Windows 部分。保留现有进程、账户和项目数据，不启动或重置 Java/数据库来做 UI 冒烟。

通过后按统筹时隙将真实能力与限制写入用户说明、架构及 Task/Todo；任务阶段只标待验收。完整区域组合、跨平台和故障回归由 HC-204 负责，不将 macOS 单机观察说成 Windows 已验证。

## 5. 开发预览与构建后产物的隔离

当前桌面只有正式 `renderer/index.html`，没有组件独立预览。实施时新增 `apps/desktop/src/renderer/hc205-preview/` 的开发夹具和独立构建配置：停点一展示主题、品牌和头像，停点二再加入 Markdown、代码/Diff、文件式高亮与可粘贴输入框，未实现的组件不提前 import；样例不含真实项目、账号、密钥或聊天数据。夹具仅从公开 UI 出口加载，不修改正式 `renderer/index.html` 为样例页。

在 `apps/desktop/package.json` 新增以下**待实施命令**，由同一份实际桌面 main/preload、来源校验、sandbox 和 CSP 生成开发/预览窗口：

| 命令 | 目标及使用时机 |
| --- | --- |
| `npm --workspace @workbench/desktop run dev:ui-preview` | 开发模式打开预览专用 renderer，供停点一/二观察；不连接旧 Web、Java 或数据库 |
| `npm --workspace @workbench/desktop run build:ui-preview` | 将预览独立构建至仓库忽略的 `tmp/hc205-ui-preview/`，包含生产模式 main/preload、预览 renderer 和 Worker，不覆盖正式 `dist` |
| `npm --workspace @workbench/desktop run preview:ui` | 构建并启动上述独立产物，用真实 `file://` 页面和实际宿主动作进行停点三冒烟 |

预览编排脚本放 `scripts/workbench/`；预览 profile 只在构建时选用夹具 HTML，正式产品构建不含预览入口或可被环境变量切换到任意 URL 的能力。可用独立构建目录保留 `main/`、`preload/`、`renderer/index.html` 的正式相对布局，以便沿用 `createWindow` 对本地页面和 preload 的校验；CSP 生成与正式构建共用实现，不复制一份更宽松规则。预览进程使用独立临时 userData，不调用协作/设备动作，不启动 Runner；只注入固定样例和真实 DesktopHost，预览退出后按实际情况清理自身进程和临时目录，不动既有用户数据。若生产模式预览无法复用这些安全边界，停下报告实际阻塞，不能降级为浏览器截图或把假复制当真。
