# HC-186 移除旧库迁移兼容实施计划

关联：[Task](../task/HC-186-移除旧库迁移兼容.md) · [Spec](../spec/HC-186-移除旧库迁移兼容.md) · [Todo](../todo/HC-186-移除旧库迁移兼容.md)

不新增范围。实现严格按 Todo 执行，一次只推进到下一个可演示停点；到达停点后勾选 Todo、写明如何观察，然后停下等用户确认。未经用户要求不得继续下一停点。

## 通俗怎么拆

先把「现在的库长什么样」用测试钉死，再换上新的打开方式，最后才删旧代码。顺序反过来就没有安全网：删着删着漏了一张表，要等到某个功能运行时才发现。

```text
停点 1  新库一次建成 + 旧库被拒绝 + 删除升级引擎
  │       （数据库这条线的核心，改动最大）
停点 2  删除 thread_binding（Agent → 协议 → CLI）
  │       （先让它不再被使用，再删旧库读取代码）
停点 3  清理只服务旧库的读取代码和表
  │       （执行绑定、两张遗留表、Plugin registry）
停点 4  文档同步 + 整体验收
```

不按 `agent / protocol / cli` 水平分层。停点 2 是一个竖切：删一个字段，三个包一起走完，才算一个可验证的结果。

## 已确认的代码事实

这些事实来自 2026-10-30 对仓库的实际核对，Spec 的判断都建立在它们之上。

- 全新安装也走升级链：`ThreadPersistence._prepare()` 从版本 0 开始逐级执行 `if version < N`，且会写迁移状态文件。实测一次全新安装后，库目录里有 `threads.sqlite3.migration.lock` 和 `threads.sqlite3.pre-v0-migration.bak`。
- 当前 v20 库有 **34 张表、18 个索引**。
- 升级链里混有 `CREATE TABLE`、`ALTER TABLE ADD COLUMN`、`DROP TABLE harness_prompt_epochs`，所以「最终 schema」不能靠拼接各步的建表语句得到，必须以实测导出为准。
- `harness_thread_model_bindings`、`harness_thread_runtime_profiles` 在现役代码中没有任何 `INSERT`/`UPDATE`，只有读取。
- `harness_thread_history_metadata` 的唯一写入点在 v6 导入函数 `_bootstrap_legacy_transcripts`，但它的读取方 `legacy_incomplete_history` 属于「本任务不动」的 Transcript legacy 字段，所以该表默认保留。
- 名字带 `migration` 的函数不全是迁移专用：`_validate_final_database_async`、`_create_checkpointer_tables_in_transaction`、`_migration_validate_final_schema_sync` 等是「当前 schema 校验」，新流程要复用，保留时需改名去掉 `migration` 前缀。
- `thread_binding` 在 `agent_host.py` 的 `_handle_models_list` 里下发；CLI 只在 Agent 没有 `models.select` 能力时才读它，现役路径走不到。
- `compose/recovery.py` 被 `tools/file_tools.py` 使用，并依赖 `compose_work_item_store`，不属于本任务。

## 架构决策

- **先钉住现状，再换实现。** 在改任何生产代码之前，用现有代码导出 golden schema 并让它先通过。新实现必须与它等价，之后每次表结构变化都会让这个测试变红，从而在评审中被看见。
- **golden 以结构化比较为主。** 比较每张表按顺序排列的列信息（名称、类型、非空、默认值、主键）、外键、索引及其列。`ALTER TABLE ADD COLUMN` 会把新列追加在 `CREATE` 语句末尾，扁平化建表时必须把这些列也放在原来的位置，列顺序一致。
- **打开流程是一次「只读判断 + 单事务建库」。** 用 SQLite 自己的 `BEGIN IMMEDIATE` 保证并发首次启动安全，不再需要 `.migration.lock` 文件。
- **删除优于包装。** 不留兼容别名、不留空钩子、不预置升级框架（发版后的升级机制另开 Task）。
- **删表和删它的读取代码同一个提交。** 否则运行时会查询不存在的表。
- **每个停点都是可单独回滚的提交序列。** 停点内按小步提交，不攒成一个大提交。

## 依赖顺序

```text
0. 开工：确认分支、认领 Task、记录基线
   ↓
1. 导出 golden schema，让它在旧代码上先通过（无生产改动）
   ↓
2. 先写失败测试：空库建库、不兼容库拒绝、建库原子性、并发首次启动
   ↓
3. 实现新的 open()：只读判断 → 单事务建库；此时旧升级代码尚未删除，但不再被调用
   ↓
4. 删除升级引擎：thread_persistence 内的升级链和迁移机制、migration_worker.py、migration_recovery.py、故障注入变量、错误码
   ↓
5. 删除/改写依赖旧库的测试
   ↓
6. 停点 1 可演示
   ↓
7. 删除 Agent 的 thread_binding 下发 → 协议字段和生成产物 → CLI 确认框链路
   ↓
8. 停点 2 可演示
   ↓
9. 执行绑定旧格式、两张遗留表（连同 golden）、AgentEngineProfile 遗留判定、Plugin registry v2
   ↓
10. 停点 3 可演示
   ↓
11. 用户文档、架构总览、斜杠命令体系、ADR 状态、全量门禁、Review
   ↓
12. 停点 4：交付与归档
```

停点 2 排在停点 3 之前，是因为 `describe_thread_binding` 消费 `PersistedBindingState` 的旧字段；先让消费方消失，再删数据来源。停点 2 内部固定为 CLI → Agent → 协议：CLI 先停止读取，Agent 再停止下发，协议最后删除定义。反过来会让协议校验拒绝 Agent 的响应，或让 CLI 编译不过。

## 停点 1 — 新库一次建成、旧库被拒绝、升级引擎删除

**改什么：** `ThreadPersistence.open()` 改成「只读判断 → 单事务建库」。空库直接建出最终 schema 并写入 `user_version=1`；非空且版本不等于 1 的库抛 `CHECKPOINT_SCHEMA_INCOMPATIBLE`，文件不被修改。删除升级链、迁移子进程、标记文件、故障注入变量及对应错误码和测试。

**为什么：** 这是整个任务的核心，也是风险最集中的一步。其余停点都是在它之上的收尾，所以放最前面，且先用 golden 测试把安全网搭好。

**怎么验证：** 见 Todo 停点 1。golden 等价测试、新增的行为测试、Python 全量测试，外加 `rg` 负向断言。

**用户怎么看：**

```text
# 全新环境：用一个空的 HOME 启动
HOME=$(mktemp -d) 启动 harness，发一条消息，退出
  → 库的 user_version 为 1，库目录里只有 threads.sqlite3，没有 .migration.lock 和 .bak
  → 再次启动能恢复刚才的 Thread

# 旧库：拿一份现有的 v20 库放进空 HOME
  → 启动失败，提示 CHECKPOINT_SCHEMA_INCOMPATIBLE 和库的绝对路径
  → 库文件的校验和与启动前一致
```

## 停点 2 — 删除 `thread_binding`

**改什么：** Agent 的 `models.list` 不再下发 `thread_binding`，删除 `describe_thread_binding`。协议删除字段和 `threadModelBinding` 定义并重新生成产物。CLI 删除「模型不可变」确认框整条链路。

**为什么：** 这个字段在旧库的 Thread 模型锁定功能下才有数据，现在没有数据来源，CLI 的对应分支在现役路径上也走不到。

**怎么验证：** CLI 先写失败测试（Agent 没有 `models.select` 能力时 `/model` 仍应直接打开选择器，不弹确认框）；Agent 测试断言响应不含该字段；协议用 `npm --workspace @za38/protocol run check` 确认生成产物与 schema 一致。

**用户怎么看：** `bun run dev` 进入 TUI，输入 `/model`，选择器正常打开，选择模型后状态栏更新，与改前完全一致。`rg thread_binding packages` 无命中。

## 停点 3 — 清理只服务旧库的读取代码

**改什么：** 删除 `LegacyModelBindings` 及执行绑定的旧分支；删除 `harness_thread_model_bindings`、`harness_thread_runtime_profiles` 两张表和它们的读取代码（同一提交，同步更新 golden）；按 Spec §5 判据处理 `AgentEngineProfile` 的 v1 形态；Plugin registry 只认 v3。

**为什么：** 这些代码的唯一输入来源是旧库。停点 1 之后旧库已无法进入系统，它们成为永远走不到的分支。

**怎么验证：** `resolve_execution_binding` 的解析顺序测试只剩三级；golden 更新后仍通过；`registry.json` 为 v2 时被拒绝、文件不变、不生成备份。

**用户怎么看：** 在空 HOME 下放入一份 `version: 2` 的 `registry.json` 并启动，报 `PLUGIN_REGISTRY_INVALID`，且 `~/.harness/plugins/` 下没有 `registry.v2.backup.json`。

## 停点 4 — 文档同步与整体验收

**改什么：** `docs/user/故障排查.md` 删除迁移 attempt/poison/子进程相关段落并新增「库版本不兼容」处理步骤；架构总览改写迁移相关段落并写入「Schema 变更规则（发版前）」；斜杠命令体系删除 `model-binding` 描述；ADR 0004 标为已废弃，ADR 0003 的迁移小节加废弃说明，ADR README 同步。

**怎么验证：** `rg` 负向断言；`npm run project:check`、`npm run tasks:check`；Python、CLI、协议全量门禁；`code-review-and-quality` Review 结论写回 Task。

**用户怎么看：** 打开 `docs/user/故障排查.md`，不再出现迁移 attempt 和 poison 的描述，能找到「库版本不兼容」一节和处理步骤。

## 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 扁平化建表时漏表、漏索引、漏列或列顺序不同 | 高，功能在运行时才坏 | golden 结构化等价测试在改任何生产代码前建立；停点 1 完成前不得合并 |
| 误删被新流程复用的「当前 schema 校验」函数 | 高 | 先列出保留清单（Todo 停点 1 第 4 组），删除前逐个确认调用方 |
| 删除测试时误删仍有价值的行为测试（Transcript 幂等、事务回滚、项目隔离） | 中 | 删除前按测试主题逐个确认；行为仍存在的必须保留（Spec §6.4） |
| 依赖旧版本 fixture 的测试数量大，改写工作量超预期 | 中 | 先统计再动手；`thread_fixtures.py` 统一改一处，各测试复用 |
| 并发首次启动测试不稳定 | 中 | 用 `asyncio.gather` 加多次循环；不依赖时序睡眠 |
| 其他进行中任务（HC-167、HC-178、HC-180）同时修改 `thread_persistence.py` | 中 | 开工时先 `git status` 与 `git log` 核对；冲突时按 `resolving-merge-conflicts` 处理 |
| 删表导致 golden 与已有开发库不一致 | 低 | 预期行为；停点 3 完成后开发者需再删库一次，在停点说明里提示 |
| 协议 minor 号是否需要提升存在不确定 | 低 | 默认不提升，契约测试明确要求时以测试为准并记录 |
