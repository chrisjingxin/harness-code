# HC-214 链路日志完整采集 — 实施计划

来源：[Task](../task/HC-214-链路日志完整采集.md) / [Spec](../spec/HC-214-链路日志完整采集.md)。

一次只做到下一个可演示停点，勾选对应 Todo、更新 `tmp/handoff.md` 后停下。不提前做后面的停点。

## 依赖顺序

```text
写入器 schema v2、档位、脱敏、目录
        │
        ├─ 执行期绑定 TraceSession
        │       │
        │       ├─ 模型调用写成 llm.call / step     ← 停点 A 到这里
        │       │
        │       ├─ 审批与等人                        ← 停点 B
        │       │
        │       └─ 工具、落库、压缩、子代理、去掉记账节点  ← 停点 C
        │
        └─ CLI 改读新目录，Web 按 Step 展示          ← 停点 D
                │
                └─ 文档与架构                        ← 停点 E
```

界面依赖文件格式，所以排在写入器之后。审批和工具都依赖同一个 `TraceSession`，但彼此不依赖，仍然按停点分开，避免一次改完看不见中间结果。

## 停点 A：一次模型调用能在用户目录里看全

先改写入器，再接到模型调用。`[trace]` 的 `capture`、`retention_days` 在这一停点生效：`off` 不建文件，`meta` 不写 payload。日志改写到 `~/.harness/trace/<workspace_fingerprint>/`。`_execute` 入口用 `run.trace_context` 绑定 session。

模型中间件链最内层发出 `step` 和 `llm.call`。结束记录带 Spec 第 6 节的模型字段，消息、系统提示词、工具 schema、输出走 `payload` 去重。有重试才写 `llm.attempt`。LangChain 的 `on_chain_start`、`on_tool_start` 不再产生 `graph.node`、`agent.run`、`tool.call`。工具 span 留到停点 C，这一停点的文件里可以暂时没有工具节点。

**怎么看：** `npm run dev` 发一轮不调用工具的对话。在 `~/.harness/trace/` 下按工作区指纹找到新的 `Trace-log-*.jsonl`。里面有 `schema_version: 2`、一条 `llm.call` 结束记录，以及能对上 `message_refs` 的 `payload` 行。项目目录下不再新增 `log/Trace-log-*.jsonl`。界面还是旧的，这一停点不看界面。

## 停点 B：审批和等人出现在同一次运行里

父代理在 `_make_approval_preflight` 每次决定写 `policy.evaluate`，带 `decision`、`layer`、`args_ref`。子代理仍从 `evaluate_permission` 写同名 span。

`interaction.wait` 加在 `_collect_serial_approvals` 和 `_ComposeStageObserver.interact` 里真正调用 `interaction_port.request` 的地方。`request_interaction` 继续覆盖提问等其余交互。三处都使用 `run.trace_context`，不读当时碰巧存在的 contextvar。

**怎么看：** `npm run dev` 用会触发询问的审批模式，让模型调用一次需要批准的工具。同一份 jsonl 里，该工具对应的 `policy.evaluate` 决策是 `ask`，随后有 `interaction.wait`，里面有等待时间和选择结果。放行的只读工具只有 `policy.evaluate`，没有 `interaction.wait`。

## 停点 C：文件里的树和 Spec 第 4 节一致

工具中间件写出 `tool.call`，带入参、结果和 shell / 文件的附加字段，并填上 `policy_span_id`。

`thread.persist` 的结束属性改为 Spec 的 `db.persist` 字段，span 名改为 `db.persist`。不改事务次数。

`context.project` 只在执行阶段占一个节点；准备阶段的耗时进 `run.prepare.projection_ms`。`context.compact` 写触发原因、档位、前后 token、结果和摘要 payload；摘要模型调用挂在它下面，不占用 Step 序号。

删除 `run.complete`、`runtime.acquire`、`runtime.release`、`run.execute` 这四个 span。它们的耗时和结果并入 `run.prepare` 或 `trace.end`。`trace.end` 带终态、总耗时、token 汇总和缓存命中率。

子代理启动时传入父 session 和当前 `tool.call` 的 span id，子 `step` 挂在那个工具下面。

中间件 span 只在失败或耗时达到 50ms 时出现。

**怎么看：** 再跑一轮包含工具的对话。jsonl 里每个面向用户的 `llm.call` 父节点都是 `step`，工具和审批挂在同一个 `step` 下。文件里搜不到 `run.complete`、`runtime.release`、`graph.node`。若这轮触发了压缩，能看到 `context.compact` 和它下面的摘要 `llm.call`。

## 停点 D：Web 按新文件展示

CLI 工作区读取器改为读 `~/.harness/trace/<fingerprint>/`。指纹算法与 Python `workspace_fingerprint` 相同，用同一次启动的工作区路径计算。解析器接受 `schema_version = 2`，跳过 v1 行。`~/.harness/trace` 根目录上的内网索引读取保持不动。

Web 树按 `step` 分组，同一 step 的多条 `db.persist` 收成一组。详情分参数、输入、输出、用量、耗时、错误六区；`*_ref` 展开后显示 payload 正文。引用缺失时该区显示「载荷不在当前读取范围内」。简化视图耗时只读 `duration_ms`。

**怎么看：** `npm run dev` 打开 Web 轨迹页。能看到停点 C 那次运行的 Step 树，点开模型调用能展开消息正文，点开工具能看到参数和结果。旧的 v1 文件不再出现在这棵树里。

## 停点 E：文档收口

更新 `docs/user/` 里配置和 Web 轨迹的相关页，说明 `[trace]`、日志位置和保留天数。增量更新 `docs/developer/architecture/` 里已有的轨迹或诊断文档，不新建平行文档。把 Task 验收清单对照一遍，证据写回 Task。

**怎么看：** 用户文档能独立告诉人日志在哪、怎么关掉。`npm run project:check`、`npm run typecheck`、agent pytest 与 CLI trace 测试通过，或在 Task 里写明没跑的原因。
