# 架构总览

Harness Code 采用“多个表现层 + Project-scoped Python Agent Host”的本机结构：

```text
OpenTUI / 无头 CLI ── JSON-RPC v3 / stdio JSONL ──┐
                                                  ├─ Python AgentHost
Web ─────────────── JSON-RPC v3 / WebSocket ──────┘   ├─ ThreadPersistence
                                                       ├─ AgentEnginePool
                                                       └─ RunCoordinator
```

- `packages/cli/`：参数解析、Python sidecar 生命周期、React/OpenTUI 渲染与交互。
- `packages/protocol/`：v3 canonical JSON Schema、生成的 TypeScript/Python 类型、常量和运行时校验。
- `packages/agent/`：Project-scoped AgentHost、ProtocolConnection、配置、持久化和 Agent Core。

本机 Agent 的文件修改入口保持单一：`HarnessFileToolsMiddleware` 把 DeepAgents 的文件 schema 与
ToolNode 执行都接入同一个 Snapshot contract。`read_file` 只返回局部源行与当前 Thread 的短
Snapshot；`write_file` 只能创建不存在的文件；`edit_file` 必须带同一 Thread 的 Snapshot 和唯一
`old_string`；唯一例外是已读空文件可用空 `old_string` 把整个空文档替换为初始内容，空字符串
不能表示非空文件中的插入位置；`delete_file` 必须带完整读取得到的 Snapshot。创建/编辑后以实际重读内容生成新
Snapshot、实际 changed range 和有界局部窗口；可选 LSP diagnostics 只是提交后的只读摘要。当前不提供批量
`edits[]`、unified diff、`replace_all` 或行号 range 文件入口。未信任的工作区外路径触发目录信任审批；非法路径在审批前直接拒绝。

配置来源、TOML v1 契约和项目配置的可信边界见 [配置架构](配置架构.md)。Plugin
Settings 的 user/workspace secret store、immutable identity、最小 env 注入和
next-host 生命周期见 [HC-158 Settings Phase 4A/4B 设计与实现](扩展与插件机制设计方案.md)；
Phase 4B 的 `plugins.remove --purge-data` 也在 registry lock 内绑定当前
Plugin/package/revision，partial/conflict 不提交移除；平台 credential backend 无法证明
安全时保持 fail closed。它不把插件秘密并入通用 config.toml、Plugin registry 或 Transcript。
Agent、模型、
执行策略、Thread 选择与 Run 历史的长期领域边界见 [ADR 0001：Agent 领域对象、生命周期与兼容映射](adr/0001-agent-domain-model.md)；当前实现与目标 canonical model 的差异必须通过兼容 adapter 和迁移任务收敛，不能以新增 Thread 私有 AgentEngine 绕过。

## Plugin Catalog 与 Agent Plugins 1.0

Plugin 能力在 Python AgentHost 内沿同一条 canonical catalog 链路进入运行时：

```text
PluginStore/PluginManager
  → 已验证的 ExtensionCatalogSnapshot
  → Skill / MCP / Agent / Team / Runtime consumers
  → AgentEngineProfile 与下一次 Run
```

portable Plugin 以根部 `plugin.json` 为身份和 schema 门禁，只从固定的 `skills/` 与 `mcp.json`
位置发现 Agent Plugins 1.0 core。MCP 使用本地 closed schema，按 server 隔离 invalid、unsupported
和 runtime failure；stdio 只接收最小环境与 `PLUGIN_ROOT`/`PLUGIN_DATA`，HTTP/SSE 的 Plugin client
factory 禁止自动跟随 redirect，避免配置 header 跨 origin 转发。Claude Plugin 与 portable Adapter
保持分离：Claude `.mcp.json` 继续使用 Claude 自有 placeholder/timeout 语义，但共享相同的
Plugin HTTP/SSE redirect 安全边界；Hybrid 同时保留两种来源的身份和配置语义。

PluginStore 当前 canonical registry 为 v3。新 Host 在没有 registry 时不创建 `.harness/plugins`、
空目录或 `registry.lock`；首次读取 v2 registry 时在同一锁内严格校验、写入一次性
`registry.v2.backup.json`，再原子迁移为 v3。迁移保留已安装 artifact 与 user/workspace activation，
丢弃 Plugin 专用 fingerprint/trust 字段；replace 前迁移故障保持原 v2 bytes 并 fail closed，replace 已发生但目录 fsync 或结果无法确认时返回 commit-uncertain、保留 backup 并尽力恢复，不能承诺旧文件绝对不变。该能力不把
package digest、registry revision 或内部 ID 变成 CLI/Protocol 用户输入。

HC-175 第一轮（2026-09-01）已将 Plugin 管理收敛为“名称 + 作用域 + 后续启动”：Shell CLI 的
`plugins install/update` 先展示真实组件和 Settings，再通过 `interaction.plugin_consent` 确认；
确认后 install 直接启用所选 scope，update 保留 activation。`list/inspect/enable/disable/remove`
和 Settings 均按名称工作；产品状态只有 loaded、disabled、warning、failed。TUI/Web 不增加管理 UI，
已经运行的 Host 不监听外部 registry，启动加载的 catalog 仍由后续启动的 Host 固定。

第二轮把该启动边界接入所有既有 consumer：`initialize` 只在 Host 资源初始化时按当前 workspace
生成一次 `ExtensionCatalogSnapshot`，再从同一 snapshot 派生 `SkillRegistry`、`AgentCatalog`、
Context blocks、Settings snapshot、MCP generation 和 Hook/LSP/Monitor runtime catalog；CLI 用
同一份 `agent_commands` 构造唯一 `CommandRegistry`。TUI 与 Web 共享 CLI 进程内的
`InteractiveController` 和 Host/catalog，不按 Qwen、Claude、portable 或 Hybrid 增加 UI 分支。
Shell 后续的 enable/disable/update/remove 不改写已运行 Host/Thread/Run；只有新 Host 才读取新的
activation/artifact，workspace override 也只在其绑定目录生效。disabled/failed Plugin 不进入任何
consumer，warning 只反映实际有效组件之外的诊断。

## 企业 OpenTUI 依赖

CLI 固定 Bun `1.2.19`、企业 `@opentui/core` / `@opentui/react` `0.4.3`、React `19.2.6` 和 `react-reconciler` `0.33.0`。其中 `@opentui/react` 以 `react-reconciler@^0.33.0` 作为传递依赖；`@types/react-reconciler@0.32.0` 仅为企业当前可用的编译期声明。完整直接/传递依赖契约见 `../project/dependency-versions.json` 与企业环境生成的 `bun.lock`。

HC-179 的临时 Windows x64 预验证分支把五个精确 npm 发布包放在 `third_party/npm/` 并作为 Bun workspace：`@opentui/core@0.4.3`、`@opentui/react@0.4.3`、`@opentui/core-win32-x64@0.4.3`、`bun-ffi-structs@0.2.4` 和 `react-devtools-core@7.0.1`。根 workspace、CLI 直接依赖及五包运行时边都使用 `workspace:*`；`bun.lock` 对这五个名称只允许 workspace 解析，其他依赖仍由显式内网源安装。`third_party/npm/provenance.json` 以基线 lock 的 SHA-512、完整发布目录（含两个包的 `dist/**`）确定性目录 hash、license 元数据、目标平台和 `ws@7.5.10` patch 来源作为安装前 fail-closed 证据。

`@opentui/core-win32-x64` 必须声明 `win32/x64` 并携带完整 `opentui.dll`；Core 的其他平台 optional package 仍由内网源按实际 runner 选择。五个目录来自精确 tarball，不复制 macOS `node_modules`，不提交 tarball/cache/node_modules；OpenTUI import、JSX runtime 和 native loader 保持原发布内容。`@opentui/react` 保留 `@types/react@19.2.14` 作为 workspace 声明解析依赖。安装后门禁还会检查五包真实消费者的 package/入口 realpath 必须回到 `third_party/npm/`；`deps:install` 与 `deps:resolve` 只允许 win32/x64。该源码化边界只存在于临时分支，正式内网 registry 可用并完成 Windows 空缓存安装/TUI 验收后退出，不构成 canonical master 的永久 vendoring 策略。

TUI 启动时注册 `packages/cli/src/tui/platform/assets/syntax/` 内随源码分发的 Tree-sitter WASM parser 与查询文件。`<markdown>` 使用这些离线资源显示 Agent 输出与 fenced code；网络不可用或未知语言时保持可读降级，审批和 IPC 不受影响。

Python 服务端 stdout 只能输出换行分隔的 JSON-RPC；日志必须进入 stderr 或结构化事件。不得让 TUI 直接依赖 Agent 内部实现，也不得把业务决策放进 `cli`。协议变更必须同时修改两端和跨进程测试。

Build `/goal` 把长期目标、人工审核的验收条件和独立 grader 接到同一条 Run 路径上：SQLite 是 Goal 真源，CLI 只渲染 snapshot 并派发 typed operation，DeepAgents `RubricMiddleware` 只作为验收循环。详见 [目标闭环](目标闭环.md)。

## JSON-RPC v3 与 Host 生命周期

CLI 启动参数在进程创建时绑定 workspace 与 config；`initialize` 只协商版本、调用能力 `requests` 和 Interaction 处理能力 `handles`，客户端不能提交 `cwd/config_path`。CLI Connection 是 Host owner；CLI EOF 关闭 Host、全部 WebSocket、active Run、AgentEnginePool 和 ThreadPersistence，不再提供 `shutdown` operation。

`run.start` 必须携带 SDK 生成的 `thread_id/run_id`。同一 Thread 最多一个 active Run，不同 Thread 可以并发；相同 Run ID 和相同请求是幂等重试，内容不一致返回 `RUN_ID_CONFLICT`。发起 Run 的 Connection 是唯一 owner，独占审批、问答和取消权限。其他 Connection 只能通过 `threads.watch` 观察；该操作仅在 Thread 空闲时原子返回历史并登记未来事件。

Agent 输出统一为 `event` notification。信封包含 `event_id/type/thread_id/run_id/sequence/timestamp_ms/payload`；sequence 只排序 Event，不包含只发给 owner 的 Interaction，因此所有观察者看到相同且连续的序列。审批和问答分别使用 `interaction.approval`、`interaction.question` 反向 request，JSON-RPC ID 是唯一关联身份。文件 mutation 审批可在 payload 中附带严格 tagged `presentation.kind=file_diff`；工作区外目录信任审批附带 `presentation.kind=directory_trust`（待信任目录、目标路径、工具名、读写意图与遮蔽提示）。非文件审批与缺失展示数据仍走通用卡。

运行反馈以 `run.progress` 为主，只携带 Host 已观测的 `preparing|model` 阶段和非负 `elapsed_ms`，因此当前仅支持 Chat Completions、没有公开 reasoning 时，TUI/Web 仍有持续状态。`RunCoordinator` 对 `reasoning_content`、标量 `reasoning`、加密字段和未知供应商载荷 fail closed，不把它们当正文或摘要；摘要不会进入 assistant buffer、canonical Transcript、Thread 恢复或终态历史。

子代理（Subagent）执行时通过 `child_execution_id` 与 `parent_execution_id` 流式发出过程事件（`tool.*`、`reasoning.*` 等），供 CLI 表现层投影出独立的只读子时间线。这条不变量同时适用于内置 Inline child 和 Qwen/Claude/portable Managed Plugin child：Managed 路径的 `capture_only` 只防止子正文进入父 Transcript，不得丢弃 child 工具/思考事件。这些过程事件严格不写入父级 Transcript，也不进入主模型的后续轮次上下文。主模型侧仅通过父级 `task` 的 tool result 获取最终文本或委派失败错误码。现有 300 秒 hard deadline、排队计时、runner 取消、child 终态和 slot/lease 回收仍由 `AgentDelegator` 负责；只有主 Agent 的 `task` middleware 精确消费 `DELEGATION_TIMEOUT`，返回 `ToolMessage(status="error")`，让主图在下一轮继续。执行中 timeout 保留已绑定的 child 时间线，排队 timeout 不创建 child execution；父取消、权限/目标/身份错误以及 Compose/Team 直接调用不经过这层转换，继续 fail closed。

Run 的受理、Thread busy/幂等、owner 校验、取消、Interaction resume、DeepAgents stream、唯一终态和 AgentEngine lease 由 `harness_agent.host.run_coordinator.RunCoordinator` 统一拥有。`AgentHost` 只把协议参数转换为 `StartRun/RunRef/ConnectionRef`，在发送 accepted response 后消费 `RunExecution.events` 并负责多 Connection fanout；因此 stdio 与 WebSocket 不会各自实现一套 Run 生命周期。

Web 接管由 CLI 的 `PresentationCoordinator`（`packages/cli/src/presentation-coordinator/`）管理单实例表现层输入权状态机：`tui-active → opening-web → web-active → returning-tui → tui-active`。`/web` 只启动浏览器页面；静态 server 只在第一次 open 时绑定 `127.0.0.1` 随机端口，路由白名单只接受 `/web/h/<handoff-id>`、`/web/app.js`、`/web/app.css`、`/web/syntax-worker.js` 与 `/web/h/<handoff-id>/ui` gateway upgrade，精确校验 Host/Origin。构建产生 `web-assets.json`，运行时只读取清单内 app 与 Worker 脚本，绝不按请求路径读取文件或接受远端资源。HTML/JS/CSS 返回 no-store、no-referrer、nosniff、same-origin 与限制性 CSP（`script-src 'self'`、`style-src 'self'`、`connect-src ws://127.0.0.1:*`，HTML 不含 inline script/style），不再需要 `'wasm-unsafe-eval'`。

Browser 通过 `WebUiClient` 连接 CLI 进程内的 `WebUiGateway`（HC-114，D-02/D-03 落地）：页面只消费 `state.replace/state.patch` 视图与 `handoff.state`，提交 `intent{requestId,revision}` 并按 `intent.outcome` 与 requestId 一一对应处理结果；`revision` 由网关单调递增，Browser 丢弃晚到更新，intent 仅 `web-active` 且 revision 有效时受理。首次 URL 中的 bootstrap token 绑定 handoffId、loopback Origin 与 60 秒 TTL；renderer 被接受后，网关先下发 handoff-scoped 单次重连 token，页面只把它写入当前标签页的 sessionStorage，每次成功重连都立即轮换并使旧 token 失效。token 无任何 Agent Host capability，页面不接收 Agent endpoint、attachmentId 或 attachment token。同一 handoffId 只允许一个活跃渲染连接，第二个并发连接收到 `already-open` 并被关闭，而且拒绝发生在 token 消费前，不会破坏主页面之后的刷新。Browser 断开后进入重连宽限（默认 10 秒），宽限内同页重连自动 `state.replace` 重同步，宽限到期、ready 超时（65 秒）、归还、退出请求、畸形帧或 CLI close 都收敛到 `returning-tui → tui-active`，Host 控制权始终留在 owner（ControlLease 不被 Web 触发）。

## Web 语法高亮

根据 ADR 0003（单一 Interactive Core 与双原生 Renderer 架构），Web 端代码高亮统一由 Shiki Worker 单例（`shiki/core` + JavaScript Regex Engine + fine-grained imports）承载，不使用 Web Tree-sitter WASM。主线程 `ShikiHighlightService` 拥有 128 条 / 4 MiB 有界 LRU 缓存、64 KiB / 2,000 行限额与 3 次连续超时熔断机制。所有 16 种规范语言及暗色主题在构建阶段打包入单一 Worker 脚本，运行期零网络请求。未知语言、Worker 异常或超长代码块安全降级为纯文本，且复制代码功能始终可用。


HC-114 起 Web 页面是 React DOM 工作台：`app.tsx` 是 composition root（只负责装配 `WebUiClient`、共享视图驱动的 Web Interactive Adapter 与 React root），`application/adapter.ts` 只拥有表现状态、缓存网关视图分片并把用户动作转换为 `InteractiveIntent` 提交给网关，`presentation/` 只消费 Adapter snapshot 并派发 WebIntent；三者均不直接调用 AgentClient、RpcTransport 或 JSON-RPC method string。所有 Run、Thread、模型、Skill（含启停）、MCP、命令与 Interaction 语义都由 CLI 进程内唯一的共享 `InteractiveController` 执行，与 TUI 保持一致；Browser 只看到 `state.replace/state.patch` 序列化视图。该分层由 `tests/web/architecture.test.ts` 固化。

`PresentationCoordinator` 不查询 Host 控制权：任何阶段都不调用 `host.control.status/acquire/release`。Browser ready 前（opening-web）TUI 保持输入；`handoff.ready` 后进入 web-active，OpenTUI 根层卸载 TUI 渲染并只渲染静态接管页，TUI 输入同时由 Coordinator 的输入租约拒绝（`tuiDispatch` 仅 tui-active 受理）。任何归还路径（返回、标签页关闭、刷新宽限到期、ready timeout、畸形消息、第二窗口、CLI close）都走同一 `returning-tui → tui-active` 收敛；由于共享 Core 与无 Host 依赖，收敛不再需要轮询 owner，`threadId` 恢复与过渡重同步也随之删除——TUI 返回后与 Web 会话期间是同一个 Controller、同一条 Timeline。重复 `/web` 不创建第二个会话；第二窗口在认证后收到 `already-open` 并被关闭。主连接已失效（整页重载重连时旧 socket 关闭事件尚未驱动 consume 清理）时，同 handoff 的新连接允许替换接管（旧 channel 以 `superseded` 收敛关闭），保持单窗口 invariant 同时消除重连竞态。

页面侧对"进入 web-active 的单帧交付"有看门狗：停留在 `opening-web` 超过 5 秒（web-active 帧被浏览器冻结/休眠/扩展干扰丢弃，或首帧不完整）即整页重载，利用 sessionStorage 中当前有效的单次 token 重连同一 handoff；服务端已 active 时重连首帧直接下发新一枚 `handoff.token`、完整视图与 `handoff.state(web-active)` 恢复可写，仍在 opening-web 时旧连接关闭让 Coordinator 立即收敛回 TUI。`WebBootstrapRoot` 用 `useLayoutEffect` 同步注册 handoff 订阅并以 client 当前状态初始化，避免 React 被动效果异步 flush 与接管帧之间的竞态（真实页面历史越多渲染越慢，空隙越大）。

Host 级控制权由 `harness_agent.host.control_lease.ControlLease` 唯一持有。Host 启动后 holder 是 owner Connection；只有 owner 签发、已经认证且未撤销的 attached Connection 可以 `host.control.acquire`，任一时刻最多一个 holder。`run.start`、`run.cancel`、`context.compact`、config preview/commit 与 Skill/MCP 写操作都先取得 `ControlLease` permit，在 dispatcher 统一 gate，不在业务 handler 复制判断；`host.control.*` 与 `host.attachment.revoke` 是控制权转换接口，不受 gate 拦截。只读查询继续只受 capability 限制。

acquire 时 owner 不得有进行中的受控操作、starting/active Run 或未收敛 Interaction；release 只允许当前 attached holder 且同样要求无未收敛工作。`run.start` 的 permit 保持到 Coordinator 已登记 starting/active Run 并发送 accepted response。控制权变更与受控操作受理在同一把锁内线性化，因此 acquire 与 owner `run.start` 竞争时只有一方被受理。

`host.attachment.create` 返回稳定 `attachment_id`；owner 可调用 `host.attachment.revoke` 撤销未消费 token、认证中 socket 或已连接 Connection。撤销与自然断线共用同一收敛路径：先拒绝新 permit，再 fail closed Interaction、取消并等待该 Connection 的 Run，最后恢复 owner holder。attachment capability ceiling 是显式 allowlist（`host.control`、`run.cancel`、`config.read/write`、`threads.read`、`context.manage`、`skills.read/manage`、`mcp.read/manage`、`models.read/select`）与 owner 已协商能力的交集，显式排除 `host.attach` 与 `run.multithread`；attached 的第二个 starting/active Run 在 `RunCoordinator` 锁内被 `CONNECTION_RUN_BUSY` 拒绝。完整决策见 [ADR 0002](adr/0002-project-host-multi-connection.md)。

完整生命周期决策见 [ADR 0002：Project-scoped Agent Host、多个 Connection 与单 Run owner](adr/0002-project-host-multi-connection.md)，统一术语见根目录 [CONTEXT.md](../../../CONTEXT.md)。

## TUI Slash Command Registry

交互式命令由 `packages/cli/src/interactive/commands.ts` 的不可变 `CommandRegistry` 统一声明。每个 CommandDefinition 包含稳定 ID、canonical 名称、别名、来源、展示类型、参数提示、capability/thread/idle requirements 和安全元数据；帮助、补全、菜单、解析与未知命令建议都只能从该 Registry 导出。Builtin 不可被同名或别名覆盖，后续 Skill、MCP、Plugin Loader 只能构造新的 catalog snapshot。

握手的 `enabled_capabilities` 被收敛为 Interactive Runtime 状态。缺少 capability 的命令从菜单隐藏；需要 thread 或空闲状态的命令保留在菜单中但显示禁用原因，实际执行时仍按同一策略复核，防止状态在选择后发生变化。当前 `/continue` 是 `/resume` 的别名，解析后统一为 canonical `resume`；未知 `/command` 只显示本地建议，绝不作为 Prompt 提交。用户需要提交 `/` 开头的普通文本时以 `//` 转义。

Build 下 `/plan`（id `approval.plan`）切到计划审批模式或带着目标开跑，`/plan-view`（id `approval.plan-view`）随时打开当前计划只读审阅，Compose 隐藏这两个命令。`interactive/command-dispatcher.ts` 让现有 Builtin Handler 只按稳定 ID 返回表现层无关的 semantic operation；`interactive/controller.ts` 负责解释结果、编排 RPC 和维护共享工作流。`tui/application/adapter.ts` 是第一个 Interactive Adapter，只拥有 draft、Prompt history、Picker 展示、快捷键、滚动与 OpenTUI refs，把用户动作转换为 `InteractiveIntent`，不直接调用 AgentClient 业务方法；`app.tsx` 只把输入映射为 intent，再把 snapshot 交给 Presentation 组件渲染。`/new` 是新建 thread 的 canonical 命令，`/clear` 为兼容别名；活动 run 下通过确认 Dialog 后才取消。HC-104 的 Web Adapter 必须复用同一 `InteractiveController`，不能另写平行实现。

### Interactive Core Feature 拆分（HC-111）

`InteractiveControllerImpl` 已从 1259 行单体退化为约 300 行的薄协调器，业务逻辑按职责下沉到 `packages/cli/src/interactive/features/` 下的九个独立 Feature 模块：

## Project、Thread 与 Message

Harness 的持久化领域模型只有 `project`、`thread` 与 `message`。所有跨层身份字段统一为 `thread_id`；不建立 Harness 的 `session` 概念。LangGraph 原生要求的 `configurable.thread_id` 直接复用该字段。完整用户可见历史由 ThreadPersistence 的 append-only Transcript 保存；LangGraph checkpoint 只承担当前模型工作状态。

可恢复状态位于一个用户级 SQLite 文件 `~/.harness/threads.sqlite3`，而不是每个 project 或 thread 各自一个数据库。目录权限固定为 `0700`，新建数据库固定为 `0600`。原始 project 路径不写入数据库：服务端对规范化路径计算 SHA-256 `project_fingerprint`，并同时用于 `harness_threads` 索引筛选和 LangGraph checkpoint 的 `checkpoint_ns`：

```python
{
  "configurable": {
    "thread_id": thread_id,
    "checkpoint_ns": project_fingerprint,
  }
}
```

Harness 自有表包括 `harness_threads(project_fingerprint, thread_id, created_at_ms, updated_at_ms, first_message, latest_message, message_count, title, title_origin)` 和 v7 的 `harness_thread_transcript`。两者均按 `(project_fingerprint, thread_id)` 隔离；Transcript 以稳定 `record_id`、单调 `sequence`、类型化 payload、内容摘要/长度和可选 Artifact 引用保存 user/assistant/tool/context 语义。`harness_threads` 只索引恢复选择器所需的摘要；`title` 是短标题（无则为 NULL），`title_origin` 只在存储层区分 `auto` / `user`，不进协议。`threads.list` 与 `threads.open` 仅在协商 `threads.read` 后可调用，只返回当前 project；JSON-RPC 客户端可以传递内部 `thread_id`，但 TUI 不得将其渲染或要求用户输入。

`harness --resume` 与 `/resume` 共用 TUI 浮层选择器。恢复时从 Transcript 读取完整 UI 历史，不把 checkpoint 当作 UI fallback；活动 run 或待处理交互期间禁止切换。v6 迁移只导入当时 checkpoint 能证明的消息，并以 `legacy_incomplete_history` 标记不完整边界。sidecar 关闭时提交并关闭 SQLite 连接，用户只能在 Harness 停止后手动删除主数据库及其 `-wal`、`-shm` 文件。

Python Agent 调用持久化时只依赖 `ThreadPersistence` 的生命周期操作：`accept_run` 在一个 `BEGIN IMMEDIATE` 事务中完成 Run binding、Thread 索引和用户 Transcript；`append_transcript_batch` 原子追加完整 assistant/tool 语义及大型工具 Artifact；`load_transcript`/`open_thread` 提供 UI 恢复，`load_run_state` 提供 Run 绑定恢复，`load_context_state` 只读取压缩策略状态，`load_latest_valid_compression_checkpoint` 与 `commit_context` 提供投影生命周期。SQLite 表、legacy 读取、schema bootstrap 和事务顺序都留在该 module 内部；`checkpointer` 与 `graph_config` 只作为 LangGraph 的 project-scoped adapter 暴露。

HC-104 已新增 `ContextProjector` 和 Harness 自有的版本化
`CompressionCheckpoint`。每个新顶层 Run 在进图前都按以下唯一链路生成模型历史：

```text
最新有效 CompressionCheckpoint.projected_messages
+ source_record_sequence 之后的 Transcript tail
→ 校验 user / assistant tool-call / tool-result 原子组
→ 单向刷新 LangGraph messages 缓存
→ 追加当前 Run 已受理的 user 记录并执行
```

检查点保存覆盖边界、覆盖 Transcript 前缀的完整 typed digest、重写版本、严格编码的投影消息、Artifact 引用、触发原因和压力摘要。候选的 source sequence/digest、重写版本、消息 JSON、工具原子组或 Artifact project/thread 归属任一无效时，Projector 跳过它并尝试较早的有效版本。压缩产生的 Artifact、Summary、熔断状态和最终检查点在同一 SQLite 事务提交；Server 和 Middleware 不组合表级写入。`load_context()` 只保留为 LangGraph 缓存诊断/兼容测试入口，不是生产模型历史来源。

### HC-107 最终连续性路径

最终生产路径由 `RunCoordinator` 和 `AgentHost` 共同组成，顺序不可交换：

```text
run.start
→ AgentHost._prepare_run：刷新并冻结同一 SkillRegistry，解析 requested Skill、Profile
  和 ContextLifecycle snapshot
→ ThreadPersistence.accept_run：原子写入 Run binding、snapshot、Thread 索引和用户 Transcript
→ AgentEnginePool.acquire：取得与该 preparation 对应的 AgentEngine
→ 构造 RunContext：注入同一 snapshot/Skill registry、取消令牌和执行策略
→ ContextProjector.project：latest-valid checkpoint + Transcript tail
→ ContextProjector.sync_cache：只向 LangGraph messages 做全量缓存替换
→ RunCoordinator 执行当前 user message，并由 ContextWindowMiddleware/ContextCompactor
  处理 report、micro、full、overflow、skipped、failed
```

`threads.open` 只从 Transcript 返回完整 UI 历史，不读取 checkpoint 作为 fallback；模型输入只
来自 Projector，当前已受理的 user 记录作为本次执行输入，不再从另一份完整历史拼接。Server
生产路径不直接构造或提交 `RemoveMessage`，唯一的 LangGraph 全量替换位于
`ContextProjector.cache_rewrite()`；它只改投影缓存，不改 Transcript。PromptEpoch 的生产
`load/persist` 入口和旧 Context commit alias 已删除，旧类型仅用于明确的非共享嵌入兼容以及
v6 迁移事务。Skill catalog 由 Host 的 `SkillCatalogManager` 在顶层 Run 边界刷新；requested
Skill、虚拟文件、ResolvedAgentSpec、Profile 和 RunContext 使用同一 immutable snapshot，
不会由进程永久 registry 吞并后续 Run 的文件变化。

HC-107 的正式决策见 [ADR 0003：Transcript 事实层与上下文投影生命周期](adr/0003-transcript-context-projection-lifecycle.md)。

## 持久化与可观测性四层分界

Harness 的数据体系严格区分为四层，详细架构见 [本地诊断日志](本地诊断日志.md)：

1. **Transcript 业务事实层**（SQLite `harness_thread_transcript`）：保存完整的用户可见消息、工具调用与结果、大型工具 Artifact。这是会话恢复（`threads.open`）、UI 渲染与模型上下文投影的唯一事实来源。
2. **CompressionCheckpoint 上下文检查点层**（SQLite `harness_compression_checkpoints`）：保存分级压缩投影检查点、覆盖的 sequence 与 digest，供 `ContextProjector` 选取 latest-valid 重建模型上下文。
3. **LangGraph Checkpoint 图状态层**（SQLite adapter）：保存 LangGraph 图执行的瞬时节点状态，负责单次 Run 的流转。
4. **Diagnostic Log 本地诊断日志层**（磁盘 `~/.harness/logs/<date>/` 独立 JSONL）：低流量、结构化、异步脱敏的生命周期与耗时事件，由 CLI 和 Python sidecar 独立写入。它作为纯粹的单向观察者（Observer），绝不参与恢复、幂等、业务判断或 SQLite 事务。


## AgentEngineProfile 与运行状态

### Agent 领域对象与当前实现

Harness 的长期 Agent canonical model 固定为 `ProviderDefinition`、`ModelProfile`、
`ExecutionPolicyDefinition`、`AgentDefinition`、`ThreadExecutionSelection` 和
`RunExecutionBinding`。其中 Provider/Model 来自 TOML adapter，Plugin Policy/Agent 来自已验证 Plugin catalog；ThreadSelection 是下一次运行的可变意图；
RunBinding 是每次实际执行的不可变历史。完整字段归属、优先级、生命周期和当前兼容映射以
[ADR 0001](adr/0001-agent-domain-model.md) 为准。

当前 TOML v1 的单个模型 Profile 仍同时承载 OpenAI-compatible 连接和模型参数；它是到
`ProviderDefinition + ModelProfile` 的输入 adapter，而非未来 Agent/Policy 的配置模板。
`runtime/execution_binding.py` 以一个纯函数集中解析根模型：本次请求优先，其次是最近 Run、
v5 legacy `executor` 绑定和 `models.default_profile`。解析结果同时提供 AgentEngine 所用模型、
脱敏 Protocol 展示和不可变 `RunExecutionBinding`，Server 与 ThreadPersistence 不再重复解释字段。
`/model` 仍会独立尝试同步未来默认值；v4/v5 的 Thread AgentEngine/模型绑定只读兼容，
无法恢复 Profile ID 时明确显示 legacy unknown。

AgentEngineProfile 是可共享 AgentEngine 的稳定、脱敏配置身份；它不是 thread
或用户会话。当前 v2 Profile Key 以 canonical JSON 的 SHA-256 计算，固定包含
角色 `agent_id`/definition fingerprint、`project_fingerprint`、topology ID/版本、模型角色配置
指纹、实际工具/Skill 能力视图、MCP、Sandbox、Policy、middleware 和 Prompt 模板指纹。
Key 记录中不保存原始工作区路径、模型 endpoint、Header、凭据或完整 Prompt；v1 record
仍可读取，但会标记为 legacy，不能进入新的 AgentEnginePool 或重新持久化。

MCP 由 `ConfigChangeService` 产生带文件 revision 的深度不可变 snapshot。AgentHost
在创建或热更新 AgentEngine 时同时截取该 snapshot 和 MCP 工具列表，AgentEngineProfile 的
MCP fingerprint 与实际 graph 输入因此保持一致；后续配置写入只创建新的 Profile，旧
AgentEngine 仍可完成当前 Run。指纹只保留 transport、command/URL 形状、args、超时以及
环境变量/Header 名称；认证 query 值会脱敏，普通 query 参数仍参与身份计算。

以下内容不参与 Profile Key，且必须保持在 ThreadPersistence/Checkpointer 或单次 Run
Context：`thread_id`、ThreadExecutionSelection、消息、RunContextSnapshot 正文、上下文摘要与 artifact、Todo、审批
状态、取消令牌、run ID、RunExecutionBinding 执行树以及未来的 Agent mailbox。相同 Profile 的 thread 因此可在
已由 AgentEnginePool 复用一张图，而稳定能力变化会构造新 Profile。

`ModelCatalog` 保存命名的 OpenAI-compatible Profile、默认 Profile 和现有配置角色绑定。
当前 Single Agent 只解析 root 模型，不把角色映射带入 AgentEngine；`[models.roles].executor`
仅用于读取 v5 legacy 快照。当前内置 `main` 由 `resolve_builtin_main_agent_spec()` 一次性汇合
模型、EffectiveExecutionPolicy、实际工具、Skill catalog、MCP snapshot、Prompt 和执行后端描述，
得到不可变 `ResolvedAgentSpec`。Profile 通过 `spec.runtime_profile` 生成，AgentHost 按 Profile key
取回同一个 spec 交给 builder 和 RunContext；不再维护独立的 `_AgentEngineBuildSpec` 解析路径。
可派发子代理（内置 `general-purpose`、`explore` 以及已启用的 Plugin Agent）统一由单一 `AgentCatalog` 管理与解析；内置角色通过受控 Inline 子图执行，Plugin 角色通过 Managed adapter 执行。内置 `general-purpose` 继承父 MCP/Skill 并在父 `default` 模式下内部按 `auto-edit` 放宽审批，`explore` 严格限制为 5 个只读工具且启动免审批；Plugin Agent 保持审批 fail closed。委派深度固定为 1，并发上限为 4（超额排队）。
`ProviderClientPool` 仅按 endpoint/timeout 复用不携带认证信息的 HTTP transport；
每个 ChatOpenAI adapter 仍独立保存模型、认证和 Header。

HC-095 已固定运行资源的 owner 边界：`AgentHost` 独占
`ProviderClientPool`、按不可变 snapshot 管理的 `McpConnectionManager` 和
`ThreadPersistence`；workspace/execution-environment owner 管理本地执行 backend 或
远端 sandbox/worktree。AgentEngine 只在 `AgentEngineResourceBundle` 中保存共享资源的
lease，关闭时释放 lease，不调用 Provider、MCP 或 sandbox 的 owner close；编译图、角色
wrapper、middleware 和 model binding 才属于 AgentEngine 自己。共享 handle 进入
`DRAINING` 后拒绝新借用，已有 execution 释放后由 owner 回收。

MCP 热更新先建立新 snapshot resource，并将旧 resource 排空；AgentHost 再按
`snapshot/profile fingerprint → affected AgentEngine → draining` 定向失效旧图。新的
execution 只能租用新 Profile，正在运行的旧图可以带着旧工具集合完成并释放。
`AgentEnginePool.invalidate()` 提供带稳定原因的显式定向失效 seam，供 Skill、模型、Policy、
工具、middleware 或 Prompt snapshot producer 调用；当前已接入 MCP 配置 snapshot 和
HC-103 Skill catalog 热刷新 producer。Skill 变化只按 `skill_catalog_fingerprint` 定向
draining 受影响旧图，活动 Run 的 lease 和旧 snapshot 不被强制替换。
Pool 诊断额外返回脱敏
`agent_id`、资源 scope、drain reason、构建耗时和 scope 计数。

sidecar 以 AgentEngineProfile 为键从 AgentEnginePool 租用默认 Agent 图，而不再缓存
`thread_id -> Agent` 或 `thread_id -> ContextWindowMiddleware`。`RunContext` 是
一次 `astream`/`ainvoke` 调用的不可持久化输入，携带 `thread_id`、`run_id`、
`execution_id`、父 execution、`agent_id`、执行模式、RunContextSnapshot、审批模式、取消令牌和可选
Profile Key。图内
`RunContextSnapshotMiddleware` 在模型调用边界读取它并注入前缀；`ContextWindowMiddleware`
同样优先由它路由到目标 thread。若 LangGraph 的 `configurable.thread_id` 与
RunContext 不一致，调用会 fail closed。

### AgentExecution 与两种执行策略

一次用户请求仍然是一个 `Run`；一个 Agent 为完成一项任务经历的完整模型循环是一个
`AgentExecution`；单次模型调用、工具调用或 delegation 只是该 execution 内的操作，不单独
创建 execution。关系如下：

```text
Run
└─ AgentExecution(main)
   ├─ model / tool operations
   └─ delegation operation
      └─ child AgentExecution
```

所有 execution 共用稳定身份、父子关系、模型/Policy 事实、状态、取消和事件归属；执行基础设施
按隔离需求分为两种模式：

- `Inline`：可信、短期、同步的内置 worker，保留 DeepAgents 临时子图，不单独持有
  AgentEngine lease 或 checkpoint。
- `Managed`：根 `main` 以及未来独立角色/Plugin，拥有独立 AgentEngine、namespace 和可恢复状态。

当前已落地轻量 `AgentExecutionRegistry`：根 Run 创建 `root-<run_id>` execution，事件 envelope
携带 `execution_id`/`agent_id`，取消会收敛未终结 execution，Run 封口后不能追加 execution。
registry 以 `(thread_id, run_id)` 隔离，Coordinator 在封口后释放短期记录；已完成 Run 的幂等历史
仍由 `ThreadPersistence` 保存。子 Agent delegation、Managed 状态持久化和 checkpoint 隔离分别留给
后续任务，不把模型/工具调用提前建成 Step 表。

`/.harness/history` 不是图的固定 backend 成员。共享图在工具调用时按当前
RunContext 生成只读虚拟挂载，确保归档只能被所属 thread 读取。自动、手动和 overflow
都进入 `ContextCompactor` typed service；调用方只提供 trigger、当前
`ContextProjector` 投影、RunContextSnapshot 和结构化运行态，Server/Middleware 不拼接
Context 表事务。手动 `context.compact` 在短期 AgentEngine lease 内绕过自动熔断但强制
请求 full；成功后只由 `ContextProjector` 单向刷新 LangGraph `messages`，Todo、interrupt、
子图和其他 channel 不被重置。消息、PromptEpoch、归档、审批恢复和取消状态仍由
ThreadPersistence、Checkpointer 和 RunCoordinator 管理。

手动 `context.compact` 在 TUI 中是独立的 `pendingOperation`，不伪装成 Agent Run。
Controller 在发送前设置该状态，输入栏失焦且提交入口再次拒绝新消息；成功、
skipped、failed 或 transport 关闭都通过 `finally` 释放。AgentClient 等待服务端终态而不使用
通用 30 秒超时；`run.start` 的受理也不在本地提前判失败，避免服务端成功、
界面失败的幽灵 Run。其他保留本地超时的请求会在有界 ID 集合中标记，只忽略其对应的
迟到响应，从未发出的响应 ID 仍是协议错误。

`RunCoordinator.idle_thread()` 会在全局 registry 锁内检查并登记目标 Thread 的
maintenance reservation，随后在压缩模型调用或 `threads.watch` 读取前释放全局锁。
同 Thread 的 Run/watch/compact 因 reservation 互斥，不同 Thread 仍能受理和执行；
context manager 的 `finally` 负责在所有异常路径释放占用。

`agent_engine.AgentEnginePool` 已提供 Profile 级的核心生命周期：相同 Profile Key 的
并发 acquire 共享一个 single-flight 构建任务；`AgentEngineLease` 和
`AgentEngineRunLease` 分别保护租约、排队 run 与活动 run；状态严格经过
`MISSING → BUILDING → READY → ACTIVE/IDLE → DRAINING → CLOSED`。DRAINING
AgentEngine 拒绝新 lease，但既有 lease 可以完成或取消；只有 lease/run 均释放后才可
关闭。AgentEngine 的 `aclose()` 按“取消后台任务 → 刷新持久状态 → Tool → MCP →
Sandbox → AgentEngine 独占模型资源 → 释放共享 lease → 释放图引用”继续执行；其中
MCP/Sandbox 只有在被明确建模为 AgentEngine 独占 adapter 时才进入 Bundle，Host/workspace
共享 handle 不会被 AgentEngine 关闭。单项失败只记录并不会阻断后续释放。

sidecar 的 run 与 manual compact 均通过 Pool acquire/release；run 同时持有
`AgentEngineRunLease`。Pool 使用 `max_profiles`、空闲 TTL 与 LRU 只淘汰无 lease/run/queue
的未固定 IDLE AgentEngine；已接入的 MCP snapshot producer 变化时，受影响旧 Profile
定向进入 DRAINING，新 execution 不再复用它；普通 Thread 模型选择或 Profile 解析不会
推断并排空其他仍有效的 Profile。Host 关闭顺序是取消/收敛 run、关闭 AgentEnginePool
释放所有共享 lease、再关闭 MCP/workspace/provider owner，最后关闭 ThreadPersistence；
单个 AgentEngine 的关闭等待受 `close_timeout_seconds` 限制。本任务不改变现有 JSON-RPC 请求路径。

### HC-170 模型调用自动恢复与 attempt 边界

模型调用的可靠性边界位于 provider model call，而不是一次 Run 的最终结果。根 Run、Compose
Stage、Inline child 和 Managed Plugin 都把 `ModelSettings.max_retries` 冻结为同一个
`BoundedProviderRetry` attempt budget；`ChatOpenAI` 适配器的 SDK `max_retries` 固定为 0，
因此不会与 `ManagedAgentExecutor` 叠加退避。Team 不另建模型重试器，成员仍通过
`AgentDelegator` 使用对应 Inline/Managed target 的执行底座。

模型输出进入 ToolNode 前经过 `ModelOutputGuardMiddleware`。它只校验结构化
`invalid_tool_calls`、工具名、参数和重复 ID；普通正文即使包含字面量 `<tool_call>` 也不
会被 substring 规则误判。合法但缺少 ID 的 assistant call 在这一层得到非空 ID，ToolNode、
ToolMessage、下一轮模型请求和 Transcript 共用该 ID；未知或未授权工具仍是带原始 ID 的
策略错误，不会回到 provider retry。

`runtime/execution_stream.py` 在每个 model call 内建立临时 capture：content/reasoning
signal 随 chunk 实时投影，tool signal 在模型节点确认前暂存；`StreamSession` 增量和
Build observer capture 仍可回滚。尚未公开正文/reasoning 时 provider、取消或结构错误会丢弃
暂存并按策略重试；若正文/reasoning 已公开，后续临时错误收敛为
`PROVIDER_OUTPUT_INTERRUPTED`，不自动重放模型回合；终态 `retryable=true` 只表示用户可发起新的 Run，
避免重复显示。Tool/graph 边界确认后按
原顺序提交 tool signal，已越过 Tool 边界的完整 assistant/tool 批次仍即时 flush，因而
后续模型阶段阻塞时仍可从独立连接读取已完成事实。

Managed executor 之外的直接模型调用也必须使用同一 retry owner：上下文摘要
`ContextCompactor`、`/btw` side question、AUTO 审批分类器和显式 evaluation runner
均通过 `run_with_provider_retry`（同步路径使用对应 sync helper）；没有配置预算的嵌入式
调用显式使用单次 attempt。重试只覆盖 `MALFORMED_TOOL_CALL`、429、5xx 和明确的传输
故障；400/401/403、取消、审批和能力策略错误不重试，耗尽后只向 Run 暴露稳定脱敏错误码。
无 Retry-After 时退避按 provider attempt 线性增加并受最大延迟限制。

BuildRunAdapter 与 ManagedStageAgentPort 是两个真实 adapter，Transcript observer 与
Compose activity observer 分离，不存在第二条旧 translator 路径。每次 Stage invocation
由 Workflow 创建稳定 `ComposeActivityScope`（activity_id、stage、task_id/title、attempt）；
`RunCoordinator` 继续唯一拥有 Run sequence、owner、取消、Interaction 与 terminal，
root/child 共用同一 sequence。`compose.summary` 是携带 scope 的非 assistant 展示/审计
摘要，状态机仍只读取 artifact store。工具审批在 child 的同一 checkpoint namespace 恢复，
不会重建 stage attempt。Verify 无模型 stream，由 Workflow 把 command 投影为 scoped
Tool/Approval/terminal，通过与否仍只由 fresh `VerificationEvidence` 决定。

Interactive Core 用 `(run_id, execution_id or root, activity_id or root, provider_item_id)`
复合身份归组 Message/Reasoning/Tool/Interaction，scope 只决定归组，不复制 Compose
reducer；TUI/Web 只消费同一 snapshot 并持有折叠/滚动/焦点。活动阶段展开并跟随底部，
terminal 阶段折叠为「阶段 + Runtime 摘要」，失败/阻塞/取消不清空已完成的安全过程。

审计记录独立于根 Transcript：`harness_compose_activities` 只保存阶段摘要、Task/Tool
terminal、Verification/Review 结论，每 Run 500 条 / 1 MiB / 单文本 4 KiB 上限并原子
追加唯一 truncation 标记。Thread reopen 通过 `threads.open` 返回这些记录供 Timeline
恢复；Reasoning、原始 Tool 内容、Interaction 正文与 artifact JSON 不落库，也不进入
ContextProjector 或模型消息。

一个 `AgentHost` 在启动时固定绑定一个 workspace，并持有一把 `AsyncRWLock`。它在构建每张
默认 AgentEngine 图时注入 `ConcurrencyGuardMiddleware`，因此同一 Host 的不同 Profile 不会因
各自图内锁而绕过彼此：只读工具可以共享读锁，写工具、未知工具和 `task` 获取独占写锁。`task`
的默认子图可能写同一 workspace 且不继承父图 guard，所以父 `task` 调用在整个同步子图期间持锁。

HITL 在 ToolNode 实际执行前暂停并等待用户决定；锁只在审批恢复后的工具 handler 中获取，绝不
跨用户等待持有。不同工作目录通常由不同 Host 承载，彼此不互相阻塞。当前没有 worktree 或远端
sandbox 的稳定资源身份，故它们在同一 Host 内也保守共用此锁；不同进程同时操作同一物理目录同样
不受协调。若以后出现可识别资源域或吞吐瓶颈，再以独立任务替换为资源级调度。

`config.show` 额外返回 `runtime_pool_diagnostics` 和 `file_tool_metrics`，因此 `harness config show` 是无需新
capability 的本地诊断入口。前者包含 Pool 大小、状态计数、活跃 lease/run/queue、命中/未命中、
构建和关闭累计耗时、容量拒绝、按原因聚合的淘汰数、关闭失败数以及最近 64 条生命周期事件；后者仅汇总
文件工具错误码、Snapshot expired/stale/未读范围、重读、edit 成功、结果字节和 diagnostics 耗时。
每条 AgentEngine/事件只使用 12 位 `profile_id`，绝不返回完整 Profile Key、工作区路径、Prompt、
模型 endpoint 或凭据。`memory.estimated_bytes` / `memory.rss_bytes` 目前恒为 `null` 且状态为
`not_collected`：真实内存采样需独立校准，当前 CI 以 AgentEngine 数及资源关闭断言保证容量上界。

## Skill 生命周期

Host 初始化和每个顶层 Run 都通过 `SkillCatalogManager` 检查四类来源：内置 `harness_agent/built_in_skills/`、用户 `~/.harness/skills/<name>/`（兼容 `~/.harness/skills/local/<name>/`）、项目 `<workspace>/.harness/skills/<name>/` 和市场安装目录 `~/.harness/skills/market/<market>/<name>/<version>/`。项目 Skill 默认启用，不要求额外信任确认；用户可用 `harness skills disable` 暂停它。来源不会静默覆盖同名项，canonical ID 固定为 `builtin/<name>`、`user/<name>`、`project/<name>` 或 `<market>/<name>`；只有全局唯一时才允许短名称。

manager 以文件元数据做快速变化判断，并用已有 SHA-256/digest 和安全扫描确认真实内容；内容不变时复用同一个 immutable catalog snapshot，内容变化时发布新的 `SkillRegistry`。每个顶层 Run 将同一 snapshot 的 Skill 元数据按 canonical ID 排序注入 `RunContextSnapshot`（总长最多 4,000 字符），Prompt index 明确带 snapshot ID；显式 Skill、`ResolvedAgentSpec`、`AgentEngineProfile` 和 `/.harness/skills` 虚拟读取也绑定此 ID。正文、资源路径和运行时错误均不进入 system。Agent 通过统一的 `read_file` 按需读取 `/.harness/skills/<canonical-id>/SKILL.md` 或同根资源，不能调用专用的 `load_skill`/`read_skill_resource` 工具。启用、停用、安装、更新和删除在当前 Run 不变，并以 `next_run` 生效；既有 Run 继续持有旧视图。启动后的 `SKILL.md` 篡改、非法 front matter、symlink、路径穿越、大小超限和 TOCTOU/digest 不一致都会 fail closed。市场网络和认证不由核心实现，企业包可通过 `harness.skill_marketplaces` entry point 提供 Provider。

## RunContextSnapshot 与上下文预算

默认 Agent 的每个顶层 Run 都由 `ContextLifecycle` 重新读取当前支持的 AGENTS 和环境来源，并生成按权限层级、再按变化频率排序的不可变 `RunContextSnapshot`。AGENTS 来源包括用户级 `~/.harness/AGENTS.md`、项目级 `<workspace>/.harness/AGENTS.md`，以及 Git 仓库根目录到当前 workspace 祖先链中的普通 `AGENTS.md`；仓库链按远到近注入，同一路径只读取一次，不解析 `@import`。核心策略、EffectivePolicy/Sandbox/实际工具能力和稳定环境位于低可信 AGENTS、Skill 索引及 Run 动态块之前；内容与顺序不变时使用相同 system fingerprint 和 snapshot ID。Host 顶层 Run、Plugin child 和直接嵌入式 Agent 都复用这一 canonical 准备路径；`RunContext` 只接受已生成的 snapshot。快照在 `accept_run()` 中与 binding、首条用户记录同一事务持久化，`RunContextSnapshotMiddleware` 在每次模型调用注入同一 system prompt；当前 Run 开始后的文件变化不影响它，下一 Run 才重新观察。旧 PromptEpoch 只作为 legacy snapshot 单向迁移，不是新 Run 的来源。

`@` 文件提及属于 CLI 在单次用户提交上的消息增强，不属于 `RunContextSnapshot` 或 system prompt。TUI 与 Web Adapter 只维护各自的菜单状态，查询提取、候选排序、1000 项候选池和 8/5 行窗口规则位于无框架依赖的 `presentation-shared` 纯策略；内部 `WorkspaceTreeState.allEntries` 为两端提供同一份完整目录/文件快照，Web UI contract v7 只扩展本机表现契约，不修改 `packages/protocol`。菜单关闭时不计算候选，避免 Timeline 发布热路径反复扫描工作区。

提交时 `InteractiveController` 调用 `workspace/mention-resolver`，先通过 `resolveWithinRoot` 完成 realpath containment，再只读解析 UTF-8 文本。小文件或显式行号切片以 `[Attached Context: ...]` 附到发给 Agent 的消息前，当前 Timeline 仍显示用户原文；Markdown 围栏长度严格大于附件正文中的最长反引号序列，防止附件内容提前闭合结构。单文件 10KB/300 行、单轮 20KB/500 行、显式切片源文件 16MiB，以及锁文件、生成文件和二进制黑名单共同形成有界读取门禁；超限项降级为 `[Mentioned File: ...]`，非法、越界或不存在路径不读取。该链路只增加只读上下文，不扩大 Agent 工具权限，最终文件访问仍受 workspace 与 sandbox 策略约束。

模型 Profile 的 `context_window_tokens` 默认 `128000`，输入预算为 `window - clamp(4096, 16384, ceil(window * 10%))`。`ContextPressurePolicy` 将测量与执行分开，并保持 50% report、60% micro、80% full、90% hard 的有序基线。默认策略由工具密集 fixture 校准为可回收工具结果达到 8,192 token 或 2 个时提前尝试 micro，文本密集 fixture 没有可回收工具时不会制造空归档；每次 micro 都保留最近 1 个候选，空闲辅助阈值为 900,000 ms（15 分钟）。这些值集中在 typed policy 配置中，不采用第三方的固定数值。

达到 full 水位时仍先在内存中归档旧的、已完成且可从 Artifact 恢复的工具结果，再以 `pressure_after` 重测；低于 full 才原子提交 `mode=micro` 检查点，仍超出时不提交中间 micro checkpoint，直接把新投影交给 `ContextCompactor` 的 full 分支。自动 micro 足够时摘要模型不会被调用；同轮 micro+full 只提交最终 full。工具调用与结果原子组、Transcript 和最近候选保留规则不被破坏，已经是 Artifact 占位的结果再次处理为 no-op。空闲只由 Run 生命周期显式标记的顶层 Run 首次模型调用携带；工具续跑、重试、Interaction 恢复、子 Agent 以及缺失/异常时间戳均不会触发。

旧工具结果以工具名、首尾确定性预览、SHA-256 和 artifact ID 留在历史，原文仅写入本机 SQLite，并可由 `/.harness/history/<artifact-id>.md` 分页读取。空摘要、截断/结构错误、来源越界、消息不完整或投影膨胀均返回 typed `skipped/failed`，不改写历史；自动和 overflow 路径继续要求最终投影至少节省 20%，连续三次自动失败打开熔断器，成功后仅重置当前 Thread。网关溢出时复用同一 micro→full 服务，最多重试模型一次，第二次 overflow 返回稳定诊断错误。

交互客户端可通过 `/compact` 调用 `context.compact` 强制 full；它不受自动熔断器限制，固定保留最近两个完整 user turn，并只要求最终投影严格小于原投影。手动路径在摘要调用前用空摘要和真实包装构造理论最小投影；若该下界仍无正收益就直接返回 `manual_skipped`，否则调用摘要模型并在实际结果不再缩小时保持旧投影。自动/overflow 的 20% 门槛与手动正收益门槛使用独立判断，不能重新合并。

服务端不发送厂商专用缓存字段。它记录 system/schema/历史重写指纹和动态预算；网关未报告缓存 usage 时状态为 `unknown`。协议的 `context.updated` 与 `run.completed.context` 把紧凑状态交给 TUI。

协议唯一来源为 `packages/protocol/schema/v3.json`。运行：

```bash
bun run protocol:generate
bun run protocol:check
```

生成的 `src/generated.ts`、`harness_agent/protocol/generated.py` 与 Python wheel 中的 Schema 副本禁止手改。生成器只遍历 Schema metadata 与 `$ref`；两端共同消费 `packages/protocol/fixtures/v3-contract.json`，并分别由 Ajv Draft 2020-12 与 `jsonschema` 在发送和接收 seam 校验。stdio 与 WebSocket 单帧上限均为 8 MiB，工具载荷上限为 1 MiB；Python stdout 只能输出 JSONL。

v3 一次性替换未正式发布的内部 v2，不维护 compatibility adapter。未来 replay、steer、外部工具和 hooks 必须通过 minor 版本与 capability 增量提供，禁止提前声明未实现能力。

历史协议与运行行为说明保存在 [实施状态](../research/archive/2026-07-14-za38-cli-implementation-status.md)；它只用于追溯，不是开发者文档入口。

## 执行后端与安全边界

默认 `tools.sandbox = false`，Python sidecar 使用本机 `LocalShellBackend`。TUI 必须清晰显示“本机执行 · 未隔离”。

本机模式在 `create_harness_agent()` 的主 Agent 和默认 `general-purpose` 子 Agent 中分别注册 `WorkspaceBoundaryMiddleware`，委托 `WorkspaceRootRegistry`：

- 主工作区内使用 `/` 虚拟路径；已信任额外根使用真实绝对路径，内部映射为 `/@ext/<root-id>/...`。
- 未信任的外部路径触发 `directory_trust` 审批；非法路径（`..`、UNC、系统目录）返回 `ToolMessage(status="error")`。
- `glob.pattern` / `grep.glob` 禁止绝对路径和 `..`；`/.harness/` 仍仅允许 `read_file`。
- 路径经 `realpath` 后再做 containment；已信任根内的符号链接若逃逸到未信任位置仍拒绝。
- 子 Agent 共享只读 registry，不能发起信任审批。`WorkspaceBoundaryMiddleware` 不是 shell 沙箱。

不能只在主 Agent 注册此中间件：deepagents 自动的 `general-purpose` 子 Agent 有独立 middleware 栈。Harness Code 显式为默认子 Agent 注册自己的 `WorkspaceBoundaryMiddleware`，防止通过 `task` 绕过本机文件边界；并发协调则由父 `task` 持有的 Host 写锁覆盖整个同步子图，不能向子图重复注入同一把非重入锁。`AGENTS.md` 在每个顶层 Run 准备阶段读取一次，作为只读、不可信参考写入该 Run 的 snapshot；恢复同一 Run 不重新读取宿主文件，下一 Run 才刷新。

用户显式设置 `execution.backend = "remote"`、`HARNESS_SANDBOX=true` 或传入 `--sandbox` 时，服务端只接受由用户级或显式配置声明的 `execution.remote.factory`。该工厂必须返回 deepagents `SandboxBackendProtocol`，接收宿主工作区、provider 名称、逻辑远端目录和非秘密 `execution.remote.params`，负责企业认证、工作区同步、网络白名单和远端生命周期；失败时抛出配置错误，禁止回退到本机 backend。项目 TOML 在可信机制完成前会被整体拒绝，之后也不得自动导入远端 provider。

远端模式下 Agent 使用 provider 给出的逻辑工作目录，禁用宿主机 memory 和 skills，避免它们绕开远端执行边界。`js_eval`/QuickJS 已从 Agent 依赖和工具面移除。当前不实现 Docker、Podman 或本机容器 backend。未来接入企业 provider 时，必须补充同步、回写、取消、审计与网络策略的端到端测试。

### Harness 文件工具接管与 Snapshot 边界

DeepAgents 0.6.8 的 `FilesystemMiddleware` 是受保护的文件工具脚手架，不能通过
`exclude` 删除。Harness 在模型调用和工具执行之间增加唯一的
`HarnessFileToolsMiddleware`：先保留 Capability、Deferred 和 Workspace 的前置校验，
再由注入的 `FileToolContract` 按名称把 builtin schema 去重替换为 Harness schema，并
在 ToolNode 入口直接 dispatch；被接管的调用不会再进入 DeepAgents builtin handler。

```text
主 Agent / declarative 子 Agent / inline worker
        → 同一 FileToolContract 配置
        → 各图自己的 HarnessFileToolsMiddleware
        → 同一 backend 与策略边界
```

当前 contract 只镜像已确认的 exact-string 文件工具形状，并只在 Snapshot 与当前完整 identity
都证明已有文件为空时，把空 `old_string` 解释为整个空文档的受限替换。尚未确认的 Snapshot
`edits[]`、insert 或其它 mutation 参数只能在 Design 更新后注入，不能由实现步骤提前变成生产
schema。`delete_file` 也通过该 seam 进入 Harness，不能再与内置文件工具形成第二执行
入口。

共享 AgentEngine 的 Snapshot 由 Host 持有 `ThreadSnapshotStore`，每次工具调用从
`RunContext.thread_id` 取得 Thread，不捕获构图期 Thread。记录只保留强 hash、文本元数据、
已读行区间和有界生命周期信息，不写入 Transcript、SQLite 或工作区；同内容重复读取合并
`seen_lines`，内容变化产生新不可猜测 ID，跨 Thread/path/backend 或 TTL/LRU 淘汰后统一
fail closed 为 `SNAPSHOT_EXPIRED`。`/.harness/` 继续由 CompositeBackend 提供只读读取，
不生成可写 Snapshot。Store 使用独立的短期 `threading.Lock` 原子保护 records、identity index、
总字节计数与关闭状态；hash、行元数据和 ID 候选在锁外准备，backend I/O、审批、CAS 与
diagnostics 从不持有该锁。因而 `adispatch → asyncio.to_thread` 的并行读取仍可重叠，只有最终
Snapshot 元数据登记、TTL/LRU、失效和关闭被线性化。

文件提交通过 `TextMutationBackend` adapter 表达完整读取、create-if-absent、
compare-and-replace 和 delete-if-unchanged。Local adapter 负责无符号链接路径校验、
BOM/换行元数据和同目录原子替换。`FileMutationService` 是唯一的提交编排点：文件 contract
先完成 Snapshot/唯一匹配校验，再把 current、proposed content 与内部 metadata 交给它；service
生成最多 200 行、16 KiB 的精确 diff，并以 Thread、tool call 和参数指纹保存一次性批准计划。动态
HITL 回调从同一个 plan 生成短 description 与 `file_diff` presentation：后者只在当前 Run 的
`ApprovalPresentationStore` 中按工具名和完整参数指纹短暂保存，受 TTL/LRU 限制，Run 结束立即清空，
不写 Transcript、SQLite 或日志。`RunCoordinator` 逐项审批时只在同一参数身份命中时附带 presentation；
缺失或淘汰则回退通用审批卡，绝不根据工具参数或当前磁盘重算拟议内容。预览被截断或受终端高度隐藏不
取消允许/拒绝选项；批准绑定的是该计划已固定的完整拟议内容。批准后的 commit 仍只使用该计划的 expected
identity，随后重新读取实际
内容、计算新版本源行的 changed range，并将完整显示的局部窗口登记到新 Snapshot。旧批准遇到变化返回
`COMMIT_CONFLICT`；保存钩子改写则以 `POST_WRITE_DRIFT` 同时返回已批准和实际的有界 diff。

异步 ToolNode 路径在 create/edit 成功后可通过已启用的 Plugin LSP 发起一次最多 1 秒的只读 diagnostics
查询；返回最多 20 项、8 KiB 的严重级别、短 code 和行号摘要。`unavailable`、`timeout` 与 `ok,count=0`
严格区分，任何 LSP 结果都不回滚提交、不自动 formatter。`FileToolMetrics` 由 Host 跨 AgentEngine 聚合，
不保存路径、源码、参数或完整 Snapshot ID；单次结构化日志最多记录相对路径、稳定 code 和聚合字段。Remote adapter 没有原生 CAS 时返回 `BACKEND_CAS_UNSUPPORTED`，
禁止先读后盲写；这些结果优化不另起文件 mutation 入口。

## 审批模式

`harness_agent.policy.approval_mode` 是唯一的模式解析入口，规范值为 `plan`、`default`、`auto-edit`、`auto`、`yolo`。未配置时产品默认为 `auto`。它把旧 `ask` 归一为 `default`；未知值不抛出启动错误，而是安全降级为 `default`，并在 `ExecutionSettings.redacted()` 的 `security.approval_mode_warning` 中返回提示。

活动 Run 的审批模式由 `RunCoordinator` 持有一个 Host-owned `ApprovalModeState(mode, revision)`。`run.set_approval_mode` 按 capability、ControlLease、owner、活动状态、pending Interaction、取消和 Plan 单向约束顺序检查，在同一把 coordinator 锁内更新它；repository-level trust 不作为额外的活动切档门禁，只有已经存在的 `directory_trust` Interaction 会按通用 busy 规则阻塞。重复写同一 mode 不增加 revision。成功响应携带 Host 实际 mode/revision，CLI 只有收到该事实才更新本地 snapshot。切换点之前已经开始的模型/工具调用保持原决定，之后尚未决定的边界从同一 state 读取新 mode；取消/终态与切换按该锁的先后顺序线性化。新 RPC 属于 canonical Protocol v3.8，能力为 `run.approval_mode`，低 minor 连接在 handler 前由版本门禁拒绝。

解析后的初始值沿 `load_config()` → `AgentHost._create_default_agent()` → `create_harness_agent()` 传递；活动 Run 后续则由 `RunContext` 的共享 state/provider 覆盖构图期值。`approval_policy` 集中提供以下策略，禁止由 TUI 或系统提示词自行解释权限：

- `PlanModeMiddleware` 常驻主 Agent 图，统一按当前 `RunContext` mode 为 `plan` 或本 Run 的单向运行时 flag 判定约束；未开启时透明放行，开启后以明确白名单在工具执行前返回 `ToolMessage`，未知工具默认拒绝，唯一写入例外是会话计划文件 `/.harness/plan.md`。`execute` 在计划约束下走三态分类（`classify_plan_shell_command`）：只读安全 Shell 自动放行以辅助调研，明确修改项目文件或破坏性命令硬拒绝，未知命令走单次 HITL 审批（批准不改变计划约束）。`enter_plan_mode` 通过现有 `interaction.approval` 请求一次性点头（不产生 thread/project 权限规则），批准后在同一 Run 开启 flag；构图期 HITL 预检也读取该事实，确保 mutation/execute/task/MCP 直接进入 guard 而不先弹普通审批。内置 child 继续强制排除进入/退出工具；一次性 Plan flag 不能被活动档位切换解除。计划交卷走 `interaction.plan`（批准/打回/放弃），不复用工具审批五决策。
- `WorkspaceBoundaryMiddleware` 仍在实际执行前强制校验；同一策略还作为 HITL 的 `when` 预检复用，因此越界文件调用不会先产生无意义的审批请求。
- `default` 拦截 `execute`、`write_file`、`edit_file`、`delete_file`、`task`（其中只读安全的 Shell 命令在非 plan 模式均由 L3.1 自动快放）；`auto-edit` 放行工作区内非敏感编辑与普通删除（敏感路径如 `.git/*`、`.github/*` 依然强制弹窗，有副作用的 Shell 第一次仍弹窗）；`auto` 优先通过已存规则与确定性过滤器裁决，未决调用由 `SafetyClassifier`（优先专用 profile，未配或不可用时默认采用当前 Run 主模型）进行两阶段安全分类，破坏性命令硬拒绝，分类超时/失败时安全回退人工确认（Fail-Closed）；`yolo` 不注册 Harness HITL。共享 AgentEngine 为这些模式编译安全超集，HITL、AUTO classifier/guard、Workspace trust 和 system prompt 在每次模型/工具边界读取当前 mode；切档不会重建共享图。上下文归档和压缩由中间件自动维护，不暴露模型可调用的压缩工具，也不进入 HITL。
- 共享 Engine 的 `SafetyClassifier` 决策缓存按 `(thread_id, run_id, execution_id, tool_call_id)` 命名；模型后处理、HITL `when` 预检和执行层守卫对同一调用共享该命名空间内的一次分类结果，连续拒绝计数也按 Run 隔离。CLI 对同一活动 Run 的并发模式 RPC 串行提交，应用响应时读取最新确认档位，保证 Plan 恢复不引用入队时的旧 `current`。
- 审批规则持久化（`extract_command_rule`）：对解释器（`python`, `node`, `bun`, `pytest` 等）生成裸根前缀规则，支持跨文件复用；对已知子命令工具（`git`, `npm`, `cargo`, `docker` 等）提取并保留有效子命令前缀；对无子命令工具（`ls`, `cat`, `echo` 等）丢弃位置操作数生成根前缀规则；对高危命令（`rm`, `del`, `curl`, `wget` 等）严格禁止生成裸根规则。

批量 HITL 恢复以初始 `action_requests` 和原始索引为准，`decisions` 始终保持一一对应的完整长度。`approve_thread` / `approve_project` 在等待恢复消费期间只作为当前 Run 的 staged rule intent 保存；串行审批队列可在本地 overlay 中使用它们，但共享 Agent 图的 `rules_provider` 不读取这层暂存。只有 `Command(resume=...)` 对应的 resumed stream 正常返回后，`RunCoordinator` 才将 intent 去重提交到 session 或 project；恢复失败、取消、超时和 Run 清理都会丢弃暂存。project 写入异常继续向 Run 失败路径传播，不降级为 session 授权。

可选的 `ShellAllowListMiddleware` 只接受由 POSIX `shlex` 可可靠解析的单一命令。词法层禁止控制运算符、管道、重定向、子 Shell、命令替换、反引号、换行、NUL 与畸形引号；解析失败一律 fail closed。参数可以作为获准程序的普通参数传递，但中间件不解释程序自身语义。绝对路径必须与白名单条目完整匹配，禁止通过 basename 让工作区或临时目录中的同名程序冒充获准程序。同步与异步工具入口复用同一决策函数，并在拒绝时直接返回错误 `ToolMessage`，不调用 backend。

CLI 在交互模式才通过 `capabilities.handles` 声明 `approval`、`question`、`directory_trust` 与 `plan`，并声明 `run.approval_mode` 以接收活动 Run 的切档 RPC。无头 `-n` 模式不声明这些 handler，服务端遇到审批、提问或计划审阅会立即按拒绝/取消恢复，也不能通过 UI 伪造活动切档。活动切档只由 owner、ControlLease、Run 状态和 Interaction/Plan 门禁决定，不以 repository trust 状态作额外拒绝；WorkspaceBoundary/directory_trust 仍在外部目录工具执行边界强制生效。

子代理沿同一个父 `RunContext` 派生：Inline child 共享 state，Managed Plugin child 通过 provider 在每次调用时计算 `parent_current ∩ child_maximum`，因此父档位收紧立即影响后续 child 边界，父档位放宽也不会超过 Plugin 声明上限。`general-purpose` 在父 `default` 下保留 `auto-edit` 的角色默认例外；`plan` 和已激活的 `RunPlanConstraint` 始终优先。child 正在运行的调用不回滚，HC-168 的 staged approval 只有在 resumed stream 成功返回后才消费。
