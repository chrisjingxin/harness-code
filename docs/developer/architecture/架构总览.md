## 本分支目标：独立桌面协作产品

本分支已确立为独立的 Electron 桌面协作工作台，与旧版 CLI/TUI/独立 Web 入口完全解耦。最终交付 Electron + React 桌面客户端、Java/TDSQL 协作服务与标准 ACP 多代理运行接入：

```text
第 1 层：Electron + React 桌面壳与工作台（desktop/）
  ├─ 渲染层与内聚工作台 UI（desktop/src/renderer + desktop/src/ui）
  ├─ 桌面私有共享契约与主题令牌（desktop/src/shared）
  └─ 主进程装配与本机受限目录/只读文件/Git（desktop/src/main/ + project-service/）
       │
       ├─ 第 2 层：跨平台协作客户端（packages/collaboration-client）◀── 消费 contracts/
       │    └── HTTPS / SSE ── 第 5 层：Java 协作服务（server/）
       │                         ├─ TDSQL 控制面（唯一 schema.sql）
       │                         └─ Redis / Kafka / ES（热消息与索引）
       │
       └─ 第 3 层：通用本机 ACP 运行时（packages/acp-runtime）
            ├─ 第 4 层（可选 Harness 适配）：packages/harness-acp ──▶ agent/（Python ACP）
            └─ 通用外部 ACP 命令描述符（createCommandAgentDescriptor / WORKBENCH_ACP_EXECUTABLE）
```

五层目录按职责与语言清晰划分（四个根 npm workspace + 三个非 JS 顶层目录）：
- `contracts/`：语言无关线上 OpenAPI 规范、JSON Schema（Draft 2020-12）与校验 fixtures。
- `packages/collaboration-client/`（`@workbench/collaboration-client`）：纯 TS 协作客户端、HTTP/SSE/状态机与衍生类型（`./types` 无 Node/Electron 依赖）。
- `packages/acp-runtime/`（`@workbench/acp-runtime`）：通用 ACP 子进程生命周期、描述符/发现/注册表、会话绑定、交互/表单、能力与事件映射。
- `packages/harness-acp/`（`@workbench/harness-acp`）：可选 Harness ACP 适配器（探测 `agent/.venv` 与解析 `_meta.harnessCode`），仅依赖 `@workbench/acp-runtime`。
- `desktop/`（`@workbench/desktop`）：Electron main / preload / renderer / ui / shared / project-service，含安全 IPC 守卫（`ipc-guard.ts`）、目录授权（`local-directory-grants.ts`）、执行协调（`local-execution-coordinator.ts`）与薄 IPC 注册（`local-execution-ipc.ts`）。
- `agent/`（Python `harness-agent`）：可选 Harness Python ACP Agent 内核（含 `agent/examples/plugins/` 与 `agent/scripts/`），独立使用 `uv` 管理。
- `server/`（Java Spring Boot）：独立 Maven 协作服务端工程（直接读取根目录 `contracts/` 进行契约校验）。

平台可在不安装 Harness/Python 时使用外部标准 ACP Agent；Harness 推理、工具、上下文与存储只保留在 `agent/` 进程内，通用平台与云端服务不导入其 `Thread`/`Run`/SQLite/内部协议结构。

## 可选实例：Harness Python ACP Agent 内核机制（`agent/`）

`agent/` 作为可选默认 ACP Agent 实例（`harness-agent acp`），其内部引擎、持久化、上下文压缩与安全审批机制独立自治；内部通信协议与日志 schema 保存在 `agent/harness_agent/{protocol,diagnostic_log}/`，零 Anthropic 依赖补丁与检查脚本位于 `agent/scripts/`。

### Project、Thread 与 Message

Harness 的持久化领域模型为 `project`、`thread` 与 `message`（跨层标识为 `thread_id`；桌面侧协作 `Session` 与内核 `Thread` 通过 ACP 会话 ID 映射）。完整用户可见历史由 `ThreadPersistence` 的 append-only Transcript 保存；LangGraph checkpoint 只承担当前模型工作状态。

可恢复状态位于用户级 SQLite 文件 `~/.harness/threads.sqlite3`（目录权限 `0700`，文件权限 `0600`）。服务端对规范化工作区路径计算 SHA-256 `project_fingerprint`，用于 `harness_threads` 索引筛选与 LangGraph checkpoint 的 `checkpoint_ns`：

```python
{
  "configurable": {
    "thread_id": thread_id,
    "checkpoint_ns": project_fingerprint,
  }
}
```

Harness 自有表包括 `harness_threads` 与 `harness_thread_transcript`，按 `(project_fingerprint, thread_id)` 隔离。Python Agent 通过 `ThreadPersistence` 的 `accept_run`、`append_transcript_batch`、`load_transcript`/`open_thread`、`load_run_state`、`load_context_state` 与 `commit_context` 访问持久层。

`ContextProjector` 与版本化 `CompressionCheckpoint` 按单一链路为每次顶层 Run 生成模型历史：

```text
最新有效 CompressionCheckpoint.projected_messages
+ source_record_sequence 之后的 Transcript tail
→ 校验 user / assistant tool-call / tool-result 原子组
→ 单向刷新 LangGraph messages 缓存
→ 追加当前 Run 已受理的 user 记录并执行
```

最终连续性生产路径由 `RunCoordinator` 与 `AgentHost` 共同维护：

```text
run.start
→ AgentHost._prepare_run：刷新并冻结同一 SkillRegistry、Profile 和 ContextLifecycle snapshot
→ ThreadPersistence.accept_run：原子写入 Run binding、snapshot、Thread 索引和用户 Transcript
→ AgentEnginePool.acquire：取得与该 preparation 对应的 AgentEngine
→ 构造 RunContext：注入同一 snapshot/Skill registry、取消令牌和执行策略
→ ContextProjector.project & sync_cache
→ RunCoordinator 执行当前 user message，并由 ContextWindowMiddleware/ContextCompactor 处理压缩
```

详见 [上下文管理改造需求](上下文管理改造需求.md)、[上下文管理顶层设计](上下文管理顶层设计.md) 与 [ADR 0003：Transcript 事实层与上下文投影生命周期](adr/0003-transcript-context-projection-lifecycle.md)。

### 持久化与可观测性四层分界

Harness 内核数据严格区分为四层，详细架构见 [本地诊断日志](本地诊断日志.md)：

1. **Transcript 业务事实层**（SQLite `harness_thread_transcript`）：保存用户可见消息、工具调用与结果、大型工具 Artifact。
2. **CompressionCheckpoint 上下文检查点层**（SQLite `harness_compression_checkpoints`）：保存分级压缩投影检查点、覆盖的 sequence 与 digest。
3. **LangGraph Checkpoint 图状态层**（SQLite adapter）：保存 LangGraph 图执行的瞬时节点状态。
4. **Diagnostic Log 本地诊断日志层**（`~/.harness/logs/<date>/` 独立 JSONL）：低流量、结构化、异步脱敏的生命周期与耗时事件，纯单向观察者。

### AgentEngineProfile 与运行状态

Harness 的长期 Agent canonical model 固定为 `ProviderDefinition`、`ModelProfile`、`ExecutionPolicyDefinition`、`AgentDefinition`、`ThreadExecutionSelection` 和 `RunExecutionBinding`（详见 [ADR 0001](adr/0001-agent-domain-model.md) 与 [配置架构](配置架构.md)）。

- `AgentEngineProfile` 以脱敏 canonical JSON 的 SHA-256 为 Key 复用编译图（含角色指纹、`project_fingerprint`、模型配置、工具/Skill、MCP、Sandbox、Policy 与 Prompt 指纹），不泄露原始工作区路径、endpoint 或密钥；
- `AgentHost` 独占 `ProviderClientPool`、`McpConnectionManager` 与 `ThreadPersistence`，`AgentEngine` 通过 lease 借用并在配置快照变化时经 `DRAINING → CLOSED` 有序排空；
- 可派发子代理（内置 `general-purpose`、`explore` 与 Plugin Agent）由单一 `AgentCatalog` 管理，委派深度限制为 1、并发上限为 4，`explore` 严格受限为只读工具集；
- 工作模式支持 `build` 与 `compose`（`RunExecutionAdapter` seam，详见 [Compose 工作模式](Compose 工作模式.md)），目标闭环评估见 [目标闭环](目标闭环.md)；
- 模型调用由 `BoundedProviderRetry`（`run_with_provider_retry`）与 `ModelOutputGuardMiddleware` 统一承担可恢复边界，SQLite v1–v6 迁移通过受监管的 `migration_worker` 原子执行（详见 [ADR 0004](adr/0004-legacy-migration-supervision.md)）。

### Skill 与 Plugin 生命周期

Host 初始化与顶层 Run 通过 `SkillCatalogManager` 发现四类来源（内置 `built_in_skills/`、用户 `~/.harness/skills/`、项目 `<workspace>/.harness/skills/` 与市场目录），经 SHA-256/安全校验后生成不可变 `SkillRegistry` 并索引进 `RunContextSnapshot`；portable/Claude/Qwen/Hybrid Plugin 通过 `PluginStore` v3 registry 与闭源校验接入 `ExtensionCatalogSnapshot`（详见 [扩展与插件机制设计方案](扩展与插件机制设计方案.md)）。

### RunContextSnapshot、上下文预算与代码索引

`ContextLifecycle` 为每个顶层 Run 生成按信任层级排序的不可变 `RunContextSnapshot`（策略/工具能力先于 AGENTS 与 Skill 索引）。模型上下文预算按 `window - clamp(4096, 16384, ceil(window * 10%))` 计算，`ContextPressurePolicy` 维持 `50% report / 60% micro / 80% full / 90% hard` 有序阈值；`ContextCompactor` 负责自动、溢出与手动压缩校验。可选本地代码索引由 `CodeIndexManager` 管理 `.harness-index/` 并只暴露 `codebase_explore`（详见 [代码索引](代码索引.md)）。

### 执行后端、文件 Snapshot 契约与审批模式

- **工作区与执行后端**：默认 `tools.sandbox = false` 使用本机受限路径策略（`WorkspaceBoundaryMiddleware` 与 `WorkspaceRootRegistry`，主 Agent 与默认 `general-purpose` 子代理分别注册）；配置远端 sandbox 时加载受信任 `SandboxBackendProtocol` 工厂，失败关闭不回退本机。
- **单一文件修改入口（`HarnessFileToolsMiddleware`）**：
  - `read_file` 返回局部源行与 Thread 级短 `Snapshot`；
  - `write_file` 仅创建不存在文件；
  - `edit_file` 校验同 Thread `Snapshot` 与互不重叠的精确 `edits[]`（HC-185），经 `FileMutationService` + `TextMutationBackend` 原子 compare-and-replace；
  - `delete_file` 校验完整读取 `Snapshot`；所有操作严格 `realpath` 防逃逸，并在需要时触发精确 diff 或目录信任人工审批。
- **审批模式（`harness_agent.policy.approval_mode`）**：统一规范值为 `plan`、`default`、`auto-edit`、`auto`（默认）、`yolo`，由 `PlanModeMiddleware`、`WorkspaceBoundaryMiddleware`、`SafetyClassifier` 与 `ShellAllowListMiddleware` 联合执行，并与 `RunContext` 绑定。
