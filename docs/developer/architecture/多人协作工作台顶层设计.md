# 多人协作工作台顶层设计

状态：Java 方案设计草案，待评审；不是当前生产架构。日期：2026-11-05。

需求与验收以 [HC-192](../task/HC-192-协作工作台与会话交接.md) 为准，源码证据见 [Lody 协作能力对照](../research/192-Lody协作能力对照.md)。本文给出一个能外网演示、后续部署到内网的初版方案。具体 API、SQL 和错误码在 Task 确认后的 Spec 中确定。本轮更新设计文档，不生成 UI 设计稿，也不进入产品实现。

## 1. 先回答：是否需要云端记录

需要一个各台电脑都能访问、能够长期保存共享会话的服务。对本项目，建议让它保存会话、成员、交接、引用与执行记录，并向客户端推送更新。公网云服务器、企业自己的机房服务器或内网虚拟机都能承担这个角色。

本项目初版采用中心服务。不同用户连接同一个地址，消息留在服务器；他们不需要保持电脑互联或把自己的数据库发给对方。数据库与 Agent 的运行状态也要保存在持久目录中，不能只存在浏览器缓存或临时进程内。

| 信息 | 建议保存位置 | 换人或换电脑时怎样延续 |
| --- | --- | --- |
| 成员、会话、消息、交接、引用及其文本快照 | Java 协作服务的 TDSQL MySQL 兼容版 | 登录后由服务读取同一份记录 |
| 附件正文 | 服务的数据目录，数据库保存关联 | 按工作区权限下载与查看 |
| 底层 Agent 会话 ID、模型上下文与检查点 | TDSQL 中的绑定记录及 Agent 自己的数据目录 | Java 执行模块继续使用原 Agent 会话；重启后按后端支持的能力恢复 |
| 代码仓库与 Git 状态 | 执行服务器的项目目录 | 当前执行位置在页面可见，由 Runner 访问 |
| 输入草稿、打开的页签、滚动位置 | 各浏览器本地 | 各自保存，不驱动其他人的页面 |

共享的可见历史与模型内部状态分属两层。只把聊天文字保存到云端，不足以保证所有 Agent 在原机器离线后还能接着执行。因此首版建议 Agent 就运行在演示服务器，不绑定某个用户的电脑。

## 2. 已确认场景与方案选择

已确认：共享同一对话；用户 A 交给用户 B，后者用自己的电脑接续；支持 @对话；顶层工作台独立，Harness 通过 ACP 接入；先外网演示，后迁内网。初版在数据库默认创建几个普通用户账号供登录调试，不预设岗位、业务角色或按岗位划分的权限；内网登录系统留到内网阶段开发。

本文按用户要求将云端业务服务与执行编排统一为 Java，平台数据库采用用户已确认的 TDSQL MySQL 兼容版。推荐一台应用服务器、一个 Spring Boot 应用、一个 TDSQL 业务库和服务器项目目录。Runner 表示管理 Agent 进程与会话的执行模块，也在 Java 应用内；具体 Agent 为 ACP 子进程。

初版先做在线共享会话，已提交消息由服务统一排序。采用固定默认行为；暂不增加 Redis、消息中间件、微服务网关或多套同步引擎。Java 与 TDSQL MySQL 兼容版是用户已确定的约束；下文的框架和通信方式是本稿推荐，仍以评审后的 Spec 为准。

### 2.1 推荐技术栈

| 部分 | 初版推荐 | 负责什么与选择理由 |
| --- | --- | --- |
| Web | React + TypeScript，独立工作台包 | 继续利用 Harness 现有界面与 Lody 的前端参考，不因云端改 Java 重写浏览器界面 |
| 云端业务 | JDK 21、Spring Boot 4.1.x、Maven | 一个 Java 应用内按业务分包，适合现有 Java 团队共同维护 |
| HTTP 与实时更新 | Spring MVC，写操作走 HTTP，更新走 SSE | SSE 是服务向浏览器持续推送事件的长连接；发送消息、审批、取消仍是普通 HTTP 请求 |
| 调试登录与访问范围 | 数据库预置普通用户、服务端演示会话 | 选择预置账号进入工作区；Spring Security 复用会话与请求边界，不开发密码、注册或统一登录系统 |
| 业务存储 | TDSQL MySQL 兼容版、MySQL JDBC、Spring JDBC、版本化 SQL | 消息、引用、交接与排队输入按事务落库；迁移工具优先评估 Flyway，需在目标实例验证 |
| Agent 编排 | Java 内部执行模块 + ACP Java SDK | 使用现成协议库管理会话与子进程，不重写 ACP 编解码，不另建 Node 业务服务 |
| 文件与附件 | 服务器持久目录 | Java 保存关联与访问权限；文件/Git 操作限定在所绑定项目目录 |
| 部署 | Java 可执行 JAR、Web 静态资源、TDSQL 接入、Agent 制品 | 外网与内网采用相同结构；Agent 自身所需 Python/Node 等运行时随具体后端提供 |

Spring 官方文档确认上述 Spring Boot 系列支持 JDK 21；Spring MVC 已提供 SSE 支持，SQL 集成包含 JDBC 入口。来源见 [系统要求](https://docs.spring.io/spring-boot/system-requirements.html)、[MVC 异步响应](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html) 与 [SQL 集成](https://docs.spring.io/spring-boot/reference/data/sql.html)。这只是候选版本基线，正式实现前锁定具体补丁与可在内网导入的制品，不使用漂移版本或 SNAPSHOT 作为演示依赖。

平台库以 TDSQL MySQL 兼容版为唯一目标。应用使用 MySQL JDBC 访问，连接到内网提供的数据库接入地址，不依赖腾讯云管理 API。Harness 自有 SQLite 和 Agent 原生检查点继续由各 Agent 管理，不搬入平台数据库。腾讯官方给出了 [Java JDBC 接入示例](https://cloud.tencent.com/document/product/557/10238)；实际驱动版本以目标实例兼容内核为准。

### 2.2 怎样尽量利用 Lody 代码

| 材料 | 首版使用方式 | 适配边界 |
| --- | --- | --- |
| Lody 的 mentions、会话与消息组件 | 优先复用合适的纯逻辑、交互组织和测试场景，再接入 Harness 的组件与主题 | 有平台/云接口依赖的组件先拆边界，不整体搬入 Electron 或托管云依赖 |
| Lody 的平台身份接口 | 参考 `PlatformUser`、`PlatformIdentity` 与工作区订阅，把登录来源隔离在平台入口 | 账号只表示用户；调试账号由 Java/TDSQL 提供，不直接套用 Lody 的单用户本地模式 |
| Claude、Codex 等 ACP 适配器 | 优先利用已下载源码中的协议实现，实施时构建或取得固定发布制品 | 由 Java ACP Client 启动；适配器可以是 TypeScript，不变成第二个业务后端 |
| 会话身份、作者、去重与恢复机制 | 借鉴已有职责与状态模型，在 Java 中实现平台业务 | 不把 Lody 的内部 RPC 或 CRDT 对象直接当我们的公网 API |
| ACP Java SDK | 直接作为 Java 协议依赖候选 | 优先使用标准会话与 stdio；专有扩展按实际握手与互通结果提供 |
| Loro Streams、SQLite 开发服务 | 保留为同步机制与集成测试参考 | 首版不作为必需线上组件，不把 TypeScript 服务改名后当 Java 服务，也不重写一套 Java CRDT 引擎 |
| Loro Mirror、Todo、CodeMirror | 按需参考状态订阅、离线提示与后续文档协作 | 不为复用示例而新增离线共同编辑、共享输入草稿等产品范围 |

当前需求的核心是共同查看已提交消息、顺序执行和接手续聊，中心数据库与事件推送即可形成第一条链路。Loro 擅长可并发编辑的数据合并；若以后确认需要共同编辑文档，再单独评估接入。这个取舍由当前产品范围与 Java 维护目标决定，不是否定已下载材料的价值。

ACP 官网已列出 [Java SDK](https://agentclientprotocol.com/libraries/java)，其 [仓库](https://github.com/agentclientprotocol/java-sdk) 提供 Client、stdio 与测试支持。因此不必为了对接 Agent 再维护一个 TypeScript Runner 网络服务。尚未完成与 Lody 适配器的互通验证，标准方法和 Lody 专有扩展要分开验收。

### 2.3 TDSQL 接入与表结构原则

用户已确认 MySQL 兼容版，但具体兼容大版本与部署引擎尚未取得。业务使用 MySQL 兼容 SQL，不先假设完整 MySQL 8 特性或所有分布式功能都可用。以下原则让外网演示与内网采用同一套数据访问和迁移脚本：

| 设计点 | 初版做法 |
| --- | --- |
| 接入 | Java 通过数据源与 MySQL JDBC 连接 TDSQL；数据库只由服务访问，浏览器不直连 |
| 业务 ID | 应用生成稳定 ID；不依赖某种自增取值或数据库特有序列语义 |
| 业务关联 | 表中保留工作区、会话等关联 ID，应用校验归属；不依赖外键、触发器或存储过程驱动协作业务 |
| 查询与内容 | 使用常规索引和有界分页，初版会话搜索采用标题查询；正文使用兼容文本字段，不依赖全文索引、JSON 专有查询或数据库通知通道 |
| 建表 | 首版优先普通表；物理分片方式在取得实际实例条件后确认，不为演示提前做分库分表。若必须使用分表，需在 Spec 细化分片键与事务范围 |
| 事务与迁移 | 明确消息、引用、执行登记的事务边界；验证唯一约束和并发状态更新。DDL 不假定可事务回滚；迁移脚本版本化，工具适配需实测 |
| 字符与时间 | 文本使用支持中文与 emoji 的 utf8mb4；ID 比较规则与统一时间表达在 Spec 固定，不能由数据库默认排序规则改变去重结果 |

这些是本项目的 SQL 使用范围，不代表 TDSQL 所有产品版本均有相同限制。公开分布式版的 [使用限制](https://cloud.tencent.com/document/product/557/47511) 和 [建表说明](https://cloud.tencent.com/document/product/557/8767) 可作核对入口，最终以实际内网实例为准。

外网优先使用同兼容大版本的 TDSQL。没有外网 TDSQL 条件时，可用匹配大版本的 MySQL 完成业务演示与开发测试，仍使用同一套应用代码；这种结果只证明对应 MySQL 环境下的行为，不能代替 TDSQL 的驱动、迁移、事务和约束验收。不另外建立一套数据库适配分支，也不假定普通 MySQL 测试已经证明内网可用。

| 环境 | 部署方式 | 差异 |
| --- | --- | --- |
| 外网初版演示 | 可访问的 HTTPS 地址、演示账号、真实可用模型、持久化目录与数据库 | 优先同版本 TDSQL；若使用匹配大版本 MySQL，明确验收范围；Agent 制品与模型可从外部获得 |
| 最终内网 | 相同 Java/Web 产物与 MySQL 方言迁移脚本，连接内网 TDSQL | 更换域名、数据库地址、模型网关与必要的登录接入；Agent 制品、内网 SDK 按执行环境配置 |
| 本机开发 | 同一 Java 服务和隔离数据库，采用相同兼容大版本 | 自动化使用 mock Agent；核心 SQL 在匹配 MySQL 环境与目标 TDSQL 分别验证，不用 H2 替代 |

初版交付包含 Java JAR、Web 静态资源、数据库迁移、固定的服务启动方式、数据目录说明、账号初始化方式和两电脑演示步骤。Java 应用可托管已构建 Web 资源，以同一域名提供页面、API 与 SSE。HTTPS 可由服务器现有反向代理终止；反向代理需允许流式响应。TDSQL 可使用已有数据库服务，Agent 数据与项目目录位于执行服务器持久磁盘。容器打包可按实际服务器选择，不把容器当作 Agent 的执行沙箱。

当前没有服务器地址、账号或模型接入配置，不进行实际部署。设计与本地实现不依赖提前取得这些信息；上线演示前再接入实际环境。

## 4. 模块边界

以下是目标归属建议，目录名在 Spec 中确认；本轮不会搬代码。

| 模块 | 负责什么 | 与现有代码的关系 |
| --- | --- | --- |
| 独立 Web 工作台，建议 packages/workbench | 页面、主题、消息与工具组件、共享/交接、引用交互 | 从 packages/cli/src/web 提取，不再依赖 CLI 接管状态和完整 InteractiveSnapshot |
| Java 协作服务，建议 services/collaboration-server | 账号、工作区、共享会话、引用、交接、记录与订阅 | 新增 Maven 工程，不接管 Agent 的模型推理与文件工具 |
| Java 内部执行模块，位于该服务的 execution 包 | 启停 ACP 进程、会话绑定、串行执行与审批关联 | 与业务服务同一 JVM；使用 ACP Java SDK；具体 Agent 为独立子进程 |
| Java 工作目录模块，位于该服务的 workbench 包 | 文件读取、Git 人工操作、项目占用协调 | 接替原 Web 对 CLI 本机文件/Git 服务的依赖，沿用已确认的文件与 Git 行为边界 |
| 契约，packages/protocol 的独立协作命名空间 | HTTP 数据、共享事件与跨语言生成输入 | 与现有 Agent JSON-RPC v3 分开；标准 ACP 类型使用 SDK，不重复定义 |
| Harness ACP 入口，packages/agent 内独立入口 | 把 ACP 方法接到 Harness 的 Thread、Run 和 Interaction | 复用 AgentHost、RunCoordinator、ThreadPersistence 和现有策略 |

现有规则把表现层放在 CLI；用户已提出工作台上移这一目标。实施前必须在同一变更中调整根 AGENTS.md 与工程入口，不能在旧规则下偷偷建立新的跨包依赖。

Java 首版采用一个 Maven 应用，内部按 `identity`、`workspace`、`conversation`、`reference`、`handoff`、`execution`、`workbench`、`realtime` 分包。业务用例、数据访问与 HTTP 适配在各包内分清职责，不立即拆成八个 Maven 工程或网络服务。前端不能导入 Java 类；Java 也不依赖 CLI 的 TypeScript 状态对象。

协作契约采用同一份 OpenAPI 与事件 schema 作为生成输入，生成或校验 Java/TypeScript 两端载荷；具体生成器在 Spec 中锁定。现有 JSON-RPC v3 的 schema、版本号与生成链保持独立。后续工程检查需要覆盖 Java、Web、协议和 Python，不能只通过现有 npm 检查就声称新服务已验证。

完成迁移后，Web 的通用会话只走协作服务与 ACP。原 Web 接管与单浏览器状态通道在替换完成时删除，不作为长期兼容分支保留。原生 TUI 可继续作为 Harness 自己的入口，复用同一 Agent 内核。

## 5. 数据归属与最小模型

平台记录用户能共同看到和操作的工作内容；Agent 保管自身运行所需的私有状态。两层通过 ID 关联，不能互相覆盖对方数据库。

| 记录 | 最少需要表达的信息 |
| --- | --- |
| 用户 | 稳定内部用户 ID、登录名、显示名、启用状态；不包含岗位或预设业务角色 |
| 工作区与成员 | 工作区 ID、用户 ID；首版成员拥有相同的共享会话能力 |
| 平台会话 | 会话 ID、标题、创建者、当前接手人、绑定的执行后端 |
| 消息与工具事件 | 稳定 ID、会话内顺序、作者、内容、所属执行与时间 |
| 执行 | 输入 ID、原发起人、排队/运行/完成状态、底层会话与请求关联 |
| 交接 | 稳定交接 ID、发起用户、目标用户、说明、待接手/已接手/已取消状态、请求与处理时间 |
| 引用草稿快照 | 草稿 ID、创建用户、来源工作区/会话/消息、可见顺序与选区、固定正文、摘要校验值 |
| 引用 | 来源会话和消息 ID、所选内容快照、引用时的来源位置 |
| 附件 | 所属工作区与消息、服务器文件标识、类型和大小 |
| 后端绑定 | 平台会话 ID、Agent 类型、ACP session ID、执行项目、原生持久化位置的内部引用 |
| 待决人工交互 | 审批/提问 ID、所属执行、内容、待回答/已回答状态与实际回答人 |

平台会话 ID 与 ACP session ID 分开。浏览器使用平台 ID，后端自己的 ID 由 Runner 解析。标题和成员姓名可以变化，关联使用稳定 ID。

TDSQL 是平台会话、消息、交接、引用与执行状态的唯一事实源。Web 缓存、SSE 连接和 Java 内存队列都不产生第二份权威历史。作者身份取自登录会话；浏览器不得自行指定另一个成员作为作者。Agent 的原生历史和检查点仍由 Agent 自己保存，两类数据通过绑定记录关联。

建议首版一个工作区内成员共享会话，用户与成员关系通过初始化数据预置。当前不开发成员邀请、角色分配或权限管理后台；普通成员均可查看、续聊和交接。之后如需私有会话，再明确增加可见性规则。

## 6. 一次输入怎样执行

    用户发送 → Java 确认身份与引用 → 同一事务保存消息、引用和执行记录 → 返回“已保存”
    会话与执行目录空闲 → Java 执行模块取队列头 → SDK 调用原 ACP 会话
    ACP 流式返回 → 保存显示事件与会话顺序 → SSE 推送给所有在线成员
    执行完成 → 写入结果状态 → 处理下一条排队输入

同一会话一次运行一个请求，不同会话可以独立运行。每次输入保留发起人，重试使用同一个请求 ID；服务只保存和执行一次该输入。

重复请求需要同时核对请求 ID 与内容；同一 ID 携带不同内容应报告冲突。数据库保存排队状态，Java 内存调度只负责唤醒处理。事务只覆盖登记与状态变化，不跨整个模型调用长期占住数据库连接。

不同会话若绑定同一执行目录，则 Agent 运行与人工 Git 写操作还需共享项目占用规则：同一目录同时只执行一项会改变工作内容的任务，其他任务显示排队。不同执行目录可以并行。不能只用会话队列保护同一 Git 工作树，也不在首版额外引入分布式锁服务。

浏览器关闭只结束页面订阅。Agent 生命周期属于服务器服务，其他成员仍可观察和继续。重新打开按消息顺序补齐记录，实时连接只负责及时通知，持久化记录负责恢复。

SSE 事件携带可恢复的会话顺序。服务按客户端最后确认的位置读取持久记录，再继续推送；历史读取与实时订阅切换处也必须补齐差额，不能留下消息空窗。客户端按稳定 ID 去重、按顺序应用；断线后显示重连状态，慢连接需要重连补齐时也从数据库恢复。在线成员提示是临时状态，离线或掉线不改写会话正文，也不代表 Agent 已停止。

服务重启时先恢复历史和会话绑定。已知尚未发往 Agent 的队列输入可以继续处理；无法确定是否已经执行的输入显示“执行结果待确认”，由使用者决定如何处理，不自动把有副作用的请求再跑一次。这是固定恢复行为，不提供一组重试配置开关。

普通网络重试的输入去重不能保证外部工具在任意进程崩溃下全局只执行一次。Java 必须先登记派发状态再调用 ACP，恢复时保留这种不确定性，不把失联操作合成为成功，也不直接重新调用。

## 7. 任意用户之间交接

    用户 A 点击“交接” → 选用户 B → 填写说明 → 保存“待接手”记录
    用户 B 打开同一会话 → 查看历史与说明 → 点击“接手” → 更新当前接续人

交接说明提供三个简短字段：已确认事项、下一步、待定问题，允许留空。初版由用户填写；可辅助生成摘要的功能后续再决定。

新会话的当前接续人默认是创建用户。发起交接只增加待接手记录和时间线事件，当前接续人保持不变；目标用户确认接手时，才在同一事务中更新交接状态、当前接续人和时间线事件。用户 A 仍然能看后续消息，用户 B 的新消息显示其当前账号身份。候选来自当前工作区的其他启用用户，不按岗位筛选。

| 当前状态 | 操作 | 结果与当前接续人 |
| --- | --- | --- |
| 没有待接手交接 | 工作区成员发起交接 | 创建 `pending`（待接手）；当前接续人不变 |
| `pending` | 目标用户确认接手 | 原子转为 `accepted`（已接手），当前接续人变为目标用户 |
| `pending` | 发起用户取消 | 转为 `cancelled`（已取消）；当前接续人不变 |
| `pending` | 又发起另一笔交接 | 告知已有待接手记录；不覆盖目标用户，先取消或完成原交接 |
| 已处理 | 重复确认或取消 | 同一请求返回原结果；相反操作或过期页面得到已处理状态，不再改写接续人 |

同一会话最多存在一笔待接手交接；首版不增加自动过期或超时转交。目标用户确认前须仍是启用的工作区成员，其他用户不能代其确认。确认、取消以同一交接 ID 和预期状态处理，只有第一次有效状态变化写入事件。所有成员的普通发言能力保持一致，交接不转移会话访问权，不创建聊天副本或新 ACP 会话，也不发起隐藏模型请求。

交接期间已有 Agent 请求可以继续完成。之后用户 B 的输入走同一个会话队列，使用原 ACP 会话；接手人只表示当前接续工作的人，不是一种用户角色，也不需要给每位成员建立一个独占模型进程。

共享会话的成员均可参与当前允许的人工交互；同一个审批/提问只接受第一个有效回答，并记录回答人。交接不会复制、重发已回答或已过期的问题。后端连接由 Java 服务持有，不能把当前浏览器变为 Agent 的唯一 owner，再因为换人而丢失审批通道。

首版明确显示“执行位置：服务器 / 项目名”。在用户自己的浏览器续聊与在其本机执行代码是两个步骤；后者需要后续接入本机 Runner，不在交接时自动发生。

## 8. @对话与指定内容

    输入 @ → 搜索可访问会话 → 选择范围 → Java 固定引用草稿并返回预览
    发送时 → 校验草稿与访问范围 → 原样保存正式引用 → 随本次问题发给 Agent
    历史中 → 点击引用 → 打开来源会话并定位相关消息

首版在同一工作区内解析引用。预览由 Java 从有权限的来源生成，并把不可变草稿存入 TDSQL；返回草稿标识、来源位置、截取范围、可见消息顺序和实际正文。消息 ID、选区与正文摘要校验值一起记录。草稿归属当前用户与工作区，不接受浏览器自行替换正文来冒充来源。

发送时重新检查当前用户、工作区、来源可访问性与草稿归属，把该草稿原样复制为正式引用记录，与本次消息、执行登记在同一事务保存。发送流程不重新截取最新正文，也不静默补充来源后来的消息。正式引用与实际构造给 ACP 的文本来自同一份快照，因此预览、历史和模型输入一致；重复提交同一输入不会创建第二份消息或引用。

| 来源变化 | 引用处理 |
| --- | --- |
| 来源消息继续流式输出 | 草稿只包含预览时已生成并选中的内容，预览说明这一范围；新增片段不自动带入 |
| 用户希望引用更新后的内容 | 明确刷新引用，生成新草稿并重新预览；旧草稿正文不原地变更 |
| 标题变化或会话新增消息 | 固定正文和消息选区不变，来源仍按稳定 ID 定位 |
| 发送前来源被删除或失去访问范围 | 阻止发送并提示刷新或移除引用，不悄悄丢弃引用后继续提问 |
| 已发送后来源不可再定位 | 保留当前会话中已保存的引用快照，展示来源不可用，不追加读取其他来源 |

引用整段会话表示预览时选取的一段有界消息，不默认注入所有工具正文。预览须显示截取范围；过长时在预览阶段要求缩小范围，不到发送时再静默截断。具体限额、字符选区和摘要算法在 Spec 固定。

为让不同 ACP 后端都有相同的基本体验，首版由平台把已选快照形成普通文本上下文，随本次问题一起发送。界面保留结构化引用标识。可按需读取更多历史的 MCP 工具属于后续增强，不作为首版引用能够工作的前提。

Lody 当前采用会话链接与历史读取工具；我们借鉴稳定引用和按权限读取的边界，首版交付方式按自身范围简化。引用材料作为参考内容进入本次输入，不成为系统权限或运行配置。

## 9. ACP 与 Harness 的接合点

建议以 ACP v1 的通用会话能力为第一条链路，版本在实现时按选定 SDK 锁定。ACP 能力通过握手确定；没有宣告恢复、图片或专有扩展的后端，界面不提供对应操作。依据见 [ACP 初始化](https://agentclientprotocol.com/protocol/v1/initialization) 与 [会话建立和恢复](https://agentclientprotocol.com/protocol/v1/session-setup)。

Java 执行模块作为 ACP Client，首版通过 SDK 的 stdio transport 启动与管理子进程。SDK 回调接入有序的执行事件处理；等待模型结果、审批和持久化不能阻塞接收取消与协议回复的通道。后端启动命令在服务器配置，浏览器只选择已登记的后端配置。

| 工作台需要的行为 | Harness ACP 入口的目标映射 |
| --- | --- |
| 建立会话 | 建立 Harness Thread，并保存平台绑定 |
| 发送问题、流式输出 | 复用 RunCoordinator 的启动、事件与唯一终态 |
| 停止执行 | 取消对应 Run，不因页面断开而取消 |
| 审批与提问 | 映射现有 Interaction，由协作服务记录并提交成员的回答 |
| 加载原会话 | 读取 ThreadPersistence 恢复上下文并回放可见历史 |
| 专有能力 | 用协商后的扩展表达，保持标准 ACP 会话流程可独立使用 |

Harness ACP 入口复用现有业务服务，不能通过模拟 TUI 输入驱动，也不能再实现一套模型循环。现有 JSON-RPC v3 是 Harness 内部入口之一，不直接冒充 ACP。

平台保存展示历史；Harness 保存自己的执行账本和模型检查点。ACP 历史回放用于恢复显示时，需要映射到已有消息，不能再次当新消息追加。规范化消息关联与恢复行为必须在 Spec 中写清并测试。

Harness 是首个真实接入，其 ACP Agent 入口仍以 Python 实现。Claude/Codex 通过各自已有 ACP 适配器进入同一个 Java 执行模块；适配器所需 Node/其他运行时是 Agent 制品的一部分。云端改 Java 不要求把 Python 内核或第三方适配器改写成 Java，也不直接以 Spring AI 再造一个替代 Harness 的模型循环。

原生配置、授权与能力差异留在适配层。它们的上下文格式不承诺互换；换后端属于显式创建新执行分支的后续设计。Lody 适配器包含专有扩展，标准 ACP SDK 的存在不证明这些扩展已经对齐。

### 10.2 迁移验证边界

实施计划必须对上表逐行登记目标模块、保留的用例与验证结果。至少复用 HC-190 的临时 Git 仓库与本地 bare remote 场景，HC-191 的合成 marker、跨 chunk、start/end 乱序、历史/实时合并和双模式展示场景，并补 Java 与原有 TypeScript 结果对照。正文、凭据、真实用户日志不作为夹具。

Java ACP 进程接线与 stderr 采集应先形成小原型，确认新入口仍能观测 Harness 的既有轨迹产出，再迁移解析器。内网 Trace SDK 在外部不可安装时保留其原逻辑；外网显示无数据或明确不可用，不制造 Span，也不把合成测试当作真实采集结果。Claude/Codex 没有宣告该扩展时不承诺相同 Trace 能力。旧 CLI 网关与采集入口在对应新链路通过回归后删除，不长期双写或双重采集。

## 11. 最小必要配置与数据维护

部署需要服务地址、数据库连接、数据目录、项目目录和 Agent 启动配置。模型凭据由执行端现有配置管理，不复制进共享会话。首版不做任意可执行命令编辑器，也不按每个超时和限额增加环境变量。

### 11.1 预置普通用户，供登录调试

默认初始化 `user01`、`user02`、`user03` 三个普通用户账号，显示名为“用户 01”等。这些名称只区分调试身份，不代表岗位或权限等级。数据写入 TDSQL 的用户和工作区成员记录，由 Java 查询；不在前端或控制器中写三组专用分支。

    打开演示登录页 → 选择或输入预置用户名 → Java 查询启用用户
    建立演示会话 → 返回当前用户与工作区 → 进入共享会话

首版按免密码选择调试身份设计；演示会话不代表已验证真实人员身份。注册、找回密码、邀请和统一登录留到后续，内网登录系统到内网阶段再开发。Spring Security 仅复用会话与请求边界；页面与 API 同源，使用 HttpOnly 会话 Cookie，写请求保留 CSRF 校验。

| 数据或行为 | 首版约定 |
| --- | --- |
| 用户账号 | 普通用户只有稳定 ID、登录名、显示名和启用状态，不增加岗位/业务角色字段 |
| 工作区关系 | 初始化一个共享工作区及上述用户的成员关系；成员能力相同，不设置用户角色 |
| 初始化 | 以登录名等稳定标识去重，重复执行不新建重复用户、不重置原 ID，也不覆盖已有历史 |
| 登录与退出 | Java 根据预置用户记录建立/结束演示会话；不存在或停用的账号不能进入 |
| 发言与操作 | 作者、交接人和审批回答人由当前服务端会话确定；请求正文不指定另一个用户作为操作人 |
| 切换账号 | 退出旧身份、结束该页面旧订阅，再进入新身份；不重写旧消息作者，不停止服务端 Agent |
| 访问范围 | 服务按预置成员关系核对消息、引用、附件与订阅的工作区归属；文件仍按项目根解析 |

两台电脑可以分别使用 `user01`、`user02` 测试任意用户之间的交接；同一个账号也能在多设备保持相同作者身份。登录状态、工作区列表和消息作者分开提供，参考 Lody 固定提交中的 [平台身份](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/platform/src/provider.ts)、[React 订阅入口](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/platform/src/react.ts) 与 [消息作者](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/shared/src/message-author.ts)；不会把当前用户写死成某种岗位。

未来内网接入只在 Java `identity` 模块处理真实登录与外部账号映射，Web 继续消费同一种当前用户状态，业务继续使用内部用户 ID。真实账号与既有调试用户的关联届时明确绑定，不按显示名自动合并；已有消息、交接与会话的用户 ID 关联保留。不为这一步提前引入内网 SDK 或多种登录提供方配置。

### 11.2 数据与制品维护

备份范围包括 TDSQL 业务库、附件、后端绑定、Agent 原生数据目录与项目目录。初版先停止接收新执行并等待运行收敛，再停止应用，使用内网已有数据库备份方式与持久目录备份形成一组恢复材料；Agent 自有 SQLite 也在停止后备份。不能仅复制平台数据库就声称已保存模型上下文。当前设计不自动把外网演示内容导入内网，实际数据搬运按后续明确要求执行。

首演使用新建的共享会话。已有个人历史的导入与归属在正式切换前单独确认，保持原数据可读；不能默认把某个人电脑上的历史都上传到共享工作区。

外网和内网保留相同 MySQL 方言与版本化迁移脚本，避免到内网再改表结构。迁移前需要准备固定的 Maven、JDBC、迁移工具、npm/Python/Agent 制品及相应运行时，核对 TDSQL 兼容大版本与实际内网可用性；不把外网登录凭据、账号数据和模型密钥打进分发包。内网若由 DBA 执行 DDL，交付同一份版本化 SQL，不要求业务账号长期持有建表权限。

## 12. 选择依据与当前限制

| 选择 | 初版理由 | 何时重新考虑 |
| --- | --- | --- |
| 自己部署共享服务 | 外网可演示、内网可复用，不依赖某个托管产品 | 运营规模证明需要托管服务时再评估 |
| Java + TDSQL MySQL | 与团队技术栈和已确认的内网数据库一致 | 具体内核、引擎和迁移权限在目标实例核对；不同时实现多种数据库 |
| JVM 内独立执行模块 | 用 Java SDK 复用 ACP 边界，先把一个执行位置做通 | 明确需要个人电脑执行、多机器选择时再拆远端 Runner |
| HTTP + SSE | 覆盖在线共享、恢复与状态推送；不维护两套实时通道 | 出现需要双向高频通信的实际需求时再评估 WebSocket |
| 预置普通用户与演示会话 | 先调通用户维度的共享、交接和引用，不依赖内网登录系统 | 到内网阶段再实现真实登录与账号绑定 |
| 在线消息日志，首版不接 CRDT | 已提交消息统一落库，满足不同电脑接着聊 | 出现离线共同编辑文档需求时再评估 Loro 等 CRDT |
| 固定默认行为 | 首版易部署、易演示、问题可复现 | 真实用户场景证明需要调节某一项时增加对应配置 |

平台库只维护 TDSQL MySQL 这一条数据通路。Java + TypeScript Streams 服务会增加第二套后端运行时与数据边界，首版不采用。第三方 ACP 子进程与独立业务服务是不同层次，前者保留，不因控制技术栈而重写。

Loro 提供可合并文档，不能单独替代成员权限、服务存储与 Agent 执行。首版不把完整 Lody 云体系作为依赖，也不为未来可能用到的架构预建多套实现。

当前方案尚未完成原型、并发测试、ACP 互通或真实外网部署；这里的验收条目都是后续实施目标。设计评审后再按同名 Spec、Plan、Todo 细化，不把顶层草案直接当成完整实现契约。

## 13. 评审关注点

1. Java 与 TDSQL MySQL 兼容版已确定；推荐的 Spring Boot、HTTP + SSE，以及目标实例的兼容大版本、迁移工具适配需核对。
2. 首演采用服务器执行项目，成员在自己的浏览器操作；首版工作区内会话全部共享。
3. 首演真实使用的模型与 Agent；第二个 ACP 后端的验证停点，以及 Lody 适配器与 Java SDK 的能力对齐。
4. 外网服务器的系统、域名、持久磁盘与出网条件；最终内网的登录、数据库和制品来源。

这些是少量产品与部署选择，不是新增配置开关清单。初版应围绕“用户 A 交给用户 B，A 关掉自己的电脑后 B 仍能继续”完成一次完整验收。普通用户账号与预置调试登录已确定，具体岗位不进入账号模型。

评审后先写 Spec，将 Java/TS/Python 的契约、会话恢复与实时补齐写成可验证行为，再拆分可演示停点。验证至少包含：两个账号两台电脑的接续、请求去重与排队、同目录 Agent/Git 互斥、SSE 断线补齐、审批首个回答、Java 与真实 Harness/第二 ACP 后端互通、TDSQL 迁移/事务/唯一约束与服务重启恢复。当前没有这些测试已通过的结论。
