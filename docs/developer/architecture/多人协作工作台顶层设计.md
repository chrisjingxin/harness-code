## 0. 产品定位与分支边界

本产品是面向任意 ACP Agent 的桌面协作工作台。Electron 是唯一图形入口；Java 是共享业务服务；通用 Runner 在所选机器执行任务。Harness Code 保留模型循环、工具、策略与私有持久化，作为一个可替换的 ACP Agent 进程接入，与 Claude/Codex 等实现处于同一接入层级。

本分支允许与 master 完全分叉，不承担旧 TUI、Web 接管或内部 API 的兼容任务，也不以复用旧 CLI 为启动前提。继续在当前仓库设计和实现不等于平台依赖 Harness；是否另建仓库、产品命名与 Git 操作另按用户指令执行。本轮不新建仓库、不改 master、不搬代码。

目标产品不包含 TUI、独立 Web server、浏览器接管/归还、InteractiveController 或 Bun/OpenTUI。React 沿用 Web 渲染技术并可独立开发预览，不形成第二个产品入口。旧组件与策略迁出后归新包所有，不跨路径回引旧 CLI。旧内核私有协议不是工作台公共协议。

新增 Lody 参考逻辑按功能归属新包，不加入 Harness 的 Host/Thread/Run 流程；共享账号、设备、项目、交接和引用全部留在平台。Harness 特有 Trace/设置由可选集成包注册，不进入通用执行器、公共 DTO 或 Java 业务模型。没有 Harness/Python 时平台仍可运行，并通过同一 ACP 路径使用其他 Agent。

## 1. 先回答：是否需要云端记录

需要一个各台电脑都能访问、能够长期保存共享会话的服务。对本项目，建议让它保存会话、成员、交接、引用与执行记录，并向客户端推送更新。公网云服务器、企业自己的机房服务器或内网虚拟机都能承担这个角色。

本项目初版采用中心协作服务。不同用户的桌面连接同一个服务，读取共同历史；各执行器主动连接服务接收工作，电脑之间不需要开放入站端口。业务库保存共同记录，本机执行器和 Agent 保存执行所需状态，两者不通过复制数据库文件共享。

| 信息 | 建议保存位置 | 换人或换电脑时怎样延续 |
| --- | --- | --- |
| 成员、会话、消息、交接、引用及其文本快照 | Java 协作服务的 TDSQL MySQL 兼容版 | 登录后由服务读取同一份记录 |
| 附件正文 | 服务的数据目录，数据库保存关联 | 按工作区权限下载与查看 |
| 底层 Agent 会话 ID、模型上下文与检查点 | 云端保存设备/项目/会话绑定；原生上下文在执行机器的 Agent 数据目录 | 原执行器继续使用原 ACP 会话；重启后按该 Agent 支持的能力恢复 |
| 本机请求处理记录、待补传事件 | 执行器的本地持久存储 | 云端重试或重连时核对相同请求，补传事件，不凭网络重试重复执行 |
| 代码仓库与 Git 状态 | 被选择的执行机器本地项目目录 | 文件/Git 请求始终路由到该设备，不改用查看者电脑的同名路径 |
| 输入草稿、打开的页签、滚动位置、已同步历史缓存 | 各桌面当前用户的应用数据目录 | 个人视图分别保存；缓存按账号/工作区隔离，不成为第二份共享真源 |

共享可见历史与模型内部状态分属两层。执行机器离线时，其他用户可读已同步历史，但不能继续操作本机 Agent、实时文件或 Git。交接不搬迁机器、仓库、未提交修改或检查点。原稿“发起人关机后仍能执行”的承诺随执行方式变更撤回；要持续运行，可显式绑定一台常在线机器上的同种执行器。

## 2. 已确认场景与方案选择

已确认：共享同一对话；用户 A 交给用户 B，后者用自己的电脑接续；支持 @对话；顶层工作台独立，Harness 通过 ACP 接入；先外网演示，后迁内网。初版在数据库默认创建几个普通用户账号供登录调试，不预设岗位、业务角色或按岗位划分的权限；内网登录系统留到内网阶段开发。

2026-11-06 追加确认：产品入口改为 Windows/macOS 桌面，Agent 与代码仓库主要运行在本机，云端保存共享会话。桌面选用 Electron 承载现有 React，独立 TypeScript Runner 管理本机进程。Runner 是执行器：在被选机器管理 ACP、项目、文件/Git 与 Trace；Java 负责用户、共享业务、排队、设备连接和命令派发，不跨网络直接控制本机 stdio。

初版先做在线共享会话，消息由 Java 统一排序。采用一个云端应用、一套通用执行器，不增加 Redis、消息中间件、微服务网关或第二套云业务服务。桌面替代原 TUI/Web；手机端与完整离线协作不进入首版。以下目录名、具体框架版本和通信接口仍以评审后的 Spec 为准。

### 2.1 推荐技术栈

| 部分 | 初版推荐 | 负责什么与选择理由 |
| --- | --- | --- |

| 桌面外壳 | Electron、electron-vite，评估 electron-builder 打包 | 管理窗口、受限原生接口、快捷键、通知和本机执行器；具体版本在 Spec 锁定 |

| 云端业务 | JDK 21、Spring Boot 4.0.x、Maven | 一个 Java 应用内按业务分包，适合现有 Java 团队共同维护 |
| 桌面业务连接 | HTTPS 写操作与历史查询，SSE 接收共享事件 | 由桌面主进程网络适配层管理会话和订阅，渲染器消费受限接口 |
| 执行器连接 | 主动建立 WSS 双向连接 | WSS 是加密 WebSocket；云端派发命令，执行器回执/补传事件，两台电脑无需互通入站端口 |
| 调试登录与访问范围 | 数据库预置普通用户、服务端演示会话 | 选择预置账号进入工作区；Spring Security 复用会话与请求边界，不开发密码、注册或统一登录系统 |
| 业务存储 | TDSQL MySQL 兼容版、MySQL JDBC、Spring JDBC、版本化 SQL | 消息、引用、交接与排队输入按事务落库；迁移工具优先评估 Flyway，需在目标实例验证 |
| Agent 编排 | Java 持久排队/派发 + 本机 Runner 的 ACP Client | 协作命令不是 ACP；ACP stdio 仅连接同一设备上的 Runner 与 Agent |
| 公共契约 | 独立 workbench-contracts 包 | 平台 HTTP/SSE/设备消息跨语言生成，不复用旧 Harness JSON-RPC 类型 |
| 文件与附件 | 项目文件在执行机器；共享附件在云端持久目录 | 附件通过授权下载进入本次输入；项目目录不整体上传或同步 |
| 部署 | Win/Mac 安装包、Java JAR、TDSQL、Runner 与可选 Agent 制品 | 外网/内网同结构；Python/Harness 依赖只由 Harness 制品需要，通用产品不安装 Bun/OpenTUI |

Spring 官方文档确认上述 Spring Boot 系列支持 JDK 21；Spring MVC 已提供 SSE 支持，SQL 集成包含 JDBC 入口。来源见 [系统要求](https://docs.spring.io/spring-boot/system-requirements.html)、[MVC 异步响应](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html) 与 [SQL 集成](https://docs.spring.io/spring-boot/reference/data/sql.html)。这只是候选版本基线，正式实现前锁定具体补丁与可在内网导入的制品，不使用漂移版本或 SNAPSHOT 作为演示依赖。

平台库以 TDSQL MySQL 兼容版为唯一目标。应用使用 MySQL JDBC 访问，连接到内网提供的数据库接入地址，不依赖腾讯云管理 API。Harness 自有 SQLite 和 Agent 原生检查点继续由各 Agent 管理，不搬入平台数据库。腾讯官方给出了 [Java JDBC 接入示例](https://cloud.tencent.com/document/product/557/10238)；实际驱动版本以目标实例兼容内核为准。

Lody 的桌面启动本机后台进程、也可连接其他执行机器，见 [快速开始](https://lody.ai/zh/docs/quickstart/)；桌面分层可对照 [Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)。本项目采用本机 Runner 是执行位置变化带来的职责调整，Java 云业务仍保持单一实现。ACP Java SDK 保留为历史调研材料，不再是本版执行链路依赖。

### 2.3 TDSQL 接入与表结构原则

用户已确认 MySQL 兼容版，但具体兼容大版本与部署引擎尚未取得。业务使用 MySQL 兼容 SQL，不先假设完整 MySQL 8 特性或所有分布式功能都可用。以下原则让外网演示与内网采用同一套数据访问和迁移脚本：

| 设计点 | 初版做法 |
| --- | --- |
| 接入 | Java 通过 MySQL JDBC 连接 TDSQL；数据库只由服务访问，桌面与 Runner 不直连 |
| 业务 ID | 应用生成稳定 ID；不依赖某种自增取值或数据库特有序列语义 |
| 业务关联 | 表中保留工作区、会话等关联 ID，应用校验归属；不依赖外键、触发器或存储过程驱动协作业务 |
| 查询与内容 | 使用常规索引和有界分页，初版会话搜索采用标题查询；正文使用兼容文本字段，不依赖全文索引、JSON 专有查询或数据库通知通道 |
| 建表 | 首版优先普通表；物理分片方式在取得实际实例条件后确认，不为演示提前做分库分表。若必须使用分表，需在 Spec 细化分片键与事务范围 |
| 事务与迁移 | 明确消息、引用、执行登记的事务边界；验证唯一约束和并发状态更新。DDL 不假定可事务回滚；迁移脚本版本化，工具适配需实测 |
| 字符与时间 | 文本使用支持中文与 emoji 的 utf8mb4；ID 比较规则与统一时间表达在 Spec 固定，不能由数据库默认排序规则改变去重结果 |

这些是本项目的 SQL 使用范围，不代表 TDSQL 所有产品版本均有相同限制。公开分布式版的 [使用限制](https://cloud.tencent.com/document/product/557/47511) 和 [建表说明](https://cloud.tencent.com/document/product/557/8767) 可作核对入口，最终以实际内网实例为准。

外网优先使用同兼容大版本的 TDSQL。没有外网 TDSQL 条件时，可用匹配大版本的 MySQL 完成业务演示与开发测试，仍使用同一套应用代码；这种结果只证明对应 MySQL 环境下的行为，不能代替 TDSQL 的驱动、迁移、事务和约束验收。不另外建立一套数据库适配分支，也不假定普通 MySQL 测试已经证明内网可用。

旧 packages/protocol 只可在 Harness 自己确实仍需的内部生成/通信中保留；没有调用方后删除。平台公共协议使用新包，不通过重新导出旧类型或别名伪装解耦。ACP session ID 对平台是原生绑定标识，Harness Thread/Run/检查点在内核与其适配内解析，UI 和业务 SQL 不依赖其字段结构。

现有根 AGENTS/README 仍描述当前源码。实施首个工程停点时必须同步更新职责、入口和检查链；本轮不把尚未实现的目录写成当前源码事实。

Java 首版采用一个 Maven 应用，内部按 `identity`、`workspace`、`conversation`、`reference`、`handoff`、`execution`、`device`、`realtime` 分包。业务用例、数据访问与传输在各包内分清职责，不拆成多套网络服务。前端不能导入 Java 类；Java 不依赖 CLI 的 TypeScript 状态；Runner 不调用桌面渲染组件。

workbench-contracts 中的 OpenAPI 和事件/命令 schema 生成或校验 Java/TS 载荷，生成器在 Spec 锁定。设备连接使用平台协议，ACP 类型使用 SDK，Harness 内部 JSON-RPC 的生成链只留在其实现内。通用检查覆盖桌面、Runner、Java 与平台契约；Harness 集成检查另验证 Python/ACP/Trace，不能把 Python 作为所有平台检查的前置条件，也不能只通过当前 npm 检查就声称新产品已验证。

完成迁移后只交付桌面、云端和通用 Runner，以及按需安装的 Agent/集成制品。原生 TUI、独立 Web、接管网关与旧 CLI 不再属于本分支产品；无界面 Runner 只有设备运行/登记等必要启动职责，不演变为保留旧 TUI 的旁路。Harness 对上只有 ACP 和协商后的专有扩展接点，平台不直接访问其内部服务。

### 4.3 桌面与后台生命周期

Electron 主进程管理窗口和原生能力，preload 只暴露具名受限接口，渲染器不直接调用 Node、文件系统或 shell。React 组件与域逻辑保持独立；目录选择、打开外部链接和通知由主进程处理。保留现有 CSP 与内容隔离；不为预览项目文件开放任意主进程权限。参考分层而非逐项照搬 Lody 的所有窗口/加密功能。

桌面启动托管本机 Runner，关闭窗口进入后台；macOS 菜单和 Windows 托盘提供重新打开与明确退出。显式退出前展示本机运行情况并确认收敛，退出或崩溃不会假装任务完成。首版不承诺操作系统服务常驻、开机自启或退出桌面后继续执行；常在线需求用独立托管的同种 Runner。桌面重开不能启动第二个竞争同一设备身份和目录的执行器。

### 4.4 设备、项目与共享

用户登录后在本机登记设备，生成稳定设备 ID 与设备凭据；设备所有者是普通用户关联，不是新增岗位角色。云端只接收该设备的已授权命令/事件；凭据保存在本机受保护存储，不进入会话、安装包或其他成员的桌面。

用户通过原生目录选择登记项目，本机保存项目 ID 到真实根目录的映射。云端保存设备/项目标识和展示名称，业务请求不能携带任意绝对路径或启动命令替换绑定。设备所有者明确将某个项目共享到工作区后，成员才可创建/操作其共享会话；首版按项目共享，不顺带开放整台电脑的其他目录或个人历史。复制链接只定位会话，不授予权限。

Java 核对用户、成员和项目共享关系，Runner 再核对设备、项目及本机登记范围。停止共享后拒绝新的远端文件/Git/执行请求；已受理任务保留其真实状态，由设备所有者明确停止或等待完成，不因失去共享就删除上下文。共享授权的具体撤回竞态在 Spec 固定并验证，不增加逐人角色后台。

## 5. 数据归属与最小模型

平台记录用户能共同看到和操作的工作内容；Agent 保管自身运行所需的私有状态。两层通过 ID 关联，不能互相覆盖对方数据库。

| 记录 | 最少需要表达的信息 |
| --- | --- |
| 用户 | 稳定内部用户 ID、登录名、显示名、启用状态；不包含岗位或预设业务角色 |
| 工作区与成员 | 工作区 ID、用户 ID；首版成员拥有相同的共享会话能力 |
| 设备与项目 | 设备 ID、所属普通用户、连接状态；项目 ID、所属设备、展示名与工作区共享关系；根目录映射留在本机 |
| 平台会话 | 会话 ID、标题、创建者、当前接手人、绑定设备/项目与 Agent 配置 |
| 消息与工具事件 | 稳定 ID、会话内顺序、作者、内容、所属执行与时间 |
| 执行 | 输入 ID、原发起人、排队/派发/运行/完成状态、目标设备、回执和底层请求关联 |
| 交接 | 稳定交接 ID、发起用户、目标用户、说明、待接手/已接手/已取消状态、请求与处理时间 |
| 引用草稿快照 | 草稿 ID、创建用户、来源工作区/会话/消息、可见顺序与选区、固定正文、摘要校验值 |
| 引用 | 来源会话和消息 ID、所选内容快照、引用时的来源位置 |
| 附件 | 所属工作区与消息、服务器文件标识、类型和大小 |
| 后端绑定 | 平台会话 ID、设备/项目/Agent 配置 ID、ACP session ID；原生持久化位置由本机 Runner 管理 |
| 待决人工交互 | 审批/提问 ID、所属执行、内容、待回答/已回答状态与实际回答人 |

平台会话 ID 与 ACP session ID 分开。桌面使用平台 ID，Runner 解析底层 ID。标题、设备名和成员姓名可以变化，关联使用稳定 ID。设备在线状态只表示连接可达，不证明模型、项目或上一次执行结果正常。

TDSQL 是共同展示与协作状态的唯一事实源；Runner 本地账本记录实际命令受理、原生绑定和待补传事件。Java 只有收到相应回执后才更新已运行/完成，不把设备失联推断为成功。缓存、SSE 和 Java 内存不产生第二份权威历史。作者取自登录会话；本机事件只能回填已派发执行，不能自行捏造另一用户输入。

首版一个工作区，用户与成员关系预置；已共享项目内的协作会话向成员开放，成员可查看、续聊和交接。项目尚未共享时只登记本机配置，不创建自动上传的个人聊天。暂不开发成员邀请、岗位角色或逐人权限管理后台。

## 6. 一次输入怎样执行

    用户发送 → Java 确认身份与引用 → 同一事务保存消息、引用和执行记录 → 返回“已保存”
    原设备在线且会话空闲 → Java 先登记派发 → WSS 将固定输入交给绑定 Runner
    Runner 先持久受理记录 → 取得项目占用 → ACP 调用原会话 → 本机记录流式事件
    Java 按稳定事件 ID 去重保存并分配会话顺序 → SSE 推送各桌面
    Runner 回报真实终态 → Java 保存终态 → 后续排队输入才可派发

同一会话一次运行一个请求，不同会话可以独立运行。每次输入保留发起人，重试使用同一个请求 ID；服务只保存和执行一次该输入。

重复请求需要同时核对请求 ID 与内容；同一 ID 携带不同内容应报告冲突。数据库保存排队状态，Java 内存调度只负责唤醒处理。事务只覆盖登记与状态变化，不跨整个模型调用长期占住数据库连接。

Java 保证同一会话仅有一项待完成执行；Runner 对本机规范化后的项目根持有占用，同一目录的 Agent 与人工 Git 写操作串行，不同项目别名不能绕过。不同执行目录可以并行。占用由实际执行宿主维护，不依赖各桌面各自加锁，也不为此增加分布式锁服务。

关闭或切换桌面窗口只结束视图订阅；后台 Runner 在线时其他成员可继续。显式退出 Runner、关机或休眠后，本机执行不可用。失联期间允许查看云端已保存历史；新输入需云端确认，已保存的未派发输入标为等待设备，不转派其他机器。首版没有离线协作发送；个人草稿可保留。

SSE 事件携带可恢复的会话顺序。服务按客户端最后确认的位置读取持久记录，再继续推送；历史读取与实时订阅切换处也必须补齐差额，不能留下消息空窗。客户端按稳定 ID 去重、按顺序应用；断线后显示重连状态，慢连接需要重连补齐时也从数据库恢复。在线成员提示是临时状态，离线或掉线不改写会话正文，也不代表 Agent 已停止。

服务重启时恢复历史、绑定与队列。Runner 重连先报告本机命令状态和未获确认的事件，Java 按稳定 ID 补齐，再继续派发。网络连接重建不能使两个连接同时成为同一设备的命令接收者；同一命令的 ID、目标和正文必须一致。已确认尚未受理的输入可继续，已受理任务不重新调用 ACP。

Runner 使用本地持久存储保存命令状态与未确认事件；具体存储实现和容量处理在 Spec 固定。连接中断时已经开始的 Agent 可继续本地执行并记录结果，需要新人工回答的步骤等待重连；若记录持久化失败，不继续无记录地发起新副作用。失联事件不写成执行终态；崩溃后无法确定外部工具结果的输入标为“执行结果待确认”，不自动重跑或在另一机器恢复。普通请求去重不构成任意崩溃下副作用全局只发生一次的承诺。

取消与审批仍保存命令 ID。取消未送达时显示“取消待送达”，不能立即假装进程停止；结果已完成则返回实际终态。同一审批只采用云端首次有效回答，Runner 校验其所属原生执行。文件/Git 读取是可用时的即时请求；离线时明确不可用，不在后台排队一笔用户忘记的提交或推送。

## 7. 任意用户之间交接

    用户 A 点击“交接” → 选用户 B → 填写说明 → 保存“待接手”记录
    用户 B 打开同一会话 → 查看历史与说明 → 点击“接手” → 更新当前接续人

交接说明提供三个简短字段：已确认事项、下一步、待定问题，允许留空。初版由用户填写；可辅助生成摘要的功能后续再决定。

新会话的当前接续人默认是创建用户。发起交接只增加待接手记录和时间线事件，当前接续人保持不变；目标用户确认接手时，才在同一事务中更新交接状态、当前接续人和时间线事件。用户 A 仍然能看后续消息，用户 B 的新消息显示其当前账号身份。候选来自当前工作区的其他启用用户，不按岗位筛选。

| 当前状态 | 操作 | 结果与当前接续人 |
| --- | --- | --- |
| 没有待接手交接 | 工作区成员发起交接 | 创建 `pending`（待接手）；当前接续人不变 |
| `pending` | 目标用户确认接手 | 原子转为 `accepted`（已接手），当前接续人变为目标用户 |
| `pending` | 发起用户取消 | 转为 `cancelled`（已取消）；当前接续人不变 |
| `pending` | 又发起另一笔交接 | 告知已有待接手记录；不覆盖目标用户，先取消或完成原交接 |
| 已处理 | 重复确认或取消 | 同一请求返回原结果；相反操作或过期页面得到已处理状态，不再改写接续人 |

同一会话最多存在一笔待接手交接；首版不增加自动过期或超时转交。目标用户确认前须仍是启用的工作区成员，其他用户不能代其确认。确认、取消以同一交接 ID 和预期状态处理，只有第一次有效状态变化写入事件。所有成员的普通发言能力保持一致，交接不转移会话访问权，不创建聊天副本或新 ACP 会话，也不发起隐藏模型请求。

交接期间已有 Agent 请求可以继续完成。之后用户 B 的输入走同一个会话队列，使用原 ACP 会话；接手人只表示当前接续工作的人，不是一种用户角色，也不需要给每位成员建立一个独占模型进程。

共享会话的成员均可参与当前允许的人工交互；同一个审批/提问只接受第一个有效回答，并记录回答人。交接不会复制、重发已回答或已过期的问题。ACP 连接由原 Runner 持有，云端关联回答与执行；查看者的桌面不是 Agent 唯一 owner，换人不重建审批通道。

首版明确显示“执行设备：设备名 / 项目名”及在线/失联状态。交接可在设备离线时保存和接手，但继续执行等待原设备恢复，界面提示此限制。接手不会把设备所有者变为目标用户，不转移本机凭据，也不改为目标用户电脑上的同名项目。这与 Lody 的同会话交接方向相近，交接确认状态与项目共享粒度仍是本项目自己的设计。

## 8. @对话与指定内容

    输入 @ → 搜索可访问会话 → 选择范围 → Java 固定引用草稿并返回预览
    发送时 → 校验草稿与访问范围 → 原样保存正式引用 → 随本次问题发给 Agent
    历史中 → 点击引用 → 打开来源会话并定位相关消息

首版在同一工作区内解析引用。预览由 Java 从有权限、已同步的来源生成，并把不可变草稿存入 TDSQL；返回草稿标识、来源位置、截取范围、可见消息顺序和实际正文。消息 ID、选区与正文摘要校验值一起记录。草稿归属当前用户与工作区，不接受桌面自行替换正文来冒充来源。来源机器离线不影响读取仍有权限的云端快照，但无法读取尚未同步的片段或实时项目内容。

发送时重新检查当前用户、工作区、来源可访问性与草稿归属，把该草稿原样复制为正式引用记录，与本次消息、执行登记在同一事务保存。发送流程不重新截取最新正文，也不静默补充来源后来的消息。正式引用与实际构造给 ACP 的文本来自同一份快照，因此预览、历史和模型输入一致；重复提交同一输入不会创建第二份消息或引用。

| 来源变化 | 引用处理 |
| --- | --- |
| 来源消息继续流式输出 | 草稿只包含预览时已生成并选中的内容，预览说明这一范围；新增片段不自动带入 |
| 用户希望引用更新后的内容 | 明确刷新引用，生成新草稿并重新预览；旧草稿正文不原地变更 |
| 标题变化或会话新增消息 | 固定正文和消息选区不变，来源仍按稳定 ID 定位 |
| 发送前来源被删除或失去访问范围 | 阻止发送并提示刷新或移除引用，不悄悄丢弃引用后继续提问 |
| 已发送后来源不可再定位 | 保留当前会话中已保存的引用快照，展示来源不可用，不追加读取其他来源 |

引用整段会话表示预览时选取的一段有界消息，不默认注入所有工具正文。预览须显示截取范围；过长时在预览阶段要求缩小范围，不到发送时再静默截断。具体限额、字符选区和摘要算法在 Spec 固定。

为让不同 ACP 后端都有相同的基本体验，首版由平台把已选快照形成普通文本上下文，随本次问题一起发送。界面保留结构化引用标识。可按需读取更多历史的 MCP 工具属于后续增强，不作为首版引用能够工作的前提。

Lody 当前采用会话链接与历史读取工具；我们借鉴稳定引用和按权限读取的边界，首版交付方式按自身范围简化。引用材料作为参考内容进入本次输入，不成为系统权限或运行配置。

## 9. ACP 与 Harness 的接合点

建议以 ACP v1 的通用会话能力为第一条链路，版本在实现时按选定 SDK 锁定。ACP 能力通过握手确定；没有宣告恢复、图片或专有扩展的后端，界面不提供对应操作。依据见 [ACP 初始化](https://agentclientprotocol.com/protocol/v1/initialization) 与 [会话建立和恢复](https://agentclientprotocol.com/protocol/v1/session-setup)。

TypeScript Runner 作为 ACP Client，通过现成 [TypeScript SDK](https://agentclientprotocol.com/libraries/typescript) 的 stdio transport 管理本机子进程。SDK 回调接入本地持久事件处理；等待模型结果、审批和上传不能阻塞取消与协议回复。启动命令由设备所有者在本机登记的 Agent 配置决定，桌面/云端命令只选择配置 ID，不携带临时 shell 替换启动方式。设备连接协议负责命令和事件，不能直接转发未经校验的 ACP 原始帧。

| 工作台需要的行为 | Harness ACP 入口的目标映射 |
| --- | --- |
| 建立会话 | Harness ACP 入口建立 Thread，只向 Client 返回原生会话标识，内核保存私有绑定 |
| 发送问题、流式输出 | 复用 RunCoordinator 的启动、事件与唯一终态 |
| 停止执行 | 取消对应 Run，不因页面断开而取消 |
| 审批与提问 | Harness ACP 入口映射内部 Interaction；Runner 仅消费标准请求或协商扩展，云端回答路由回原执行 |
| 加载原会话 | 读取 ThreadPersistence 恢复上下文并回放可见历史 |
| 专有能力 | 用协商后的扩展表达，保持标准 ACP 会话流程可独立使用 |

Harness ACP 入口属于该 Agent 自己的适配，复用其现有业务服务，不通过 TUI/旧 CLI 驱动，也不重写模型循环。平台只启动已登记 ACP Agent 并消费协议能力；不导入 AgentHost、RunCoordinator 或 ThreadPersistence。现有 JSON-RPC v3 若仍被内核内部使用，留在该实现内，不冒充 ACP 或平台公共契约。

平台保存展示历史；Harness 保存自己的执行账本和模型检查点。ACP 历史回放用于恢复显示时，需要映射到已有消息，不能再次当新消息追加。规范化消息关联与恢复行为必须在 Spec 中写清并测试。

Harness 是首个计划接入的可选实现，其 ACP 入口仍为 Python；Claude/Codex 经各自适配器接到同一 acp-runtime。Python 只由 Harness 制品需要，不成为启动桌面、Java 或通用 Runner 的前提。旧 CLI/TUI/OpenTUI/Bun 从新产品退出；内核的模型与工具能力仍由其 Agent 进程负责。

专有能力由 harness-provider 的执行/视图注册项实现：执行扩展处理协商后的方法、Trace marker 和原生状态映射；UI 扩展提供 Trace 与专有设置视图。标准消息/工具展示走平台通用事件，运行时注册连接二者。没有安装此集成时只缺少该后端专有功能，平台不补一个直接访问 Harness 文件/数据库的兜底分支。

原生配置、授权与能力差异留在适配层。它们的上下文格式不承诺互换；换后端属于显式创建新执行分支的后续设计。Lody 适配器包含专有扩展，标准 ACP SDK 的存在不证明这些扩展已经对齐。

| Trace 树、三轨图、详情、简化模式：`packages/cli/src/web/presentation/trace/`、`packages/cli/src/web/application/trace-store.ts` | 迁入 harness-provider/ui，经工作台通用扩展槽加载 | 专有投影/类型留集成包；Java 仅保存/路由带归属的扩展记录和附件 | 不进入 workbench-ui 公共 DTO；选用 Harness 时保留 [HC-191 功能矩阵](../spec/HC-191-Web轨迹集成与模块化.md) 全部字段与交互 |
| Trace 采集与历史：`packages/cli/src/trace-log/`、`packages/cli/src/presentation-coordinator/trace-history-session.ts` | 集成视图读扩展端口；已同步历史可离线查看 | 解析/过滤/日志/索引迁入 harness-provider/runtime；acp-runtime 只提供受控 stderr 订阅；内网 SDK 产出保留 | 单一采集者与会话归属、中止/合并保持；Java 和通用 Runner 不包含 marker/Span 解析，未同步部分须原设备在线 |
| 打开的文件、草稿、滚动、工具展开、Git 选择等个人状态 | 留在各自页面，账号/工作区切换时重新绑定 | 服务器不把个人视图作为会话共同状态广播 | 他人消息和交接只更新共享内容；不替别人切页签、覆盖草稿或改变当前文件 |

表中旧路径只定位迁移来源，不是目标运行依赖。通用 React/文件/Git 与 Harness 专有 Trace/设置分别提取，迁出后替换旧类型并删除旧消费者。平台文件/Git 使用通用端口，Trace/专有设置由集成包注册；不因抽包丢失既有功能，也不为复用直接调用旧 Controller。Git 继续使用执行设备配置、hooks、签名和 upstream；平台操作用户与 Git author/committer 分别记录。

### 10.2 迁移验证边界

实施计划必须逐行登记来源→目标→消费者、保留用例与结果。HC-205～208 各自只做必要构建/类型/边界和真实渲染冒烟，不把已存在组件重写成简化替身。后续统一复用 HC-190 临时 Git 仓库/bare remote，HC-191 合成 marker、跨 chunk、start/end 乱序、历史/实时合并和双模式场景；新增桌面到 Java 到 Runner 的双端协议测试、设备离线与重连、不同账号远端文件/Git 目标校验。完整测试在 HC-204；正文、凭据、真实用户日志不作为夹具。

acp-runtime 与 harness-provider 的 stderr 接线先做小原型，验证可观测 Harness 轨迹后迁移采集。内网 SDK 不可在外部安装时保留原逻辑，不制造 Span。其他 Agent 未宣告扩展时不承诺同样 Trace。新链路回归后删除旧 TUI/Web 网关、采集入口与无消费者依赖，不长期双写或保留兼容产品。

解耦验收同时检查包依赖与真实运行：通用包禁止导入旧 CLI/协议/Harness 集成；不安装 Harness/Python 仍可构建启动桌面和 Runner、通过 mock ACP 验证协作，并真实接入第二个 ACP 后端。移除 harness-provider 不影响通用聊天/文件/Git；重新注册后完整 Trace/专有设置通过回归。mock、第二后端互通和真实 Harness 各自留证，不能相互替代。

## 11. 最小必要配置与数据维护

云端需要服务地址、数据库和附件目录；桌面需要服务地址，本机需登记设备、项目与 Agent 配置。模型凭据由执行端现有配置管理，不复制进共享会话或其他成员机器。首版不做远端任意命令编辑器，也不按每个超时和限额增加环境变量。

### 11.1 预置普通用户，供登录调试

默认初始化 `user01`、`user02`、`user03` 三个普通用户账号，显示名为“用户 01”等。这些名称只区分调试身份，不代表岗位或权限等级。数据写入 TDSQL 的用户和工作区成员记录，由 Java 查询；不在前端或控制器中写三组专用分支。

    桌面登录视图选择或输入预置用户名 → 主进程调用 Java 查询启用用户
    建立演示会话 → 返回当前用户与工作区 → 查看共享会话或登记本机项目

首版按免密码选择调试身份设计；演示会话不代表真实人员认证。注册、找回密码、邀请和统一登录到后续处理。主进程的网络适配层管理服务域的 HttpOnly 会话 Cookie、HTTPS/SSE 与退出，渲染器只获得当前用户和具名业务接口，不导出 Cookie。Java 复用 Spring Security 会话边界；具体验证/Cookie/CSRF 接线在 Spec 固定，不能继续使用旧稿“本地页面与云端 API 天然同源”的假设。

Runner 的设备凭据与用户界面登录会话分离。Runner 主动用其设备身份建立 WSS，Java 同时核对当前执行的成员授权与设备/项目绑定。本机新设备登记必须由登录用户明确触发，远端用户不能借会话命令注册目录。网络错误不当作真实退出或成功，不通过关闭 TLS 校验解决内网证书问题。

| 数据或行为 | 首版约定 |
| --- | --- |
| 用户账号 | 普通用户只有稳定 ID、登录名、显示名和启用状态，不增加岗位/业务角色字段 |
| 工作区关系 | 初始化一个共享工作区及上述用户的成员关系；成员能力相同，不设置用户角色 |
| 初始化 | 以登录名等稳定标识去重，重复执行不新建重复用户、不重置原 ID，也不覆盖已有历史 |
| 登录与退出 | Java 根据预置用户记录建立/结束演示会话；不存在或停用的账号不能进入 |
| 发言与操作 | 作者、交接人和审批回答人由当前服务端会话确定；请求正文不指定另一个用户作为操作人 |
| 切换账号 | 结束旧 UI 会话/订阅并隔离其缓存，再进入新身份；不改写历史，不把已登记设备的所有者或凭据重绑给新用户 |
| 访问范围 | Java 核对工作区与项目共享，Runner 核对本机项目；停止设备服务/共享有独立明确入口，界面退出不暗中转移或删除执行上下文 |

两台电脑可以分别使用 `user01`、`user02` 测试任意用户之间的交接；同一个账号也能在多设备保持相同作者身份。登录状态、工作区列表和消息作者分开提供，参考 Lody 固定提交中的 [平台身份](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/platform/src/provider.ts)、[React 订阅入口](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/platform/src/react.ts) 与 [消息作者](https://github.com/LodyAI/Lody/blob/58f594a27da5262cb51164daf8b6bbd0333c4541/packages/shared/src/message-author.ts)；不会把当前用户写死成某种岗位。

未来内网接入在 Java `identity` 与桌面登录适配处理真实登录，React 继续消费同一种用户状态，业务使用内部用户 ID。真实账号与既有调试用户届时明确绑定，不按显示名自动合并；既有作者、交接人与设备所有者关联保留。不提前引入内网 SDK 或多种登录提供方配置。

### 11.2 数据与制品维护

备份分两侧：云端包括 TDSQL、附件与平台绑定；执行设备包括 Runner 账本、原生绑定、Agent 数据和项目目录。停止接收新任务并等待已运行任务收敛、完成事件补传后，分别停止服务和 Runner，按现有方式备份数据库与持久目录。Agent SQLite 在停止后备份。云端备份能恢复共同历史，不能替代设备私有检查点或未提交代码；恢复到另一设备不是初版自动迁机功能。

首演使用新建的共享会话。已有个人历史的导入与归属在正式切换前单独确认，保持原数据可读；不能默认把某个人电脑上的历史都上传到共享工作区。

外网和内网保留同一 MySQL 方言与版本化迁移脚本。迁移前准备 Maven/JDBC/迁移工具、Electron/Runner、npm/Python/Agent 及目标平台原生依赖，核对 TDSQL 内核与实际可用性；不把外网用户会话、设备凭据、模型密钥和个人项目打包。内网由 DBA 执行 DDL 时交付同一份 SQL，不要求业务账号长期拥有建表权限。不自动搬运外网演示数据。

### 11.3 双平台安装、更新与验收

| 项目 | 首版建议与验证边界 |
| --- | --- |
| 支持矩阵 | Windows x64、macOS arm64/x64；最低 OS/Electron/Node/Python 版本与每个 Agent 的平台支持在 Spec 固定，框架支持不等于 Agent 已验收 |
| 安装制品 | Win/Mac 分平台构建，桌面自带通用 UI/执行器；Harness/Python 与其他 Agent 分为可选目标平台制品，不复制虚拟环境，也不携带旧 CLI/TUI/Web/Bun/OpenTUI |
| 首次启动 | 选择服务、调试登录、登记设备/项目、检查 Agent 是否可用；缺失依赖给出实际原因，不在内网首次启动偷偷访问公网下载 |
| 打包检查 | 逐目标验证原生依赖、Python stdio、Agent 启停与进程树取消、中文/空格路径、文件/Git、主题缩放、休眠/重连、托盘与明确退出 |
| 签名与分发 | Mac 对外分发需核对签名/公证，Windows 核对签名与安装体验；所需证书由实际发布环境提供，本地未签名启动不作为正式分发验收 |
| 更新 | 初版提供版本可见的手工安装升级与回退材料；升级前收敛本机运行并保留应用数据。内网可离线导入安装包，不把公网自动更新服务作为必需项 |

两个操作系统分别真机或对应 CI/运行环境验收。仅在 Mac 上构建 Windows 包、只测试 React 或仅通过源码类型检查，都不能宣称 Windows 桌面与 Agent 执行通过。首演停点应至少一次由 Mac 发起、Windows 接手，并验证原机器离线时的降级；是否追加另一方向由后续 Plan 安排。

签名与公证的官方核对入口见 [Electron 分发说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)。首版优先手工升级，不引入公网更新渠道；证书材料和签名流水线在实际打包前取得，不进入仓库。

## 12. 选择依据与当前限制

| 选择 | 初版理由 | 何时重新考虑 |
| --- | --- | --- |
| 自己部署共享服务 | 外网可演示、内网可复用，不依赖某个托管产品 | 运营规模证明需要托管服务时再评估 |
| Java + TDSQL MySQL | 与团队技术栈和已确认的内网数据库一致 | 具体内核、引擎和迁移权限在目标实例核对；不同时实现多种数据库 |
| Electron + React 桌面 | 对齐 Win/Mac 桌面形态，沿用现有 UI 与 Lody 分层参考 | 具体版本、系统最低版本与原生依赖在 Spec 固定 |
| 独立包与 TypeScript Runner | 桌面/协作独立于 Harness，标准 ACP、项目服务和专有集成分开 | 包名与接口在 Spec 固定；常在线机器仍托管同种 Runner |
| 桌面 HTTPS + SSE / Runner 出站 WSS | UI 需要业务提交/更新，执行器需要双向命令/回执；两者职责不同 | 如原型证明可进一步统一再简化，不维护同一用途的多套通道 |
| 预置普通用户与演示会话 | 先调通用户维度的共享、交接和引用，不依赖内网登录系统 | 到内网阶段再实现真实登录与账号绑定 |
| 在线消息日志，首版不接 CRDT | 已提交消息统一落库，满足不同电脑接着聊 | 出现离线共同编辑文档需求时再评估 Loro 等 CRDT |
| 固定默认行为 | 首版易部署、易演示、问题可复现 | 真实用户场景证明需要调节某一项时增加对应配置 |

平台库只维护 TDSQL MySQL 一条业务通路，不增加 TypeScript Streams 云服务。TypeScript Runner 是用户指定的本机执行层，其本地账本服务命令恢复，不承担共享业务权威库；保留它不改变 Java 云端约束。完整离线产品、CRDT、自动迁机、仓库同步、移动端与计费均不进入首版。

Loro 提供可合并文档，不能单独替代成员权限、服务存储与 Agent 执行。首版不把完整 Lody 云体系作为依赖，也不为未来可能用到的架构预建多套实现。

当前方案尚未完成原型、并发测试、ACP 互通或真实外网部署；这里的验收条目都是后续实施目标。设计评审后再按同名 Spec、Plan、Todo 细化，不把顶层草案直接当成完整实现契约。

## 13. 评审关注点

1. 本分支为独立桌面产品，移除 TUI/Web，平台与 Harness 解耦已确认；Electron、Java/TDSQL、本机执行保留，具体包名、扩展接口、版本与目标 OS 在 Spec 固定。
2. 项目由设备所有者明确共享，成员在自己的桌面操作同一原机器；关机/休眠后只能读取已同步内容，交接不自动迁机。
3. 首演模型与真实 Agent、第二 ACP 后端的验证停点；各后端在 Win/Mac 的能力与宿主支持分别留证。
4. 外网服务域名与数据库、两台演示电脑和安装包签名条件；最终内网登录、数据库、证书信任与离线制品来源。

初版围绕“用户 A 的本机 Agent 与项目经云端交给用户 B，B 在另一系统的桌面续聊”验收；原设备在线是执行前提。普通用户保留，岗位不进入账号模型。产品/分包方向已确认不等于整体接口与实施计划已评审，本稿仍不进入实现；实际 TUI/Web 删除、目录提取和依赖清理在后续停点执行。

评审后先写 Spec，将新包依赖/扩展契约、设备授权、状态/取消/审批、原生恢复和补传写成可验证行为，再拆停点。通用验证覆盖无 Harness/Python 构建启动、旧入口/依赖退出、真实第二 ACP 后端、双平台安装、两账号交接、原设备目标校验、去重/互斥、SSE/WSS 断线和 TDSQL；Harness 集成另验 Python/ACP、专有设置与 HC-191 全矩阵。当前没有这些产品验证已通过的结论。
