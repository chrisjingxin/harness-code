状态：设计草案（2026-11-20；2026-11-23 补齐企业团队协作能力拆解 HC-244～HC-254 并增量扩展 HC-239～HC-243；2026-11-23 已确认第 15 节全部全局默认项与全栈实施分工）。标“已确认”的决策已由用户在对话中确认；其余各卡细节待对应 Spec 阶段确定，见第 15 节。具体行为以各 Task / Spec 为准。

## 0. 为什么要写这份文档

**现状痛点**：当前桌面端只有“已登录 + 已选团队 + 已进入 Project”时才能使用 Agent。未加入团队时只显示“当前账号未加入团队”；本机执行每次都要先向服务端确认会话属于某个 Project。结果是：

- 个人想随手用一下本机 Agent，必须先有团队和 Project；
- 服务端或网络不可用时，本机 Agent 也跟着不可用；
- 所有试验性对话都会变成 Project 会话，制造噪音并带来隐私顾虑；
- 团队知识（开发契约、踩坑、术语）只在 Project 语境里可用，个人开发时反而拿不到；
- 每个人的 Agent 对“团队有哪些工程、彼此什么关系”各自从零摸索，经验无法沉淀共享；
- 一个会话只有一个工作目录，企业里“一个系统多个仓库”的现实无法表达。

**解决思路**：把“谁能让 Agent 干活”“谁能看到会话”“团队知识流向哪里”“仓库之间什么关系”拆成独立的几件事，各归其主；再用两个进化循环让个人经验和团队知识越用越准。

**改后收益**：登录即可用本机 Agent；加入团队后个人会话自动用上团队规约、经验和本机记忆；个人踩坑经审核回流团队并跨人融合；多仓库开发有团队共享的系统地图指导；Project 只承担共享会话、任务和看板。

## 1. 第一性原理

1. **执行权跟着“人 + 本机”走**。能否执行只取决于“当前登录账号 + 本机会话绑定 + 用户授权的目录”，不取决于云端有没有一条协作记录。
2. **可见性跟着 Project 走**。别人能看到什么，只由“会话是否发布到某个 Project、谁是 Project 成员”决定。没有“全团队可见”这一档，共享的最小范围就是 Project。
3. **知识跟着团队（Workspace）走**。团队知识属于 Workspace，不属于 Project；团队成员在个人会话里也能用。
4. **流向不对称**：
   - 团队 → 个人（消费）：只是读进本人会话，无披露风险，**默认自动可用**；
   - 个人 → 团队（贡献）：有披露、质量与投毒风险，**必须本人主动发起 + 管理员审核**。
5. **一套会话模型**。个人会话与 Project 会话是同一种会话；上传同步是挂在会话上的发布器，不是第二条执行链路。
6. **本机记忆是个人的，团队知识是共享的**。本人 Agent 可以自由更新自己本机的记忆；进入团队的内容一律经审核。

## 3. Workspace 角色（已确认）

修订旧规则：原顶层设计写“Workspace 不预设岗位角色”，现改为像 Git 托管平台一样设角色。

| 能力 | 管理员 | 开发者 |
| --- | --- | --- |
| 使用本机 Agent、个人会话 | ✓ | ✓ |
| 读取团队知识、系统地图 | ✓ | ✓ |
| 提议新增 / 修改知识与系统地图 | ✓ | ✓ |
| **审核并发布**知识与系统地图 | ✓ | — |
| 直接修改“规约”级知识 | ✓ | —（只能提议） |
| 管理成员与角色、登记 Workspace 仓库 | ✓ | — |
| 创建 Project、发布会话、发布 Task | ✓ | ✓ |

- 创建 Workspace 的人默认是管理员，可有多名管理员；最后一名管理员不能被降级或移除。
- 角色变化立即生效，已发布的版本不受影响。
- Project 内的 `owner/member`（契约已有 `ProjectRole`）与 Workspace 角色相互独立。

### 3.1 HC-240 权限与交接增量（2026-11-23）

具体契约见 [HC-240 Spec](../spec/HC-240-Workspace角色管理.md)，验证状态以 [Task](../task/HC-240-Workspace角色管理.md) 为准。成员记录使用 active/removed、角色与修订号，移除保留作者身份；团队先行行锁统一角色撤销和业务写入的先后，交接预览摘要覆盖完整责任集合与接手人资格，提交失败整笔回滚。

团队仓库沿用 Repository，唯一当前负责人 ownerUserId 与登记者分开，可待认领；系统地图以后消费同一负责人，不建第二份。活跃 Task/Project 必须有接手人；原 creator 留作贡献记录，离职后的验收职责由有效 Project owner 代管。新增 Project 阅读权逐项确认，交接不转移会话 owner 或 Agent 执行权。

在 HC-241 提议审核交付前，现有知识直接创建/改版/归档是真实发布，收为管理员权限；开发者仍可读取。成员退出后当前团队页面与知识缓存失效，工具与记忆读写在线复核资格；本人个人会话和记忆文件不删除。历史团队通过显式映射初始化管理员，不猜创建者，也不因重复初始化恢复已撤销权限。

## 4. 会话模型

### 4.1 两个相互独立的属性

| 属性 | 含义 | 取值 | 何时决定 |
| --- | --- | --- | --- |
| **团队上下文** | 从哪个团队取知识、本机记忆，AI 记忆更新写回哪个团队 | 无团队 / 某个团队 | 新建时记录选中团队；已有 Team 保持固定。无团队会话主动发布并确认后可绑定目标 Workspace，HC-233 从下一次发送使用该绑定 |
| **可见性** | 别人能否看到 | 仅本人 / 某个 Project 的成员 | 新建入口决定默认值，之后可“发布到 Project”或“停止共享” |

绑定团队上下文**不等于**团队成员能看到。可见性只由是否发布到 Project 决定。

### 4.2 一个人手里的三种会话

| 会话 | 团队上下文 | 谁能看到 | 典型场景 |
| --- | --- | --- | --- |
| 未加入团队时新建的个人会话 | 无 | 仅本人 | 个人项目、随手试验 |
| 加入团队后新建的个人会话 | 新建时选中的团队 | 仅本人 | 用团队规约开发自己的东西，暂不公开 |
| Project 会话 | 该 Project 所属团队 | Project 成员（只读） | 需要协作的事项 |

规则：

- 加入团队或切换侧栏**不会**自动搬动、上传或公开已有会话，也不自动补绑团队；允许本人将无团队会话主动通过「发布到 Project…」发布到有权访问的活跃 Project，经确认后显式绑定目标 Workspace，已有团队绑定的会话仅可发布到同团队 Project。
- 左栏双轨组织规则（2026-11-23 修订确认）：「个人」空间不设团队/无团队筛选，统一展示全部个人会话并按工程目录折叠分组；「团队」空间按 Workspace 切换团队、按 Project 折叠分组展示协作会话。
- 在 Project 内新建会话默认发布到该 Project，头部明确显示“Project 可见”；在「个人」空间新建为本机个人会话。
- Project 看板、成员简报、管理员视图都不出现个人会话。
- 离开团队后，绑定该团队的个人会话仍可继续使用，但不再注入该团队的知识与本机记忆。

## 5. 每轮发送时 Agent 收到什么

用户主动发送时，桌面主进程在真实登录与会话绑定下组装材料。用户草稿、消息展示和 Java 上传始终保存用户原始文字，自动材料只存在于实际发给 Agent 的请求中（HC-233）。

| 材料 | 来源 | 进入方式 | 预算 | 交付 |
| --- | --- | --- | --- | --- |
| 用户原文、手动 @引用、附件 | 用户 | 原样带入，优先级最高 | 现有总输入上限 | 现有 |
| 适用范围匹配的规约正文 | 团队知识（规约级） | 每轮带入 | 单独预算 | HC-241 |
| 团队知识标题目录 | 团队知识（经验、术语、系统地图及规约标题） | 只有标题，正文由 Agent 按需读取 | 8 KiB | HC-233，HC-241 加范围匹配 |
| 两份本机记忆正文 | `team.md` / `personal.md` | 每轮完整附带会话绑定 Team 下的两份有效业务正文，由 Agent 理解相关性 | 正文合计 8 KiB，在生成和更新时检查 | HC-233 |
| 会话涉及的仓库清单 | 主目录 + 附加目录 | 真实目录清单独立带入，不筛选或裁剪两份 MD | HC-242 Spec 单独约定，计入总输入上限 | HC-242 |

两份本机 Markdown 按简短概览维护，正文完整注入，不按提问关键词、Project 或工作目录挑选工程。正文篇幅在生成和更新时控制，超限提示精简；总输入无法容纳完整正文时如实反馈。团队知识的适用范围匹配是另一套读取规则，不用于过滤本机 MD。固定更新提醒最多 256 字节 UTF-8，当前文案为 187 字节。

本机 MCP 服务提供的工具（HC-233）：`query_project_memory`、`propose_project_memory_update`、`list_team_knowledge`、`read_team_knowledge`。**不提供写团队知识的工具**：沉淀由用户点按钮发起，Agent 只起草（HC-241）。

无团队上下文的会话只带用户材料，不装配知识与记忆工具。知识目录或工具暂不可用时，普通消息照常发送并显示实际状态（HC-233 第 5.4 节）。

## 6. 两个进化循环

```text
            ┌──────────── 团队（服务端）────────────┐
            │ 团队知识：规约 / 经验 / 术语 / 系统地图   │
            └────▲───────────────────────┬────────┘
   本人主动提议 → 管理员审核 │                       │ 标题目录 / 规约正文 / 按需读取
     （HC-241 / HC-243）    │                       │ 已发布地图作为 team.md 权威来源
            ┌───────────────┴───────────────────────▼────────┐
            │ 本人电脑：本机会话 + team.md / personal.md         │
            │ 每轮成功结束：本人 Agent 的新事实写回本机记忆（HC-233） │
            └──────────────────────────────────────────────┘
```

| | 个人循环（HC-233） | 团队循环（HC-241 / HC-243） |
| --- | --- | --- |
| 写到哪里 | 本人本机 `team.md` / `personal.md` | 团队知识（含系统地图） |
| 谁写 | 本人 Agent 在回复结束前提交工具提案，桌面在本轮正常完成后保存；用户确认的目录立即保存 | 本人 Agent 起草，本人编辑提交 |
| 审核 | 不需要，只影响自己 | 管理员审核 |
| 冲突 | 后提交的过期更新被拒绝，保留当前条目 | 审核时处理；本机记忆与已发布团队内容冲突时以团队为准并提示修订 |
| 取消 / 失败 | 丢弃本轮未提交的 AI 更新 | 草稿保留，未提交不生效 |
| 连通 | 本机积累而团队尚无的事实可一键整理为团队提议 | 已发布版本回流为每个人本机记忆的权威来源 |

```text
判断：
  1. 读取 Git 远端，对上团队仓库 order-service，核对或写入 personal.md（用户确认的目录立即保存）
```

### 旅程 3：带着团队上下文开发（HC-233、HC-241）

```text

```

可观察结果：未手动 @ 任何知识，Agent 实际调用工具读取团队知识；规约只在会话涉及匹配仓库时出现。

### 旅程 4：本机记忆自动积累（HC-233，个人循环）

```text
输入：对话中确认“refund-service 是退款服务，大家叫它 tk”
执行：Agent 在回复结束前调用 propose_project_memory_update → 暂存为本轮 pending
```

### 旅程 5：踩坑沉淀为团队知识（HC-241，团队循环）

```text
输入：张三踩坑——退款回调重复投递导致双倍记账，最终用幂等键解决；点击“沉淀为团队知识”

  - 无相关条目          → 起草“新增”
  - 已有《回调幂等经验》 → 起草“补充”（相对当前版本的差异）
```

## 8. 知识模型

### 8.1 分级（已确认）

| 级别 | 例子 | 进入 Agent 的方式 | 谁能改 |
| --- | --- | --- | --- |
| 规约 | 接口契约、错误码规范、安全红线 | 范围匹配时正文每轮带入，要求短小 | 仅管理员；开发者只能提议 |
| 经验 | 踩坑记录、排障手册 | 标题目录 + 按需读取 | 提议 → 管理员审核 |
| 术语 | 团队名词、服务别名 | 标题目录 + 按需读取 | 提议 → 管理员审核 |
| 系统地图 | 仓库作用与关系 | 标题目录 + 按需读取；并作为本机 `team.md` 权威来源 | 提议 → 管理员审核 |

知识只是参考，**不授予任何执行或仓库权限**。

### 8.2 适用范围（已确认）

- 每条知识的适用范围为“全团队”或“指定的一个或多个 Workspace 仓库”；路径级范围不在首版。
- 会话涉及的仓库（主目录 + 附加目录，按 Git 远端识别）与范围匹配时进入目录；“全团队”条目总是参与。

### 8.3 生命周期

```text
草稿 → 待审核 → 已发布（版本 N）→ 被提议修订 → 待审核 → 已发布（版本 N+1）
           ↘ 退回（附理由，提议人可修改重提）
已发布 → 归档（管理员操作，不再进入目录，历史版本保留可读）
```

### 8.4 为什么必须审核

会话可能含错误结论或注入指令，而团队知识会自动进入全团队的 Agent。任何自动生成内容都只能形成提议；服务端不调用模型，起草与比对在提议人本机完成。

## 9. 多仓库模型（已确认：一个 Agent，一个主目录加附加目录）

```text
Workspace 仓库目录（已有）＋ 系统地图（团队知识类型，HC-243）
        │
        │ 本机 personal.md（HC-233）：本机目录 ↔ 团队仓库；team.md：本人积累的关系
        ▼
本机会话：主目录 + 附加目录（ACP 标准 additionalDirectories，HC-242）
        首轮材料 = 仓库清单与关系 + 范围匹配的规约正文 + 知识标题目录 + 两份完整简短 MD 正文
```

- 附加目录建议的来源优先级：已发布系统地图 → 本机 `team.md`。
- 会话记录涉及的团队仓库（契约已有 `ConversationRepositoryItem`），用于知识范围匹配和 Project 简报。
- 本机未克隆的仓库只提示，不跨机器读取实时文件；仓库读写权限由 Git 托管平台决定。
- 首版不做多仓库 worktree 隔离、跨仓库 PR、每仓库一个 Agent 的编排。

## 14. 边界与暂不做

- 除 HC-233 的本机工程记忆外，不做工作台自有的个人知识库或个人偏好：各 Agent 已有用户级指令 / 记忆文件。
- 不按组织架构自动入团：用户资料已有 `orgId/orgPathName`，后续可选。
- 不在服务端运行模型；不允许任何自动内容跳过审核进入团队知识（包含 HC-245 的团队 Skill/MCP 与 HC-251 的 Playbook）。
- 不做多仓库 worktree 隔离、跨仓库 PR 自动合并、多 Agent 编排。
- 不跨机器读取他人实时文件，不远程操作他人 Agent：HC-253 的只读 Patch 快照由原开发者主动打包脱敏上传、接收方自主校验应用；HC-252 的异步批注仅进收件箱与时间线，绝不自动触发原设备 Agent 执行。
