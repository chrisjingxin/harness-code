## 一、背景

### 1.1 要解决的问题

方案提出时，Harness Code 已经具备一些分散的扩展能力：

- 可以从内置、用户和项目目录加载 Skill；
- 可以通过 TOML 或 `/mcp add` 接入 MCP Server；
- 可以复用不同配置的 AgentEngine；
- 已有 Agent 和 ExecutionPolicy 的静态领域模型；
- TUI 已有可扩展的 CommandRegistry 类型。

当时的主要问题是：

```text
Skill 有自己的目录扫描和状态
MCP 有自己的配置与连接状态
Command 目前只有内置定义
AgentCatalog 没有进入生产执行链
默认子 Agent 绕过 Harness 的 AgentEngine 与执行记录
Plugin 安装、信任、启停和更新完全不存在
```

本方案后续实施解决了这些问题；当前完成情况以第五节支持矩阵为准。

### 1.2 设计目标

本方案要实现以下结果：

1. 用户只面对一种扩展包：`Plugin`。
2. 一个 Plugin 可以包含 Skill、MCP、Command、Agent、Policy、Hook 和 Team。
3. 通用 Plugin 使用开放的 Agent Plugins 1.0 结构。
4. Claude Code Plugin 可以原样安装，不要求作者重新打包。
5. 不同外部格式最终转换成同一套 Harness 内部定义。
6. Plugin 声明的权限只能被收紧，不能扩大 Harness 或父 Agent 的权限。
7. 每个 Agent 使用独立的模型、Prompt、能力视图、执行状态和 AgentEngine。
8. 多个 Agent 可以组成动态协作组，也可以生成固定任务依赖的 Agent Team。
9. Plugin 更新、停用或删除时，不破坏正在运行的 Run。

### 1.3 不在本方案中做的事情

- 不允许普通 Plugin 把任意 Python、TypeScript 或 Bun 模块导入 Harness 主进程。
- 不让 Plugin 直接访问模型密钥、SQLite、ThreadPersistence 或内部 Python 对象。
- 不把 Skill 的 `allowed-tools` 或 Agent 的 `permissionMode` 直接当成授权。
- 不让 Team 文件重新定义 Agent 的模型、Prompt 和权限。
- 不为了兼容旧的内部类名或测试入口保留两套生产路径。

### 1.4 核心术语

| 名称 | 含义 |
| --- | --- |
| Plugin | 可安装、校验、启停、更新和删除的扩展包 |
| Component | Plugin 内的一项能力，例如一个 Skill、MCP Server 或 Agent |
| Adapter | 把 Agent Plugins、Claude Code 等外部格式转换成 Harness 内部定义的解析器 |
| Catalog Snapshot | 某一时刻所有已启用 Plugin 及其组件组成的不可变快照 |
| AgentDefinition | 一个角色的静态定义，描述用途、Prompt、模型请求和能力请求 |
| ResolvedAgentSpec | AgentDefinition 与实际模型、有效 Policy、工具、Skill、MCP 和执行环境合并后的唯一解析结果 |
| Delegation Group | 主 Agent 可以按任务动态选择的一组子 Agent |
| TeamDefinition | 多个 Agent 之间的固定任务、依赖、并行上限和失败规则 |
| TeamRun | 一次 TeamDefinition 的实际运行状态 |

Agent 与 Team 的关系是：

```text
AgentDefinition = “这个角色是谁、可以做什么”
TeamDefinition  = “这些角色怎样一起完成工作”
TeamRun         = “这次协作执行到了哪里”
```

## 二、各项目的扩展机制对比

### 2.1 对比结果

以下结论来自官方规范、官方仓库或官方文档。

| 项目 | 扩展包结构 | 主要能力 | 值得结合的部分 | 不适合直接照搬的部分 |
| --- | --- | --- | --- | --- |
| [Agent Plugins 1.0](https://github.com/agentplugins/agent-plugins-spec) | 根 `plugin.json`、`skills/`、`mcp.json`、client extension namespace | Skill、MCP | 作为通用 Plugin 基础格式；结构简单；支持客户端私有扩展；组件失败隔离 | 不包含安装、市场、信任、Agent 和 Team 的统一语义 |
| [Agent Skills](https://github.com/agentskills/agentskills) | `<skill>/SKILL.md` 和可选资源目录 | 可复用知识与工作流 | 与 Harness 当前 SkillRegistry 和虚拟文件按需读取方式高度一致 | `allowed-tools` 只能表示请求，不能自动授权 |
| [MCP](https://github.com/modelcontextprotocol/modelcontextprotocol) | 独立 Server，通过 stdio、HTTP 等传输连接 | 外部工具、资源和提示能力 | 继续复用当前 `langchain-mcp-adapters` 和连接管理 | MCP 进程不是沙箱，启动进程本身必须受信任 |
| [Claude Code Plugins](https://github.com/anthropics/claude-code/tree/main/plugins) | `.claude-plugin/plugin.json`，约定目录自动发现 | Skill、Command、Agent、Hook、MCP、LSP、Monitor、settings、marketplace | 生态成熟；组件丰富；Plugin Agent 可直接用于 subagent 和 Agent Team | 格式属于 Claude 产品；变化快；主仓库不是开放许可证，不能复制其实现 |
| [Claude Agent Teams](https://code.claude.com/docs/en/agent-teams) | 运行时生成 team config、task list 和 mailbox | lead、独立 teammate、任务依赖、互相通信 | 独立上下文、共享任务、成员控制和团队终态值得借鉴 | 当前仍是实验功能；运行时文件不是可分发 Plugin 标准；首版不应先复制 mailbox |
| [OpenAI Codex](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) | Plugin catalog、marketplace、Skill、MCP、App、Hook | 安装、目录、认证和 thread 选择 | 证明不可变 catalog、Plugin 安装和 MCP 生命周期可以与 Coding Agent Host 结合 | 产品面和 Rust 架构不同；部分 Plugin API 仍标注开发中 |
| [Gemini CLI Extensions](https://github.com/google-gemini/gemini-cli/blob/main/docs/extensions/reference.md) | `gemini-extension.json`，本地/Git 安装 | MCP、Command、Skill、Hook、Agent、Policy、Theme | copy-on-install、user/workspace scope、环境变量 allowlist、Policy 只能收紧 | 不应在 Harness 运行层再引入一套 Gemini manifest 语义 |
| [Qwen Code](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/commands.md) | Extension 管理和 Claude/Gemini 生态入口 | Skill、MCP、Command、Agent、Hook、多 Agent Review | 跨产品导入和多 Agent Review 证明有明确用户价值 | Harness 仍需独立 consent、Policy 和进程安全边界 |
| [OpenCode](https://opencode.ai/docs/plugins/) | 本地或 npm JS/TS Plugin | Hook、Tool、事件和运行时修改 | 说明 Hook 与自定义运行时有价值 | 任意 JS/TS 进程内执行不符合 Harness 企业安全边界 |

### 2.2 可以组合使用的部分

这些规范和项目解决的是不同层面的问题：

```text
Agent Plugins 解决：通用包长什么样
Agent Skills 解决：Skill 文件长什么样
MCP 解决：外部工具怎样通信
Claude Adapter 解决：现有 Claude 生态怎样直接接入
Harness 解决：安装、信任、权限、AgentEngine、执行树和 Team 怎样运行
```

因此推荐组合：

```text
Agent Plugins 1.0
├─ Agent Skills → Harness SkillDefinition
├─ MCP config   → Harness McpServerDefinition
└─ Harness client extension
   ├─ CommandDefinition
   ├─ AgentDefinition
   ├─ ExecutionPolicyDefinition
   ├─ HookDefinition
   └─ TeamDefinition
```

Claude Code Plugin 不要求作者转换成上面的目录。Harness 通过 Claude Adapter 把它映射到相同内部定义。

### 2.3 最终选择

本方案不选择单一项目作为全部标准，而是采用：

1. Agent Plugins 1.0 作为可移植基础。
2. Agent Skills 作为 Skill 标准。
3. MCP 作为外部工具协议。
4. Harness client extension 补充 Agent、Policy、Command、Hook 和 Team。
5. Claude Code Plugin 作为一级兼容格式。
6. Gemini 等格式以后只增加 Adapter；Qwen/DevAgent 通过 Adapter 进入既有 ContextLifecycle/AgentCatalog，未完成的 Hook/交互仍不进入运行层。

## 三、整体思路

### 3.1 一个内部模型，多个外部 Adapter

整体结构如下：

```text
Agent Plugins 1.0 ───────────┐
Claude Code Plugin ──────────┼─→ PluginFormatAdapter
Qwen/DevAgent 静态 Adapter ──┘          ↓
                                  PluginContribution
                                          ↓
                               ExtensionCatalogSnapshot
                               ├─ SkillDefinition[]
                               ├─ McpServerDefinition[]
                               ├─ CommandDefinition[]
                               ├─ AgentDefinition[]
                               ├─ PolicyDefinition[]
                               ├─ HookDefinition[]
                               └─ TeamDefinition[]
                                          ↓
                           Harness 唯一生产装配与执行路径
```

外部格式只在 Adapter 层出现。Server、AgentEngine、RunCoordinator、TUI 和 SQLite 不直接判断一个组件来自 Claude 还是 Agent Plugins。

HC-157 阶段一的 Qwen/DevAgent Adapter 解析根清单、包内路径和组件库存，输出
`PluginDescriptor`/`PluginComponentReport`；标准 `qwen-extension.json` 在字段缺省时扫描存在的
根目录 `commands/`、`skills/`、`agents/`；Qwen `contextFileName` 缺省或空数组时只报告实际存在的
根 `QWEN.md`，显式 Context 路径必须是包内普通文件；`devagent-extension.json` 继续使用显式字符串
路径。阶段一当时未接入 runtime 的组件保持 `unsupported/effective=false`，畸形 MCP、Hook、Skill 或 Agent
保持 `invalid` 并从有效数量中排除；阶段三已将合法 Context 接入 `ContextLifecycle`，与 Qwen Agent
一样报告 `adapted/effective=true`，并在 enabled activation 的 canonical catalog 中读取。

HC-157 第二阶段在这一 Adapter 与既有内容寻址 Plugin store 之间增加 `PluginResourceSnapshot`。
它复用组件报告的相对来源，并按 Qwen/DevAgent 的真实包关系捕获顶层 `references/*.md`、`scripts/`、
`mcp/` 等运行时依赖，明确排除 `references/origin/` 开发原始素材，保留 Skill 的 `../../references/...` 等相对结构；不伪造 Skill 私有 references。快照以
`/.harness/plugins/<plugin-id>/...` 提供只读虚拟命名空间，隐藏开发文件和凭据不进入闭包，摘要、诊断
和 Protocol 输出不暴露 store 绝对路径。Command、MCP、Hook 的明确字段只受控映射四种已知扩展根
placeholder，并对嵌入式路径、越界、未知 token、缺失目标 fail closed。MCP/Hook 的未接入子集只建立脱敏诊断条目，
不生成可启动配置；已进入 runtime 的 Commands、Skills 和 Phase 2 ZA38 stdio MCP 只从各自真实
canonical consumer 生成，不再维护独立 static preview。
未接入的 Hook/LSP/Monitor 只保留 warning/diagnostics，不作为可执行 consumer；portable、Claude、Hybrid
不建立第二套 Qwen catalog，所有实际可执行组件仍必须进入既有 canonical runtime。

HC-157 第三阶段复用两个既有 canonical seam：

1. `PluginManager.context_blocks_by_source` 只从 enabled Qwen `PluginResourceSnapshot` 读取 Context，
   转为 `ContextBlock(REFERENCE, STABLE)`；Host 将它作为 `ContextLifecycle.prepare` 的稳定参考输入，
   因而 core policy、capability、environment、Run snapshot、persistence 和 projector 仍只有一条链路。
   Context 正文只携带 `/.harness/plugins/<plugin-id>/...` 虚拟来源，重复 key/digest 不叠加，异常 fail closed。
2. `AgentCatalog` 为 Qwen Markdown 使用专用 frontmatter Adapter，产出既有 `AgentDefinition` 与
   `ExecutionPolicyDefinition`；`permissionMode` 按 Qwen 源枚举独立映射，`approvalMode` 单独校验；
   `resolve_plugin_agent_spec` 继续计算 Plugin request、父 Agent 和 Host/workspace policy 的交集，
   不能绕过 normal middleware。

因此启用后的 ZA38 三个 executor 进入实际 AgentCatalog，已接入 Agent 只从 canonical catalog 提供；
Commands/Skills 已进入对应 canonical runtime，Phase 2 的 ZA38 stdio MCP 也进入同一 MCP snapshot，Context 只进入同一
startup catalog。Hook、Qwen LSP 和子 Agent Question/Approval 的其他扩展仍按各自阶段接入。

HC-157 第四阶段继续复用这条 canonical runtime 链路，而不是为 Qwen 建立私有 Agent loop：

```text
Managed child final output
  → Qwen SubagentStop matcher / HookRunner
  → allow 或父 Run question Interaction
  → submit 注入提交门禁指令，复用同一 child checkpoint 再次过 gate
  → skip 返回当前结果
  → continue 写入同一 child checkpoint，Managed executor 开始下一回合
```

SubagentStop 只有在 Qwen Plugin 同时满足 enabled activation、AgentCatalog effective、
已安装组件报告为 `hooks: adapted/effective=true` 且 matcher 命中时才会运行；invalid、unsupported、
混合坏条目、范围外事件和 async Hook 不会被重新解析后带入 runtime。Adapter/runtime 共用 matcher、
command、timeout、shell、async 及 Qwen 受控字段纯校验；即使安装报告因损坏或漂移错误地保持
`adapted/effective`，runtime 转换失败或目标定义为空也会写入 `HookRuntimeFailure` 并由 Host
对匹配 child fail-closed，不会降级为无 gate。Hook stdin 只包含 Agent 身份、最后输出、Harness 虚拟 workspace 和
`stop_hook_active`；Hook 文本是不可信反馈，不能修改 Core Policy、EffectiveCapabilityView、审批或
workspace guard。`ChildInteractionRegistry` 只在 Run 生命周期内保存 request 与
`execution_id/parent_execution_id/agent_id/checkpoint_namespace`，由现有 RunCoordinator owner
InteractionPort 派发，响应/取消/断连/Run 终态清理；它不持有第二个 child execution。

Hook runtime 构造失败、无客户端、无效答案以及 PreToolUse/Policy/权限/MCP 等安全边界仍失败关闭；但
Qwen matcher 已命中的 SubagentStop Hook 若发生非零、超时、非空畸形输出、异常或 runner 关闭，按
Qwen Code 终态语义记录脱敏 warning 并放行已完成 child result。正常 blocking 仍按同一 child
checkpoint 继续，达到连续 blocking cap 时覆盖阻断并返回最新结果及 warning；用户的 submit 会把
提交门禁指令送回同一 child，skip 才只放行当前 gate；两者都不改变 policy，Shell/Git 仍通过正常
Policy/approval middleware。matcher miss 不执行 Hook；Run/parent/user cancellation 继续传播，
不转换为成功。未接入的 Qwen Hook/LSP/Monitor 只保留 warning/diagnostics，Phase 2 的 ZA38 stdio MCP 走
canonical MCP generation。portable、Claude、Hybrid 不建立 Qwen 专用 catalog，也不改变其既有
Hook/Agent/Interaction 行为。

HC-157 的 Agent control-plane 使用同一份 canonical `agentSummary`。由于 Qwen Agent 的用户可见
frontmatter 包含 `color`、`approvalMode` 和独立映射后的 `permissionMode`，这三个 nullable 展示字段
必须写入 `packages/protocol/schema/v3.json`，再生成 Python/TypeScript 类型、validators、schema 副本和
contract fixtures；Host/CLI 不得另造 Qwen 专用摘要。`mcp.status` 只返回真实 server 状态和诊断，
不伪造 static preview。Host dispatch 对 handler 结果继续 fail-closed 校验，但单次畸形
结果不得关闭后续 dispatch loop；真实 Qwen `agents.list` dispatch 回归覆盖了这条双端契约。

HC-157 第五阶段使用清洁目录和带单层包根 ZIP 分别经过独立 staging/store 与 activation 链路，确认
两种来源得到同一资源库存、Agent/Context/Hook runtime。最终兼容
边界如下；`adapted` 表示外部格式已转换到既有 canonical consumer，不表示整个 Qwen 生态全部可执行：

| Qwen/DevAgent 组件 | 最终状态 | canonical consumer | 当前边界 |
| --- | --- | --- | --- |
| 根清单与安装 | `adapted` | PluginManager / PluginStore | 目录与 ZIP 等价；auto/显式 `qwen-code`；冲突、越界和畸形输入失败关闭 |
| Context | `adapted/effective` | ContextLifecycle | enabled 后作为 `REFERENCE/STABLE` 注入，不覆盖 Core Policy |
| Agents | `adapted/effective` | AgentCatalog / ManagedAgentExecutor | 三个 executor 可列出和委派；权限是 Plugin、父 Agent、Host/workspace 的交集 |
| SubagentStop Hook | `adapted/effective` | HookRunner / final output gate | 只支持同步 command 子集；构造/身份/取消失败关闭，命中 Hook 执行失败告警放行并保留 child result |
| Commands | `adapted/effective`（安全子集） | CommandRegistry / SkillRegistry | 有效条目进入 canonical command runtime；坏条目只保留 warning |
| Skills | `adapted/effective`（安全子集） | SkillRegistry | 有效条目进入 Qwen Skill runtime；坏条目只保留 warning |
| MCP | `adapted/effective`（ZA38 stdio 子集） | McpServerConfig / McpConnectionManager | 有效条目进入 namespaced MCP snapshot；坏或停用条目不连接 |
| Settings | `adapted/effective`（安全子集） | SettingsStore / SettingsResolver | 有效声明经 credential backend 注入 MCP/Hook/LSP child；修改在 next-host 生效 |
| themes/channels/workflows 等 | `unsupported` 或 `invalid` | compatibility report | 不静默忽略，不产生运行能力；Channels 已从 HC-158 移出 |

### 3.2 为什么必须统一转换

如果不同格式各自进入运行层，会出现：

- Claude Agent 使用一套工具过滤，Harness Agent 使用另一套；
- TUI 显示的能力和实际构图能力不一致；
- AgentEngineProfile 按一份配置计算，builder 按另一份配置执行；
- Plugin 更新后 MCP 已变，旧图仍持有旧工具；
- 未支持的 Claude 字段被静默忽略。

统一转换后的规则是：

```text
外部文件
  → Adapter 解析与校验
  → canonical definition
  → Policy 与模型解析
  → ResolvedAgentSpec
  → AgentEngineProfile 和 AgentEngine builder
```

`AgentEngineProfile` 和 builder 必须消费同一个 ResolvedAgentSpec，不能再分别解析。

### 3.3 Plugin 的安装与生效流程

```text
本地目录 / zip（HC-175 当前管理入口）
  → 解包或复制到 staging
  → 检测格式
  → 校验 manifest、路径、组件和 Adapter 诊断
  → 计算内部 package digest
  → 展示来源、真实组件、Settings 和 warning
  → Shell 通过 plugin_consent 确认
  → 安装并写入 user/workspace activation
  → 后续 Host 启动时发布新的 ExtensionCatalogSnapshot
```

安装确认成功即启用所选 scope。任何包含 MCP、Hook、LSP、Monitor 或可执行脚本的 Plugin，仍必须
在本次提交前展示真实组件和风险；运行时继续受既有 Policy、审批、workspace 和进程边界约束。

### 3.4 不可变快照与生命周期

Plugin Manager 发布不可变快照：

```text
PluginManager
  → ExtensionCatalogSnapshot
      ├─ Skill snapshot
      ├─ MCP snapshot
      ├─ Command snapshot
      ├─ Agent/Policy snapshot
      └─ Hook/Team snapshot
```

快照变化时：

- 新 Run 和新 child execution 使用新快照；
- 已开始的 execution 固定旧快照 ID；
- 受影响 AgentEngine 进入 draining；
- 未受影响的角色继续复用原 AgentEngine；
- 旧 AgentEngine 在没有 lease 后关闭；
- 不在正在运行的图上原地增加或删除工具。

### 3.5 权限只允许收紧

Plugin 文件只表达能力请求：

```text
managed/global boundary
  ∩ 父 Agent delegation envelope
  ∩ 目标 Agent Policy
  ∩ Plugin activation 与组件 gate
  ∩ 当前 workspace/sandbox boundary
  = EffectiveExecutionPolicy
```

同一个有效能力视图必须同时控制：

1. 模型看到的 Tool Schema；
2. Agent 可以读取的 Skill；
3. Agent 可以使用的 MCP Tool；
4. 实际 Tool 执行前的 Policy Guard；
5. AgentEngineProfile 指纹；
6. AgentExecutionBinding 中记录的执行事实。

### 3.6 Agent 协作分成两层

#### 动态协作组

```text
main
├─ security-reviewer
├─ test-reviewer
└─ performance-reviewer
```

主 Agent 根据任务选择一个或多个 Agent。子 Agent 有独立上下文，完成后把结果返回调用方。没有共享任务表和成员互聊。

适合：

- 一次性代码搜索；
- 专项审查；
- 生成测试建议；
- Planner → Executor → Reviewer 的层级派发。

#### 固定 Agent Team

```text
security ─┐
          ├─→ synthesis
tests ────┘
```

Team 有显式任务依赖、并行上限、失败规则、取消传播和持久化终态。

适合：

- 多个成员长期并行；
- 明确的任务 DAG；
- 成员需要独立重试或取消；
- 进程恢复后继续未完成任务。

大多数场景先用动态 delegation。只有 delegation 无法满足时才创建 Team。

### 5.2 Skill：HC-099 已接入 Plugin 启动快照

#### 当前已经支持

`packages/agent/harness_agent/skills.py` 已经支持：

- builtin、user、project、market 四类目录来源，以及 PluginManager 显式提供的 Plugin 来源；
- canonical ID；
- 不可变 Skill snapshot；
- `SKILL.md` 按需读取；
- 资源路径、symlink 和大小限制；
- `/.harness/skills/` 虚拟路径；
- enable、disable、install、remove；
- TUI Skill 选择器和显式调用。

#### 已实现方式

当前生产链路：

```text
ExtensionCatalogSnapshot
        ↓
PluginSkillSource[] → _parse_manifest(dialect)
        ↓
SkillRecord[] → SkillRegistry snapshot
        ↓
/.harness/skills/ 按需读取
```

具体修改：

1. `PluginManager` 从已捕获的 enabled catalog 生成 `PluginSkillSource[]`，`SkillRegistry` 不扫描 PluginStore。
2. `_parse_manifest()` 保留 Harness 严格模式，并增加 portable/Claude dialect。
3. 支持 `argument-hint`、`disable-model-invocation`、`user-invocable` 和 `allowed-tools`。
4. Skill ID 为 `plugin/<source-id>/<plugin-name>/<skill-name>`。
5. package digest 和 Skill digest 一起进入 snapshot ID。
6. `allowed-tools` 只保存为 `requested_tools`，不改变 Policy 或审批。
7. `/.harness/skills/` 改用最长 canonical 前缀解析，多段 Plugin ID 的正文和资源继续通过统一 `read_file` 读取。
8. 单个坏 Skill 只写入 diagnostics；同包其他有效 Skill 和 MCP 继续装配。

#### 验证

- 现有 builtin/user/project/market Skill 行为不变；
- 标准 Agent Skill 可直接加载；
- Claude Plugin Skill 可原样加载；
- 一个坏 Skill 不影响同包其他 Skill 和 MCP；
- Plugin 更新后旧 execution 继续使用原快照。

### 5.3 MCP：HC-099（含 ZC-099）与 HC-141 统一连接快照

#### 当前已经支持

`packages/agent/harness_agent/extensions/mcp.py` 已经支持：

- `McpServerConfig`；
- stdio、HTTP、SSE 等配置；
- `McpConfigSnapshot`；
- `McpConnectionManager`；
- MCP Tool 转 LangChain Tool；
- `/mcp add`、`/mcp remove` 和状态查询；
- MCP snapshot digest 进入 AgentEngineProfile；
- 配置变化后重建连接。

#### 已实现方式

新增统一构建器：

```text
用户 TOML McpServerConfig
        +
PortableMcpAdapter(mcp.json)
        +
ClaudeMcpAdapter(.mcp.json / inline)
        ↓
namespaced McpServerDefinition[]
        ↓
McpConfigSnapshot
        ↓
McpConnectionManager
```

实现细节：

1. Server 名规范化为 `plugin__<source>__<plugin>__<server>`，因此不能覆盖普通用户 MCP。
2. Agent Plugins Adapter 读取 root `mcp.json`，用本地 closed schema 校验 stdio/streamable-http/SSE，
   只在 args/env/cwd 中展开 `${PLUGIN_ROOT}` 和 `${PLUGIN_DATA}`；URL/header 中的 placeholder 被拒绝。
3. Claude Adapter 读取 `.mcp.json`、manifest path 和 inline `mcpServers`，展开
   `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PLUGIN_DATA}`、`${CLAUDE_PROJECT_DIR}`，保留 Claude 自有 timeout 语义。
4. package digest 作为内部 artifact identity 保存；Plugin 内容变化由下一次 Host 启动重新解析，
   不变成用户侧授权凭据。
5. Plugin stdio 子进程使用最小环境变量 allowlist，不继承模型密钥等任意 Host 环境。
6. 每个 Server 独立转换和连接；坏 Server、unsupported transport 或连接/认证失败产生独立 diagnostic/status，
   不阻断同包 Skill 和其他 Server。
7. Host 使用同一 catalog 同时构建 Skill 与 MCP；用户 `/mcp add/remove` 重建连接时重新合并固定的 Plugin MCP，不会将其丢失。
8. Plugin HTTP/SSE 使用 `follow_redirects=False` 的 client factory，Claude 与 portable 仍各自保留
   placeholder、environment 和 timeout 语义；MCP add/remove 已使用 generation owner/borrower 和定向 draining。

#### Qwen/DevAgent ZA38 stdio：HC-158 Phase 2

Qwen `mcpServers` 不复用 Claude 的 manifest loader，也不建立第二套 MCP Manager。`qwen.py` 只把 Qwen
manifest 交给显式 `_load_qwen`，Adapter 与安装报告共用逐 server 校验，转换结果直接进入上面的
`McpServerConfig → McpConfigSnapshot → McpConnectionManager` 链路。

- 首个运行子集只接受 `stdio`；command、args、cwd、env、timeout 逐字段有界校验，且只展开
  `${extensionPath}`、`${workspacePath}`、`${/}`、`${pathSeparator}`。未知 token、越界/宿主绝对路径、缺失目标、
  symlink/special file、错误类型和超限均 fail closed。
- Server 名使用现有 `plugin__<source>__<plugin>__<server>` namespace；连接超时、工具命名空间、工具调用、Run
  取消、Host close、generation replacement 和 lease draining 全部复用 canonical manager。单项转换或连接失败只
  影响该 server；转换诊断通过 `mcp.status.diagnostics` 返回，连接异常保留逐 server status。
- effective Qwen MCP 只从真实 canonical MCP consumer 构造；disabled、invalid 或 unsupported 条目
  不连接，只保留为 Plugin warning，且不会构造 `MultiServerMCPClient`。Settings、HTTP/SSE、真实
  外部 ZA38 server 不在此停点。

Phase 2 的离线 fixture 覆盖 Qwen MCP 字段与状态；其中 `test_qwen_mcp_real_fake_stdio_round_trip_cancel_and_close` 启动仓库内
真实 fake newline-delimited stdio 子进程，经 Adapter → canonical manager 观察 initialize/tools/list/call、取消和 close；patch
`MultiServerMCPClient` 的测试只覆盖 manager seam、Host status 和 generation lease。当前 Qwen MCP focused `14` 项、canonical MCP manager
`72` 项、Host server focused `12` 项回归；真实 ZA38 只读临时安装只做 Commands/Skill/MCP 配置转换与资源快照，未连接外部进程或网络。

#### 仍未实现

- Plugin MCP OAuth 与凭据 UI（HC-176 明确非范围）；
- WebSocket transport（Agent Plugins 1.0 portable core 明确不支持）；
- 运行中的 Plugin reload（当前管理契约在下一次 Host 启动生效）；
- 删除 `McpConnectionManager` 的测试兼容 sequence 构造入口。

#### 验证

- 一个 Plugin MCP 启动失败不影响其他 Server 和 Skill；
- placeholder 不递归展开且不能逃逸 Plugin root/data；
- Plugin MCP 看不到模型密钥；
- Tool namespace 不冲突；
- disable/update 后新 execution 不再取得旧工具；
- Host 退出不残留 stdio 子进程。

HC-176 的当前 140 项 focused/expanded 测试已覆盖上述 portable core 与 Plugin runtime 边界；OAuth UI、
WebSocket 和运行时 reload 不作为本任务的失败项。

```text
  → AgentCatalog(Builtin + Plugin AgentDefinition + ExecutionPolicy)
  → resolve_plugin_agent_spec(parent envelope) / resolve_builtin_child_view()
  → ResolvedAgentSpec
  → DelegationTarget(mode=Managed/Inline)
  → AgentEnginePool / Inline child graph
```

主 Agent 构图时把当前 active Agent ID 加入 delegation allow-list。模型仍只通过 `task`
选择 Agent ID 和任务文本，不能从 Prompt 指定模型、Policy、执行模式或工具。Managed adapter
用 project + Thread + Run + execution 生成稳定摘要的内部 checkpoint `thread_id`，并保留
logical child namespace；运行结束后释放 run/engine/MCP lease 与本 execution 的 checkpoint/writes。

Claude Tool 只使用明确映射；未知名称产生 `CLAUDE_TOOL_UNMAPPED` 并停用该 Agent，不猜测相近
Harness Tool。`permissionMode` 不是授权入口（Plugin 定义不能放宽审批），`tools` 是目标角色上限，最终还要与父 Agent 和
Host 硬边界取交集。Plugin 子代理需要人工 Interaction 时保持 fail closed。
内置角色 `general-purpose` 和 `explore` 统一进入 `AgentCatalog`（排在 Plugin 前面），`general-purpose` 继承父 MCP/Skill 与工具集并在父 default 下内部按 auto-edit 放宽审批，`explore` 严格限制为 5 个只读工具且启动免审批。
Plugin Agent 只取得其 `skills` 与 `mcpServers` 显式声明的组件子集；缺省是空集合，不会继承父
Agent 的全部 Plugin Skill 或用户 MCP。子集及其受限 MCP snapshot digest 会进入 Profile。

#### Managed child checkpoint identity：HC-158 真实运行返修（2026-09-01）

LangGraph 顶层图会归一化或丢弃非空 `checkpoint_ns`，所以 namespace 不能单独承担 Managed
child 的状态隔离。Host 为每个 `ExecutionRef` 计算稳定 SHA-256 摘要作为内部根图

### 5.5 Delegation：HC-096 已建立受控 Inline/Managed seam

#### 当前状态

### 5.6 Agent Team：HC-097 已建立固定 DAG 协调层

三个 ZA38 命令以 `/za38-init`、`/za38-sdd`、`/za38-index` 的自然名进入单一 Registry，嵌套目录使用

schema、双端类型、validator、Python schema 副本和 contract generation 仍只从

snapshot。排除范围之外的 symlink、hardlink、socket、FIFO 和其他 special file 仍 fail closed，确保正常 Git

### 5.8 Hook、LSP 和 Monitor：HC-102 已交付受控运行子集

#### Hook

当前已把 Claude command Hook 接到 Tool 生命周期：

```text
PreToolUse / PostToolUse / PostToolUseFailure
  → Claude 兼容 input JSON
  → HookRunner
  → exit code 与 stdout JSON 解释
  → allow / deny / diagnostic
```

支持 shell form 和 `command + args` exec form；`${CLAUDE_PLUGIN_ROOT}`、
`${CLAUDE_PLUGIN_DATA}`、`${CLAUDE_PROJECT_DIR}` 在加载时解析。`PreToolUse` 的 exit 2 或
`permissionDecision=deny` 会阻止工具调用；普通非零退出只产生诊断。stdin/stdout/stderr、
超时和进程关闭都有上限，子进程只得到最小环境，不继承模型密钥。

当前不支持 prompt、agent、HTTP、MCP-tool Hook，也不支持 command Hook 的其他 Claude 事件。
这些子项在 compatibility report 中显示 `unsupported`，不会被静默执行。

#### LSP

当前使用 Host-owned `PluginLspManager`：

- Plugin 只声明 command、args、语言映射和初始化参数；
- 首次调用 Harness `lsp` 工具时按文件扩展懒启动 stdio server；
- 已接入 initialize、didOpen、definition、references、hover 和 diagnostics；
- 文件必须位于当前 workspace，多个 Plugin 不能争用同一扩展；
- Host 负责超时、LSP framing、shutdown/exit 和子进程清理；
- socket transport 当前明确为 `unsupported`。

#### Monitor

Host-owned `MonitorManager` 已实现：

- 每个 Monitor 是受控长期子进程；
- stdout 按行进入有界 ring buffer，再作为“明确不可信的 Monitor 数据”注入模型上下文；
- 单行、总行数和进程生命周期均有上限；
- Host close 时终止整个子进程组；
- Plugin 只有在安装 consent 通过、activation enabled 且包含受支持 `process` 组件时，Monitor 才会启动。

首版不会自动重启 Monitor，也不会把 stdout 伪装成可信系统指令。

#### Qwen/DevAgent Hook + LSP：HC-158 Phase 3

Qwen 不建立私有进程管理器，而是把已通过 `runtime_component_eligibility` 的子项转换到同一
`HookRunner`/`PluginLspManager`：

```text
Qwen hooks                    Qwen lspServers
  ├─ PreToolUse                 ├─ shared qwen_lsp validation
  ├─ PostToolUse                └─ stdio LspServerDefinition
  ├─ PostToolUseFailure                    ↓
  └─ SubagentStop              Harness lsp tool → PluginLspManager
          ↓
      HookRunner → Tool/Run seam
```

Hook 的 Pre 结果只能阻断，不能改写 Tool 参数或越过既有 policy/approval；Post 的
`additionalContext` 是一次性、有界、低可信模型输入，真实 Tool 结果保持原样；PostFailure 的 Hook 异常不覆盖原始 Tool 错误。
无 Host seam 的 Prompt、Session、Compact、Permission、Todo、Message 等事件不产生 runtime definition；混合清单按事件隔离，不能以一条
有效 Hook 让其他事件借道执行。payload 使用虚拟 workspace 和脱敏/有界字段。Qwen Hook/LSP 在 catalog 阶段将 bare executable 冻结为
受控绝对路径；Qwen Hook command 进一步冻结为 executable + argv 并使用 `create_subprocess_exec`，不通过 POSIX shell 重新组合 argv，因此 Windows 风格反斜杠和带空格的路径不会被重解释。子进程不继承 `PATH`、`NODE_OPTIONS` 或动态加载器变量；Claude/portable 继续使用既有 `inherit-path` 环境语义。

Qwen command Hook 的原生 `timeout` 单位是毫秒，Adapter/runtime 共同校验边界为正数且不超过
`600000ms`；缺省为 `60000ms`，并在 `HookDefinition` 中统一转换为 `1..600s`。零、负数、
布尔值、字符串和超上限值保持 `PLUGIN_HOOK_TIMEOUT_INVALID`。Claude/portable 的既有输入仍是
秒，缺省 `60s`、上限 `600s`，不经过 Qwen 转换。

`qwen_lsp.py` 同时服务 Adapter 静态报告与 runtime 构造，闭合校验 command、args、cwd、env、timeout、workspaceFolder、
extensionToLanguage、四类路径 token、普通文件/symlink、workspace containment 与扩展冲突。只接受 stdio；未知 token、socket/HTTP、
越界、缺失、错误类型和超限逐项诊断，disabled/invalid/unsupported 不 spawn。查询仍只能进入 Harness 既有四类 `lsp` tool action，
取消、超时、Host close 和 generation replacement 关闭同一 `PluginLspManager` 的 client；EOF、畸形 header/body、非法 JSON 和 server early exit
归一化为稳定 `PLUGIN_LSP_*`，同时清理 process、stderr task 和 client；Settings 依赖留在 Phase 4。

Hook 的一次性反馈以真实 `RunContext` 的 `(thread_id, run_id, execution_id)` 隔离，不能使用 Host 单例全局队列；Managed child release 只清精确
execution，顶层 Host Run release/close 清理同一 `(thread_id, run_id)` 下全部 execution，Run 取消/异常也不留未消费反馈，缺失上下文直接
fail closed。已取消的 model middleware 不调用模型并返回稳定 `PLUGIN_HOOK_RUN_CANCELLED`。这个 owner 边界与 MCP/LSP generation 一样属于 Host 生命周期，不向 Plugin 暴露
宿主路径或任意环境变量。

Managed Plugin Agent 的 MCP 视图遵循同一条最小权限边界：`ResolvedAgentSpec.tools` 为空时不
依赖 MCP Manager；非空时只借用当前完整 generation 的连接 lease，再按已解析的 immutable
tool view 投影工具。子 Profile 的过滤 digest 不是 manager resource key，不能直接 acquire；
server identity、tool view 或 generation 漂移均 fail closed。共享 lease 只保护连接生命周期，
child graph 永远不会收到未授权工具。Delegation 的未知异常只保留类型，只有严格格式且带
受控域前缀的稳定错误码才向 Tool 输出透传，避免 `RuntimeError` 丢失可诊断性，也不泄漏宿主
路径、命令参数或凭据。

#### Qwen/DevAgent Adapter report 重解析与 SubagentStop 终态修订：HC-158 Phase 4C

安装时生成的 component report 不是永久的 Adapter 事实。Host 启动、控制面暴露 runtime 和
Run preparation 前，`PluginManager.refresh_catalog()` 必须从 PluginStore 读取已安装记录，先
复核 package digest，再用当前 Adapter 重建 descriptor/report。`adapter_revision` 与
plugin/package identity、source binding 一起校验；同一 package 的 report 未变时幂等刷新，
变化时在 registry lock 内原子写入新 report。Adapter 变化只改变下一代 catalog 的组件事实，
不产生重新授权状态，也不要求用户复制任何 hash。若组件变为 invalid/unsupported，则从
canonical consumer 排除并归入 Plugin warning；若没有任何可用组件，产品状态为 `failed`。

```text
已安装 package + digest 校验
  → 当前 Adapter + adapter_revision 重解析
  → report 原子更新
  → enabled activation + 有效组件进入下一 Host/runtime snapshot
  → invalid/unsupported 只产生 warning，全部失败则为 failed
```

Qwen Code 的 `runSubagentStopHookLoop` 对命中 matcher 的 Hook 异常采用 warning + allow；Harness
因此只在 qwen-code `SubagentStop` 的 Hook 执行层复现该语义：exception、timeout、非零退出、
非空畸形输出和 runner closed 记录稳定、脱敏 diagnostic，并返回已经完成的 child final result；
exit 0 的空 stdout、空 `{}` 和合法 no-decision 不记录 failure warning。多个结果先完整聚合，任意
有效 block 优先，reason/additionalContext 有界合并。
正常 block/continue 仍回到同一 child checkpoint，连续 blocking 达到 cap 时返回最新 child result
和 warning；matcher miss 不调用 Hook。Run/parent/user cancellation 仍按 canonical cancellation
传播，不能被包装成 Hook warning 后的成功。PreToolUse、Policy、权限、MCP、非 Qwen、Hook
runtime 构造/identity/report 失败继续 fail-closed；Qwen command Hook 的 `timeout: 10000` 仍按
毫秒转换为 canonical 10 秒；Channels 不在本 Task 内实现。

#### Qwen/DevAgent Settings：HC-158 Phase 4A 设计与 Phase 4B 实现

本节是 HC-158 Settings 的唯一架构落点。Phase 4A 设计已通过主任务评审；Phase 4B
按本节接入现有 ConfigChangeService、PluginStore、PluginManager、AgentHost、
Run/generation lease 与 Thread 持久化 seam，不建立第二套平行配置系统。下面保留
Phase 4A 的约束，并在第 7 小节记录当前 Phase 4B 实施证据；Channels 已决策延期，继续
保持 `unsupported/effective=false`，不阻塞 HC-158 收口。

##### 1. 真实 Qwen Settings schema 与兼容映射

Qwen 的 ExtensionSetting 必须包含 name:string、description:string 和 envVar:string；
sensitive 是可选 boolean。Qwen 的 settings.ts 只表示“值可以不配置”，不表示 envVar
字段可以缺省。Harness 因此将缺少 envVar、空字符串、错误类型、控制字符、超长值、
不符合安全环境变量标识符规则或命中 process-control denylist 的条目标为
declaration invalid，并给出稳定的 SETTINGS_DECLARATION_INVALID 或
SETTINGS_ENV_FORBIDDEN；不能把这类条目当作可选 setting。

Harness 的唯一内部映射是“精确 envVar”：

- envVar 经过有界语法校验后按原样保留，不 trim、不大小写折叠、不用 name 替代；
  setting_key 就是 exact canonical envVar。name 只是展示字段，description 只是展示
  文案；两者变化都不改变 setting_key、record identity 或 declaration_digest。
- Qwen 的 required 固定为 false，含义是 credential value 可以缺失；它不放宽
  envVar 字段要求。sensitive 缺省为 false。value type 和 component consumer 不是
  Qwen manifest 字段；未来 Harness-native schema 如需这些能力，必须另行定义，不能
  在 HC-158 中反写到 Qwen。
- 同一插件中 exact envVar 重复或 declaration mapping 无法唯一化时，所有冲突条目标为
  invalid，返回 SETTINGS_DECLARATION_AMBIGUOUS；不能按加载顺序选择一个。
- declaration_digest 只绑定 mapping schema/version、exact envVar、effective sensitive
  boolean、required=false 常量和 qwen-extension-wide-v1 consumer rule；不绑定 name、
  description。envVar 或 sensitive 变化会使旧值 stale 并要求重新确认；name/description
  变化本身不会改变 declaration_digest，也不能被误报为 declaration drift。
- package_digest 是包含 manifest bytes 的完整 package 内容 hash，仍是 Plugin
  runtime identity/provenance 的外层绑定。因此只要重新安装后的 package_digest 发生变化，
  旧 credential 不能无条件复用；更新时由 HC-175 Host 按 name + envVar 尝试内部 rebind，
  声明变化则返回 reconfigure warning。不能把 declaration_digest 忽略 display 字段解释成
  所有 package 变化都可安全复用。

Qwen 没有 component consumer 字段，本阶段选择唯一的 extension-wide 映射：同一插件的
每个有效 Qwen MCP、Hook、LSP 子项都获得该插件在
workspace > user 解析后、通过 denylist 且已配置的全部 declared settings，作为只对
该 child 生效的最小环境 overlay。未配置的 optional value 不创建对应 env entry；有
配置但 backend、scope binding 或 declaration digest 不可验证时，相关 executable
consumer fail closed，而不是静默省略可能已存在的 secret。若 extension-wide settings
集合含 invalid/ambiguous/forbidden 条目，MCP/Hook/LSP gate 不能声称环境闭合，相关
插件 executable consumers 均保持 blocked，并逐项保留稳定 diagnostics。

这个 overlay 不修改 Host 全局环境，也不进入 command、args、cwd、MCP config、LSP
JSON-RPC、Hook payload 或模型 transcript。Commands、Skills、Agents 不 spawn，也不
接收 Settings env；Qwen setting 本身永远不会令这些 component effective。这样
Adapter、declaration_digest、runtime gate 和三个 executable consumer 使用的是同一条
extension-wide 规则。

##### 2. 物理存储、身份与平台能力探测

唯一主方案是 user/workspace metadata 加当前 OS credential manager。物理路径为：

- user metadata：Harness home 下 .harness/settings/v1/index.json、index.lock，
  journal/<operation-id>.json；
- workspace metadata：同一 settings/v1 下 workspaces/<scope-binding-digest>/
  index.json、index.lock、journal/<operation-id>.json；
- secret value：当前 OS 用户的 credential manager，使用固定 Harness service、
  immutable plugin identity、package digest、declaration digest、scope 和
  setting_key 组成 account。值不进入 PluginStore、registry、catalog snapshot、
  fingerprint、Protocol response、Transcript、日志、workspace/Git 文件或 fixture。

metadata 文件创建目录权限 0700、文件权限 0600；Windows 使用当前用户 SID 的
owner-only DACL。文件锁使用 POSIX owner-only lock file；Windows 使用 owner-only
named mutex 或独占句柄。锁、权限、原子 rename、fsync 和恢复状态任一无法验证时，
操作返回稳定 SETTINGS_STORAGE_UNAVAILABLE，不降级明文。

scope_binding_digest 的 canonical 输入也必须绑定 user scope：

- user：固定域 harness-settings-user-v1、规范化 Harness home 的文件系统身份、
  当前 OS user principal/profile identity、credential backend namespace。POSIX 使用
  uid 与 home filesystem identity；Windows 使用 SID、profile/home filesystem identity；
  macOS 使用登录用户 principal、login-keychain/profile 与 home filesystem identity。
  原始 uid/SID/path 不进入 wire、日志或普通 index，只用于本地 digest。换 OS 用户、
  Harness home/profile、credential backend namespace 或可验证的 home filesystem identity
  都使 record stale，不能跨用户或 profile 取 secret。
- workspace：固定域 harness-settings-workspace-v1、canonical workspace root 的
  filesystem identity、root symlink resolution、额外 trusted roots 和 Host trust
  policy。root、symlink、extra root 或 policy 改变即 stale；display name 永不参与
  查找。

Phase 4B 实现必须探测具体 backend，而不是把目标安全性质当成现状：

- macOS 使用 Python ctypes 调用 Security.framework 的 SecItemAdd、
  SecItemCopyMatching、SecItemDelete，固定 login keychain、service 和
  synchronizable=false。capability probe 必须实际创建随机测试项、读回、删除并检查
  account/service 属性；不能声称已经有跨用户 ACL 隔离。
- Linux 通过系统 `/usr/bin/secret-tool` 访问 session D-Bus 的
  org.freedesktop.secrets default collection 完成随机项 create/read/delete probe；
  D-Bus、服务、collection 或解锁能力不可用即 fail closed，不把 Secret Service 的
  同一用户边界夸大为额外 owner ACL。
- Windows 使用 ctypes 调用 CredWriteW、CredReadW、CredDeleteW；metadata DACL
  通过 GetNamedSecurityInfoW 与当前 token SID probe。Credential Manager 项目的
  自定义 DACL 若不能由 API 证明则不宣称，probe 失败即 fail closed。
- 每个平台都必须记录 capability result 的非敏感状态；不得记录 backend 错误中的
  secret/account/value。禁止 iCloud/synchronizable 写入，禁止明文 TOML、环境变量、
  PluginStore 和 fallback 文件。

v1 是 metadata 的唯一当前版本。遇到未知版本、损坏 journal 或旧的明文配置来源时，
Host 不猜测、不自动导入，稳定返回 SETTINGS_STORAGE_UNAVAILABLE。Phase 4B 不导入旧
明文来源，也不执行跨版本迁移；`MigrationPending` 作为 closed union 的保留形状，未来
若启用迁移必须先写不含值的 durable intent，再按第 4 节的 new-generation/account
规则实现和验证。任何中断都不能靠扫描 backend 或从 TOML、shell 环境恢复 secret。

##### 3. Durable metadata、wire contract 与启动/运行边界

durable v1 metadata 与运行时摘要严格分层。index 只保存 index-level revision；单个
record 不保存 store_revision、store_state、runtime_state、pending_operation 或
diagnostic。live credential backend 校验和当前 Host/generation snapshot 都是读取时
派生值，绝不能回写 metadata。name/description 是展示字段，不参与 Qwen identity 或
declaration_digest；record 不含 value、value hash、credential backend 返回值、account、
宿主绝对路径或 workspace raw path。受限本地 journal 为恢复保存精确 credential
account；该 account 可能因崩溃持久保留至成功恢复，但不进入 Protocol、registry、catalog
snapshot、fingerprint、Transcript 或日志。

v1 的 durable index 顶层 shape 是闭集；所有 digest 都是 64 位小写 hex，所有整数都是
非负整数，未知字段或类型均 fail closed：

    MetadataIndexV1 = {
      "schema_version": 1,                         // required literal
      "scope": "user" | "workspace",              // required
      "scope_binding_digest": string,              // required
      "revision": integer,                         // required, index-level CAS value
      "records": DurableSettingRecord[],            // required
      "tombstones": DurableTombstone[],             // required
      "journal_refs": JournalRef[],                 // required journal/intent refs only
      "workspace_registry": WorkspaceRegistryEntry[] // required; [] in workspace index
    }

    DurableSettingRecord = {
      "setting_id": string,                         // required, derived without display name
      "plugin_id": string,                          // required
      "package_digest": string,                     // required, 64 lowercase hex
      "declaration_digest": string,                 // required, 64 lowercase hex
      "scope": Scope,                               // required, equals index.scope
      "scope_binding_digest": string,               // required, equals index binding
      "name": string,                               // required, display only
      "description": string,                        // required, display only
      "env_var": string,                            // required, exact canonical envVar
      "sensitive": boolean,                         // required
      "required": false,                            // required Qwen mapping constant
      "consumer_scope": ConsumerScope,              // required
      "generation": string                          // required, opaque credential generation
    }

    DurableTombstone = {
      "setting_id": string,                         // required
      "plugin_id": string,                          // required
      "package_digest": string,                     // required, 64 lowercase hex
      "declaration_digest": string,                 // required, 64 lowercase hex
      "scope": Scope,                               // required
      "scope_binding_digest": string,               // required
      "tombstone_generation": string,               // required, opaque monotonic value
      "committed_revision": integer                 // required, non-negative
    }

    JournalRef = {
      "operation_id": string,                       // required, opaque local reference
      "file": string                                // required, exactly journal/<id>.json
    }

    WorkspaceRegistryEntry = {
      "scope_binding_digest": string,               // required, no raw workspace path
      "metadata_locator": string,                   // required, workspaces/<digest>/index.json
      "state": "registering" | "registered" | "removal_pending" |
        "partial" | "removed",                     // required
      "registered_revision": integer                // required, non-negative
    }

只有 user index 的 workspace_registry 能登记 workspace scope；workspace index 的字段
必须是空数组。登记时先在 user index 的 user-lock 下写入 state=registering 的受限 digest
引用和 durable intent，再在该 digest 对应的 workspace-lock 下创建/校验 workspace index，
最后把 user entry 原子推进为 registered。崩溃留下 registering 时只按该固定 locator
重试或标记 partial，绝不把未登记 scope 当作可枚举目标。移除时先在 user index 标记
removal_pending，再按同一 scope lock 完成 tombstone/cleanup，成功后原子改为 removed
并归档 entry；partial 保留 entry 和 journal 供重试。user registry 的读取、登记和移除
都必须验证当前 Harness home/profile/OS user binding，并按 user lock → workspace binding
digest 字典序的锁顺序执行；不枚举 credential backend。

`journal/<operation-id>.json` 与 `index.journal_refs` 的提交顺序是唯一的：在 scope lock
（workspace 操作先持有 user lock）内，先把完整 journal 写入同目录的临时普通文件，
fsync 文件与目录，再 atomic rename 为固定文件名并 fsync 目录；随后才原子写入
`index.journal_refs`、fsync/rename index 并再次锁内重读，确认 ref 的 operation_id 与
安全相对 locator 一致。只有 ref 已 durable 且重读一致，才允许 credential 写入或
record/tombstone mutation。每次 journal phase 变化先以同样的文件替换落盘；ref 指向的
文件缺失、损坏、类型/权限/文件名不合法时，整个 scope 返回
SETTINGS_STORAGE_UNAVAILABLE 并 fail closed，不猜测恢复。

若在 ref 提交前崩溃，只会留下没有副作用的 orphan journal。启动恢复只允许枚举固定
scope journal 目录，逐项验证 owner-only 权限、普通文件、非 symlink/hardlink/special
file 和 `journal/<安全 operation-id>.json` 文件名；未被 refs 引用的安全 orphan（包括
未完成的临时文件）删除，不枚举 credential backend。目录、特殊文件、越权权限或未知
路径本身即 storage error。操作完成后先从 index 原子移除 journal_ref 并重读确认，再
删除 journal 文件；两步之间崩溃留下的文件会按上述 orphan 规则清理。

journal phase 与 index record/tombstone 无法跨文件原子更新时，不增加第三种状态，而
按 index 的 active generation/tombstone 和上述 closed PendingOperation union 做唯一
裁决：

- set：index 仍是 old generation 且 journal phase 为 prepared/credential_written 时，
  精确回滚 new account；journal 已到 metadata_committed 时，即使 index 仍是 old 也
  从完整 journal 前滚 new record。index 已是 new generation 时一律前滚 old cleanup，
  不回滚 new account；
- remove：index 仍有 active record 且 journal 仍为 prepared 时保持 active；journal 已
  到 tombstone_committed/credential_cleanup_pending 时前滚 tombstone。index 已有
  tombstone 时一律只前滚 old cleanup；
- uninstall：按每个 scope 的 tombstone 和 item state 前滚；migration 按 new record
  是否已提交前滚或按精确 new account 回滚。任何 phase/index 组合不在这些闭集规则内，
  整个 scope 返回 SETTINGS_STORAGE_UNAVAILABLE，禁止 credential 写入、删除或复活
  record。

#### 空 store/bootstrap CAS

settings.list 对尚不存在的 user 或 workspace index 返回逻辑上的 `store_revision=0`，
只计算并校验 scope binding，不创建目录、index、registry entry 或 journal。set/remove
在 scope lock 下重新读取：只有 `expected_store_revision=0` 且 index 仍不存在时，set
才可按上述 journal/ref 顺序原子 bootstrap v1 index；已有 index 一律按其真实 revision
做 CAS，不能把缺失文件再次当作空 store。

bootstrap 的第一次 index 提交本身就是 ref 提交：在 absence 被锁内确认后，set 将
`revision=1`、空 records/tombstones 加上唯一 journal_ref 作为一个 v1 index atomic
replace 落盘，之后才写 credential；record 成功提交再递增 index revision。这样 list
不会创建文件，且不会出现“已经写 credential 但 index 没有 ref”的窗口。

workspace 的首次 set 同时持有 user lock → workspace lock；它先把 user index 的
workspace_registry 写成 registering 并链接带完整 scope intent 的 set journal，再创建
workspace v1 index 和第一条 record，最后把 registry 原子推进 registered。整个过程由
同一 journal replay；任何 crash window 只能完成注册或返回 partial，不能留下未登记
workspace。两次并发首次 set 中只有持锁且重读仍为 0 的一方成功，另一方看到已创建的
workspace revision 并返回 SETTINGS_STORE_REVISION_CONFLICT；不允许第二方覆盖。user
首次 set 使用相同的 absent+expected=0 规则，但不产生 workspace registry。

remove 对不存在的 index 或没有目标 record 的已存在 index 都返回
SETTINGS_RECORD_NOT_FOUND，保持 index 不创建、不写 revision、不写 journal；list 的
逻辑 revision=0 与该错误不冲突。上述 bootstrap 语义、两个并发首次 set、workspace
registering 崩溃恢复及 absent remove 都属于 Phase 4B 的离线 TDD 必测项。

index 的 `revision` 在 records、tombstones、journal_refs 或 workspace_registry 的
每次原子提交时递增。record 没有重复 revision；journal 文件保存完整可重放 payload、
old/new generation、精确 account 与逐项 phase，但这些内部字段永不穿过 wire。读取时
先锁后重读 index 与 journal refs，再用由 immutable identity 推导的 exact account 做
backend 校验：

- `configured`：当前 record、scope binding 和 exact credential 均有效且无 pending journal；
- `absent`：没有 active record，也没有生效 tombstone；
- `stale`：record、package/declaration/binding 或 credential identity 不再匹配；
- `pending`：该 setting 有未完成 journal；`tombstoned`：当前 tombstone 已提交；
- `partial`：cleanup 或跨 scope 操作留下可重试 partial journal；
- `blocked`：metadata、权限或 credential backend 无法安全验证。

以上 `store_state` 只在 settings.list 或 mutation result 现场派生。当前 Host/generation
的 SettingsSnapshot 只派生 `runtime_state`，不写回 index/record；settings.list 现场
组合 live index/backend、当前 snapshot 和脱敏 pending summary，因而 restart 或并行
Host 不会继承陈旧 runtime_state。

Phase 4B 的 canonical wire contract 直接按下列类型写入 v3 schema；JSON-RPC id 和
JSON-RPC error envelope 仍由现有 Protocol 包装：

    Scope = "user" | "workspace"
    StoreState = "configured" | "absent" | "stale" | "pending" | "tombstoned" |
                 "partial" | "blocked"
    RuntimeState = "effective" | "missing" | "pending_restart" | "blocked" |
                   "not_loaded" | "not_applicable"
    ConsumerScope = "qwen-executable-child" | "none"

    SetPending = {
      "operation": "set",
      "phase": "prepared" | "credential_written" | "metadata_committed" |
        "cleanup_pending",
      "operation_id": string,                    // required, journal-only
      "retryable": boolean,                      // required, journal-only
      "record": DurableSettingRecord,             // required, journal-only
      "old_generation": string | null,            // required, journal-only
      "new_generation": string,                   // required, journal-only
      "new_account": string,                      // required, journal-only
      "old_account": string | null                // required, journal-only
    }

    RemovePending = {
      "operation": "remove",
      "phase": "prepared" | "tombstone_committed" |
        "credential_cleanup_pending",
      "operation_id": string,
      "retryable": boolean,
      "record": DurableSettingRecord,
      "old_generation": string,
      "old_account": string
    }

    UninstallItem = {
      "scope_binding_digest": string,
      "setting_id": string,
      "record": DurableSettingRecord,
      "old_account": string,
      "state": "pending" | "tombstoned" | "deleted" | "blocked"
    }

    UninstallPending = {
      "operation": "uninstall",
      "phase": "planned" | "tombstones_committed_per_scope" |
        "deleting_per_record" | "partial_retryable",
      "operation_id": string,
      "retryable": boolean,
      "plugin_id": string,
      "package_digest": string,
      "declaration_digest": string,
      "scope_bindings": string[],
      "items": UninstallItem[]                  // exact records/accounts, journal-only
    }

    MigrationItem = {
      "setting_id": string,
      "old_record": DurableSettingRecord,
      "new_record": DurableSettingRecord,
      "old_account": string,
      "new_account": string,
      "state": "pending" | "rewritten" | "committed" | "blocked"
    }

    MigrationPending = {
      "operation": "migrate",
      "phase": "prepared" | "rewriting_credentials" | "metadata_committed" |
        "cleanup_pending",
      "operation_id": string,
      "retryable": boolean,
      "from_schema_version": integer,
      "to_schema_version": 1,
      "scope_binding_digest": string,
      "items": MigrationItem[]                  // exact records/accounts, journal-only
    }

    PendingOperation = SetPending | RemovePending | UninstallPending | MigrationPending

每个 pending object 必须先按 `operation` 选择上述一个 closed union，再按该 union 的
phase 校验；例如 `set+tombstone_committed`、`remove+credential_written`、带有
uninstall 字段的 set 和缺少 operation-specific 字段的对象都 fail closed。`operation_id`、

CLI Settings 的唯一公开语法是 `harness plugins settings <list|set|remove>`：`set` 与
`remove` 接受两个位置参数 `<name> <setting>`，不要求用户携带任何 digest 或 CAS；`list`
可选接受 Plugin name。`--secret-stdin` 只属于 `set`，`remove/list` 携带它必须失败；
每个 action 另允许受控的 `--scope`、`--workspace`、`--cwd`、`--config`。解析器对未知
option、option 缺值、重复 option、`--plugin-id/--setting-key/--env-var` 等旧身份
输入一律 fail closed，不把未知 option 静默当作位置参数或忽略；`--workspace` 与 `--cwd`
是同一 workspace 选择的互斥别名，同时出现不得按优先级猜测。
`settings.list` 的 Protocol summary 字段是 `name`、`setting`、`scope`、状态和稳定诊断；
Qwen 的 exact `envVar` 映射使 `setting` 成为后续 set/remove 的位置参数值。wire summary
不提供 plugin_id、package/declaration digest、env_var 或 store revision。

Settings value 的唯一 validator 同时约束 Protocol schema/string、CLI stdin 和 Host：
值必须是一个不含 NUL 的 UTF-8 string，允许空字符串作为显式值但不与“未配置”混同，
不做 trim、大小写变换或隐式解码，UTF-8 编码后的长度上限为
`MAX_SETTING_VALUE_BYTES=65536`。验证顺序固定为先检查类型/单值输入形状和 byte
上限，再检查 UTF-8/NUL：CLI 从 stdin 最多读取 65537 bytes，超出上限立即返回
SETTINGS_VALUE_TOO_LARGE；在上限内的错误 JSON 类型、非法/不完整 UTF-8、NUL、多个
stdin record 或其他输入形状返回 SETTINGS_VALUE_INVALID。Host 对 Protocol string
再次执行同一 byte 上限与 NUL 校验。两者都不回显 value，且不会进入 journal 之外的
任何持久化或诊断字段。

用户不提交 store revision。Host 在取得 scope lock 后从当前 scope metadata 派生
compare-and-swap revision，revision 不一致时返回 SETTINGS_STORE_REVISION_CONFLICT，不能
覆盖并发更新；必要的重试仍只在 Host 内部完成。pending summary 只把 journal
内部 phase 映射为 operation + `pending`/`cleanup_pending`/`tombstoned`/
`partial_retryable`/`migrating` 状态和 retryable 标志，不返回 operation_id、account、
record、路径或 scope 列表。

settings.list 读取 live metadata/backend 的 store_state，同时附带当前 Host startup
snapshot 的 runtime_state；它不读取 live secret 来热更新旧 Run。set 成功后旧 Host
仍运行时返回 configured + pending_restart；remove 返回 tombstoned/absent +
pending_restart。没有当前 Host 时 runtime_snapshot.state=not_loaded，runtime_state=
not_loaded。workspace scope 的 binding 由 Host 从当前可信 workspace 得出，客户端
不能提交任意 path；user scope 也必须由当前 Harness home/profile/OS user binding 得出。
set/remove response 只返回 SettingsMutationResult，value、account、backend path、
workspace raw path 永不出现。修改在管理进程提交后由后续 Host 启动读取；当前 Host 不热刷新。

Host startup 创建 immutable SettingsSnapshot，内部绑定 registry/package/declaration/scope
digests，并属于一个 Host/generation；只有 generation replacement 或 Host close 才
释放该 snapshot。每个 Run/child 只持有自己的 resolved env/value 临时引用，在对应
Run terminal、cancel 或 child close 时做 best-effort 释放；Run terminal 不能释放仍被
并行 Run 使用的 Host/generation snapshot。disable 保留 record 但不产生 runtime env，
uninstall 不自动恢复旧 secret。

##### 4. 事务状态机与崩溃恢复

所有 mutation 先取得确定顺序的 user/workspace locks，并在每次状态提交时使用
fsync + atomic replace。唯一恢复规则是：任何 credential 写入或 metadata 改动前先写
durable intent；恢复只能依据 journal 中的 immutable identity 和精确 account，不能
枚举 credential backend、模糊删除或依赖尚未持久化的 transaction_id。

set 的单条状态机是 prepared → credential_written → metadata_committed →
cleanup_pending → done：

1. 先原子写 phase=prepared 的 journal，包含完整 durable record、old/new generation、
   new/old credential account、scope binding 和 operation_id，并 fsync/rename。
2. 再写 new credential。若在写入前崩溃，恢复按 journal 对 new account 做幂等删除
   （没有该项即 no-op），旧 record 仍是唯一 active；若写入后但在 phase 推进前崩溃，
   或恢复看到 phase=credential_written，必须按同一精确 new account 回滚删除，旧
   active 保持不变。删除失败就把 journal 推进到 cleanup_pending，store_state=blocked、
   返回 SETTINGS_CLEANUP_PENDING 并重试；恢复动作固定为按 journal 精确删除 new account，
   不允许保留该 account 的分支，也不允许扫描 backend。
3. 只有确认 new credential 写入成功后，才原子提交 metadata，使 new generation active，
   并推进 phase=metadata_committed。若崩溃发生在 metadata 已提交但 journal 尚未推进的
   窗口，恢复通过 index 中的精确 new generation 识别已 commit，继续前滚而不回滚新值。
4. metadata_committed 之后只按 journal 的 old account 做 cleanup；旧 credential 残留
   进入 cleanup_pending，不会被新 record 使用。清理成功后归档 journal；删除失败返回
   SETTINGS_CLEANUP_PENDING，禁止删除 journal 之外的 account。

remove 的单条状态机是 prepared → tombstone_committed → credential_cleanup_pending
→ done，不伪造 new credential generation：

1. phase=prepared 的 journal 保存完整旧 record、旧 generation、精确 old account，并
   校验 current record identity/digest；不匹配返回 SETTINGS_RECORD_STALE。
2. 原子提交 tombstone，生成 monotonic tombstone generation，再推进
   phase=tombstone_committed。提交前崩溃时旧 record 仍可用；提交后 resolver 立即拒绝
   旧 record，即使 credential 尚未删除。
3. 仅按 journal 的 old account 删除 credential，推进
   phase=credential_cleanup_pending；缺项视为已删除，删除失败保留 tombstone 与
   journal，store_state=partial/blocked，并返回 SETTINGS_CLEANUP_PENDING。
4. 清理成功后仍持久保留非敏感 tombstone 与 index revision，先按 journal/ref 协议完成
   journal 归档，防止旧 list/Run 或迟到 retry 复活 record。v1 不因时间自动删除
   tombstone；只有显式、有界的 tombstone GC 才能处理它，并且必须同时满足：没有相关
   journal_ref、exact old account cleanup 已确认、scope index revision 至少达到
   `committed_revision + 1`，且 Host registry 证明不存在 snapshot revision 不高于该
   tombstone 的 active Host/generation/Run lease。GC 每次最多处理固定数量并以 30 天为
   最小保留期、180 天为触发上限；超过上限但无法证明无旧 lease 时继续保留并报告
   SETTINGS_CLEANUP_PENDING，不能牺牲安全条件。重试和 GC 只匹配 immutable
   plugin/package/declaration/scope/setting identity，不使用 display name 或 wildcard；
   整个过程不依赖 backend 反查 transaction。

uninstall 是 user registry 语义下跨 scope 的状态机：planned →
tombstones_committed_per_scope → deleting_per_record → partial_retryable 或 done。
它清理目标 user record 以及 user index 已记录的全部 workspace scope，不仅是当前
trusted workspace；未登记 scope 不触碰。先取得 user registry lock，冻结 immutable
plugin/package/declaration identity、registry revision 和全部 scope binding，再按 user
lock → workspace binding digest 字典序取得 scope locks。任何 registry revision 漂移都
返回 SETTINGS_UNINSTALL_CONFLICT，不扩大或猜测清理范围。

uninstall 的目标设计是 planned → tombstones_committed_per_scope → deleting_per_record
→ partial_retryable 或 done。当前 Phase 4B 的实现以每条 setting 的 `RemovePending`
journal 加 user registry 的 `registering/registered/removal_pending/partial/removed`
状态组合这条状态机：逐 scope 原子提交 tombstone，逐项只删除精确 account；跨
user/workspace 部分失败、缺失或不可读的已登记 scope 返回 SETTINGS_UNINSTALL_PARTIAL，
保留 registry 状态与可重试的 per-record journal。重试只处理同一 immutable identity，
禁止 credential backend 枚举、wildcard 或按 display name 删除；若新安装/声明 revision
已占用同一 identity，返回 SETTINGS_UNINSTALL_CONFLICT。`UninstallPending` 是未来复合
操作的 closed-union 形状，Phase 4B 不把它伪装成已落盘的单一 journal。disable 不是
uninstall，成功卸载不恢复 secret，重装必须重新确认。

`MigrationPending` 只允许 prepared → rewriting_credentials → metadata_committed →
cleanup_pending；Phase 4B 对未知旧版本/旧明文来源保持 fail closed，未来迁移必须先写
不含值的 intent 和精确 item 列表，按 set 的上述恢复规则重建新 account，提交新 metadata
后再清理旧 account。每个 crash window 都由 journal 重试，不能通过 backend 枚举、TOML
或 shell 环境恢复 secret。

##### 5. Resolver、gate 与威胁模型

解析优先级固定为 workspace > user。Qwen required=false 只表示 credential value
可缺失；缺值时对应 env entry 不存在，不是 Qwen manifest invalid。缺少、为空、非法
或被 denylist 的 envVar 则是 declaration invalid；Harness-native 的 required 缺值
规则只适用于非 Qwen schema。声明漂移、scope stale、backend capability 缺失、权限
不可证明、disabled/invalid/unsupported 都是 fail closed，且稳定写入
diagnostic。Qwen 每个有效 MCP/Hook/LSP 子项按 qwen-extension-wide-v1 接收该插件
所有已配置且通过 gate 的 declared envVar；不把全局 settings 映射成 Host 全进程环境。
Commands、Skills、Agents 不 spawn、不接收 Settings env。PATH、
NODE_OPTIONS、PYTHONPATH、LD_*、DYLD_* 和等价 process-control 变量拒绝；当前 shell
中的同名值不作为 fallback。setting value 不进入 command argv、cwd、lsp JSON-RPC、
MCP tool result、Hook payload 或模型 transcript。

日志、异常、status、inspect、config/show、registry、catalog snapshot、fingerprint、
Protocol、Transcript、core dump 和子进程 argv/env 都是泄漏面。实现必须只传脱敏摘要，
子进程 env 在创建时按最小声明集构造；stderr、取消、超时和诊断做稳定分类而不拼接
value/account。core dump 禁止或仅在平台 probe 能证明关闭/隔离时允许。值在 resolver/
spawn 的最短生命周期内使用，随后 best-effort 释放引用；Python/TypeScript 字符串会
复制且不能可靠擦除，残余内存、swap、调试器和崩溃转储风险必须记录为未完全消除的
威胁，不能承诺传输完成后内存中绝对不存在值。

### 5.9 Plugin 安装、存储和 activation：HC-175 第一轮

HC-175 将此前以用户授权哈希为中心的管理模型收敛为名称和作用域。Plugin 文件仍由 Adapter
解析为统一的 `PluginDescriptor`，但用户只看到名称、版本、来源、真实组件、Settings 和 warning。

```text

├── store/<source-id>/<plugin-name>/<package-digest>/
├── data/<source-id>/<plugin-name>/
├── staging/
├── registry.json                 # canonical registry v3
├── registry.v2.backup.json      # v2 首次迁移保留的原文备份
└── registry.lock
```

当前管理内核保证：

- 目录和 zip 都先进入安全 staging，再 copy-on-install、只读化并原子提交；
- registry v3 以 artifact identity、内部 package digest、Adapter report 和
  `activation.user/workspaces` 保存状态；digest、revision 和 internal ID 不进入正常管理输入；
- v2 首次读取在同一锁内严格校验并用当前 Adapter 重解析，先 durable backup 再原子写 v3；迁移
  replace 前故障或大小写不敏感的名称冲突保持 v2 原文并 fail closed；replace 已发生但目录 fsync/结果无法确认时返回 `PLUGIN_REGISTRY_COMMIT_UNCERTAIN`，保留 backup 并尽力恢复，不承诺旧文件绝对不变；
- Qwen、Claude、portable/Hybrid 共用 `format=auto` 的管理入口。显式 format 只留给
  `plugins validate` 等高级诊断；
- Plugin name 大小写不敏感地唯一。重复安装返回 `PLUGIN_ALREADY_INSTALLED`，update 不允许改名；
- install/update 先产生有界 preview，Shell 以 `interaction.plugin_consent` 确认；确认后的 install
  直接启用选定 scope，update 保留 user/workspace activation；preview identity 与实际提交绑定，
  来源在确认后变化则返回冲突而不安装未展示内容；
- user activation 是默认值，workspace activation 按专用 workspace identity 覆盖 user；没有 watcher，
  已运行 Host 不被外部 Shell mutation 改写，后续 Host 才读取新 generation；
- product status 只有 `loaded`、`disabled`、`warning`、`failed`。组件列表只包含实际进入
  canonical consumer 的组件；坏或不支持条目只进入 warning，不作为可执行能力展示；
- 保留 Tool Policy、审批、workspace、最小进程环境和 Settings credential backend 等既有运行安全边界，
  但不把 Plugin trust grant、capability fingerprint 或 reauthorization 作为管理状态。

### 5.10 Protocol 与 Shell CLI：HC-175 第一轮

Plugin 管理 Protocol 在 v3 minor 8 提供：

```text
plugins.list / plugins.inspect / plugins.validate
plugins.install / plugins.update / plugins.set_enabled / plugins.remove
settings.list / settings.set / settings.remove
interaction.plugin_consent
```

用户参数只包含 Plugin name、scope、source、enabled、purge-data 和 Settings 的 name/setting/value；
Host 在内部补齐 artifact/declaration identity 与 CAS。正常 response 和错误不要求用户复制 digest、
revision、capability hash 或 internal ID；高级 inspect 仅可返回脱敏 internal locator。

Shell grammar 为：

```text
harness plugins install <source> [--scope user|workspace]
harness plugins list [--scope user|workspace] [--enabled-only]
harness plugins inspect <name> [--scope user|workspace]
harness plugins enable|disable <name> [--scope user|workspace]
harness plugins update <name> [--source path-or-zip]
harness plugins remove <name> [--purge-data]
harness plugins settings list [<name>] [--scope user|workspace]
harness plugins settings set|remove <name> <setting> [--scope user|workspace]
```

Install/update 只有 Shell CLI 处理 consent；取消或无 handler 分别返回稳定的取消/需要确认错误，
不增加 `--yes`。TUI/Web 不提供 Plugin 管理 UI，不监听 registry，也不在当前会话重注入 Context。

### 5.11 启动 catalog 与 TUI/Web 共享 consumer：HC-175 第二轮

HC-175 第二轮把第一轮的管理结果接回既有启动链路。Host 的 `initialize` 是 Plugin activation 的
generation 边界，顺序固定为：

```text
Host initialize
  → PluginManager.refresh_catalog()
  → ExtensionCatalogSnapshot（按当前 workspace 过滤 enabled）
  → Skill / Command / Agent / Policy / Team / Context 来源
  → SettingsSnapshot 与 child-only overlay
  → MCP snapshot 与 Hook/LSP/Monitor runtime catalog
  → initialize.agent_commands + 既有 RPC consumers
```

`AgentHost` 只在第一次资源初始化时读取 Plugin registry 并保存这份不可变 catalog。`SkillRegistry`、
`AgentCatalog`、`ContextLifecycle`、`McpConnectionManager` 和 `PluginRuntimeManager` 都从这份
catalog 派生；Settings 也只在同一 Host/generation 解析。`skills.list` 等既有控制面刷新可以刷新
非 Plugin Skill 来源，但不能重新读取 Plugin registry 或替换上述 Plugin generation。

CLI 在启动握手后用 `initialize.agent_commands` 建立唯一 `CommandRegistry`，再把它注入
`InteractiveRuntime` 和唯一 `InteractiveController`。TUI 直接消费该 Controller；Web 通过
`PresentationCoordinator`/`WebUiGateway` 接入同一 Controller 和同一 Host，不创建第二套 Plugin
catalog、管理 UI 或格式分支。因此同一 user Plugin 在不同工作区的新 TUI/Web Host 中得到相同
的 user catalog，而 workspace override 只在其绑定 workspace 的新 Host 中生效。

Shell 的 install/update/enable/disable/remove 完成后，已运行 Host 不监听外部 registry，也不重建
Plugin runtime、MCP generation 或当前 Run 的 Context。旧 Host/Thread/Run 继续持有启动 snapshot；
关闭并启动新 Host 后，才重新执行上面的 catalog 生成。disabled、failed 或转换失败的 Plugin
不会向任一 consumer 发布来源；warning 只包含实际有效组件之外的脱敏诊断。Qwen、Claude、
portable 和 Hybrid 的差异止于 Adapter，canonical consumers 不按格式分支。

第二轮离线回归使用临时 home、临时 workspace、仓库 fixtures、fake credential backend 和 fake MCP
连接；Hook/LSP/Monitor 只验证 runtime catalog 构造，不执行外部脚本。真实 ZA38 的 install 与新进程
观察保留为人工验收步骤，不纳入自动化启动。

### 6.2 “直接安装”的定义

用户可以执行：

```bash
harness plugins validate ./my-claude-plugin --format auto
harness plugins install ./my-claude-plugin
```

或者：

```bash
harness plugins install ./my-claude-plugin.zip
```

原包不需要：

- 新增 Harness manifest；
- 移动目录；
- 改写 Agent Markdown；
- 把 `.mcp.json` 转成 TOML；
- 复制 Skill 到 `~/.harness/skills`；
- 重新打包。

Harness 自动识别 `.claude-plugin/plugin.json`，由 `ClaudeCodePluginAdapter` 完成转换。

Claude 当前允许省略 manifest。对于 manifestless Plugin：

- 显式 `--format claude-code` 时按 Claude 默认目录识别；
- `--format auto` 只在目录具有明确 Claude 组件且没有冲突 manifest 时识别；
- Plugin 名从安装目录派生；
- 不能因为没有 manifest 就退化成只加载 Skill。

### 6.4 Claude Skill 兼容

Claude Skill 常用字段包括：

- `name`；
- `description`；
- `when_to_use`；
- `argument-hint`；
- `disable-model-invocation`；
- `user-invocable`；
- `allowed-tools`；
- `disallowed-tools`；
- `context`；
- `agent`。

Adapter 负责字段语义转换：

```text
disable-model-invocation → modelInvocable = false
user-invocable          → userInvocable
argument-hint           → argumentHint
allowed-tools           → requested preapproval，不是授权
disallowed-tools        → capability deny

${CLAUDE_PROJECT_DIR}   → workspace root
```

Claude 的 `allowed-tools` 只作为本轮 requested preapproval；仍须经过全局和 Agent Policy/审批，
不产生 Plugin trust grant。

### 6.5 Claude Agent 兼容

Claude Agent Markdown：

```markdown
---
name: security-reviewer
description: Reviews authentication and trust boundaries
tools: Read, Glob, Grep
model: inherit
skills:
  - review-checklist
maxTurns: 12
---

You are a security reviewer...
```

字段映射：

| Claude 字段 | Harness 处理 |
| --- | --- |
| `name`、`description`、body | Agent ID、用途和 Prompt |
| `tools` | 最大请求工具集合，再与 EffectivePolicy 取交集 |
| `disallowedTools` | 永远作为 deny |
| `model: inherit` | 继承父级实际 ModelProfile |
| `model: sonnet/opus/haiku` | 优先使用同名 ModelProfile；未配置时安全继承父实际 Profile |
| 其他 `model` 值 | 必须精确引用 Harness ModelProfile，否则该 Agent inactive |
| `effort` | 当前解析但不改变模型参数，兼容报告/诊断不得声称已生效 |
| `maxTurns` | 已进入 AgentDefinition 与 Profile 指纹；运行时 turn budget 待预算层接入 |
| `skills` | 同一 Plugin snapshot 内的 canonical Skill ID |
| `memory` | execution-scoped memory policy |
| `background` | 受父 Run 管理的后台 child execution |
| `isolation: worktree` | worktree execution environment |
| `color` | TUI 展示元数据 |
| `permissionMode` | Plugin Agent 中不作为权限入口 |
| agent-local `hooks`、`mcpServers` | Claude 对 Plugin-shipped Agent 本身也限制这些字段；Harness 给出诊断，不借此扩权 |

Claude Tool 名使用显式映射：

```text
Read  → read_file
Glob  → glob
Grep  → grep
Write → write_file
Edit  → edit_file
Bash  → execute
Agent → delegate_agent
```

未知 Tool 不模糊猜测。Adapter 返回 `CLAUDE_TOOL_UNMAPPED`，该 Agent 保持 inactive，直到管理员提供明确映射。

### 6.7 Claude Hook 兼容

Claude 当前 Hook 事件包括但不限于：

- `SessionStart`、`SessionEnd`；
- `UserPromptSubmit`、`UserPromptExpansion`；
- `PreToolUse`、`PermissionRequest`、`PostToolUse`、`PostToolUseFailure`；
- `SubagentStart`、`SubagentStop`；
- `TaskCreated`、`TaskCompleted`；
- `TeammateIdle`；
- `PreCompact`、`PostCompact`；
- `WorktreeCreate`、`WorktreeRemove`；
- `Notification`、`ConfigChange`、`FileChanged`。

Claude Hook handler 支持 command、HTTP、MCP tool、prompt 和 agent。

Harness 当前已经交付的兼容链路是：

```text
Harness Tool lifecycle event
  → ClaudeEventAdapter 生成 Claude 兼容 stdin JSON
  → HookRunner 执行 command handler
  → ClaudeResultAdapter 解释 stdout JSON、stderr、exit code 和 timeout
  → 转成 Harness allow / deny / diagnostic
```

具体支持矩阵：

| Claude Hook 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| `PreToolUse` command | adapted | exit 2 或 JSON deny 阻断 Tool |
| `PostToolUse` command | adapted | Tool 成功后运行并记录诊断 |
| `PostToolUseFailure` command | adapted | Tool 失败后运行并记录诊断 |
| shell form、exec form | adapted | exec form 使用 `args`，不经 shell 拼接 |
| prompt、agent、HTTP、MCP tool handler | unsupported | 验证报告逐项显示，不执行 |
| 其他 Hook event | unsupported | 尚未建立对应 Harness 生命周期事件 |
| `updatedInput`、`ask`、`defer` | unsupported | fail closed，不假装兼容 |

实现不只是把 Hook command 扔给 shell：它解释 `PreToolUse` 拒绝、exit code、JSON 输出，
限制输入输出与超时，并在 Host close 时终止子进程。这样“安装成功”和“组件实际生效”才不会
混为一谈。

Observation Hook 的日志也必须沿同一 canonical 路径传递：`RunContext` 提供当前 Run 的
`diagnostic_log`，`PluginRuntimeMiddleware` 在 `PostToolUse`/`PostToolUseFailure` 调用
`_run_observation_hook` 时显式传入，最终由 `HookRunner` 记录稳定摘要。日志不包含 Hook payload、
标准输出/错误、宿主路径或秘密；观察 Hook 异常只记录失败分类，不覆盖原始 Tool 结果。真实
middleware 与离线 fixture 必须覆盖该关键字调用，防止接口签名漂移重新把成功 Tool 变成运行失败。

### 6.8 Claude Agent Teams 兼容

Claude Agent Teams 是运行时功能，不是 Plugin 中可以预先分发的固定 team config。官方运行时 team 文件位于用户目录，由 Claude 会话生成和维护。

因此 Harness 的正确兼容方式是：

1. 直接导入 Claude Plugin 的 `agents/*.md`。
2. 自动生成一个 Delegation Group，使主 Agent 可以派发这些角色。
3. 用户可以用自然语言要求创建 Team。
4. Harness 根据 AgentDefinition 生成 TeamDefinition 预览。
5. 用户确认后由 TeamCoordinator 运行。
6. 不导入 `~/.claude/teams/*` 和 `~/.claude/tasks/*` 运行状态。

Claude Agent Team 的体验映射：

| Claude Team 能力 | Harness 对应能力 |
| --- | --- |
| lead | 根 Agent 或 Team 入口任务 |
| teammate 独立上下文 | 独立 Agent execution namespace |
| shared task list | TeamTask 持久化 |
| task dependencies | TeamDefinition DAG |
| teammate model | ResolvedAgentSpec 模型绑定 |
| teammate tools | EffectiveCapabilityView |
| member cancel/retry | TeamCoordinator 状态机 |
| team status | TUI `/teams` |
| mailbox | 首版不实现；先使用结构化 task input/result |

如果后续真实场景证明成员必须直接互聊，再设计 mailbox。不能为了表面兼容先引入第二套 Thread 和文件轮询。

### 6.9 Compatibility report

每个发现的组件必须有明确状态：

```text
supported
adapted
unsupported
invalid
```

示例：

```text
Format: claude-code-plugin
Adapter baseline: 2026-07-30
Compatibility: partially-compatible

Skills:   3 supported
Commands: 2 supported
Agents:   4 supported
MCP:      1 supported
Hooks:    2 adapted
LSP:      1 unsupported

Blocking issue:
  CLAUDE_LSP_RUNTIME_UNAVAILABLE
```

只要存在 `unsupported`，默认不能显示 `fully-compatible`。Plugin 可以安装为 inactive，但不能静默声称全部生效。

### 6.10 双 manifest Plugin

一个包可以同时包含：

```text
plugin.json
.claude-plugin/plugin.json
```

处理规则：

1. Agent Plugins manifest 决定 portable Skill/MCP。
2. Claude Adapter 补充 Agent、Command、Hook、LSP 等 Claude 私有组件。
3. 同一路径组件只加载一次。
4. 两份 manifest 的身份或版本冲突时拒绝。
5. 不通过优先级猜测作者意图。

- 畸形 manifest/frame；
- MCP/Hook/LSP/Monitor 子进程清理；
- Plugin 更新和恢复。

## 八、总结

最终方案可以概括为：

```text
一个 Plugin 产品概念
  +
Agent Plugins 1.0 通用基础
  +
Claude Code 一级兼容 Adapter
  +
一个 ExtensionCatalogSnapshot
  +
一个 ResolvedAgentSpec 执行事实
  +
AgentDelegator 和 TeamCoordinator 两层协作
```

当前代码不是从零开始：

- Skill 运行、MCP 连接、AgentEnginePool、RunCoordinator 和 ThreadPersistence 已经具备；
- Agent/Policy 类型和动态 Command 类型已有基础。

当前已经完成：

- Plugin 安装、信任、不可变 catalog 和多格式 Adapter；
- Plugin Skill、MCP、Command、portable/Claude Agent；
- 角色级 ResolvedAgentSpec、只收紧 Policy 和 Managed delegation；
- 固定 TeamDefinition、Plugin Team Adapter、TeamCoordinator 和 `/agents`、`/teams` 产品入口；
- Claude command Hook、stdio LSP 与有界 Monitor 运行层。

仍缺少的是：

- prompt/agent/HTTP/MCP-tool Hook、其他 Hook 事件和 socket LSP；
- settings、output styles、themes、dependencies、channels、workflows 等 Claude 扩展组件；
- Team 统一 token/cost budget；
- Git/HTTP/marketplace 来源、依赖求解与运行中 Plugin reload。

因此当前版本已经可以安全安装 Claude Code Plugin，并让其 Skill、MCP、Command 和
`agents/*.md`，以及受支持的 command Hook、stdio LSP 和 Monitor 在下一次 Host 启动进入统一
运行快照。不能把这一结论扩大为 Claude 的全部 Hook handler、socket LSP 和实验组件都已
生效；compatibility report 会按子项明确标为 `adapted`、`unsupported` 或 `invalid`。
