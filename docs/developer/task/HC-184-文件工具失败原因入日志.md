# HC-184 文件工具失败原因入日志

## 需求来源与当前阶段

2026-10-22，排查 `edit_file` 频繁失败时发现：诊断日志里的 `tool.completed` 只有 `outcome=error` 和 `result_bytes`，看不出失败原因。当时只能靠结果字节数反推，再去 `~/.harness/threads.sqlite3` 的 transcript 里查到真正的错误码。用户已确认先做这一项（见 `tmp/handoff-edit-file-conflicts.md` 中的 C-1）。

范围判定：本项要修改诊断日志的公开 Schema（`packages/protocol/diagnostic-log/schema/v1.json`）以及由它生成的 Python/TypeScript 产物和 fixtures，不属于快速通道，走完整流程。

## 通俗说明

现状：文件工具失败时，日志只说"出错了，返回了 N 字节"，要知道是版本过期还是提交冲突，必须翻数据库。
做法：文件工具本来就会给每次失败一个固定的大写错误码（如 `COMMIT_CONFLICT`、`STALE_FILE`、`UNREAD_RANGE`）。日志中间件在记录 `tool.completed` 时，如果结果是失败，就把这个错误码一并记下。

```text
工具返回结果 → 判断是否失败 → 取出固定格式的错误码 → 校验符合 safeName 白名单 → 写入 tool.completed.error_code
```

改后收益：`harness logs --thread <id> --event tool --flat` 直接看到每次失败的原因，下次排查类似问题不用再查数据库。

## 范围

- `tool.completed` 新增可选字段 `error_code`，仅在失败时出现，类型沿用现有 `safeName`（字母、数字与 `._:/-`，最长 120）。
- 日志中间件从失败的工具结果中取出稳定错误码；取不到或格式不合法时省略该字段，不得因此改变工具结果或抛错。
- 同步 Schema、Python 与 TypeScript 生成产物、fixtures 以及 `docs/user/日志与诊断.md`。

## 非范围

- 不记录错误消息正文、文件路径、文件内容或模型输出。
- 不改变 `tool.failed`（工具 handler 抛异常）的现有字段。
- 不修复 edit_file 冲突本身，那是 HC-185 的内容。

## 待 Spec 确认的问题

- 错误码从哪里取：文件工具的结果是 JSON 文本，中间件解析正文可能违反"不投影业务正文"的约束。Spec 需要决定是让文件工具把错误码放进 `ToolMessage` 的结构化字段（如 `artifact` 或 `additional_kwargs`），还是由中间件做受限解析。倾向前者。
- MCP 等非文件工具是否也上报错误码，还是先只覆盖 Harness 内置文件工具。

## 验收标准

1. 构造一次 `edit_file` 的 `COMMIT_CONFLICT` 失败，诊断日志中对应 `tool.completed` 含 `"error_code":"COMMIT_CONFLICT"`。
2. 成功调用的 `tool.completed` 不含 `error_code`。
3. 带有路径和文件内容的失败结果，其正文不出现在日志任何字段（沿用 `test_tool_middleware.py` 的 canary 断言）。
4. `harness logs --event tool --flat` 的输出能显示该字段。
5. Python 诊断日志测试、`packages/protocol` 契约测试与 `npm run project:check` 通过。
