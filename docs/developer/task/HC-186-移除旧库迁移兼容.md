# HC-186 移除旧库迁移兼容

## 需求来源与当前阶段

2026-10-30，`ub-mode` 全仓检视（`tmp/ub-mode-review-report.md`）指出：仓库处于开发阶段、没有外部兼容承诺（见 `AGENTS.md`「发布阶段与兼容性原则」），但 `thread_persistence.py` 仍保留着完整的旧库升级机制。用户已确认：**当前没有面向客户的发布，没有历史存量数据包袱，旧库数据可以丢弃**。

用户已确认的三个设计决定：

1. 遇到旧版本库时，程序直接报明确错误并提示删除后重启，**不自动删除、不自动备份重建**。
2. 数据库版本号 `_SCHEMA_VERSION` **重置为 1**。
3. Plugin registry v2→v3 迁移、执行绑定 v4/v5 旧格式兼容**一并纳入**本任务。

范围判定：本任务改变 SQLite 持久化的启动语义，并涉及多个生产模块与大量测试，不属于快速通道，走完整流程。

与既有任务的关系：`HC-178` 明确把「迁移仪式」排除在外，`HC-108` 已归档（当年的目标是把迁移做得更安全，本任务则是整体移除），所以两者都不冲突。

## 通俗说明

现状：每次启动，程序会先检查本机 `~/.harness/threads.sqlite3` 的版本号。如果是旧版本，就在一个单独的子进程里一步步升级到最新版，同时给数据库打指纹、记录尝试次数、超时后打"毒化"标记，防止反复破坏数据。这套机制总共有上千行生产代码和大量专用测试，但它保护的是"用户升级前的老数据"，而目前并没有这样的用户。

做法：把整套升级机制删掉。启动时只做一个判断：

```text
读取库的版本号 → 等于 1？→ 正常打开
              → 不等于 1（旧版或更新版）→ 报错：版本不兼容，请删除该文件后重启（不动文件）
              → 文件不存在 → 新建版本为 1 的空库
```

Plugin registry 和执行绑定也是同样处理：只认当前格式，认不出就失败并给出明确提示，不再悄悄升级或兼容读取。

改后收益：持久化底座去掉一大块只在升级时才运行的代码，启动路径更短、更好读；以后改表结构只需把版本号加 1，不需要同时写升级脚本和迁移测试。

代价（必须知晓）：升级到本任务合入后的版本时，**所有开发机上现有的库（包括 v20 的库）都会被判为不兼容**，需要手动删除一次 `~/.harness/threads.sqlite3`，其中的历史对话、检查点和 Goal 数据会丢失。如有需要保留的内容，请在合入前自行备份。

## 范围

- `threads/thread_persistence.py` 中的跨版本升级逻辑：legacy 来源识别（含 PromptEpoch v2~v6）、schema 契约比对、数据库指纹、子进程迁移入口与监管、poison / attempt / state 标记文件、迁移用故障注入全局变量和测试开关。
- `threads/migration_worker.py`、`threads/migration_recovery.py` 及其测试 `tests/threads/test_migration_recovery.py`。
- 版本号处理：`_SCHEMA_VERSION` 重置为 1；启动时版本不等于 1 一律失败，错误码稳定、消息包含库路径和「删除后重启」的提示；文件本身不被修改或删除，也不产生任何标记文件。
- `plugins/store.py` 的 registry v2→v3 迁移，改为只认当前版本。
- `runtime/execution_binding.py` 及相关位置对 v4/v5 旧绑定格式的读取兼容（具体符号由 Spec 精确定界）。
- 所有依赖旧版本 fixture 或迁移行为的测试，一并删除或改写为「只验证当前版本」。
- `docs/user/故障排查.md`：删除迁移 attempt/poison/Windows 迁移子进程等段落，新增「库版本不兼容怎么办」；更正与代码不符的 registry 描述。

## 非范围

- 不删除或修改 Compose 相关的表和代码（`compose_work_item_store`、`work_item_engine` 等），那归后续的 Compose 统一改造；其表结构变化届时通过版本号 +1 体现。
- 不拆分 `thread_persistence.py`，不改变现有表结构和业务读写逻辑。
- 不提供自动备份、自动重建或数据导出工具。
- 不改变协议、CLI 命令和面向用户的 Thread 功能行为。

## 待 Spec 确认的问题

- 版本不兼容的稳定错误码名称，以及它如何经由 `THREAD_STORE_UNAVAILABLE` 等现有错误路径展示给 CLI 用户。
- 执行绑定中 `legacy_models`、`has_legacy_runtime` 等符号哪些属于「旧数据形状兼容」应删除，哪些是当前仍在使用的正常字段。
- 全新空库的版本号写入时机：确保不会出现「文件已创建但版本号未写入」而被下次启动误判为旧库的中间状态。
- 版本号高于当前（库来自更新的程序）时，沿用现有的 `CHECKPOINT_SCHEMA_TOO_NEW` 语义还是与「不兼容」合并为同一个错误。

## 验收标准

1. 在没有 `threads.sqlite3` 的干净环境启动并创建 Thread，库的 `user_version` 为 1，退出后再次启动能恢复该 Thread。
2. 手工构造一个 `user_version` 为 20（以及 0 以外的其他非 1 值）的库文件，启动报稳定错误码；错误消息含库路径和「删除后重启」提示；该文件内容的哈希与启动前一致，同目录下不出现 `.migration-*` 之类的标记文件。
3. 手工构造版本号高于 1 的库，同样被拒绝，且不被修改。
4. 在 `packages/agent/harness_agent` 与 `packages/agent/tests` 下搜索 `migration_worker`、`migration_recovery`、`_run_legacy_migration_child`、`_MIGRATION_`、`legacy_prompt_epoch`，结果为零命中。
5. Plugin registry 文件版本不是当前版本时，启动按 `PLUGIN_REGISTRY_INVALID` 失败关闭，行为与 `docs/user/故障排查.md` 的描述一致；代码中不存在 v2→v3 迁移。
6. 执行绑定遇到旧格式时失败并给出明确提示，不再被兼容读取（具体表现由 Spec 定义）。
7. `docs/user/故障排查.md` 不再出现迁移 attempt、poison marker 和迁移子进程的描述，并包含「库版本不兼容」的处理步骤。
8. `cd packages/agent && .venv/bin/python -m pytest -q` 全部通过；`cd packages/cli && bun test` 的失败项与改动前基线一致；`npm run tasks:check` 通过。
