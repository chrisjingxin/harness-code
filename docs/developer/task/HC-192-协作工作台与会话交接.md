# HC-192 协作工作台与会话交接

## 需求来源与阶段

2026-11-05，用户明确提出：将 Web 抽为独立的上层工作台，原 Harness Code 成为通过 ACP 接入的一种 Agent 实现，并能继续接入 Claude、Codex 等实现。初版对齐本地 Lody 的主要协作能力，优先共享上下文对话、交接和 @引用。

交接表示用户之间接续同一个会话：用户 A 先讨论并确认已有结论，用户 B 在自己的电脑打开同一个会话，继续后续讨论与工作。账号以用户为维度，不预设岗位或业务角色，交接不要求某种岗位组合。

用户随后要求按大功能流程先出设计文档，并补充：初版必须能够在外网演示，可以准备服务器；最终仍需迁入内网；实现优先简单直接，允许后续迭代，不增加大量防御性配置。此前“跳过 Skill 调用”的要求继续适用于本任务，正式文档与评审步骤保留。

本次补充约束：团队 Java 开发者更多，云端技术栈改为 Java；数据库使用内网现有的 TDSQL，用户已明确为 MySQL 兼容版；在已核对的 Lody / Loro 公开源码与示例基础上尽量利用已有实现。本轮只更新设计文档，不生成 UI 设计稿。Java 与 TDSQL MySQL 约束已明确，Spring Boot、HTTP + SSE 和 Java ACP SDK 是本稿提出的具体建议，尚未代替后续规格评审。

登录与访问范围先由数据库中的预置普通用户和工作区关系提供，默认创建几个用户账号供登录调试；内网登录系统到内网阶段再开发。首版不增加岗位字段、角色分配或用户权限管理后台。具体设计采用 `user01`、`user02`、`user03`，名称不代表职责或等级。

当前为需求整理与顶层设计评审阶段。已交付文档草案，不表示 Task 或技术方案已评审通过。实现任务尚未认领；本轮不写 Spec、Plan、Todo 或生产代码。流程依据为根目录 [AGENTS.md](../../../AGENTS.md) 的“无确认的 Task 不写 Spec；无确认的 Spec 不写 Plan；无 Todo 不进入实现”。

## 用户能得到什么

    用户 A 讨论问题 → 确认已有结论 → 交给用户 B
    用户 B 用自己的账号登录 → 打开原会话 → 看到历史与交接说明 → 继续讨论
    讨论需要其他结论 → @选择原对话或消息 → 查看引用内容 → 带入当前问题

大家查看同一条会话历史；每条发言保留对应用户账号。对话与 Agent 执行由服务器常驻服务管理，不依附发起用户的电脑或浏览器。

## 首版范围

| 能力 | 可观察结果 |
| --- | --- |
| 共享会话 | 至少两个账号、两台电脑可打开同一会话，看到相同的消息、附件和执行状态 |
| 会话接续 | 另一用户接手后，Agent 能继续使用该会话之前的上下文；无需人工复制历史 |
| 交接记录 | 发起后显示待接手且当前接续人不变，目标用户确认后更新；支持发起用户取消，双方可查看进展 |
| @引用 | 可搜索有权限的会话/消息，预览时固定有界快照，发送时原样带入，点击后定位来源 |
| ACP 接入 | Web 的通用会话流程通过 ACP 执行；Harness 是第一个后端，设计中包含 Claude/Codex 等适配器位置 |
| Java 云端 | 共享业务、执行排队和 ACP Client 由 Java 服务负责；Harness Python 内核与第三方适配器保留自己的运行时 |
| 内网数据库 | Java 通过 MySQL JDBC 访问 TDSQL；SQL 与迁移脚本按 MySQL 方言设计，具体内核与约束在实际实例验证 |
| 调试登录 | 数据库默认创建几个普通用户，选择或输入预置账号进入；通过账号区分作者、交接人和回答人，不模拟岗位 |
| 外网演示 | 通过演示服务器的受登录保护地址，完成真实跨电脑交接，不以两个浏览器窗口冒充跨设备验收 |
| 内网迁移 | 相同构建产物与数据结构通过部署配置进入内网，模型、Agent 制品从相应环境获得 |
| 现有 Web | 沿用主题变量、三栏布局、头像与工具展示；文件、Git 和 Trace 的迁移边界明确 |

## 初版简化原则

- 建议一台应用服务器、一个 Java 常驻应用，连接一份 TDSQL MySQL 业务库；执行模块在同一 JVM 内，Agent 通过 ACP 子进程执行。
- 先支持一个共享工作区，初始化普通用户和工作区成员记录；成员能查看、续聊和交接该工作区的会话，成员能力相同，不设置用户角色。
- 同一会话一次执行一个 Agent 请求，后来的请求排队。用户看到已保存、排队、执行中和完成的区别。
- 页面选择、滚动和未发送草稿属于个人；共享消息、交接、引用与执行状态属于工作区。
- 登录先使用预置账号建立演示会话，访问范围按数据库中的成员关系判断；保留请求去重和持久化，采用固定默认行为。
- 优先利用 Lody 的引用交互、会话职责和 ACP 适配器；现成 TypeScript 同步服务作为参考，不因下载了示例就额外增加一套线上业务后端。

## 首版边界

首版“在自己电脑继续”表示在各自浏览器访问共享会话，执行默认留在服务器。把运行中的 Agent 搬到开发本机、实时同步整个代码目录、跨 Agent 转换私有检查点另行设计；不能由交接动作暗中触发。

不追求 Lody 的计费、移动原生应用、GitHub 云集成、端到端加密、离线共同编辑和多机器调度全部对齐。Loro 与具体云产品的使用是技术选择，不等于功能验收目标。

当前不开发真实人员认证、注册、找回密码、统一登录或复杂授权体系。用户、工作区关系和消息作者参考 Lody 的独立接口设计；未来内网登录替换身份来源时保留内部用户 ID，不改写既有会话、作者和交接记录。

Claude 或 Codex 作为第二后端的真实接入验证应在后续 Spec 明确停点。首演优先完成共享交接主链，不能只用 mock 声称第三方 Agent 已接通。

## 验收场景

1. 用户 A 使用 `user01` 创建会话，用户 B 在另一台电脑使用 `user02` 登录后看到相同历史与发言账号。
2. 用户 A 填写说明向用户 B 发起交接，状态为待接手且当前接续人不变；用户 B 确认后才更新接续人，时间线记录两步，不检查岗位。
3. 用户 A 关闭浏览器并关闭电脑，用户 B 继续在原会话提问；Agent 能回答先前确认的内容。
4. 用户 B 通过 @引用另一会话或具体消息，预览时生成固定快照；来源继续输出也不自动改变引用，历史与模型实际收到的内容和预览一致。
5. 两个成员同时发送不同问题，两个输入各保存一次并依次执行；重复点击或网络重试不产生重复提问。
6. 两端刷新或重连，消息与交接状态恢复；页面切换不打断 Agent。
7. 重启服务后已保存历史仍可读；支持恢复的后端能够继续原会话。中断中的执行有明确状态，不自动重复执行未知结果的操作。
8. 未建立演示会话时不能读取工作区正文；已登录账号仅访问其预置成员关系允许的工作区，不能通过修改 ID 越过范围。
9. 外网演示有部署说明、启动方式和两账号演示步骤；内网采用同一程序，环境差异有明确清单。
10. 对照现有 Web 回归清单验证颜色变量、对话工具、文件页签、Git 和可用的 Harness Trace；缺少内网 SDK 的外部环境不伪造生产轨迹。
11. Java 服务通过同一 ACP Client 链路接入真实 Harness 与选定的第二后端；模型循环继续由对应 Agent 负责，不依赖一套额外的 TypeScript 业务服务才能启动。
12. SSE 断线和历史切换不漏消息或重复显示；同一审批只接受一次有效回答；同一执行目录的 Agent 与人工 Git 写操作按统一规则协调。
13. 在目标 TDSQL 上验证迁移脚本、消息与引用原子保存、请求 ID 唯一约束和并发状态更新；如外网使用匹配版本 MySQL 演示，不把该结果当作 TDSQL 已验收。
14. 初始化创建 `user01`、`user02`、`user03` 普通用户，不含岗位/业务角色字段；重复初始化不新增重复账号或改变原用户 ID；切换账号后新发言归属新账号，旧记录不改。
15. 同一会话只允许一笔待接手交接；取消与接手并发时仅一次有效状态变化，重复请求不再追加事件，已取消交接不能被旧页面接手。
16. 刷新引用产生新草稿并重新预览；发送前来源不可访问时明确阻止发送。已发送快照不因来源后续变化被改写。
17. 逐行核对顶层设计中的功能迁移表：文件阅读、中央页签、Git 勾选/提交/推送、设置和 HC-191 全部 Trace 呈现均有目标模块及回归证据；标准 ACP 未提供的能力采用明确平台/扩展端口。

- 首版工作区内全部会话对成员共享，暂不加入会话私有权限，是否满足使用范围。
- 首演使用的外部模型与真实 Agent；第二 ACP 后端选择 Claude 或 Codex，以及是否同场演示。
- 真实登录明确留待内网阶段开发；当前保留身份接入点，不把内网登录作为外网调试的前置条件。在个人电脑执行代码另行设计。
