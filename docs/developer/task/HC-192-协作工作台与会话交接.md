# HC-192 协作工作台与会话交接

## 需求来源与阶段

2026-11-05，用户明确提出：将 Web 抽为独立的上层工作台，原 Harness Code 成为通过 ACP 接入的一种 Agent 实现，并能继续接入 Claude、Codex 等实现。初版对齐本地 Lody 的主要协作能力，优先共享上下文对话、交接和 @引用。

交接表示用户之间接续同一个会话：用户 A 先讨论并确认已有结论，用户 B 在自己的电脑打开同一个会话，继续后续讨论与工作。账号以用户为维度，不预设岗位或业务角色，交接不要求某种岗位组合。

用户随后要求按大功能流程先出设计文档，并补充：初版必须能够在外网演示，可以准备服务器；最终仍需迁入内网；实现优先简单直接，允许后续迭代，不增加大量防御性配置。此前“跳过 Skill 调用”的要求继续适用于本任务，正式文档与评审步骤保留。

团队 Java 开发者更多，云端技术栈使用 Java；数据库使用内网现有的 TDSQL MySQL 兼容版。在已核对的 Lody / Loro 公开源码与示例基础上尽量利用已有实现，项目文档统一引用公开固定提交，不依赖某位研究者的本机下载目录。

2026-11-06，用户进一步要求把 Web 升级为类似 Lody 的 Windows/macOS 桌面产品，并确认“本机执行、云端共享会话”。本稿据此替换原先的浏览器产品入口与服务器默认执行方案。桌面选用 Electron 承载现有 React，TypeScript 本机执行器管理 ACP、文件、Git 与 Trace，Java 继续负责云端业务、排队和设备派发；不再由云端 JVM 启动用户电脑上的 ACP 子进程。具体依赖版本、传输方式与架构契约仍需后续规格评审。

同日补充架构约束：本分支视为与 master 独立演进的新项目，产品入口只保留桌面，不再保留原 TUI 或独立 Web。Lody 相关新增逻辑按职责抽为独立包，平台与 Harness 内核分开；Harness 是通过 ACP 接入的底层 Agent 实现之一。原稿保留 TUI 入口、把协作类型加入旧 packages/protocol 的建议随之取消。当前仍在原仓库编写设计，不据此新建仓库、切分支或修改 master。

登录与访问范围先由数据库中的预置普通用户和工作区关系提供，默认创建几个用户账号供登录调试；内网登录系统到内网阶段再开发。首版不增加岗位字段、角色分配或用户权限管理后台。具体设计采用 `user01`、`user02`、`user03`，名称不代表职责或等级。

2026-11-06，用户认可当前需求与总体架构方向，要求先提交本版设计，再生成任务。HC-192 作为总 Task 进入子任务拆分；具体 Spec、接口、版本与实施计划尚未评审，实现尚未认领。任务拆分不代表直接开始生产开发，各子任务继续按根目录 [AGENTS.md](../../../AGENTS.md) 的 Task → Spec → Plan → Todo → implement → review 推进，既有跳过 Skill 调用要求保留。

## 用户能得到什么

    用户 A 在自己的电脑注册项目并共享 → 本机 Agent 讨论问题 → 交给用户 B
    用户 B 在另一台电脑的桌面端登录 → 打开原会话 → 继续操作原执行机器上的 Agent
    讨论需要其他结论 → @选择原对话或消息 → 查看引用内容 → 带入当前问题

大家查看同一条云端会话历史；每条发言保留对应用户账号。执行机器、项目目录和 ACP 会话在交接前后不变。关闭桌面窗口进入后台不终止本机执行；退出执行器、关机或休眠则不能继续本机任务，已同步历史仍可阅读。原方案“A 关机后 B 仍能执行”的验收不再适用于本机执行模式。

## 初版简化原则

- 建议一台云端应用服务器、一个 Java 常驻应用和一份 TDSQL MySQL；每台执行设备运行同一种 TypeScript 执行器，不在桌面另装 Java 业务服务。
- 先支持一个共享工作区和预置普通用户；成员能力相同，不设置岗位角色。本地项目经设备所有者明确共享后，成员才可操作其中的共享会话。
- 同一会话一次执行一个 Agent 请求，后来的请求排队。用户看到已保存、排队、执行中和完成的区别。
- 页面选择、滚动和未发送草稿属于个人；共享消息、交接、引用与执行状态属于工作区。
- 登录先使用预置账号建立演示会话，访问范围按数据库中的成员关系判断；保留请求去重和持久化，采用固定默认行为。
- 执行器主动连接云端接收命令并回传结果；建议桌面业务走 HTTPS + SSE，执行器走出站 WSS。标准 ACP 只在执行器和本机 Agent 之间使用。
- 优先利用 Lody 的桌面分层、进程托管、引用交互与 ACP 适配器。TypeScript 执行器只负责宿主执行，不建立第二套云端业务或同步服务。
- 当前分支按独立产品演进，不为与 master 保持相同入口/内部 API 而保留旧代码；不自动同步、合并或修改 master。
- 旧界面与文件/Git 代码可迁出复用，迁出后只依赖新公共契约；不以跨目录 import 或代理旧 InteractiveController 的方式表面分包。

## 独立项目与依赖边界

    Electron + React 工作台 → Java 协作服务 → 通用本机执行器 → ACP → 任一 Agent
    本机文件/Git → 独立项目服务；Harness Trace/专有设置 → 独立 Harness 集成包

新包不导入旧 CLI、InteractiveSnapshot、Harness Thread/Run/SQLite 结构或私有 JSON-RPC 类型。共享 HTTP/SSE/设备协议使用新契约包；标准 ACP 直接使用 SDK。Harness ACP 适配只把协议映射到原内核，用户、设备、工作区、交接和 @引用业务均不写入 Python 内核。

Harness 专有 Trace 与设置由独立集成包通过通用扩展接口注册；未安装该包时通用聊天、协作、文件/Git 仍可运行。可选扩展的关闭不会减少选用 Harness 时应保留的 HC-191 功能，完整功能矩阵仍需逐项回归。包的职责与依赖方向见顶层设计第 4 节，具体名字在 Spec 固定。

## 首版边界

首版“在自己电脑继续”表示在接手人的桌面界面操作原执行机器。交接不会复制仓库、搬迁未提交修改、迁移运行中的进程或转换私有检查点。需要常在线执行时，可在常在线机器托管同一执行器；这属于显式选择执行位置，不自动把离线任务转到其他设备。

桌面端是唯一图形产品入口。React 浏览器技术用于渲染、开发预览与测试，不形成独立 Web 交付，也不保留原 TUI 产品或 `/web` 接管流程。无界面 Runner 是设备执行进程，不提供旧 TUI 功能。网络断开时可读已同步历史并保留草稿；首版不做离线协作发送。新执行需云端确认，既有任务按实际持久记录恢复/补传。

不追求 Lody 的计费、移动原生应用、GitHub 云集成、端到端加密、离线共同编辑和多机器调度全部对齐。Loro 与具体云产品的使用是技术选择，不等于功能验收目标。

当前不开发真实人员认证、注册、找回密码、统一登录或复杂授权体系。用户、工作区关系和消息作者参考 Lody 的独立接口设计；未来内网登录替换身份来源时保留内部用户 ID，不改写既有会话、作者和交接记录。

Claude 或 Codex 作为第二后端的真实接入验证应在后续 Spec 明确停点。首演优先完成共享交接主链，不能只用 mock 声称第三方 Agent 已接通。

## 验收场景

1. 用户 A 在桌面使用 `user01` 登记本机项目并明确共享后创建会话；用户 B 在另一台电脑使用 `user02` 登录后看到相同历史与发言账号。
2. 用户 A 填写说明向用户 B 发起交接，状态为待接手且当前接续人不变；用户 B 确认后才更新接续人，时间线记录两步，不检查岗位。
3. 用户 A 关闭桌面窗口但保持本机执行器在线，用户 B 可在原会话续聊；A 的机器关机/休眠后，B 可读云端历史但执行入口明确不可用。恢复在线后仍绑定原项目与 Agent 会话，不自动重跑结果未知的操作。
4. 用户 B 通过 @引用另一会话或具体消息，预览时生成固定快照；来源继续输出也不自动改变引用，历史与模型实际收到的内容和预览一致。
5. 两个成员同时发送不同问题，两个输入各保存一次并依次执行；重复点击或网络重试不产生重复提问。
6. 两端重开窗口或重连，消息与交接状态恢复；切换页签不打断 Agent，显式退出和后台运行有明确区别。
7. Java 服务或执行器分别重启后可恢复已保存历史与绑定；支持恢复的 Agent 能继续原会话。已派发但结果未知的任务显示待确认，不自动重跑；执行器重连不接受第二份相同输入。
8. 未建立演示会话时不能读取工作区正文；已登录账号仅访问其预置成员关系允许的工作区，不能通过修改 ID 越过范围。
9. 外网演示有部署说明、启动方式和两账号演示步骤；内网采用同一程序，环境差异有明确清单。
10. 对照现有 Web 回归清单验证颜色变量、对话工具、文件页签、Git 和可用的 Harness Trace；缺少内网 SDK 的外部环境不伪造生产轨迹。
11. 本机执行器通过同一 ACP Client 链路接入真实 Harness 与选定的第二后端；模型循环继续由对应 Agent 负责。Java 不接管用户电脑上的 stdio，也不依赖额外的 TypeScript 云业务服务。
12. 桌面 SSE、执行器 WSS 分别断线后可补齐记录，不漏消息或重复执行；同一审批只接受一次有效回答；同一设备同一目录的 Agent 与人工 Git 写操作按统一规则协调。
13. 在目标 TDSQL 上验证迁移脚本、消息与引用原子保存、请求 ID 唯一约束和并发状态更新；如外网使用匹配版本 MySQL 演示，不把该结果当作 TDSQL 已验收。
14. 初始化创建 `user01`、`user02`、`user03` 普通用户，不含岗位/业务角色字段；重复初始化不新增重复账号或改变原用户 ID；切换账号后新发言归属新账号，旧记录不改。
15. 同一会话只允许一笔待接手交接；取消与接手并发时仅一次有效状态变化，重复请求不再追加事件，已取消交接不能被旧页面接手。
16. 刷新引用产生新草稿并重新预览；发送前来源不可访问时明确阻止发送。已发送快照不因来源后续变化被改写。
17. 逐行核对顶层设计中的功能迁移表：文件阅读、中央页签、Git 勾选/提交/推送、设置和 HC-191 全部 Trace 呈现均有目标模块及回归证据；标准 ACP 未提供的能力采用明确平台/扩展端口。
18. Windows x64、macOS arm64/x64 分别验证安装/升级、窗口、浅深色、缩放、中文与空格路径、Agent 启停、取消和文件/Git；支持的系统最低版本与各后端平台限制在 Spec 明确。
19. 用户 B 的文件预览、Git 提交与推送落到会话绑定的原机器，不读取或修改 B 电脑的同名目录；复制会话链接不会单独授予设备/项目操作权。
20. 新设备仅由本机用户登记并选择项目；未共享项目无法被其他成员浏览或执行。停止共享后拒绝新的远端读写，正在执行的任务保留真实状态并由设备所有者处理。
21. 执行器连云断开但本机 Agent 未退出时，界面显示设备失联/状态待确认；持久化事件在重连后按稳定 ID 补传，不把断线直接当作完成或再次派发原请求。
22. 内网安装与更新使用预先准备的目标平台制品，不要求首次启动访问公网下载；桌面安装包不包含真实账号会话、设备凭据、模型密钥或个人项目。
23. 新产品安装、启动、构建和发布不启动或打包旧 TUI/Web server/接管网关，依赖树不再要求 Bun/OpenTUI；原界面的可用组件迁出后不回引 packages/cli。
24. 不启动或不安装 Harness/Python，桌面、Java 和通用 Runner 仍可用 mock ACP 完成协作协议验证，并可真实接入选定的第二 Agent；前者不替代后者验收。
25. 新公共契约与通用包没有 Harness Thread/Run/数据库/JSON-RPC 类型或跨源码 import；依赖检查能拦截回引旧 CLI、集成包和内核的错误边。
26. 移除 Harness 集成包后通用协作、文件/Git 仍可启动；安装并选用 Harness 后通过扩展恢复其设置与完整 HC-191 Trace，云端不解析 SDK marker，通用 UI 不硬编码 Harness 判断。

## 待评审的建议

- 独立桌面项目、移除 TUI/Web、与 Harness 解耦已明确；Electron、Java/TDSQL 与本机执行方向保留，包名、扩展接口、依赖版本和传输契约在 Spec 细化。
- 建议首版覆盖 Windows x64、macOS arm64/x64；项目明确共享后向工作区成员开放其共享会话，暂不增加复杂角色与逐人授权界面。
- 首演使用的外部模型与真实 Agent；第二 ACP 后端选择 Claude 或 Codex，以及是否同场演示。
- 真实登录明确留待内网阶段开发；当前保留身份接入点。公开演示分发的签名条件、Mac 公证与内网手工升级材料在打包停点前核对。

这些问题不阻止本轮交付设计草案；涉及的推荐选择尚未成为实现契约。
