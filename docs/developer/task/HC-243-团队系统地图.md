# HC-243 团队系统地图

## 当前阶段

2026-11-20 用户确认：仓库作用与调用关系由任何成员提议、管理员审核，并且应能由 AI 自己生成与进化。2026-11-23 补齐交互呈现能力：增加“交互式仓库依赖拓扑图 ↔ 列表”切换、节点一键拉起多目录会话以及证据路径直达本机文件面板。待认领，排在 HC-241、HC-242 之后。

## 要解决的问题

- Workspace 仓库登记只有名称、远端地址和默认分支（`RepositorySummary`），没有“这个仓库做什么、和谁有关系”。
- HC-233 的本机 `team.md` 让每个人的 Agent 积累工程用途与关系，但它只在个人本机，不共享、不审核，每个人各自从零积累，结论可能互相矛盾。
- 新人或新会话缺少全局视角，Agent 无法知道改接口时还要动哪些仓库；纯文本表格也难以直观理解上下游调用拓扑并直接发起多仓库开发。

## 预期使用过程

```text
触发：登记新仓库 / 成员手动“分析仓库关系” / 会话中 Agent 发现代码调用与地图不符
  → 本人 Agent 在本机分析 personal.md 中已有本地副本的团队仓库：
     依赖清单（package.json / pom.xml / go.mod 等）、proto / OpenAPI 及引用方、调用配置与客户端代码、README
  → 生成提议：仓库作用说明、仓库间关系（依赖 / 调用 / 共享契约），每条附证据文件路径
  → 管理员审核（复用 HC-241）→ 发布新版本
  → 成员 team.md 以该版本为权威来源之一；HC-242 的附加目录建议使用它
  → 成员在“系统地图”页切换拓扑图/列表视图，点击节点查看详情与规约，点击证据路径直达本机代码，或一键拉起多目录会话
```

## 已确认的范围

1. 系统地图属于 Workspace，带版本，成员可读。已确认作为团队知识的一种类型，复用知识的版本、HC-241 的审核与 HC-233 的读取工具，不另建服务端对象（HC-233 也写明共享的工程别名通过团队知识库提供）。
2. 任何成员可提议，管理员审核发布，复用 HC-241 的提议与审核界面。
3. AI 生成在提议人本机完成；每条关系必须附证据文件路径，无证据的推断标为“推测”。
4. 只分析提议人本机已有的仓库；提议只增改其覆盖的部分，不删除未覆盖仓库的已有关系。
5. 与 HC-233 `team.md` 衔接：在 HC-233 的条目来源中新增“系统地图版本”，已发布地图作为 `team.md` 的权威来源之一；`team.md` 中积累而地图尚无的事实可一键整理为提议；冲突时以地图为准并提示发起修订。需同步修订 HC-233 第 7.2 节的合并依据。
6. **交互式依赖拓扑图与动作联动**：系统地图页面提供“可视化依赖拓扑图 ↔ 列表”双视图切换；选中仓库节点显示用途、负责人、关联规约与本机克隆状态（来自 `personal.md`），支持一键将该仓库与本机已克隆的上下游依赖组合发起多目录会话（联动 HC-242）；点击提议或已发布关系中的证据文件路径且本机存在对应仓库副本时，直接在右侧本机文件面板打开定位对应文件。
7. 系统地图只是参考资料，不授予仓库访问权限。

## 职责与前置

- 本卡全栈实施：服务端（`contracts/` + `server/` + `packages/collaboration-client/`）负责系统地图存储、版本与审核查询接口；桌面端负责分析发起、提议编辑、拓扑图渲染与动作联动、证据直达及 `team.md` 衔接。
- 依赖 HC-241 的审核流程、HC-242 的多目录会话与 HC-240 的管理员角色。
