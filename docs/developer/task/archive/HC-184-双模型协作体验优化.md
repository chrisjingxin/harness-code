# HC-184 双模型协作体验优化

## 背景与目标

用户反馈“一句话需求也反复派单失败”和“占用要切回旧会话手动恢复、取消”。已授权全面排查、优化实现，并沿用此前同步编写、运行测试的要求。继续在当前 dev_wdl 分支开发，保留已有修改。

源码确认的问题：

1. Lead 必须自行填写逐字引用的 user_requirements，转述或加入实施步骤就整单拒绝。
2. Sidekick 等待模型时取消，即使执行已退出，派发记录仍可能停在 dispatched，造成结果不明。
3. 暂停、受阻的任务在没有未停操作时仍持有目录；重复查询未知状态还不断增加版本。
4. 占用处理指向旧会话，多条命令和错误码使用户难以完成恢复。
5. 多 Host 的查询和同时继续会干扰同一任务，需分别管理运行归属与目录写者。
6. 中断后的 checkpoint 与上一完整轮不一致，需要受控续接，不能把半轮历史当成完整记录。
7. 命令结果不明后仍可能请求模型、补报告，造成长时间反复失败；待查清单还混入已停止派发。
8. 旧运行、旧取消或恢复响应可能影响新任务，需要终态和异步身份保护。

## 单一可演示停点 A

实现、验证并交付一次完整流程：短需求 → Sidekick 改码 → 可观察过程 → 中断并安全停止 → 新任务直接使用目录；确有占用时，在当前会话处理后继续。此停点包含下面全部验收项，不在中途交付只有提示的半条链路。

- 程序从保存的原始用户消息生成需求条目，Lead 只填写实施内容。
- 普通取消、模型错误的已停止执行不遗留派发不明记录；真正未确认停止的操作继续拦截。
- 暂停或受阻的安全任务自动让出目录，恢复审阅时重新取得目录并验证文件。
- /fusion resolve 在当前对话结束占用任务；结果不明时同处使用 --stopped 核查说明。
- 取消和核查原子提交；保留已有文件；版本变化、其他项目与新占用者不会被误处理。
- 恢复沿用上个完整 Sidekick checkpoint；第一轮中断可在保留文件后重建执行上下文。
- 参数错误给出字段和修正办法，连续同类错误有限停止；Lead 禁写、路径、检查与逐项审阅仍有效。

## 实施结果与审查

| 用户遇到的问题 | 已实现的处理 |
| --- | --- |
| 一句话需求反复报原文引用无效 | 从 source_message 自动生成完整引用，移除模型的 user_requirements 参数。 |
| 模型等待时取消、断流后一直占用 | Native 执行退出后按准确执行身份记录停止，安全暂停任务自动让出目录。 |
| 两窗口查询或继续互相干扰 | 运行归属与目录写者分别管理；查询不暂停其他 Host，旧清理不能影响新 Run。 |
| 准备成功但受理失败留下空任务 | on_abandon 清理归属；新空任务取消，已有任务暂停并保留。 |
| 中断后无法继续、误用半轮历史 | 恢复上一完整 checkpoint；首轮无完整记录时保留文件和任务单后重新准备。 |
| 需要回旧会话、多次恢复取消 | 当前会话 resolve；cancel/resolve --stopped 在同一事务核查并结束准确任务。 |
| 命令结果不明后反复执行、补报告 | 两角色立即结束模型循环；保留未知命令和写者，清除已停止派发的过期提示。 |
| 取消后旧回调复活任务、旧响应覆盖新任务 | 终态不可反向更新；过期执行结束；界面检查 Thread、Task 和版本。 |
| 原始错误难理解、重复猜参数 | 参数错误带字段和修正方法；相同控制错误三次停止；断流说明保留文件及继续方法。 |

审查结论：沿用现有 Host、RunCoordinator、ManagedAgentExecutor 和 Store；未建立另一套执行器或状态库。取得写者和阶段更新在短事务中完成，网络、模型和审批不在事务内等待。Lead 权限、路径范围、写者代号、可信检查、逐项审阅仍在真正工具与验收边界校验。

删除的内部参数已迁移全部调用和测试，没有保留别名。新增停止说明只来自用户显式输入，保存摘要，不由模型生成。跨窗口退出、迟到 Worker 返回、准备失败、真正未知命令均有回归；真实的未停操作不会按时长、PID 或模型声明自动放行。协议生成源包含共享正反例，生成物由统一脚本生成，维持未发布的 v3.11，不增加表、依赖或版本号。
