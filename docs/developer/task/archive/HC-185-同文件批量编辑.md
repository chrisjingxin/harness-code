# HC-185 同文件批量编辑

## 需求来源与当前阶段

2026-10-22，用户反馈测试时 `edit_file` 频繁失败。10-20 至 10-21 的日志统计为 15 次成功、19 次失败，失败原因是 `COMMIT_CONFLICT` 15 次、`STALE_FILE` 3 次、`UNREAD_RANGE` 3 次，没有一次是文本匹配失败。调研了 8 个开源 Coding Agent，结论与方案对比见 `tmp/handoff-edit-file-conflicts.md`。用户已于 2026-10-22 确认：先做方案 A；`edit_file` 接受改为嵌套 `edits[]` 且不保留旧参数；评测先用 mock replay，不调用真实企业模型；方案 B（服务端自动顺延自己造成的过期）等 A 上线后看数据再决定。

当前阶段：实现、测试、Review 与多轮实测验收均已完成。

## 通俗说明

现状：模型常在一轮里对同一个文件连发 3 到 8 个 `edit_file`，它们带着同一个"文件版本凭证"（`snapshot_id`）。第一个编辑成功后，文件变了，凭证作废，后面的编辑全部被拒，并且每个编辑还各弹一张审批卡片。

做法：让一次 `edit_file` 调用就能带上多处修改。

```text
输入：file_path + snapshot_id + edits[{old_string, new_string}, ...]
→ 每处都在同一份读到的内容里做精确唯一匹配
→ 检查各处互不重叠，且都在模型读过的范围内
→ 全部通过：一次写入、一张审批卡片、返回一个新 snapshot_id
→ 任何一处不通过：整批都不写，并指出是第几处、什么原因
```

改后收益：同文件多处修改只需一次调用，不再自己和自己冲突；审批卡片从 N 张减为 1 张（与 HC-146 方向一致）。

## 范围

- `edit_file` 参数改为 `file_path`、`snapshot_id`、`edits[]`；单次编辑是只有 1 个元素的 `edits[]`。
- 批内匹配规则沿用 HC-131：精确匹配、必须唯一、不做模糊匹配。
- 批内任一处失败整批零写入，错误里带上失败项序号。
- 审批摘要与 diff 展示合并为一张卡片。
- 在 `packages/agent/evaluations/zc133/` 增加字符串型 `edits[]` 候选及"同轮多编辑"场景，评测结论写入 `弱模型文件编辑评测.md`。
- 工具描述写明：同一文件多处修改放进同一次调用；跨调用继续编辑须使用上一次返回的 `snapshot_id`。

## 非范围

- 不做服务端自动顺延自己造成的过期（方案 B）。
- 不做模糊匹配、`replace_all`、按行号 range（HC-131 的既有决定不变）。
- 不改全局写锁（执行阶段已串行，调研确认与业界一致）。
- 不调用真实企业模型评测，除非用户之后另行明确允许。

## Spec 已回答的问题（详见 Spec）

- 批内编辑重叠、空 `edits[]`、超过条数或字节上限时的错误码与文案。
- 编辑成功后返回的新快照要带回多少上下文，才能缓解 `UNREAD_RANGE`（3 次）。
- 评测中"弱模型对嵌套结构出错率"用什么 mock 变体衡量，通过线是多少。
- `approval_preflight`、审批描述、两阶段提交三处如何共用同一份批量 prepare 结果。

## 验收标准

1. 回放 Run `1327ba32` 中"一轮 8 个 edit_file"的场景，改为一次 `edits[]` 调用后全部成功，只出现一张审批卡片。
2. `edits[]` 中第 K 处匹配失败或与其他处重叠时，文件内容与调用前逐字节相同，错误指出第 K 处。
3. 提交后返回新 `snapshot_id`，用它再发起下一次 `edit_file` 成功。
4. zc133 评测中，字符串型 `edits[]` 候选的 silent corruption 为 0，结论与数据写入研究文档。
5. 代码库中不再存在扁平 `old_string/new_string` 的 `edit_file` 入参、校验与测试。
6. Python 全量测试、CLI 测试、`npm run project:check` 通过；`docs/user/` 与架构文档已同步。
