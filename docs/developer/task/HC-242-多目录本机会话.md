# HC-242 多目录本机会话

## 当前阶段

2026-11-20 用户确认多仓库开发采用“一个 Agent，一个主目录加附加目录”。2026-11-23 补齐冷启动体验：增加由用户主动选择本机代码根目录并一键扫描 Git remote 批量初始化 `personal.md` 的能力。待认领，依赖 HC-239 的个人会话模型与 HC-233 的本机记忆。

## 要解决的问题

企业里一个系统由多个服务仓库组成，开发一个功能常要同时改调用方、被调用方和共享接口定义。现在一个会话只绑定一个工作目录，Agent 看不到相关仓库，用户只能选一个共同上级目录凑合，Agent 也不知道这些仓库之间的关系；同时新人面对十几个团队仓库，逐一手动建立本机路径映射冷启动成本太高。

## 预期使用过程

```text
冷启动（可选）：
  加入团队或新建多目录会话 → 点击“扫描本机代码目录”并选 ~/code
  → 读取各子目录 Git remote，与 Workspace 仓库清单对比 → 列出候选映射 → 用户确认后批量写入 personal.md

发起多目录会话：
  选择主目录 ~/code/order-service
  → 按实际 Git 配置识别为团队仓库 order-service（写入或核对 personal.md）
  → 查系统地图 / team.md：依赖 common-proto，被 pay-service 调用
  → personal.md 中 common-proto 有本机路径，pay-service 没有
  → 提示“order-service 依赖 common-proto，要一起加入吗？”；pay-service 显示“本机未克隆”
  → 确认后：一个 Agent，主目录 + 附加目录；首轮带上仓库清单与关系
```

## 已确认的范围

1. 会话 = 一个主目录 + 零到多个附加目录，由同一个 Agent 访问。
2. 使用 ACP 标准 `additionalDirectories`（`packages/acp-runtime/src/session-setup.ts` 已支持传递并在能力缺失时诊断）。
3. Agent 未声明附加目录能力时，明确提示只能访问主目录，用户可改选共同上级目录作为主目录、换用支持的 Agent，或在目标仓库新建会话并带上引用继续（HC-233 第 6.1 节的做法）；不做符号链接等静默替代。
4. 本机目录与团队仓库的对应直接使用 HC-233 的 `personal.md`，不另建映射存储。写进 `personal.md` 只记录仓库在本机的位置，不会自动加为附加目录；加入附加目录需用户确认（沿用 HC-233 对“关联本机目录”与“会话起始目录”的区分）。
5. **本机代码根目录一键扫描初始化 `personal.md`**：由用户主动发起并选定根目录（避免后台全盘扫描带来隐私顾虑），桌面主进程仅在选定目录的有限层级内读取 `.git` 远端信息，匹配 Workspace 仓库目录后交由用户勾选确认，再批量写入 `personal.md`。
6. 附加目录建议来源：已发布的团队系统地图（HC-243）；未发布前使用本机 `team.md` 中的关系。
7. 会话记录涉及的团队仓库（契约已有 `ConversationRepositoryItem`），用于知识适用范围匹配和 Project 简报展示。
8. 从 Project 内新建会话时，建议本机已对应的 Project 关联仓库。
9. 本机未克隆的仓库只提示，不跨机器读取实时文件。仓库读写权限仍由 Git 托管平台决定。

## 不在本卡范围

- 多仓库各自建 worktree 隔离、跨仓库关联 PR、每仓库一个 Agent 的编排。
- 系统地图本身的生成与审核：HC-243。

## 职责与前置

- 桌面负责目录选择、建议、能力提示与会话装配；附加目录目录授权沿用现有本机目录授权端口。
- ACP 通用接线如需调整，与通用 ACP 维护方确认具名接点，不新增专用 ACP 方法。

## 待定问题（Spec 阶段确定）

1. 会话进行中能否增删附加目录，以及对原生会话恢复的影响。
2. 附加目录数量上限。
