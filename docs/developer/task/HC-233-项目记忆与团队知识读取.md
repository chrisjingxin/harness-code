# HC-233 项目记忆与团队知识读取

## 当前阶段

2026-11-20 用户确认沿用 HC-233，将原团队知识自动索引与读取、本机项目记忆及跨机引用解析合为一份设计。编号继续使用 HC-233，统一行为以[同名 Spec](../spec/HC-233-项目记忆与团队知识读取.md)为准。当前状态为待认领，本文记录审阅范围。

2026-11-19 的[团队知识源码调研](../research/233-团队知识按需上下文.md)保留固定提交证据，供统一设计中的知识发现与按需读取部分使用。项目记忆新增范围按本次确认的行为推进。

2026-11-23 用户确认两份文档按类似 AGENTS.md 的简短概览维护，每轮完整附带有效正文，删除按相关性挑选工程的方案。篇幅在生成和更新阶段控制，同时保留已确认的 AI 更新时机、256 字节提醒上限与轻量工具卡反馈。本次恢复本地设计并整合远端新旅程，保留 HC-241 踩坑分工，明确个人会话、多目录与地图的后续接点。以下是本卡待实施的机制，当前尚未交付 MD 自动更新能力。

## 要解决的问题

用户需要反复手动引用团队知识，Agent 容易遗漏规约。跨机引用中，A 的工程名、相对目录和口语表达，也难以直接对应 B 的本机副本。

桌面为每个账号、Team 维护两份本机项目记忆，同时自动提供用户维护的知识标题。当前 Agent 读取相关材料、判断工程和任务所需规范，缺信息时询问用户，并通过工具保存本轮获得的新事实。

## 已确认的首版范围

1. **团队知识发现与读取**。现有标题目录自动附带，正文按需读取固定版本。知识规约按任务相关性使用，工程定位成功后也能读取相关规范。
2. **知识列表共享刷新**。A 保存知识后，同团队 B 的列表和候选沿现有通知更新。Agent 已取得的材料保留其来源版本。
3. **两份简短本机 Markdown**。`team.md` 概括团队工程、用途、关系和仓库，`personal.md` 概括本人的目录、副本与团队工程对应关系。按服务实例、账号和 Team 隔离，每轮完整附带两份有效业务正文。
4. **统一上下文与工具服务**。标准 ACP 文本附带 Skill 式说明、两份完整正文及知识标题。由同一个本机 MCP 服务提供两种记忆工具和两种知识只读工具；记忆查询用于核对最新条目、来源和版本，模型推理沿用当前 Agent。
5. **跨机引用解析**。保留共享原文，B 的 Agent 结合 B 自己的资料理解工程。缺失或冲突时查知识，再询问用户或请用户选择本机目录。
6. **记忆更新与纠正**。每轮附带更新指引，Agent 发现新增或被纠正的项目事实时，在结束回复前提交更新提案；桌面在成功轮次结束后合并。用户确认的目录立即保存，条目版本、原子写入和重复提案处理保证更新结果一致，失败返回实际状态。
7. **现有交互复用**。使用当前引用、目录选择、工具卡和知识页展示，区分关联工程副本与变更会话起始目录。更新状态通过轻量工具卡反馈，默认显示用户能理解的变更摘要，展开可看文件与条目详情。额外目录访问沿用实际 Agent 能力和授权。

## 简短正文与完整注入

两份文档使用普通 Markdown 概括当前工程信息，每个工程保留简短用途、关系、必要的仓库地址及本人目录。技术维护字段放在文件头，由工具管理。每轮发送和恢复后发送时，桌面在当前账号、会话所属 Team 和权限范围内，完整附带两份业务正文，由 Agent 理解哪些工程与当前需求有关。

发送端不按提问关键词、当前目录或当前 Project 筛选、裁剪工程。两份正文合计 8 KiB UTF-8 的上限用于生成和更新阶段的篇幅检查。Agent 精简重复描述，保留已确认的工程身份、关系、仓库地址与本机路径；超限时提示精简，保留原有效文件。文件不可读或总输入无法容纳完整正文时反馈实际状态。

团队知识库继续由用户维护，仍采用标题目录自动提供、正文按需读取；本机记忆查询工具用于核对最新记录和修订号。行为及正文示例见 [Spec 第 3、4 节](../spec/HC-233-项目记忆与团队知识读取.md#3-两份-markdown-记录什么)。

## AI 更新两份文档的时机与流程

**触发时机**：每次用户主动发送，包括恢复会话后的发送，桌面都附带固定更新指引。当前 Agent 在本轮处理需求时，比较已注入或查询到的记忆与本轮实际取得的信息。发现新增或被纠正的项目事实，就在结束本轮回复前调用更新工具；已有相同事实时保持原条目。

**提醒大小**：这段逐轮更新提醒使用固定精简模板，上限 **256 字节 UTF-8**，Spec 中的当前示例为 187 字节。工具参数与详细规则写入工具定义和桌面处理逻辑。记忆条目、知识目录等材料继续使用各自预算，并计入现有总输入上限。

| 本轮取得的信息 | 应更新的文档 |
| --- | --- |
| 确认工程名称、用途、别名、团队仓库地址、工程之间的关系 | `team.md` 中的对应 Project 或仓库条目。 |
| 确认本人的本机目录、相对路径、Git 远端及团队上游、工程对应关系 | `personal.md` 中的对应副本条目。其他人的原文路径只作线索，本人目录需实际核对或由本人确认。 |
| 用户纠正工程关系、重新选择目录或明确移除旧记录 | 更新或移除对应条目；用户在界面确认的目录和移除操作立即保存。 |

**实现流程**：当前 Agent 负责归纳并调用 `propose_project_memory_update`，提交新增、修改或移除的条目、已有条目版本和事实来源。工具校验后返回 `pending`，桌面将提案暂存在当前账号、Team、会话和轮次。收到本轮正常完成事件后，主进程复核身份、来源和条目版本，按条目合并，再原子写入对应 MD。成功保存后显示更新结果，下一次发送和查询使用新版本。

归纳与提案使用当前 Agent 本轮已有的模型。AI 写回以实际工具提案和文件写入结果为准；没有提案或没有实际变化时，不产生 AI 写入，也不递增修订号。本轮取消、失败或旧账号结果到达时丢弃尚未保存的 AI 提案，已经由用户确认并保存的目录继续有效。工具不可用、条目冲突或写入失败时展示实际原因。完整行为见 [Spec 第 7 节](../spec/HC-233-项目记忆与团队知识读取.md#7-ai-更新并发与失败处理)。

## 用户可见的更新反馈

沿用现有工具卡，由桌面依据提案和实际保存结果更新状态，模型无需在回答结束后额外追加更新播报。

- 提案已暂存时显示「准备更新项目记忆」，表示等待本轮成功完成。
- 实际保存成功后显示简短结果，例如「已记住账务工程的新目录」。展开可查看 `team.md` 或 `personal.md` 及变更条目。
- 保存失败时显示「项目记忆保存失败」，展开查看原因。取消、冲突或部分保存沿用真实结果展示。
- 没有提案或没有实际变化时不额外提示更新；成功提示仅在对应文件保存成功后出现。

## 设计交付与默认值

[统一 Spec](../spec/HC-233-项目记忆与团队知识读取.md)完整描述简短正文与维护字段、完整注入、身份范围、工具、知识刷新、跨机目录解析、写回时机和必要冒烟。独立本机记忆草案的正文迁入此 Spec。

首版默认逐轮更新提醒上限 256 字节，单条维护记录上限 4 KiB，两份 Markdown 业务正文合计上限 8 KiB，在生成和更新阶段检查，发送时完整附带。知识标题正文预算 8 KiB，显式记忆查询最多 10 条且完整结果最多 8 KiB。知识标题元数据第一页内存缓存 60 秒，更新通知使缓存失效。这些是实现常量。

## 验收与下一阶段

实施后演示 A 保存知识、B 看到并通过实际工具读取，随后 B 引用 A 的多工程对话、确认缺失目录、成功写回本机记忆并在下一轮复用。沿同一条必要冒烟主路径观察以下结果：

- [ ] 首次发送和恢复后的发送均完整附带当前账号、Team 的两份有效业务正文，其他工程不因当前 Project、工作目录或提问关键词不匹配而遗漏。
- [ ] 正文保持简短，生成和更新时检查合计 8 KiB UTF-8 上限，超限提案提示精简并保留有效文件；提醒正文不超过 256 字节 UTF-8。
- [ ] Agent 从本轮材料归纳新的工程用途或别名、确认本机副本，实际调用更新工具；分别观察 `team.md`、`personal.md` 的对应条目及来源。
- [ ] AI 提案先返回 `pending`，本轮正常完成后才保存；用户在界面确认目录则立即保存。下一次发送完整附带新正文，工具查询取得实际新版本。
- [ ] 轻量工具卡在暂存时显示准备更新，实际保存后显示变更摘要，展开可看文件与条目；失败展示实际原因，无变化时不额外提示更新。
- [ ] 本轮没有用户直接保存操作时，已知相同事实或没有工具提案的文件与修订号保持原样，界面反馈与实际保存结果一致。
- [ ] 顺带确认取消、失败、账号和 Team 隔离、条目冲突及写入失败时的结果，保留共享原文与固定引用。

设计阶段只检查文档、任务和样例一致性，当前运行证据仍按各既有 Task 记录。用户审阅后建立同名 Plan、Todo 并确认实施分工，必要冒烟完成后标待验收，完整组合验收沿用 HC-204。
