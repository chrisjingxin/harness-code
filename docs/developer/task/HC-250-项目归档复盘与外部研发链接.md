# HC-250 项目归档复盘与外部研发链接

## 当前阶段

2026-11-23 结合企业级协作闭环与知识自进化触发点拆解立项。待认领，认领后按 Spec → Plan → Todo 推进。

## 要解决的问题

- 团队项目上线结项后一直堆在活跃项目列表与看板中，导致左栏越来越长、成员难以聚焦在研事项；而直接删除又会丢失宝贵的历史决策与会话证据。
- 知识沉淀（HC-241）和系统地图进化（HC-243）在日常忙碌中常被遗忘，缺少一个在项目结束时“顺手完成复盘沉淀”的自然触发器。
- 企业内部的工作实际围绕需求单（Jira/TAPD/禅道）、Wiki 设计文档与 GitLab/GitHub MR/PR 展开，当前 Project 与 Task 缺少结构化的外部研发链接锚点，导致工作台变成信息孤岛。

## 预期使用过程

```text
项目推进中（外部链接锚点）：
  输入：在 Project 资料或 Task 表单填入需求单、Wiki 或 MR/PR 链接与类型标签
  输出：项目头部、看板卡片与任务详情页展示结构化外链芯片，点击直达企业对应系统

项目结项归档与复盘：
  输入：Workspace 管理员或 Project Owner 点击“归档项目”
  执行：
    1. 弹出轻量复盘引导：“项目即将归档为只读，是否顺便由本机 Agent 回顾本次会话与任务？”
    2. 若选择复盘 → 本机 Agent 汇总项目内已同步的结论、踩坑与新识别的仓库调用关系 → 起草 HC-241 经验提议或 HC-243 系统地图提议草稿（仍须人工确认提交与管理员审核）
    3. Project 进入“已归档”列表，停止新增执行与发布会话，历史数据与产物完整保留只读可查
  输出：活跃工作区清爽有序；项目经验自然沉淀为团队长期资产；必要时支持管理员解档恢复
```

## 已确认的范围

1. **Project 归档与解档恢复**：仅 Workspace 管理员或该 Project 的 `owner` 可触发归档与解档；已归档 Project 从主切换器活跃区移入折叠的“已归档项目”分组，内部会话、看板与 Task 全部进入只读态但可检索、可被跨项目引用（遵循原有成员可见权限）。
2. **归档即复盘引导（可选跳过）**：归档对话框提供非强制的一键“由本机 Agent 整理复盘提议”按钮，复用 HC-241 与 HC-243 的草稿提议机制，严禁在归档时自动跳过审核直接发布知识。
3. **结构化外部研发链接**：支持在 Project 资料与 Task 中挂接类型化的外链条目（如 `需求单`、`文档`、`代码变更/PR`、`告警/工单`），记录标题、URL（校验合法 `http/https`）、外部编号与可选手动/只读状态标记。

## 不在本卡范围

- 强绑定双向同步改造企业外部系统工作流（不强制替代 Jira/TAPD 成为全公司唯一需求管理库）。
- 单条个人会话的本地归档整理（属于个人会话列表交互细节）。

## 职责与前置

- 服务端（由后端同事维护）负责 Project 归档状态字段及只读写拦截、解档接口、Project/Task 外部链接列表持久化；缺口按分工交同事，前端不私自新增后端 API。
- 桌面端负责活跃/归档分组切换 UI、归档复盘弹窗与调用本机 Agent 起草提议、外部链接卡片渲染与校验。
- 依赖 [HC-217](HC-217-项目导航与资料.md) 的 Project 导航与资料页、[HC-241](HC-241-知识分级与审核沉淀.md) 与 [HC-243](HC-243-团队系统地图.md) 的提议草稿入口。

## 待定问题（Spec 阶段确定）

1. Project 归档时若内部仍有未完结 Task，是提示先转交/关闭，还是允许带未完结态强制归档并集中标示。
2. 外部链接（如 GitLab PR）后续是否通过可选 Webhook/只读配置自动刷新合并状态，首版固定为人工/提交附带链接。
