## 当前阶段

## 要解决的问题

- 现有知识只有 `termKey/category/title/text`，`category` 是自由文本，没有约束力区分和适用范围，保存即发布（`collaboration.schema.json` 的 `KnowledgeCreateRequest`）。
- 踩坑最常在个人会话中被发现，但没有从会话沉淀到团队的入口；同一个坑被多人各记一条，会互相重复甚至矛盾。
- 知识会自动进入全团队的 Agent，没有审核就等于给全团队开了错误结论和注入指令的入口。
- 团队知识写进去容易、维护难：如果缺少读取命中统计与过期纠错反馈，半年后过期的规约和旧接口经验会持续误导全员 Agent。

## 分级与范围

| 级别 | 例子 | 进入 Agent 的方式 | 谁能改 |
| --- | --- | --- | --- |
| 规约 | 接口契约、错误码规范、安全红线 | 范围匹配时正文随会话带入，要求短小 | 仅管理员；开发者只能提议 |
| 经验 | 踩坑记录、排障手册 | 标题目录 + 按需读取（HC-233） | 提议 → 管理员审核 |
| 术语 | 团队名词、服务别名 | 标题目录 + 按需读取（HC-233） | 提议 → 管理员审核 |

适用范围为“全团队”或“指定的一个或多个 Workspace 仓库”。会话涉及的仓库与范围匹配时进入目录；“全团队”条目总是参与。路径级范围不在本卡。

## 预期使用过程

```text
会话中踩坑 → 「沉淀为团队知识」
  → 本人 Agent 读取本会话，并用 HC-233 的知识工具检索已有条目
  → 判断：新增 / 补充到已有条目 / 与已有结论冲突
  → 生成草稿或相对当前版本的差异；本人编辑，选择级别与适用范围，提交为“待审核”
  → 管理员看到差异、来源会话摘要与范围，批准 / 退回（附理由）/ 修改后批准
  → 发布新版本，记录贡献者
日常消费与保鲜：
  Agent 读取知识 → 工具卡展示可读芯片并记录聚合命中计数
  → 成员发现过时可点“已过期/有误”（附简短说明）→ 条目进入管理员待复核队列 → 发起修订或归档
```

## 已确认的范围

1. 级别与适用范围成为结构化字段；规约仅管理员可直接修改。
2. 提议生命周期：草稿 → 待审核 → 已发布（新版本）或退回；已发布可被归档，历史版本保留可读。
3. 待审核内容不进入任何人的 Agent 目录。
4. 提议时合并：起草和比对由提议人本机 Agent 完成，优先合并进已有条目，实现跨人融合。
5. 定期整理：管理员可在本机让 Agent 扫描全部知识，提出合并、过期、冲突建议，同样走审核。
6. 任何自动生成内容只能形成提议，不能直接发布；服务端不调用模型。
7. 规约正文随会话带入受预算约束，与 HC-233 的标题目录预算分别计量。
8. **知识保鲜与腐化治理**：本机 Agent 每次实际读取某条目固定版本时上报匿名聚合命中计数；对话工具卡与知识正文页提供“有用 / 已过期或有误”轻反馈按钮；超过复核周期或收到过期反馈的条目自动进入管理员“待复核队列”，触发人工或辅助修订/归档。

## 对 HC-233 的修订

本卡在 HC-233 交付后实施，并明确修订其以下首版规则（HC-233 本身首版按原规则交付）：

- **规约进入方式**：HC-233 首版只附带标题；本卡起，规约级知识在适用范围匹配时正文每轮带入，与 HC-233 的 8 KiB 标题目录预算分别计量。
