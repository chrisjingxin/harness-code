# HC-231 五层架构与多语言目录重构

> 对应规格：[HC-231 Spec](../spec/HC-231-五层架构与多语言目录重构.md) · 实施计划：[HC-231 Plan](../plan/HC-231-五层架构与多语言目录重构.md) · 执行清单：[HC-231 Todo](../todo/HC-231-五层架构与多语言目录重构.md)

## 1. 现状痛点与重构动机

[HC-203](./HC-203-旧入口与依赖退役.md) 清理了旧 CLI、TUI、独立 Web、旧协议与第三方厂商补丁目录后，仓库虽然卸下了历史表现层包袱，但在**多语言大仓分层（TypeScript + Python + Java）**与**严格五层架构边界**上仍存在四类结构性问题：

1. **协调层 Client 未独立成包，锁死在桌面主进程中**：
   - `collaboration-client.ts`（542 行）、`collaboration-state.ts`（171 行）、`conversation-uploads.ts`（304 行）、`project-updates-service.ts`（125 行）及 SSE 流/游标模块均零 `electron` 依赖，却直接放在桌面主进程源码目录下，无法给其他产品（CLI、插件或独立后端）直接引用；并且 `conversation-uploads.ts` 还反向引入了桌面本地执行层的 `localExecutionKey`。
2. **ACP 统一接入层与默认实例边界倒置，且残留测试桩分包**：
   - Provider 描述符接口 `LocalAcpProviderDescriptor` 与 GUI `PATH` 探测辅助没有沉淀在 `acp-runtime`，而是复制在 `harness` / `pi` / `qwen` 三个 Provider 目录里；多代理注册表停留在桌面主进程，并直接从 `@workbench/harness-provider` 导入类型，造成“通用接入层反向绑定默认实例”；同时，最初用于联调多代理切换的 `pi` / `qwen` 包属于测试桩产物，不应留在正式分包结构中。
3. **跨语言与单子节点目录“假复数套壳”混淆多语言工具链**：
   - 仅余 1 个桌面应用却套在 `apps/` 下，仅余 1 个 Java 服务端却套在 `services/` 下，仅余 1 个默认适配桥却套在 `packages/providers/` 下；而约 19.9 万行独立 `uv` 管理的 Python 内核 `packages/agent` 被混放在 npm 包目录中（包名仍沿用 `za38-agent`），与根目录零散的插件示例目录分离；Java 服务端为了读取线上协议还需要跨目录伸进前端 npm 包。
4. **共享契约混杂、桌面 IPC 过重**：
   - `@workbench/contracts` 同时混放服务端线上协作协议、Electron 桌面专属端口定义（`desktop-hosts.ts` / `session.ts` / `personal.ts`）以及早已被 [HC-211](./HC-211-协作模型重构与只读同步.md) 与 [HC-228](./HC-228-宿主架构收敛与契约统一.md) 淘汰的旧设备/旧执行契约；桌面主进程同时出现了 954 行的混合文件 `local-execution-ipc.ts`，且未统一接入 `ipc-guard.ts`。

## 2. 解决思路与五层终态

遵循“**先理清所有权、再去套壳减冗余、保持单向严格依赖**”的原则，在独立分支与独立 worktree（`harness-code-hc231`）中一步到位完成三语言五层收敛：

| 架构层次 | 终态目录 | 语言与工具链 | 核心职责与对外独立性 |
| --- | --- | --- | --- |
| **第 1 层：Electron UI 与宿主壳** | `desktop/` | TypeScript（`npm` / `electron-vite`） | 仅保留窗口壳、Preload 安全桥、薄 IPC 转发、内聚后的纯 React `src/ui/` 与本机只读 `src/main/project-service/`、以及 `src/shared/` 桌面内部契约 |
| **第 2 层：协调层 Client 端** | `packages/collaboration-client/` | TypeScript（`npm`） | **单包零内部依赖**，可直接发布/复用给其他产品；封装认证/Cookie/CSRF、代次防串台、Ajv 报文校验、SSE 轻量通知流、定稿消息待传账本；通过 `.` 与 `./types` 两个导出满足节点与浏览器/UI 复用 |
| **第 3 层：ACP 统一接入层** | `packages/acp-runtime/` | TypeScript（`npm`） | 零 Electron、零特定 Agent 依赖；统一持有 `LocalAcpHost`、`BoundSession`、`AcpAgentDescriptor` 接口、公共 GUI `PATH` 探测、`AcpAgentRegistry` 注册表及配置化接入任意外部标准 ACP 命令的工厂；多代理兼容性通过 `tests/` 中 Mock ACP 进程测试验证 |
| **第 4 层：ACP 默认实例（Harness Code）** | `packages/harness-acp/` + `agent/` | TypeScript + Python（`uv`） | `packages/harness-acp` 作为极薄 TS 适配桥，探测顶层独立 Python 工程 `agent/`（包名 `harness-agent`，归并插件示例）并解析 `_meta.harnessCode`；即使本机未安装 Python 内核，第 1/2/3 层仍可独立编译运行与接入外部命令 Agent |
| **第 5 层：Java 中继层与跨语言协议源** | `server/` + `contracts/` | Java（Maven / Spring Boot） + 纯 JSON/OpenAPI | 去除 `services/` 套壳直接立足根级 `server/`；顶层 `contracts/` 仅存放语言无关的 `platform` / `organization` / `collaboration` OpenAPI、JSON Schema 与夹具，供 Java Maven 与 TS `collaboration-client` 双向对齐 |

## 3. 范围边界（做什么 / 不做什么）

- **本 Task 要做**：
  - 按上述五层目录与包边界完成物理迁并、导入改写、废弃测试桩与死契约清理、桌面 IPC 模块拆薄与守卫统一；
  - 更新根 `package.json`（4 个 workspace）、`check-boundaries.mjs` 五层单向依赖与防回流门禁、`scripts/project/*`（同步版本与文档检查）及三语言测试脚本路径。
- **本 Task 不做**：
  - 不改变现有服务端 HTTP/SSE 线上接口路径、数据结构与业务行为，不新增云端数据库表或 API 字段；
  - 不更改产品界面交互、功能特性与 Python Agent 内部对话推理行为（内部 ACP `_meta.harnessCode` 与既有协议字段保持兼容）。
