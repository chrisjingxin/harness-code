# HC-247 任务交付物共享附件与验收

## 当前阶段

2026-11-23 结合企业级多团队协作演进需求拆解立项。待认领，认领后按 Spec → Plan → Todo 推进。

## 要解决的问题

- 现行顶层设计第 12 节已明确记录“共享附件仍缺正式承接任务”，且快照正文硬上限为 64 KiB，大型设计稿、OpenAPI 规范、日志包、错误截图或超大引用材料无法随协作流转。
- 当前 Task 交接主要靠关联一条会话，验收人不得不去翻几十轮对话过程才能拼凑结论；同时缺乏严格的“产物先落库再通知”与显式“验收通过 / 退回修订”闭环，导致交接经常出现“收到完成提醒但打不开产物”或责任不清。

## 预期使用过程

```text
提交交付：
  输入：被指派人在本机完成工作，点击“提交任务交付”
  执行：填写结构化结论摘要，附带涉及仓库/PR 链接、关联会话快照及上传的设计稿/日志/截图附件
  判断：必须等待共享附件与关联会话同步全部落库并拿到服务端确认回执（sync-before-notify）
  输出：原子推进 Task 状态为“待验收”，随后才向发起人发出通知与收件箱待办

验收闭环：
  输入：发起人打开 Task 详情页，直接浏览交付摘要卡片与预览/下载受权产物
  执行：点击“验收通过”完结任务，或点击“退回修订”并填写修改意见
  输出：记录不可篡改的状态迁移历史与提交版本；若退回则重新激活被指派人待办
```

## 已确认的范围

1. **Project 级共享附件与对象存储**：承接顶层设计留白，为 Project 会话引用超限材料与 Task 交付物提供服务端受控附件存储，严格按当前 Project 成员资格鉴权（非成员不可枚举与下载），并约束单文件大小、类型校验与项目配额。
2. **“长产物不塞进聊天正文”原则**：超过轻量阈值的报告、日志、契约文件优先作为共享附件或产物文件挂接，在对话流与任务中以结构化卡片引用，避免拖慢时间线渲染。
3. **结构化交付物卡片**：Task 提交时承载结论摘要、关联仓库/分支/PR 链接、可选固定快照引用和附件列表，并关联稳定提交序号/标识防止重复或旧提交覆盖。
4. **P0 顺序约束（sync-before-notify）**：任何附件上传或会话同步未拿到服务端落库确认前，禁止提前发送完成通知或把任务置为“待验收”，杜绝接收方看到通知却拉不到内容。
5. **显式验收与退回修订**：区分“被指派人提交（待验收）”与“发起人验收通过 / 退回修订”，保留完整历次提交与退回意见时间线。

## 不在本卡范围

- 非实时代码 Diff Patch 的交互式对比与本机一键 apply：HC-253。
- 自动合并远程 GitLab/GitHub PR 或远程操作他人代码仓库。
- 为整个组织提供通用个人云盘或无限容量视频存储。

## 职责与前置

- 本卡全栈实施：服务端（`contracts/` + `server/` + `packages/collaboration-client/`）负责共享附件对象存储接入与鉴权下载、Task 结构化交付物模型、验收/退回状态流转及状态迁移历史接口；桌面端负责附件上传进度与失败重试 UI、交付物提交表单、产物预览/下载以及任务详情页的验收/退回操作与历史时间线展示，并配合 [HC-249](HC-249-共享出口脱敏与组织审计日志.md) 在上传前做本地脱敏检查。
- 依赖 [HC-212](HC-212-协作应用与看板通知.md) 与 [HC-219](HC-219-引用任务与团队知识.md) 的现有 Task 基础，协同 [HC-246](HC-246-全局待办收件箱与IM轻通知.md) 触达验收人。
