# 链路日志完整采集

## 现在有什么问题

仓库自己的 `TraceRecorder` 会给每次 Run 写一份 `Trace-log-*.jsonl`（schema v1）。用来定位问题时有三类毛病：

1. **记得太少。** 为了不落正文，写入时会丢掉 `content`、`prompt`、`messages`、`command`、`tool_args`、`tool_result` 等字段。结果是：
   - 模型调用只剩模型名、消息数、finish_reason 和 token；
   - 工具调用只剩工具名和参数键名；
   - 上下文投影只剩 `matched` 和 `count`；
   - `run.complete` 只剩 `status` 和 `duration`。
   出了问题时，看不到模型到底收到了什么、回了什么，也看不到工具拿到了什么参数、返回了什么。
2. **树太碎，重点不突出。**
   - 每次 Run 有 6 个生命周期节点，其中 `run.complete`、`runtime.release` 基本是 0ms，只起记账作用。
   - LangGraph 中间件节点（如 `PatchToolCallsMiddleware.before_agent`）每个约 1ms。
   - 模型调用和工具调用并排挂在一堆 `graph.node` 下，看不出哪次模型调用触发了哪些工具。
   - `context.project` 每次 Run 记两次，`thread.persist` 被拆成很多条很小的记录。
   - 节点名等字段只写在 `span.start` 上，`span.end` 不带。
3. **有疑似缺陷。**
   - 审批埋点 `policy.evaluate`、`interaction.wait` 在代码里存在，但现有 8 个日志文件里一条都没有。
   - `run.complete` 写的字段是 `duration`，Web 简化视图读的是 `duration_ms`。
   - 日志写在每个项目工作区的 `log/` 目录下。记了完整正文以后，有被误提交的风险。

## 准备怎么解决

### 执行树改成 Run → Step

一次 Run 是根节点；一次模型调用加上它触发的审批和工具执行算一个 Step。树上保留的节点只有这些：

```text
run（根）
├─ run.prepare          受理、运行时准备
│  └─ db.persist        accept_run
├─ context.project      上下文投影
├─ context.compact      只在发生压缩时出现
│  └─ llm.call          生成摘要的那次模型调用
├─ step #N
│  ├─ llm.call
│  │  └─ llm.attempt    只在重试时出现
│  ├─ policy.evaluate   每个工具调用一条
│  ├─ interaction.wait  只在需要人工审批时出现
│  ├─ tool.call × n     子 Agent 的整棵子树挂在对应的 tool.call 下
│  └─ db.persist        本 Step 的 transcript 批量提交
└─ db.persist           run_complete
```

- `run.complete`、`runtime.acquire`、`runtime.release`、`run.execute`、`agent.run` 和中间件节点都从树上去掉。它们的耗时、来源、结果改为父节点上的属性。
- 中间件只有失败或超过耗时阈值时才单独成为节点。
- Run 的终态、总耗时、Token 汇总、缓存命中率和错误都写在根节点的结束记录上。
- 每个节点的结束记录都带上开始时的全部属性，看图的一方只读结束记录就够了。

### 五类调用默认完整记录

| 调用 | 必须能从 trace 还原的内容 |
|---|---|
| 模型调用 | provider、model、模型档位、接口类型、base URL 主机名、response id、实际服务的模型名；全部请求参数（temperature、top_p、max_tokens、reasoning_effort、stop、tool_choice、timeout、重试次数等）；系统提示词、完整消息列表、工具 schema；完整输出（正文、reasoning、tool_calls 原始参数、finish_reason）；input、output、total、cache_read、cache_write、reasoning 各项 token 和缓存命中率；首 token 时间、最后一个 token 的时间、chunk 数、输出速率；每次重试的 HTTP 状态、错误码、是否可重试 |
| 上下文压缩 | 触发原因、档位（micro/full）、压缩前后的 token 数和消息数、窗口与阈值、生成的 artifact、摘要正文、摘要那次模型调用、结果（已提交/跳过/失败）及原因、checkpoint 标识 |
| 工具执行 | 工具名和来源（内置、哪个 MCP server、Skill、子 Agent）、call_id、关联的审批节点；完整入参、完整结果、字节数、是否截断、是否转存为 artifact；状态和错误；按工具类型补充：shell 记命令、cwd、exit_code、输出字节数、是否超时，文件类记路径、操作类型、diff 增删行数 |
| DB 持久化 | 操作、涉及的表、thread_id、run_id、行数、seq 范围、写入字节数、事务耗时和其中的锁等待、结果（已提交/幂等重复/失败）、record_id 列表。正文已在 SQLite 中，trace 不重复保存 |
| 审批 | 工具名、call_id、入参、审批模式、最终决策、做出决定的层级（L1–L6）、命中的规则（来源与模式串）、分类器结果、触发的安全底线；人工交互的类型、等待时长、用户的选择、新增规则的作用范围 |

### 存储与安全

- **采集档位可配置。** 分 `full`（默认）、`meta`（只记元数据）、`off` 三档。
- **全部内联存储。** 载荷都写在同一个 jsonl 里，不另存文件。同一会话内的消息、系统提示词、工具 schema 按内容哈希只写一次，模型调用通过引用指向它们，避免像旧格式那样每一步都把整份上下文重写一遍。
- **只脱敏密钥类内容。** 包括 api_key、Authorization、Cookie、疑似 token 的环境变量值，任何档位都适用。工作区路径和普通内容不脱敏。
- **日志迁到用户目录。** 位置是 `~/.harness/trace/` 下按项目区分的子目录，不再写入项目工作区 `log/`。按天数自动清理，天数可配置。
- **埋点故障不影响业务。** 写入失败或解析失败都与业务隔离，这一点保持不变。

### 看图界面

Web 看图界面适配新的 Step 树。详情面板按「参数 / 输入 / 输出 / 用量 / 耗时 / 错误」分区展示；载荷默认折叠，可以展开看原文。

## 改完后有什么变化

- 排查一次失败的 Run 时，只打开 trace 文件，就能逐 Step 看到模型收到了什么、回了什么、花了多少 token、缓存命中多少，工具拿到了什么、返回了什么，审批为什么放行或拦截，哪次落库慢了。
- 树上一层是一轮模型调用，下面挂着它触发的审批和工具，不再有 0ms 的 completed 节点。
- 项目目录里不再出现 `log/`。
